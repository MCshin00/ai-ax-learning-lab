# 12주차 통합 구현 학습 노트

## 개발 하네스가 먼저 필요했던 사례 — 작업자 동시 실행

### 진행 방식과 당시 갖춘 것

제공 IT 문의 업무를 참고 구현을 읽는 대신 [inquiry_desk](inquiry_desk/)에 직접 구현하는 방식으로 진행했다. 설계 결정은 학습자가 내리고, 메인(Claude)이 요구를 요청문으로 정리해 Codex 작업자에게 넘기며, 별도의 Codex 검토자가 결과를 읽기 전용으로 검토한다. 메인은 작업자를 비대화형 실행(`codex exec`)으로 시작했다.

첫 작업으로 11주차의 개발 환경을 이 프로젝트로 옮겼다. 작업자 원칙을 담은 [AGENTS.md](inquiry_desk/AGENTS.md), 변경 절차를 담은 [Skill](inquiry_desk/.agents/skills/inquiry-change/SKILL.md), 종료 검사와 시작 문맥을 맡는 [Hook](inquiry_desk/src/harness/java/lab/harness/)이다. 두 번째 작업은 Day 1의 범위인 서비스 상태 조회 구현이었다. 다른 프로그램이 호출할 수 있는 도구로 공개하기 위해 MCP 서버로 만든다. 이 시점에 갖춘 것은 한 작업자가 한 세션 안에서 따를 원칙·절차·종료 검사였고, 작업자를 시작하고 멈추고 서로 떼어 놓는 처리는 메인이 셸 명령으로 직접 했다. 프로젝트 폴더는 커밋 전이었고 작업별 worktree를 두지 않았다. 11주차의 [AGENTS.md](../week11-development-environment/development_harness/AGENTS.md)에는 메인이 "현재 작업 공간의 미커밋 변경과 기존 Worktree를 확인"한다는 규칙이 있었다. 메인이 Codex에서 Claude로 바뀌면서 메인의 규칙을 새 파일로 옮겼는데, 이 문장은 옮겨지지 않았다.

### 발생한 순서

1. 두 번째 작업을 넘긴 실행이 표준 입력을 기다리며 멈췄다. 로그에는 `Reading additional input from stdin...` 한 줄만 남았고 약 10분 동안 결과 파일이 생기지 않았다.
2. 메인이 그 실행을 중단하고 같은 요청문으로 작업자를 다시 시작했다.
3. 중단한 뒤에도 같은 요청문을 인수로 가진 Codex 프로세스가 프로세스 목록에 남아 있었고, 생성 시각은 중단 시각과 같았다. 중단으로 입력이 닫히면서 멈춰 있던 실행이 작업을 시작한 것으로 추정한다. 셸·래퍼·자식 중 어느 프로세스가 남았는지까지는 확인하지 못했다.
4. 두 작업자가 같은 폴더에서 같은 요구를 구현했다. 한쪽은 `lab.inquiry.status`에, 다른 쪽은 `lab.inquiry`와 `lab.inquiry.mcp`에 서버와 클라이언트를 만들었고, 같은 이름의 `StatusResult`를 서로 다른 형태로 썼다. `build.gradle`에는 진입점 지정과 검사 설정이 두 번씩 들어갔다.
5. 두 작업자 모두 자기가 쓰지 않은 변경을 발견하고 편집을 멈췄다. 결과 보고의 `blocked`를 `true`로 두고 "기준 구현을 정해 달라"는 요청을 남겼다. 기존 파일은 지우지 않았다.

두 작업자가 남긴 충돌 당시의 기록은 `inquiry_desk/.local/tasks/checkpoint-20261007-conflict.md`에, 나중에 끝난 작업자의 보고는 `inquiry_desk/.local/tasks/02-result.json`에 있다. 두 실행이 같은 결과 파일과 같은 로그 파일을 쓰도록 지정돼 있어서 먼저 끝난 작업자의 보고는 덮어써졌다.

같은 실행에서 드러난 문제가 두 가지 더 있다. 작업자의 Gradle은 `--offline`으로 실행하도록 지정돼 있었고, 캐시에 일부만 있던 `langchain4j-open-ai:1.20.0`을 해석하지 못해 두 작업자 모두 업무 검사를 실행하지 못했다. `--offline`은 작업자의 실행 환경에 네트워크가 없다는 전제에서 넣은 것인데 이 전제는 확인한 적이 없다. 이후 실행의 로그에는 네트워크 접근이 켜져 있다고 나온다. 그리고 Codex는 신뢰 등록을 거친 Hook만 실행하므로, 등록 파일을 새로 만든 직후의 작업자 실행에 종료 Hook이 걸렸는지는 확인되지 않았다.

### 일어난 일과 빠져 있던 처리

| 일어난 일 | 그때 없었던 처리 |
|---|---|
| 실행이 입력을 기다리며 멈춤 | 요청을 전달한 뒤 표준 입력을 닫고, 입력 전달 실패와 제한 시간 초과를 구분해 기록하는 처리 |
| 중단한 프로세스가 살아남아 작업을 시작함 | 시작한 프로세스를 식별해 종료까지 지켜보고, 중단을 요청한 뒤 실제로 사라졌는지 확인하는 처리 |
| 같은 작업이 두 번 시작됨 | 작업과 실행 시도를 각각 식별자로 기록하고, 앞선 시도의 종료가 확인되기 전에는 같은 작업을 다시 시작하지 않는 처리 |
| 두 작업자가 같은 파일을 편집함 | 작업마다 worktree를 따로 주어 한 작업 폴더에 작업자가 하나만 있게 하는 처리. 브랜치 이름만 나누고 폴더를 같이 쓰면 격리되지 않는다 |
| 한쪽 보고가 다른 쪽에 덮어써짐 | 결과와 로그의 위치를 실행 시도마다 따로 두는 처리 |
| 검사를 실행하지 못한 채 작업이 끝남 | 작업자의 환경에서 검사가 실행 가능한지 미리 확인하는 준비와, 작업자의 보고와 별개로 실행하는 최종 검사. 중복 실행과는 원인이 다른 환경 문제다 |

표의 오른쪽은 5주차와 10주차 엔진이 맡았던 프로세스 실행·결과 분류와, 12주차 교재가 Day 1에서 갖추라고 한 책임(중복 실행 방지, 프로세스 종료 확인, 최종 검사)과 겹친다. 앞의 두 행은 이미 만든 코드에 출발점이 있다. 5주차의 [ProcessRunner.java](../week05-development-harness/quality_demo/src/main/java/lab/week05/ProcessRunner.java)는 작업 입력을 표준 입력에 쓰고 닫으며, 제한 시간이 지나면 하위 프로세스까지 강제 종료를 요청한다. 종료가 실제로 끝났는지 확인하는 부분과 사람이 중간에 중단했을 때의 정리는 그 코드에도 없다. 이번에는 그 엔진을 거치지 않고 메인이 같은 일을 명령 한 줄씩으로 대신했고, 한 번의 멈춤이 중복 실행으로 이어졌다.

### 작업자가 멈춘 방식과 정리

충돌이 더 번지지 않은 것은 두 작업자가 낯선 변경을 덮어쓰지 않고 멈췄기 때문이다. 결과를 항목이 정해진 JSON 문서로 받도록 해 둔 덕에 멈춘 이유와 각자 만든 파일 목록이 `blocked`, `blocked_reason`, `changed_files`로 돌아왔다. 한쪽 작업자는 자기 작업본의 사본을 따로 남겼다.

정리는 검사까지 작성한 쪽을 기준으로 했다. 그 작업자의 사본과 현재 파일이 같은 것을 확인하고, 다른 쪽의 미완성 파일은 `inquiry_desk/.local/tasks/02-discarded/`로 옮겼으며, `build.gradle`의 중복 두 곳을 지웠다. 네트워크가 되는 환경에서 `test`와 `harnessTest`를 실행해 실패 없이 끝난 것을 확인했다. 결과는 `inquiry_desk/.local/harness/main-check/build/test-results/`에 있다. 검토자는 정리 뒤 깨진 참조나 남은 중복을 찾지 못했다.

### 11주차 환경이 맡는 범위와 그 바깥

지침·Skill·Hook은 이미 시작된 작업자 한 명이 무엇을 읽고, 어떤 절차로 바꾸고, 끝낼 때 무엇을 검사하는지를 정한다. 이번 사례의 문제는 그 바깥에서 생겼다. 같은 작업이 이미 돌고 있는지, 어느 폴더에서 일하는지, 앞선 실행이 끝났는지는 여러 실행에 걸친 정보인데, 그것을 기록하고 확인할 책임이 어디에도 정해져 있지 않았다. 작업자는 충돌을 발견하고 멈출 수는 있었지만 충돌을 막을 수는 없었다.

이 사례에서 AI 라이브러리는 아직 쓰이지 않았다. 구현하던 것은 모델 호출이 없는 조회 도구 하나였다. 문제가 난 곳은 전부 작업을 맡기고 돌려받는 과정이었다. 구현을 AI 작업자에게 맡기는 방식에서는 기능의 크기와 관계없이 첫 작업부터 이 과정이 필요하다.

### 판단 — 하네스를 먼저 구성하는 순서

이 사례에서 두 가지를 정했다. 같은 폴더에 작업자를 둘 두지 않고 작업마다 별도 브랜치의 worktree를 준다. 그리고 문제 상황이 주어지면 개발 하네스를 먼저 구성하고, AI 라이브러리와 프레임워크는 기능에 필요해질 때 붙인다.

이번 사례가 그 순서의 근거가 된다. 작업자의 시작·격리·중복 방지·종료 확인·최종 검사를 코드로 먼저 갖춰 두면, 이후의 기능은 모두 그 과정을 거치는 작업 한 건이 된다. 새로 만들 필요는 없고 5·10주차 엔진을 연결하는 데서 시작할 수 있다. 하네스는 마지막에 한 번 써 보는 대상이 아니라 기능을 추가할 때마다 쓰이고 고쳐지는 대상이 된다. 다만 검사할 앱이 전혀 없으면 하네스가 제대로 도는지 확인할 수 없다. 앱 검사가 없던 동안 종료 Hook은 실행 불가만 반환했다(`inquiry_desk/.local/harness/stop-response.json`). 그래서 첫 단계는 하네스와, 그 하네스를 통과시켜 볼 가장 작은 기능 하나를 함께 두는 구성이 된다. 이번에는 서비스 상태 조회가 그 기능이다.

작업자 격리가 필요 없는 조건도 있다. 한 사람이 대화형 세션 하나로 직접 지켜보며 개발한다면 시작·종료·중복은 사람이 보고 있으므로 11주차의 환경으로 충분하다. 메인이 작업자를 대신 시작하거나, 이슈가 작업을 시작하거나, 작업자가 둘 이상이면 이 처리가 코드로 있어야 한다.

## 작업을 맡기고 돌려받는 방식의 결정

### 역할

| 맡는 쪽 | 하는 일 |
|---|---|
| 학습자 | 공개 입출력과 실패했을 때의 동작을 정한다. 계획을 승인하고, 풀 리퀘스트를 합쳐 승인한다 |
| 메인(Claude) | 설계, 작업 지시, 최종 검사. 구현 방식을 지정받으면 그것을 계획으로 옮기고, 계획을 요구받으면 계획을 제시한다 |
| 작업자(Codex) | 승인된 계획대로 구현하고 검사를 직접 실행한다 |
| 검토자(Codex, 별도 세션) | 변경을 요구·계획과 대조한다. 메인이 최종 검사를 하는 것과 별개로 둔다 |

메인에게 설계와 최종 검사를 함께 맡기면 최종 검사는 구현이 계획대로 됐는지만 본다. 계획 자체의 빈칸은 계획을 승인하는 자리와 검토자가 잡는다. 검토자를 따로 두는 이유가 여기서 성립한다.

### 작업자가 정해지지 않은 조건을 만났을 때

같은 입력의 결과·오류·저장 내용을 바꾸는 조건이 계획에 없으면 작업자는 스스로 정하지 않고 멈춘다. 선택한 이유는 원하지 않는 방향으로 구현된 뒤 다시 작업하는 비용이 왕복 한 번보다 크다는 것이다. 맡긴 항목만 스스로 정하게 하는 방식도 맡긴 일의 목적보다 덜 하고 끝낼 수 있어 같은 문제가 남는다.

이 규칙만으로는 작업자가 선택인 줄 모르고 지나간 경우를 잡지 못한다. 앞선 상태 조회 구현에서 "자료의 한 행이 잘못되면 파일 전체를 조회하지 못함으로 본다"와 "서비스 ID의 대소문자를 구별한다"가 그렇게 들어갔고, 앞의 것은 작업자의 보고에도 없었다. 그래서 작업자 바깥의 세 자리에서 함께 잡는다.

| 자리 | 하는 일 |
|---|---|
| 넘기기 전 | 계획을 쓸 때 새로 공개하는 동작마다 정상, 없음, 잘못된 입력, 자료가 잘못됨, 일부만 실패, 같은 요청의 반복, 표기 차이를 대 보고 기대 결과가 비어 있는 것을 먼저 정한다 |
| 작업 뒤 | 검토자가 공개된 동작의 경로에서 결과가 갈리는 분기를 모두 찾아 계획의 조건에 대응시키고, 대응되지 않는 분기를 보고한다 |
| 합치기 전 | 풀 리퀘스트 본문의 입력별 결과와 메인이 실제로 실행한 출력을 읽고 합친다 |

검사가 실패하면 작업자는 코드를 고친다. 계획에서 온 검사의 기대값은 바꾸지 못하고, 그 검사를 지우거나 건너뛰지 못한다. 기대 결과를 바꿔야만 통과한다고 판단되면 멈춘다. 결과를 바꾸는 선택을 스스로 하지 않는다는 같은 선이 검사에도 적용된 것이다.

고칠 기회는 세 종류이고 상한이 다르다.

| 누가 | 언제 | 상한 |
|---|---|---|
| 작업자 | 세션 안에서 검사가 실패할 때 | 횟수 제한 없음. 실행의 제한 시간까지 |
| 종료 Hook | 작업자가 응답을 끝내려는 순간 검사가 실패할 때 | 같은 세션에서 한 번 |
| 메인 | 세션이 끝난 뒤 최종 검사나 검토에서 나온 것 | 같은 실패에 한 번 |

메인의 한 번과 검토의 세 번은 포기하는 지점이 아니라 학습자에게 가져가 계속할지 정하는 지점이다. 횟수로 끊으면 고칠 수 있는 것을 버리게 되고, 상한이 없으면 계획이 틀렸는데 구현만 계속 고치게 된다. 같은 실패가 한 번의 수정 요청 뒤에도 남는다면 구현보다 계획이나 요청문에 원인이 있을 가능성이 커서 사람이 볼 차례다.

### 흔적을 남기는 자리

구현을 작업자에게 맡기면 무엇이 어떻게 만들어졌는지 모르는 채 넘어갈 수 있다. 처음에는 작업자의 결과가 메인이 읽는 JSON으로만 돌아왔고, 프로젝트 설명은 구현 전 상태에 머물러 있었다. 읽는 사람이 누구인지가 아니라, 지금의 구조를 갱신하는 문서인지 작업마다 쌓이는 기록인지로 자리를 나눴다.

| 자리 | 담는 것 | 바뀌는 방식 |
|---|---|---|
| [docs/project.md](inquiry_desk/docs/project.md) | 지금의 구조 | 구조를 바꾸는 변경과 같은 변경 안에서 고친다 |
| [docs/adr](inquiry_desk/docs/adr/) | 결정 하나당 상황, 결정, 이유, 다시 볼 조건 | 쌓는다 |
| 풀 리퀘스트 본문 | 작업 한 건에서 무엇을 왜 바꿨고 어떻게 확인했는지 | 작업마다 하나 |

이 길 자체를 만든 변경(지침, 작업자 실행 관리, Hook, 결정 기록)은 작업자에게 넘긴 작업이 아니어서 풀 리퀘스트를 열지 않고 검토 뒤에 커밋한다. 그 경위는 이 노트와 `inquiry_desk/.local/tasks/`의 검토 기록에 있다.

작업자가 세션 사이에 남기던 인계 메모는 없앴다. 지금 상태는 구조 문서가, 작업의 내용은 풀 리퀘스트 본문이 맡으므로 같은 내용을 세 곳에 쓰게 되고, 메모는 Git에서 제외된 폴더에 있어 작업별 폴더로 따라가지도 않는다. 교재 본문의 Day 2는 인계 메모를 남기고 세션을 재개해 보라고 안내하는데, 여기서는 재개한 세션이 구조 문서·결정 기록·풀 리퀘스트 본문을 읽어 다음 작업을 찾는다.

## 서비스 상태 조회의 설계 결정

결정과 이유는 결정 기록에 있다. 여기에는 결정들을 가른 기준을 적는다.

| 결정 | 기록 |
|---|---|
| 자료에 없는 것은 정상 응답 안의 "없음", 하지 못한 것은 원인 값과 함께 오류 | [0003](inquiry_desk/docs/adr/0003-absent-is-a-normal-result.md) |
| 응답 형식을 오류의 모양까지 선언하고, 변환은 표면마다 한 곳에 두고, 대표 응답을 글자 그대로 비교하는 검사로 고정 | [0004](inquiry_desk/docs/adr/0004-declared-response-shape.md) |
| 모르는 필드는 무시, 모르는 원인 값은 원인 불명의 실패, 모르는 결과 구분은 해석할 수 없는 응답 | [0005](inquiry_desk/docs/adr/0005-tolerant-reader.md) |
| 잘못된 입력은 별도의 결과, 모르는 인수는 거절, 서비스 ID는 정확히 일치, 자료는 행 단위로 판단, 조회 실패는 값으로 전달 | [0006](inquiry_desk/docs/adr/0006-status-lookup-inputs.md) |

학습자가 직접 정한 것은 네 가지다. 자료에 없는 것은 오류가 아니라 "없음"이다. 도구의 응답 형식도 공개한다. 응답의 모르는 필드는 무시한다. 모르는 원인 값은 응답 전체를 잘못된 응답으로 처리하지 않고 원인 불명의 실패로 받는다. 나머지는 메인의 안을 검토해 받아들인 것이다. "없음"의 규칙을 모든 도구에 적용하는 것, 오류의 모양과 원인 값 목록까지 선언하고 변환을 한 곳에 두고 글자 그대로 비교하는 검사로 고정하는 것, 모르는 결과 구분의 처리, 0006의 항목들이 그렇다.

**호출이 실패한 것과 값이 없는 것은 다르다.** 급여 시스템이 자료에 없는 것은 조회가 실패한 것이 아니다. HTTP라면 상태 코드가 이 구별을 맡지만 MCP의 도구 오류에는 표준 구분 값이 없어서, 오류로 알릴 때는 구분 값을 응답에 직접 넣어야 한다.

**읽는 쪽이 그 값으로 다음 행동을 가르는가.** 모르는 것을 받았을 때의 처리가 이 기준 하나로 갈린다. 쓰지 않는 필드는 버려도 된다. 원인 값은 몰라도 "조회하지 못함"으로 진행할 수 있으므로 원인 불명으로 받고 받은 값을 보존한다. 응답 전체를 잘못된 응답으로 처리하면 실제 원인이 가려진다. 결과 구분은 받은 상태 값을 사실로 써도 되는지를 가르므로 모르면 진행할 수 없다.

**요청은 엄격하게, 응답은 너그럽게.** 모르는 인수가 붙은 요청은 거절해 호출한 쪽의 실수가 바로 드러나게 하고, 응답에서는 모르는 필드를 무시해 서버가 먼저 바뀌어도 읽는 쪽이 계속 동작하게 한다.

**"없음"은 확실할 때만 말한다.** 자료의 한 행이 잘못됐을 때 찾는 서비스의 행이 온전하면 그 결과를 돌려준다. 찾는 ID가 없는데 ID를 읽을 수 없는 행이 있으면 그 행이 찾는 서비스일 수 있으므로 "없음"이 아니라 "조회하지 못함"이다.

**안의 이름이 밖의 형태가 되지 않게 한다.** 앞선 구현은 안에서 쓰는 결과 타입을 변환 없이 그대로 응답으로 내보냈다. 그 구조에서는 결과 구분의 이름을 코드 안에서 바꿔도 컴파일과 기존 검사가 모두 통과하는데, 응답을 글자로 읽던 다른 프로그램은 그때부터 그 결과를 알아보지 못한다. 변환을 한 곳에 두고 대표 응답을 글자 그대로 비교하는 검사를 두면 형태가 바뀌는 순간이 검사 실패로 드러난다.

앞선 구현은 이 결정들보다 먼저 만들어졌다. 응답 형식 선언, 변환 위치, 응답을 읽는 방식, 자료를 판단하는 단위가 모두 달라 고쳐 쓰지 않고 새로 구현하기로 했다. 계획의 입력별 기대 결과는 `inquiry_desk/.local/tasks/03-status-lookup/plan.md`에 있다.

### 계획의 빈칸에서 나온 결정

승인된 계획을 검토자가 읽었을 때 결과가 정해지지 않는 입력이 남아 있었다. 계획은 "잘못된 행"이라고만 했고 어떤 행이 잘못된 행인지는 적지 않았다. 예를 들어 변경 번호가 -1인 VPN 행은 계획만으로는 "있음"인지 "조회하지 못함"인지 정해지지 않는다. 이 빈칸을 그대로 넘기면 작업자가 공개 동작을 정하게 되고, 앞선 구현에서 생긴 일이 되풀이된다. 메인의 안을 검토해 다음처럼 정했다.

| 빈칸 | 결정 | 기준 |
|---|---|---|
| 어떤 행이 잘못된 행인가 | 엄격하게 본다. ID와 설명은 공백이 아닌 글자가 있는 문자열, 상태값은 정해진 목록의 값, 변경 번호는 0 이상의 정수여야 한다. 행의 모르는 필드는 무시한다 | 틀린 값을 사실로 전달하는 것보다 조회하지 못했다고 하는 쪽이 낫다. 읽는 값에 영향이 없는 것만 너그럽게 받는다 |
| 해당 없는 필드를 빼는가 `null`로 보내는가 | 뺀다. 결과 구분마다 반드시 있는 필드를 선언한다 | 두 방식을 섞으면 읽는 쪽이 둘 다 다뤄야 한다. 잘못된 입력처럼 값이 없을 수 있는 경우도 같은 규칙으로 설명된다 |
| 문장과 원인 값 | 문장은 사람이 읽고, 코드는 원인 값으로만 분기한다 | 문장을 고쳐도 읽는 코드가 깨지지 않는다 |
| 필드의 타입이 다른 응답 | 필드가 없는 응답과 같이 잘못된 응답으로 처리한다 | 둘 다 약속한 형식이 아니다 |
| 구조화된 내용과 텍스트가 다른 응답 | 읽는 코드는 구조화된 내용만 읽는다 | 텍스트는 사람이나 모델이 읽는 표현이다. 두 곳을 다 읽으면 어긋날 때 어느 쪽이 사실인지 정해야 한다 |
| 운영 도구의 종료 코드 | 있음·없음은 0, 조회하지 못함과 잘못된 입력은 1, 인수가 사용법과 다르면 2 | "없음"은 정상 결과라는 결정과 같다. 조회 결과가 나쁜 것과 도구를 잘못 부른 것을 구별한다 |

계획의 표에서 한 칸에 변형이 여럿이면 변형마다 검사를 두도록 적었다. "서비스 ID가 없음·빈 값·공백뿐"을 한 칸에 적고 "칸마다 검사 한 건"이라고 하면 그중 하나만 검사해도 그 칸을 확인한 것이 되기 때문이다.

빈칸은 한 번에 다 드러나지 않았다. 위 결정을 반영한 계획을 다시 검토했을 때 실패 조건이 겹치는 입력이 남아 있었다. 인수도 잘못됐고 자료 파일도 없는 요청, 다른 서비스의 응답에 모르는 원인 값이 붙은 응답처럼 두 규칙에 함께 걸리는 입력은 규칙을 하나씩 적은 표로는 결과가 정해지지 않는다. 규칙마다 사례를 적는 것과 별개로 규칙을 적용하는 순서를 적어야 했다. 남은 아홉 가지는 세 기준으로 정리됐다. 인수의 개수와 모양이 틀리면 사용법 오류로 보고 값이 틀린 것은 서버의 판정을 받는다. 형식을 먼저 확인하고 내용은 그다음에 해석한다. 읽는 쪽은 필요한 것만 읽고 자료의 조건은 서버에 둔다.

**처음부터 모든 경우를 따질 것인가.** 이 아홉 가지를 정하면서 학습자는 시작부터 모든 경우를 따지는 것이 과하지 않은지 물었다. 검토를 거듭할수록 경우는 더 나오고, 조회 도구 하나의 계획이 표 세 개와 쉰 줄이 넘는 사례가 됐다. 계획에 적는 것과 작업자가 만났을 때 멈춰 묻는 것은 같은 빈칸을 다루는 두 방법이다. 앞의 것은 넘기기 전에 시간이 들고, 뒤의 것은 왕복이 한 번 든다. 자주 만나는 입력과 한번 공개하면 바꾸기 어려운 형태(응답의 필드, 결과 구분, 종료 코드)는 먼저 정할 가치가 있다. 두 가지 실패가 겹치는 드문 입력까지 미리 적는 것은 그 왕복 한 번보다 비쌀 수 있다. 이번에는 이미 찾은 경우를 계획에 적었다. 다음 기능의 계획을 어디까지 적을지는 이 두 비용을 견줘 정한다.

## 작업자 실행 관리 — 5주차 엔진에서 가져온 것과 더한 것

첫 절의 사고에서 빠져 있던 처리를 코드로 갖췄다. 코드는 [inquiry_desk/src/harness/java/lab/harness/run](inquiry_desk/src/harness/java/lab/harness/run/)에 있고, 구조와 실행 방법은 [docs/project.md](inquiry_desk/docs/project.md)의 "작업자 실행 관리" 절에 있다. 이 부분은 작업자에게 넘기지 않고 대화형 세션에서 구현했다. 작업자에게 일을 넘기는 길 자체를 만드는 일이어서 그 길로 넘길 수 없다. 구현 뒤 별도의 Codex 세션이 읽기 전용으로 검토했다.

### 5주차 엔진이 맡던 것과 없던 것

대상은 [week05-development-harness/quality_demo](../week05-development-harness/quality_demo/src/main/java/lab/week05/)의 `ProcessRunner`와 `harness` 패키지다.

| 책임 | 5주차 엔진 | 이번 |
|---|---|---|
| 작업 접수 기록, 같은 작업의 중복 시작 거절 | 없음. 실행마다 임의 번호의 결과 폴더만 만듦 | `TaskLedger`를 새로 만듦 |
| 작업별 작업 폴더 | 없음. 요청 파일이 가리키는 폴더에서 바로 실행 | `Workspaces.GitWorktrees`를 새로 만듦 |
| 작업자 실행(입력 닫기, 제한 시간) | 있음 | `ProcessRunner`를 가져와 고침 |
| 종료 확인 | 제한 시간 뒤 하위 프로세스까지 강제 종료를 요청하고 5초를 기다림. 실제로 사라졌는지는 판정하지 않음. 엔진이 중단됐을 때의 정리 없음 | `ProcessRunner`에 더함 |
| 실행 시도별 결과 | 실행마다 폴더를 두고 작업자의 마지막 응답과 검사 결과를 남김 | 작업 아래 시도별 폴더로 바꾸고 요청문·출력·결과·검사·프로세스 기록을 남김. 작업자의 결과는 정해진 형식으로 받아 형식을 확인 |
| 최종 검사(통과·실패·실행 불가) | 있음 | `GradleVerifier`를 가져와 `GradleChecker`로 고침 |
| 수정 요청 | 검사가 실패하면 엔진이 작업자를 한 번 다시 실행 | 뺌. 수정 요청은 메인이 같은 작업의 새 시도로 넘김 |

### 가져와 고친 두 부분

**`ProcessRunner`.** 요청을 표준 입력에 쓰고 닫는 것, 제한 시간, 요청 전달 실패를 따로 기록하는 것은 그대로다. 달라진 것은 다섯 가지다.

- 출력을 메모리에 모으지 않고 시도의 로그 파일에 쓴다.
- 중단 요청을 지켜본다. 시도 폴더에 중단 요청 파일이 생기면 제한 시간과 같은 경로로 종료한다.
- 살아 있는 동안 하위 프로세스를 계속 찾아 번호와 시작 시각을 기록한다. 부모가 먼저 끝나면 하위 프로세스를 다시 찾기 어렵고, 번호만 적으면 번호가 다시 쓰였을 때 다른 프로세스를 그 작업자로 오인한다.
- 종료를 요청한 뒤 정해진 시간 안에 모두 사라졌는지 판정해 결과에 담는다. 정상 종료였어도 하위 프로세스가 남아 있으면 함께 끝낸다.
- 시작한 뒤에는 지켜보는 중의 오류나 종료 요청의 오류가 나도 종료 확인을 거치고, 확인하지 못했으면 그렇게 돌려준다.

끝난 이유는 정상 종료, 제한 시간 초과, 중단, 시작 실패로 나뉜다. 5주차에는 종료 코드 124가 제한 시간 초과를 겸했다.

**`GradleVerifier` → `GradleChecker`.** 이번 실행이 새로 만든 결과 파일만 읽어 통과·실패·실행 불가를 가르는 것과, 검사 작업마다 실행된 검사가 있어야 통과로 보는 것은 그대로다. 달라진 것은 네 가지다.

- 실패한 검사가 하나라도 있으면 다른 검사 작업의 결과가 없어도 실패다. 5주차에는 모든 검사 작업에 실행된 검사가 있어야 실패로 판정했고, 그렇지 않으면 실행 불가였다. Gradle은 첫 검사 작업이 실패하면 뒤의 작업을 실행하지 않으므로, 그 판정으로는 실제 실패가 실행 불가로 기록된다.
- 검사를 캐시 없이 다시 실행하게 하는 옵션을 프로그램이 붙이지 않는다. 5주차에는 자동으로 붙였다. 지금은 설정의 검사 명령에 직접 적으므로, 명령에서 빼면 앞선 실행의 결과가 재사용될 수 있다.
- 결과 폴더를 넘기는 방식을 이 프로젝트의 빌드 폴더 지정으로 바꿨고, 요약에 첫 실패의 이름과 메시지를 넣는다.
- 검사 프로세스도 작업자와 같은 방식으로 중단하고 종료를 확인한다.

### 새로 더한 것

**접수 기록.** 작업마다 폴더 하나, 시도마다 그 아래 폴더 하나를 둔다. 잠금 파일이 있으면 그 작업의 시도 하나가 실행 권한을 갖고 있다는 뜻이고, 그 시도의 종료가 확인돼야 풀린다. 잠금을 살피고, 풀고, 새로 만들고, 시도의 끝을 기록하는 일은 작업마다 한 번에 한 곳에서만 하도록 운영체제의 파일 잠금으로 감쌌다.

**실행 관리가 도중에 사라진 경우.** 첫 절의 사고처럼 실행을 중단한 뒤에 프로세스가 남는 경우를 다룬다. 사고에서 어느 프로세스가 남았는지는 확인하지 못했다. 잠금과 프로세스 기록이 남으므로, 다음 접수는 기록된 프로세스나 그 하위 프로세스가 살아 있으면 거절하고, 모두 사라진 것이 확인되면 앞선 시도를 버려진 것으로 기록하고 접수한다. 살아 있는 프로세스는 중단 명령이 끝내고 사라졌는지 확인한다.

**프로그램이 종료를 확인할 수 없는 경우.** 잠금 기록을 읽을 수 없을 때, 기록된 번호의 프로세스가 살아 있는데 같은 프로세스인지 가릴 수 없을 때, 기록되지 않은 프로세스가 있을 수 있을 때다. 마지막 경우에는 프로세스를 시작한 직후 번호를 기록하기 전에 실행 관리가 사라진 것, 이미 본 프로세스를 기록하지 못했는데 종료도 확인하지 못한 것, 작업 폴더를 만들던 git의 종료를 확인하지 못한 것이 든다. 이때는 접수도 중단 명령도 끝났다고 판단하지 않고, 사람이 남은 프로세스가 없음을 확인한 뒤 시도 번호를 지정해 잠금을 푼다.

**작업 폴더.** 기준 커밋에서 작업별 브랜치와 worktree를 만든다. 커밋하지 않은 변경은 새 폴더로 전달되지 않는다. 같은 작업의 다음 시도는 같은 폴더를 이어서 쓴다. Hook 등록은 Git으로 공유하므로 기준 커밋에 들어간 등록이 작업 폴더로 따라온다. 아래 "작업자에게 Hook을 거는 방식" 절에 적었다. 설정의 프로젝트 경로가 작업 폴더 밖을 가리키면 폴더를 만들기 전에 거절한다. 그런 설정에서는 브랜치만 다르고 실제로는 같은 폴더에서 작업자가 실행된다.

**작업의 상태.** 실행 중, 검토 대기, 검사 실패, 검사 실행 불가, 질문 대기, 확인 필요의 여섯 가지다. 작업자가 질문을 남기고 멈춘 시도는 검사하지 않는다. 멈춘 코드는 검사에 실패할 수 있고, 그것을 수정이 필요한 실패로 읽으면 안 되기 때문이다.

상태가 겹치는 세 경우는 다음처럼 정했다.

| 경우 | 상태 | 이유 |
|---|---|---|
| 작업자가 비정상 종료했는데 질문을 남기고 멈춘 결과도 있음 | 확인 필요 | 프로세스가 남았을 수 있는 실행에 답을 붙여 바로 다시 넘기면 안 된다 |
| 중단 명령이 최종 검사 중에 들어옴 | 검사도 끝내고 확인 필요 | 중단은 그 작업의 프로세스를 모두 멈춘다는 뜻 하나로 둔다 |
| 종료 Hook이 작업자의 세션을 멈췄는데 작업자는 끝났다는 결과를 남김 | 최종 검사의 판정을 따르고, Hook이 멈췄다는 사실을 이유에 남김 | Hook은 작업자가 스스로 하는 검사이고 판정은 독립된 최종 검사가 맡는다 |

### 작업자에게 Hook을 거는 방식

**걸리지 않던 원인.** 이 프로젝트에 Hook을 옮긴 뒤 실제 Codex 세션에서 걸리는지는 확인한 적이 없었다. `inquiry_desk`에서 Codex를 비대화형으로 실행해 보니 시작 Hook과 종료 Hook이 호출은 되지만 둘 다 실패로 끝났고 판정 기록이 남지 않았다. 등록의 Windows용 명령에 들어 있던 `-Dfile.encoding=UTF-8`을 원인으로 판단했다. PowerShell은 이 옵션을 `-Dfile`과 `.encoding=UTF-8`로 쪼개고, Java는 뒤의 것을 실행할 클래스 이름으로 읽어 시작하지 못한다. 같은 명령을 PowerShell에서 직접 실행해 `Could not find or load main class .encoding=UTF-8`을 확인했고, 옵션을 따옴표로 묶으면 정상 동작했다. 11주차의 등록에는 이 옵션이 없었다. Hook 프로그램의 검사는 판정 로직을 직접 호출하므로 등록의 명령이 틀린 것은 드러내지 못했다.

**작업 폴더에 거는 방법.** 등록이 절대경로를 쓰고 Git에서 제외돼 있어서, 작업별 폴더에는 등록이 없었고 그대로 복사하면 원래 폴더의 코드를 검사했다. 두 가지를 바꿨다.

- 명령을 프로젝트 루트 기준 상대경로로만 적는다. Codex는 세션의 작업 폴더에서 Hook 명령을 실행하므로 같은 등록이 폴더마다 그 폴더의 코드를 가리킨다.
- 절대경로가 없어졌으므로 등록을 Git으로 공유한다. 작업 폴더는 기준 커밋에서 만들어지므로 등록이 따라온다.

교재 본문은 `.codex`가 Git으로 전달되지 않으므로 새 폴더에서 다시 연결한다고 안내한다. 여기서는 등록을 폴더마다 다시 만드는 대신 등록에서 장비에 묶인 경로를 없애 Git으로 전달하는 쪽을 골랐다.

한글 출력은 Hook 프로그램이 UTF-8 바이트로 직접 쓰게 했다. 문제의 옵션은 처음에 명령에서 뺐다가 작은따옴표로 감싸 다시 넣었다. 두 Hook은 빌드 없이 소스 파일 하나로 실행되는데, Java 17은 그 소스 파일을 운영체제의 기본 문자 집합으로 읽는다. JDK 17에서 기본 문자 집합을 한국어 Windows의 것으로 두고 시작 Hook을 실행하면 소스의 한글이 깨져 구조 문서를 자르는 제목을 찾지 못했고, 옵션을 주면 정상이었다. 옵션은 출력이 아니라 소스를 읽는 방식을 정하고 있었다. 고친 등록의 명령은 문자열 그대로 PowerShell과 `sh`에 넘겨 실행해 확인했다.

**종료 Hook의 동작.** 11주차 Day 5에는 Hook이 판정만 하고 멈추게 했다. 한 세션이 메인과 작업자를 겸해서 Hook과 메인이 같은 실패에 수정 요청을 겹쳐 냈기 때문이다. 지금은 작업자가 따로 실행되고 "검사를 통과시킨 뒤 돌려준다"가 작업자의 일이다. 그래서 첫 실패에는 같은 세션이 한 번 고치게 하고, 고친 뒤에도 실패하면 멈추게 했다. 메인의 수정 요청은 세션이 끝난 뒤의 일이라 겹치지 않는다. 작업자의 지침에 문장으로만 있던 "통과시킨 뒤 돌려준다"를 종료 Hook이 코드로 맡는다.

질문을 남기고 멈춘 작업자에게는 검사하지 않는다. 종료 Hook이 받는 사건에 작업자의 마지막 응답이 들어 있어, 그 응답 전체가 JSON 객체이고 멈춤이며 질문이 하나 이상이면 검사를 건너뛴다. Hook은 이 둘만 보고, 결과의 나머지 항목이 형식에 맞는지는 실행 관리가 확인한다. 글로 쓴 질문은 멈춤으로 읽지 못한다. 처음에는 이 판정을 사건 문자열에 대한 정규식으로 했다. 마지막 응답은 사건 안에 문자열로 한 번 더 들어가므로, 결과 JSON의 줄바꿈이 사건에서는 역슬래시와 `n` 두 글자가 된다. 정규식은 그 모양에 따라 같은 뜻의 결과를 놓쳤고, 질문이 빈 멈춤 결과도 건너뛰었다. 사건과 그 안의 결과를 차례로 JSON으로 해석하도록 고쳤다. Hook은 라이브러리 없이 실행되므로 필요한 만큼의 해석기를 프로그램 안에 두었다.

검사의 결과를 얻지 못한 경우(실행 불가)에는 고치게 하지 않고 멈춘다. Gradle을 시작하지 못한 경우도, 작업자의 코드가 컴파일되지 않아 결과 파일이 생기지 않은 경우도 실행 불가다. Hook은 둘을 가리지 못하므로 멈추고 로그 위치를 알린다.

**시작 Hook의 내용.** 구조 문서 전체가 아니라 앞부분(업무 요구, 처리 순서, 지금 구현된 것, 제공 자료)만 전달하고 나머지의 위치를 알린다. 문서가 사람이 읽을 만큼 자세해지면서 전체를 넣기에는 길어졌다.

**최종 검사와의 관계.** 둘 다 둔다. 종료 Hook은 작업자가 통과한 상태로 끝내게 하고, 최종 검사는 작업자와 Hook의 보고와 별개로 확인한다. 실행 관리는 종료 Hook이 그 실행에서 남긴 판정 기록을 시도 폴더로 가져온다. 기록이 없으면 Hook이 호출되지 않았거나, 호출됐지만 판정을 기록하기 전에 실패한 것이다. 앞의 "걸리지 않던 원인"이 뒤의 경우였다.

**신뢰한 뒤의 실제 실행.** Codex는 등록의 내용이 바뀌면 사람이 `/hooks`로 다시 신뢰하기 전까지 그 Hook을 건너뛴다. 등록을 고친 직후의 실행에서는 로그에 Hook을 호출한 줄이 없었다. 신뢰한 뒤 Codex를 비대화형으로 실행해 다음을 확인했다. 기록은 `inquiry_desk/.local/tasks/07-hook-verify/`에 있다.

| 실행 | 결과 |
|---|---|
| 원래 폴더, 아무것도 고치지 않는 요청 | 시작 Hook과 종료 Hook이 걸렸고, 종료 Hook의 검사가 통과로 기록됨 |
| 새 작업 폴더(worktree), 일부러 실패하는 검사를 넣은 상태 | 다시 신뢰하지 않아도 두 Hook이 걸림. 첫 종료에서 Hook이 세션을 이어가게 했고, 작업자는 검사의 기대값을 두고 코드를 고쳤으며, 두 번째 종료 사건에는 이어진 턴이라는 표시가 왔고 통과로 끝남 |

한 번의 신뢰가 작업 폴더로 이어진다는 것은 등록의 내용이 같으면 폴더가 달라도 신뢰된다는 뜻이고, 등록을 상대경로로 적어 폴더마다 같은 내용이 되게 한 선택이 여기서도 쓰였다.

같은 실행에서 환경 문제가 하나 드러났다. 세션을 시작한 셸의 환경에 따라 종료 Hook 안의 Gradle이 프로세스 사이 연결용 소켓을 만들지 못했고, 그 실행은 검사를 실행하지 못해 세션을 멈췄다. 소켓을 둘 폴더를 환경변수로 넘기자 통과했다. Hook의 판정 로직은 의도대로 동작했다. 결과를 얻지 못했으므로 통과로 넘기지 않고 멈춘 것이다. 다만 작업자를 시작하는 쪽이 이 환경을 갖춰 주지 않으면 작업자가 일을 다 하고도 매번 멈춘다. 작업자의 환경에서 검사가 실행되는지를 넘기기 전에 확인하라는 메인의 규칙이 이 경우를 가리킨다.

### 대역 프로세스로 확인한 것

실제 코딩 작업자 대신 `FakeWorker`를 실행했다. 입력이 닫혀야 결과를 쓰는 동작, 끝나지 않는 동작, 하위 프로세스를 띄우고 끝나지 않는 동작, 하위 프로세스를 남기고 자기만 끝나는 동작을 한다. 검사는 [src/harnessTest/java/lab/harness/run](inquiry_desk/src/harnessTest/java/lab/harness/run/)에 있다. 본문의 여섯 가지는 다음과 같다.

| 확인한 것 | 입력 | 결과 |
|---|---|---|
| 같은 작업의 두 번째 접수 거절 | 끝나지 않는 대역이 실행 중일 때 같은 작업을 다시 접수 | 거절되고 시도 폴더는 하나. 다른 작업은 같은 시각에 접수됨 |
| 제한 시간 뒤 종료 확인 | 끝나지 않는 대역, 제한 1초 | 제한 시간 초과로 기록, 종료 확인됨, 기록된 프로세스가 남지 않음, 잠금 풀림 |
| 중단 요청이 하위 프로세스까지 종료 | 하위 프로세스를 띄운 대역에 중단 요청 | 부모와 하위 프로세스 모두 사라짐, 중단으로 기록 |
| 종료 미확인이면 새 실행을 막음 | 종료 요청이 먹히지 않게 한 실행 뒤 같은 작업을 접수 | 확인 필요로 거절. 중단 명령으로 종료를 확인한 뒤 두 번째 시도가 접수됨 |
| 두 번 실행한 결과가 각각 남음 | 같은 작업을 요청문을 바꿔 두 번 실행 | 시도 1과 2에 각자의 요청문·결과·로그·검사 산출물이 있음 |
| 검사 실패와 실행 불가의 구분 | 최종 검사가 실패를 돌려준 실행과 실행 불가를 돌려준 실행 | 검사 실패와 검사 실행 불가가 다른 상태로 기록됨 |

대역은 표준 입력을 끝까지 읽어야 결과를 쓰므로, 결과가 생겼다는 것이 요청을 전달한 뒤 입력을 닫았다는 확인이 된다. 처음에 사고를 만든 것이 닫히지 않은 입력이었다.

실행 관리가 사라진 경우는 실행 진입점을 별도 프로세스로 띄운 뒤 그 프로세스만 강제로 끝내 확인했다. 작업자가 살아 있는 동안 같은 작업의 접수가 거절됐고, 중단 명령이 작업자를 끝낸 뒤 접수됐다. 작업 폴더는 임시 저장소에서 작업 둘이 서로 다른 폴더와 브랜치를 받고, 한쪽의 변경이 다른 쪽과 원래 폴더에 보이지 않으며, 커밋한 Hook 등록은 새 폴더에 따라오고 Git에서 제외된 로컬 기록은 따라오지 않는 것을 확인했다. 등록을 Git에서 제외했던 동안에는 같은 검사가 등록이 따라오지 않는 것을 확인했다.

### 검토에서 드러난 것

처음 구현은 위 여섯 가지 검사를 모두 통과한 상태였다. 검토는 그 상태에서 같은 종류의 결함을 여러 개 찾았다. **종료를 확인하지 못했는데 확인한 것으로 기록하고 잠금을 푸는 경로**다.

| 경로 | 처음 구현 | 고친 뒤 |
|---|---|---|
| 프로세스를 시작한 뒤 프로세스 기록을 남기다 오류가 남 | 시작하지 않은 것으로 기록하고 잠금을 풂. 작업자는 살아 있음 | 시작한 뒤의 오류는 종료 확인을 거침. 확인하지 못하면 잠금을 남김 |
| 프로세스를 시작한 직후, 번호를 기록하기 전에 실행 관리가 사라짐 | 기록이 없으니 남은 프로세스가 없다고 판단 | 시작 직전에 표시를 남기고 번호를 기록한 뒤 지움. 표시가 남아 있으면 끝났다고 판단하지 않음 |
| 최종 검사의 프로세스가 남음 | 작업자의 종료만 보고 잠금을 풂 | 검사도 같은 방식으로 중단하고 종료를 확인함 |
| 두 실행 관리가 오래된 잠금을 동시에 회수 | 한쪽이 새로 만든 잠금을 다른 쪽이 지워 둘 다 접수됨 | 살피고 풀고 만드는 일을 한 번에 한 곳에서만 함 |
| 기록된 번호의 프로세스가 살아 있는데 시작 시각을 비교할 수 없음 | 사라진 것으로 판단 | 가릴 수 없음으로 두고 접수를 막음. 종료 대상으로 삼지도 않음 |

이 결함들은 대역 검사가 기대한 순서대로만 일이 일어난다고 볼 때는 드러나지 않는다. 검사는 "프로세스 기록이 생긴 뒤에 두 번째 접수를 시도"했고, 결함은 기록이 생기기 전이나 두 처리가 겹치는 순간에 있었다. 검사가 통과했다는 것은 검사한 순서에서 맞다는 뜻이고, 순서가 어긋나는 경우는 코드를 읽는 검토가 찾았다.

고치는 방향은 하나로 모였다. **확인하지 못한 것은 확인하지 못한 것으로 남기고, 그 상태를 푸는 일은 사람에게 넘긴다.** 프로그램이 추측으로 잠금을 풀면 같은 폴더에 작업자가 둘 들어갈 수 있고, 잠금을 남기면 사람이 한 번 확인하면 된다.

검토 기록은 `inquiry_desk/.local/tasks/04-worker-run-manager/`에 회차별로 있다. 세 번째 검토가 남긴 두 건은 모두 고쳤다. 프로세스 기록과 종료 요청이 함께 실패했을 때 시작 표시가 지워지는 경로에는 검사를 더했다. 한 실행 안에서 번호가 다시 쓰였을 때 새 하위 프로세스를 놓치는 경로는 추적 방식을 번호와 시작 시각의 쌍으로 바꿔 고쳤고, 번호가 다시 쓰이는 상황을 만드는 검사는 두지 못했다.

그 뒤 지침·문서·Hook까지 포함한 전체를 세 번 더 검토받았다. 기록은 `inquiry_desk/.local/tasks/06-full-review/`에 있다. 코드에서는 같은 종류의 경로가 더 나왔고 같은 방향으로 고쳤다. 마지막으로 본 프로세스는 종료를 요청하기 전에 기록한다. 작업 폴더를 만드는 git도 실행 관리가 시작한 프로세스이므로 작업자와 같이 시작 전에 표시를 남기고 종료를 확인한다.

문서 쪽의 지적은 대부분 문서가 코드나 결정보다 넓게 말한 곳이었다. 미추적 상태의 Hook 등록을 공유된 것처럼 적은 곳, 기록이 없으면 Hook이 호출되지 않았다고 단정한 곳, 메인의 안을 받아들인 결정을 선택지를 놓고 고른 것처럼 적은 곳, 메인이 정해 코드에 넣은 실행 정책을 정해진 것으로 적은 곳이 그랬다. 마지막 것은 학습자에게 가져가 위 "작업의 상태"의 표처럼 정했다.

### 실제 저장소에서 확인한 것과 남은 것

이 저장소에서 대역 작업자로 실행했다. 기준 커밋에서 작업 폴더가 만들어졌고, 그 폴더에서 실제 Gradle 검사가 실행돼 검토 대기로 기록됐다. 이 실행에서 Gradle과 검사가 띄운 프로세스까지 기록됐고 끝난 뒤 남지 않았다. 기록은 `inquiry_desk/.local/harness/tasks/probe3/`에 있다.

실제 Codex 작업자를 이 경로로 실행한 것은 서비스 상태 조회가 처음이다. 대역으로는 프로세스의 시작과 종료, 잠금, 작업 폴더의 분리까지 확인됐고, 다음은 이 실행에서 처음 확인됐다.

| 확인된 것 | 근거 |
|---|---|
| 작업자의 실행 환경 안에서 Gradle 검사가 실행된다 | 작업자가 남긴 검사 기록과 작업 폴더의 검사 결과 |
| 작업 폴더에서 종료 Hook이 걸려 검사를 다시 실행한다 | 시도 폴더의 `hook-event.json` |
| 작업자가 끝난 뒤 최종 검사가 따로 실행돼 상태가 기록된다 | 시도 폴더의 `attempt.json`과 `check/` |

기록은 `inquiry_desk/.local/harness/tasks/lookup/`에 시도별로 있다. 대역에서 보지 못한 것도 하나 있었다. 작업자 쪽의 Gradle 데몬이 시도가 끝난 뒤에도 남아 작업 폴더를 잡고 있어서, 폴더를 지우기 전에 데몬을 끝내야 했다.

## 첫 업무 기능을 작업자에게 맡긴 결과

서비스 상태 조회는 계획의 사례 쉰한 줄을 그대로 넘겼고, 돌아온 구현은 그 사례를 모두 통과했다. 그런데 계획에 없는 것이 함께 들어와 있었다.

| 들어온 것 | 왜 필요 없었나 |
|---|---|
| 클라이언트에서 SDK의 응답 형식 자동 대조를 켜고 실패를 전용 예외로 구별 | 응답 확인은 이미 `StatusWire.decode` 한 곳에서 한다 |
| SDK의 동작 자체를 확인하는 검사 | 이 앱의 동작이 아니다 |
| 운영 도구 검사만 따로 병렬로 실행하는 설정, 검사 안의 출력문 | 기능이 요구하지 않는 빌드 설정이다 |
| 연결을 닫을 때 예외를 한 번 더 잡는 처리 | SDK가 안에서 잡아 값으로 돌려준다 |

**계획의 사례를 모두 통과하는 것과 계획이 요구한 것만 있는 것은 다르다.** 검사는 있어야 할 동작이 있는지를 확인하고, 없어야 할 것이 없는지는 확인하지 않는다. 그래서 검토를 요청할 때 "계획이 요구하지 않는데 들어온 것"을 따로 찾아 달라고 했고, 그 목록을 같은 작업자에게 수정으로 넘겨 덜어냈다. 공개 동작과 계획에서 온 검사의 기대값은 그대로였다. 다음 작업의 요청문에는 구현의 크기를 미리 적었다. 계획이 요구하지 않는 분기·예외 종류·설정을 더하지 않고, 더 넣고 싶은 것은 넣지 말고 후보로 적으라는 내용이다.

운영 도구의 실행 결과는 "없음"과 "조회하지 못함"의 구별이 끝까지 전달되는 것을 보여 준다.

| 입력 | 출력 | 종료 코드 |
|---|---|---|
| `get VPN` | `FOUND`, 상태 `normal`, 변경 번호 1 | 0 |
| `get PAYROLL` | `NOT_FOUND` | 0 |
| `--data-dir <없는 폴더> get VPN` | `UNAVAILABLE`, `DATA_UNREADABLE` | 1 |

`PAYROLL`은 자료에 없다는 정상 응답이고, 없는 폴더는 조회 자체를 하지 못한 실패다. 값은 `OperationsMain → StatusClient.get → (stdio MCP) → StatusServerMain → ServiceCatalog.lookup → services.json`으로 가고, 응답은 `StatusWire.encode`와 `StatusWire.decode`를 거쳐 돌아온다. 변경과 확인 내용은 풀 리퀘스트 [#4](https://github.com/MCshin00/ai-ax-learning-lab/pull/4)에 있다.

## 자연어 접수의 설계 결정

| 결정 | 기록 |
|---|---|
| 모델은 OpenAI Java SDK로 직접 호출하고 응답 형식은 엄격한 JSON Schema로 강제한다. 약속과 다른 응답은 다시 호출하지 않고 원인 값이 있는 실패로 돌려준다 | [0007](inquiry_desk/docs/adr/0007-intake-model-connection.md) |
| 접수 결과는 서비스·증상·오류 메시지 세 필드다. 서비스가 자료에 있는지는 상태 조회가 정한다 | [0008](inquiry_desk/docs/adr/0008-intake-result-and-service-existence.md) |
| 대화마다 현재 접수 결과와 발언 원문을 보관하고, 모델에는 이전 결과와 새 발언만 보낸다. 서비스가 없으면 코드에 정해 둔 질문을 돌려준다 | [0009](inquiry_desk/docs/adr/0009-conversation-state-and-missing-target.md) |
| 지침에 서비스로 적는 범위와 예를 둔다 | [0010](inquiry_desk/docs/adr/0010-intake-instructions-and-service-scope.md) |

학습자가 직접 정한 것은 두 가지다. 모델 연결은 SDK로 한다. 접수가 서비스 목록을 따로 두고 목록 밖의 서비스를 가려내는 안은 받아들이지 않는다. 나머지는 메인의 안을 검토해 받아들인 것이다.

**SDK를 직접 쓰는 것과 프레임워크에 맡기는 것의 차이는 누가 요청을 조립하고 응답을 해석하는가다.** 프레임워크는 요청 조립, 타입 변환, 도구 호출의 반복, 대화 메모리를 맡아 준다. 접수에는 도구 호출의 반복이 없고, 대화 메모리는 메시지 목록을 다시 보내는 구조여서 이전 접수 결과만 보내는 방식과 맞지 않는다. 남는 두 가지는 직접 쓰는 편이 형식의 강제와 실패의 구분이 코드에 드러난다. 운영 문서 검색을 모델이 도구로 요청하게 정하면 이 판단을 다시 본다.

**같은 판단을 두 곳에 두지 않는다.** 처음 안은 접수가 서비스 목록을 갖고 목록 밖의 서비스를 별도 자리에 적어 조회하지 않는 것이었다. 상태 조회가 이미 자료에 없는 서비스를 `NOT_FOUND`라는 정상 결과로 돌려주므로, 접수가 목록을 따로 두면 "어떤 서비스가 있는가"의 답이 두 곳에 생긴다. 둘이 어긋나면 자료에 있는 서비스를 없다고 안내하게 된다. 그래서 접수는 직원이 말한 서비스를 전부 적고, 코드는 전부 조회하며, 있는지 없는지는 조회 결과가 정한다. 이름과 ID의 대응표가 남는 것은 자료에 직원이 부르는 이름이 없기 때문이고, 표기를 맞추는 데만 쓴다.

**문장을 이해해야 하는 일만 모델에게 맡긴다.** "통합 로그인도 느려요"는 서비스를 더하는 발언이고 "VPN이 아니라 통합 로그인 문제예요"는 바꾸는 발언이다. 이 구별은 모델이 한다. 서비스가 없을 때 무엇을 물을지, 조회를 어떤 순서로 할지, 실패한 발언을 상태에 반영할지는 코드가 정한다. 질문 문장을 코드에 두면 항상 같은 질문이 나가고 검사에서 글자 그대로 비교할 수 있다.

계획은 상태 조회 때와 다르게 적었다. 공개되는 형태와 규칙, 대표 경우 열세 줄만 적고, 규칙으로 결과가 정해지지 않는 입력은 작업자가 멈춰 묻게 했다. 작업자는 멈추지 않고 끝냈다. 검토에서 분류가 갈리는 경우가 하나 나왔는데(응답 본문을 받는 도중의 시간 초과가 형식 오류로 분류되는 경로), 어느 쪽이든 실패로 돌아가고 대화 상태는 그대로여서 고치지 않았다.

### 대역으로 확인한 것과 실제 모델로 확인한 것

| 무엇으로 | 확인된 것 |
|---|---|
| 준비한 모델 응답과 실제 상태 서버 연결(자동 검사) | 모델에 가는 요청에 스키마와 이전 결과·새 발언이 들어가는 것, 접수 결과의 서비스가 순서대로 조회되는 것, 한 서비스의 실패가 다른 결과를 지우지 않는 것, 실패한 발언이 대화 상태를 바꾸지 않는 것, 공개 결과의 형태 |
| 실제 모델(gpt-5.4-mini, IDE 실행) | 발언에서 서비스·증상·오류 메시지를 읽어 내는 것, 이름을 ID로 바꾸는 것, 이전 결과에 새 발언을 합치는 것 |

자동 검사는 모두 통과한 상태였는데 실제 모델의 첫 실행에서 다음이 나왔다.

| 입력 | 나온 것 | 기대 |
|---|---|---|
| `급여 시스템이 안 돼요` (세 번) | 서비스 없음, 질문 | `급여 시스템`을 적고 `NOT_FOUND` |
| `VPN이랑 급여 시스템이 안 돼요` | 서비스 `VPN`만 | `VPN`, `급여 시스템` |
| `VPN이 자꾸 끊겨요` → `VPN이 아니라 통합 로그인 문제예요` | 서비스 `통합 로그인`(`NOT_FOUND`), 증상 `문제예요` | 서비스 `SSO`, 증상 유지 |

세 완료 조건(해석이 조회로 이어짐, 질문 뒤 같은 문의가 이어짐, 대화가 섞이지 않음)은 이때도 충족됐다. 어긋난 것은 표현의 해석이었고, 이것은 대역 검사가 볼 수 없는 부분이다. 대역 검사에서는 "모델이 `VPN`, `급여 시스템`을 돌려주면"이라는 가정이 준비한 응답으로 들어가 있어서, 모델이 실제로 그렇게 돌려주는지는 검사의 대상이 아니다.

지침을 고친 뒤 같은 입력을 다시 실행했다.

| 입력 | 고치기 전 | 고친 뒤 |
|---|---|---|
| `급여 시스템이 안 돼요` | 서비스 없음, 질문 | `급여 시스템`, `NOT_FOUND` |
| `VPN이랑 급여 시스템이 안 돼요` | `VPN`만 | `VPN`의 `FOUND`와 `급여 시스템`의 `NOT_FOUND` |
| `통합인증이 느려요` | `통합인증`, `NOT_FOUND` | `SSO`, 상태 조회됨 |
| `VPN이 아니라 통합 로그인 문제예요` | `통합 로그인`, 증상 `문제예요` | `SSO`, 증상 `자꾸 끊김` 유지 |
| `인증서 만료 메시지가 나와요` (새 대화) | 오류 메시지가 증상에 들어감 | `errorMessage`에 들어감 |
| `사내망 연결이 자꾸 끊겨요`, `인터넷이 안 돼요` | 서비스 없음, 질문 | 같음 |

### 지침을 고친 방법

고친 것은 네 가지다. 대응표를 `"통합 로그인", "통합인증" → SSO`처럼 이름에서 ID로 가는 방향으로 적었다. 서비스로 적는 범위를 적었다. 바로잡는 발언에서도 표로 ID를 맞추고 말하지 않은 필드를 유지하라고 적었다. 모델이 실제로 받는 입력과 같은 형식의 예를 다섯 개 넣었다.

**규칙을 강하게 쓰면 반대쪽이 흔들린다.** "표에 없는 서비스도 적으라"만 강조하면 `사내망`이나 `인터넷`도 서비스로 적혀 질문 대신 `NOT_FOUND`가 나갈 수 있다. 이름을 말한 업무 시스템은 적고 와이파이·네트워크·PC 같은 일반적인 환경은 적지 않는다는 경계를 함께 적었고, 다시 실행했을 때 두 입력은 그대로 질문이 돌아왔다.

**확인할 발언을 예에 넣지 않는다.** 예에는 `그룹웨어`, `전자결재`, `와이파이`를 쓰고 `급여 시스템`, `사내망`, `인터넷`과 정정 사례는 넣지 않았다. 확인할 문장이 지침에 그대로 있으면 다시 실행해 맞게 나와도 그 문장을 외운 것인지 규칙이 통한 것인지 가릴 수 없다. 고친 뒤의 결과는 지침에 없는 발언에서 나온 것이어서 규칙과 예가 다른 표현에도 통했다고 볼 수 있다.

**관찰과 원인은 나눠 적는다.** 확인된 것은 표에 없는 서비스가 접수 결과에서 빠졌다는 결과다. 모델이 대응표를 허용 목록처럼 읽었다는 것은 추정이다. 표의 방향을 적고 예를 넣자 결과가 바뀌었다는 것은 그 추정과 맞지만, 네 가지를 한꺼번에 고쳤으므로 어느 것이 효과를 냈는지는 가려지지 않았다.

이 결과는 모델 하나로 입력마다 한두 번 실행한 것이다. 모델을 바꾸면 같은 입력으로 다시 확인해야 한다. 표기를 맞추는 일은 계속 모델이 맡고 있고, 표의 이름이 ID로 바뀌지 않는 경우가 다시 나오면 코드가 정확히 같은 이름을 ID로 바꾸는 방식을 검토한다.

두 번째 실행의 첫 줄에서는 증상이 `접속이 안 돼요a|접속이 안 돼요`로 나왔다. 모델에는 대화 ID를 보내지 않으므로 `a|`는 발언에 들어 있던 글자다. 콘솔에 같은 줄이 두 번 이어 들어간 것으로 보이고, 입력 줄은 첫 `|`에서만 나누므로 나머지가 그대로 발언이 됐다. 이 값이 뒤의 두 발언에서도 그대로 유지된 것은 이전 결과가 이어진다는 근거이기도 하다.

### 작업 기록에 적을 것

작업 한 건의 기록은 풀 리퀘스트 본문이다. 처음 두 건의 본문에는 변경과 무관한 것이 섞여 있었다. 누가 어느 단계에서 다시 실행했는지, 검토가 몇 번이었는지, 커밋된 적 없는 중간 상태에서 무엇을 덜어냈는지, IDE에서 실행하지 않았다는 사실 같은 것이다. 실제 키가 필요한 실행을 IDE에서 한다는 것은 학습을 위한 작업 방식이고 변경의 내용이 아니다.

문장을 가르는 기준은 하나로 정리됐다. **지웠을 때 입력의 결과, 책임을 나눈 이유, 검사가 보장하는 범위를 다르게 이해하게 되면 남긴다.** "모델 응답은 준비한 값이어서 해석의 품질은 확인되지 않았다"는 남고, "IDE에서 실행하지 않았다"는 빠진다. 본문에 "확인하지 못한 것"이라는 절을 반드시 채우게 한 지침이 채울 것을 찾게 만들었으므로, 그 항목은 작업자가 메인에게 돌려주는 결과에만 두고 본문에는 읽는 사람이 오해할 만한 것만 해당 설명 옆에 적게 했다. 기준은 `inquiry_desk/AGENTS.md`의 "풀 리퀘스트 본문 초안"에 있다.
