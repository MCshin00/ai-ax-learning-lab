# 문의 처리 앱 변경

## 요구와 현재 처리 확인

1. `AGENTS.md`에서 작업 원칙을, `docs/project.md`에서 합의한 업무 조건과 현재 구현·검사 위치를 확인하고 관련 코드와 대조한다.
2. 요청에서 확정된 조건과 결과를 바꿀 미정 조건을 구분한다. 기존 합의를 사용하고, 새 업무 선택이 필요하면 실제 입력별 결과 차이와 추천 이유를 메인에 돌려준다. 요구 합의는 메인이 맡는다.
3. 입력부터 출력까지 호출을 따라가며 변경할 처리를 찾는다. 공개 입력·반환값에 영향을 받는 호출부와 검사를 함께 확인한다. 아직 없는 기능을 구현된 것으로 가정하지 않는다.

## 검사 입력과 구현

1. 요구와 합의한 규칙에서 작은 입력과 기대 결과를 도출한다. “접속이 안 돼요”처럼 서비스가 없으면 다시 묻는지, “급여 시스템이 안 돼요”처럼 자료 밖의 서비스는 상태를 만들지 않는지 확인한다.
2. 새 조건을 구별하는 입력과 영향을 받는 기존 입력을 검사에 담는다. 예를 들어 “VPN이 끊기고 통합 로그인도 느려요”에서는 서비스별 사실·근거를 나누고, 한 조회가 실패해도 다른 결과가 보존되어야 한다. 자료에 서비스가 없는 정상 응답과 조회 자체의 실패도 구별한다.
3. 저장 관련 변경에서는 문의 처리만으로 저장되지 않는지, 담당자의 확인 뒤 편집한 본문이 전달되는지 확인한다. 필수 상태 조회와 저장 조건은 코드가 관리하며 모델에는 저장 도구를 주지 않는다.
4. 합의한 위치를 구현하고 호출부·관련 검사·프로젝트 설명을 함께 갱신한다. 같은 설계 안의 단순 수정은 정해진 조건에 따라 진행한다. 검사는 대역 모델·가짜 설정·임시 자료로 실행하고 환경변수 파일을 읽는 로더와 인증 입력은 대역으로 바꾼다.

## 실행과 결과 해석

`AGENTS.md`에 따라 Gradle `test`를 실행한다. Hook 변경이면 `harnessTest`, 공통 빌드 설정 변경이면 두 작업을 확인한다. 실패는 입력·기대값·실제값을 대조해 원인과 결과 위치를 메인에 돌려준다. 작업자가 수정 요청을 스스로 반복하지 않으며 Stop Hook도 수정 요청을 만들지 않는다. 실행하지 못했거나 검사가 없는 상태는 통과가 아니다.

결과에는 요청한 조건, 바뀐 처리, 대표 입력과 실제 출력을 연결한다. 예상과 달랐던 이유와 추가 확인이 필요한 동작은 해당 근거와 함께 설명한다. 검사 통과와 실제 모델 품질·Codex Hook 발동 확인을 구분한다. 변경 파일·확인한 동작·남은 결정과 다음 행동은 `.local/harness/checkpoint.md`에, 확정된 조건과 현재 구조는 `docs/project.md`에 반영한다.
