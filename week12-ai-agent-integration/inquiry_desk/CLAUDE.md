# 메인(Claude)의 작업 규칙

메인은 설계, 작업 지시, 최종 검사를 맡는다. 구현은 Codex 작업자가 `AGENTS.md`에 따라 하고, 변경의 검토는 별도의 Codex 검토자가 한다.

## 계획과 승인

- 학습자가 구현 방식을 정해 주면 그것을 계획으로 옮기고 빠진 경우를 짚는다. 학습자가 계획을 요구하면 계획을 제시한다. 어느 경우든 학습자가 승인한 계획이 있어야 작업자에게 넘긴다.
- 계획에는 공개할 동작, 입력의 종류별 기대 결과, 건드릴 범위, 추가할 라이브러리를 적는다. 이미 정해진 것, 메인이 설계로 정해 승인을 요청하는 것, 작업자에게 맡기는 것을 구분한다.
- 공개 입출력과 실패했을 때의 동작은 학습자가 정한다. 새로 공개하는 동작마다 정상, 없음, 잘못된 입력, 자료가 잘못됨, 일부만 실패, 같은 요청의 반복, 표기 차이를 대 보고, 기대 결과가 정해지지 않은 것을 넘기기 전에 학습자에게 가져간다.
- 학습자의 답이 제안과 다른 내용을 다루면 그 제안은 승인되지 않은 것이다. 다시 묻는다.
- 지침·문서의 문장이나 파일 배치처럼 앱의 결과를 바꾸지 않는 것은 메인이 정하고 요약해 알린다. 한 줄씩 묻지 않는다.
- 공개된 형태를 바꿔야 하면 필드 추가로 해결되는지 먼저 본다. 이름 변경·삭제·뜻의 변경이면 계획에 밝히고 읽는 쪽의 수정을 같은 작업에 넣는다.
- 설계에 참고 구현 `../references/incident_desk`를 쓰지 않는다. 구현이 끝난 뒤 같은 입력으로 비교한다.
- 정해진 결정과 이유는 `docs/adr/`에 결정 하나당 한 파일로 남긴다.

## 작업 지시

- 작업자는 작업마다 별도 브랜치의 worktree에서 실행한다. 메인 작업 폴더에서 작업자를 직접 실행하지 않는다. 한 worktree에는 작업자 하나만 둔다.
- 새 작업을 넘기기 전에 앞선 실행의 프로세스가 끝났는지 확인한다. 실행을 중단했다면 프로세스가 실제로 사라졌는지 확인한 뒤 다시 넘긴다.
- 서로 다른 파일과 검사로 나뉘는 작업만 동시에 맡긴다. 같은 파일을 바꾸는 작업은 순서대로 맡긴다.
- 넘기기 전에 작업자의 환경에서 검사가 실행되는지 확인하고, 계획에 적은 라이브러리를 미리 내려받아 둔다.
- 요청문에는 승인된 계획, 담당 범위, 검사 방법, 돌려받을 항목을 적는다. 요청문과 결과는 `.local/tasks/`에 실행마다 따로 남긴다.

## 검토

- 작업자의 결과는 별도의 Codex 검토자가 읽기 전용으로 검토한다. 작업자와 같은 세션을 쓰지 않는다.
- 검토자는 저장소 루트를 작업 폴더로 실행한다. 이 프로젝트 폴더에서 실행하면 종료 Hook이 검토자의 세션에도 걸려, 검사가 실패한 상태일 때 검토자에게 코드를 고치라고 한다.
- 검토를 요청할 때는 바뀐 파일을 코드·검사·지침·문서·결정 기록·계획까지 모두 적고, 파일마다 끝까지 읽었는지와 판정을 받는다. 앞선 검토 뒤에 고친 것도 대상에 넣는다.
- 요청문에는 검토자가 대화를 보지 않고도 판단할 수 있게 상황을 적는다. 학습자가 정한 것과 그 이유, 앞선 지적마다 어디를 어떻게 고쳤는지, 메인이 실행해 확인한 것과 확인하지 못한 것, 메인이 스스로 정한 것, 메인이 놓쳤을 만한 곳이다. 메인이 고쳤다고 적은 것도 코드와 대조해 달라고 요청한다.
- 검토자는 변경을 요구·계획과 대조하고, 계획이 요구를 덮었는지도 본다. 공개된 동작의 경로에서 결과가 갈리는 분기를 모두 찾아 계획의 조건에 대응시키고, 대응되지 않는 분기를 보고한다.
- 검토자의 지적은 인용한 파일과 행을 직접 확인한 뒤 수용하거나 반박한다. 같은 변경의 검토가 세 번을 넘어가면 남은 쟁점을 학습자에게 가져가 계속할지 정한다. 설계 선택에 대한 이견은 메인과 검토자가 결론 내지 않고 학습자에게 묻는다.

## 최종 검사와 합치기

- 작업자가 통과를 보고해도 메인이 검사를 직접 실행한다. 업무 코드와 그 검사의 변경은 Gradle `test`, 작업자 실행 관리·Hook·그 검사의 변경은 `harnessTest`, 빌드 설정의 변경은 둘 다 실행한다. 계획의 기대 결과와 검사의 기대값이 같은지 대조하고, 대표 입력의 실제 출력을 확인한다.
- 고칠 기회는 세 종류이고 서로 다르다.

  | 누가 | 언제 | 상한 |
  |---|---|---|
  | 작업자 | 세션 안에서 검사가 실패할 때 | 횟수 제한 없음. 실행의 제한 시간까지. 기대 결과를 바꿔야만 통과하면 멈춤 |
  | 종료 Hook | 작업자가 응답을 끝내려는 순간 검사가 실패할 때 | 같은 세션에서 한 번 |
  | 메인 | 세션이 끝난 뒤 최종 검사나 검토에서 나온 것 | 같은 실패에 한 번. 다시 남으면 결과 위치와 이유를 학습자에게 가져가 계속할지 정한다 |

- 메인의 한 번과 검토의 세 번은 포기하는 지점이 아니라 학습자에게 가져가는 지점이다.
- Hook 등록(`.codex/hooks.json`)을 고치면 Codex가 그 Hook을 건너뛴다. 학습자에게 `/hooks` 신뢰를 요청하고, 신뢰 뒤 실제 세션에서 걸리는지 확인한다. 시도 폴더에 `hook-event.json`이 없으면 그 실행에서 종료 Hook이 호출되지 않았거나, 호출됐지만 판정을 기록하기 전에 실패한 것이다. 어느 쪽인지는 그 시도의 `worker.log`에서 `hook:` 줄을 찾아 가린다.
- 종료 Hook이 작업자의 세션을 멈춘 실행도 상태는 최종 검사의 판정을 따른다. 멈췄다는 사실은 상태의 이유와 시도 폴더의 `hook-event.json`에 남으므로, 최종 검사가 통과했더라도 Hook이 멈춘 이유를 확인하고 검토 요청문에 적는다.
- 작업 한 건의 기록은 풀 리퀘스트 본문이다. 작업자의 초안을 `AGENTS.md`의 "풀 리퀘스트 본문 초안"에 맞춰 편집하고, 메인의 재검사에서 달라진 사실이 있으면 해당 설명을 고친다. 재검사와 검토의 경과, 결과 JSON의 항목은 덧붙이지 않는다. 로컬 절대경로와 민감정보가 없는지 확인한 뒤 올린다. AI 기여자 표기를 넣지 않는다.
- 합치는 동작이 학습자의 승인이다. 학습자가 합쳐도 된다고 하기 전에는 합치지 않는다.
- 합친 뒤에는 합친 코드에서 같은 검사를 다시 실행한다. 작업 브랜치에서 통과한 것과 합친 결과가 통과하는 것은 다르다.
- 실제 모델 키가 필요한 실행은 학습자가 IDE에서 한다. 환경변수 파일은 읽지 않는다.
