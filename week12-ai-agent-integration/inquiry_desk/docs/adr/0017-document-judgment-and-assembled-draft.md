# 0017 — 문서를 못 찾으면 서비스의 문서를 넘기고, 문서마다 적용 여부를 값으로 받아 코드가 본문을 조립한다

- 정한 날: 2026-10-12

## 상황

실제 모델에서 서비스의 상태는 확인됐는데 초안 없이 끝난 문의가 있었다. "VPN 접속이 안 돼요", "통합 로그인이 안 돼요", "VPN과 급여 시스템이 안 돼요"의 VPN, 대상을 정정한 뒤의 통합 로그인 문의다. 넷 모두 어휘 검색의 결과가 `NONE`이었다. `NONE`은 낱말이 하나도 겹치지 않았다는 뜻인데 흐름은 그것을 근거 없음으로 끝냈다([0012](0012-runbook-search.md)의 한계).

문서가 걸려도 그 문서가 문의에 적용되는지는 초안 본문의 문장에 맡겨져 있었다([0013](0013-source-check-and-missing-evidence.md)의 한계). 인증서 만료만 접수된 문의의 초안에 일반 연결 문서의 확인 항목이 들어갔다. 지침의 문장으로 고치려던 네 차례의 확인에서는 문서 제목을 준 다시 쓰기가 속도 문의에도 연결 문서를 찾았고, 일부 초안이 적용 조건이 확인되지 않은 문서의 항목을 할 일에 넣었다. 이 후보들은 채택하지 않았다.

정하기 전에 접수 결과와 문서를 고정하고 판정 호출만 실제 모델로 세 차례 확인했다.

| 실행 | 지침과 입력 | 결과 |
|---|---|---|
| 1 | 문서별 판정을 값으로 받는 첫 지침, 상태 조회 결과를 함께 줌 | 맞지 않는 문서를 적용으로 판정한 것 없음. 문서의 조건을 옮긴 글자가 조건문이 없는 문서에서 실행마다 달랐음 |
| 2 | 조건을 옮기는 문단을 고치고 응답의 필드 순서를 고정 | 조건의 글자는 문서 그대로가 됨. 통합 로그인 "로그인이 안 됨"이 두 번 모두 적용으로 판정됨 |
| 3 | 판정 호출의 입력에서 상태 조회 결과를 빼고 판정 문단을 고침 | 15번에서 맞지 않는 문서의 적용 판정 없음. 다루지 않음이던 판정 일곱 개가 조건 미확인이 됨 |

실행 3에서 실행 2와 같은 지침·입력·필드 순서를 세 번 더 돌렸을 때는 세 번 모두 조건 미확인이었다. 같은 구성에서 다섯 번 중 두 번 적용 판정이 나온 것이고, 원인은 특정하지 못했다.

## 결정

| 정할 것 | 결정 |
|---|---|
| 문서를 못 찾았을 때 | 검색어를 모델이 다시 쓰지 않는다. 낱말이 겹치는 문서가 없고 그 서비스에 문서가 있으면 그 서비스의 문서를 자료 순서대로 모두 넘긴다. 검색 결과의 값은 `FOUND`(점수 순, 최대 2개), `ALL`(서비스의 문서 모두), `NONE`(그 서비스에 문서 없음), `FAILED`다 |
| 모델 호출 | 발언 하나에 최대 2회(접수, 판정)다 |
| 판정 호출의 입력 | 접수 결과와 문서(ID, 서비스, 제목, 본문)다. 상태 조회 결과는 주지 않는다 |
| 모델이 돌려주는 것 | 문서마다 `id`, `condition`(문서가 다루는 증상이나 오류를 문서의 표현 그대로), `judgment`(`APPLIES`, `CONDITION_UNCONFIRMED`, `NOT_COVERED`), `actions`(`APPLIES`일 때만. 문서가 확인·요청하라고 한 일과 금지한 일을 문장마다 한 항목, 조건과 의무·금지의 세기는 그대로) |
| 조건을 알 수 없는 문의 | 그 문서가 다루는 경우인지 확인하는 줄 하나만 본문에 싣는다. 문서의 대응 항목은 싣지 않는다 |
| 본문 | 코드가 조립한다. 접수 내용은 접수 결과로, 상태는 상태 조회 결과로, 할 일은 판정으로, 확인하지 못한 서비스는 상태 조회 결과와 알림으로 쓴다. 모델이 쓴 글은 `APPLIES`인 문서의 `actions`와 조건 미확인인 문서의 `condition`만 들어간다 |
| 구획 | 접수 내용, 상태 조회로 확인된 것, 운영 문서 기준으로 확인하거나 요청할 일, 상태나 문서를 확인하지 못한 서비스의 순서다 |
| 출처 | `APPLIES`와 `CONDITION_UNCONFIRMED`인 문서의 ID를 넘겨준 문서의 순서로 코드가 정한다. 모델은 출처를 돌려주지 않는다 |
| 초안이 있는 때 | `APPLIES`나 `CONDITION_UNCONFIRMED`인 문서가 문의 전체에 하나 이상일 때다. 넘긴 문서가 모두 `NOT_COVERED`이면 초안은 없고 담당자가 본문을 쓴다 |
| 쓸 수 없는 판정 | 넘겨준 문서마다 정확히 한 항목이 아니면 `SOURCE_MISMATCH`, `APPLIES`인데 `actions`가 비었거나 `CONDITION_UNCONFIRMED`인데 `condition`이 공백이면 `INVALID_OUTPUT`이다. 어느 경우든 판정 전체를 버리고 초안을 만들지 않는다 |
| `NO_EVIDENCE` | 그 서비스에 문서가 없거나 넘긴 문서가 모두 `NOT_COVERED`일 때 그 서비스에 붙는다. 판정 전체를 버렸을 때는 버린 판정으로 이 알림을 붙이지 않는다 |

## 이유

이전 검색의 `NONE`은 서비스에 문서가 있어도 낱말이 겹치지 않으면 나왔다. 이것을 문서가 문의를 다루지 않는다는 판정으로 다루지 않고, 서비스에 문서가 있으면 `ALL`로 범위를 넓혀 판정하게 한다. 서비스당 문서가 한두 개여서 모두 넘겨도 입력이 커지지 않는다. 검색어를 다시 쓰는 단계는 문서의 용어를 모르는 모델이 표현을 바꿔 보는 일이었고, 실제 모델에서 서비스 이름을 넣거나 뜻이 다른 낱말을 가져와 맞지 않는 문서를 걸었다([0012](0012-runbook-search.md)).

판정을 값으로 받는 것은 조건이 맞지 않는 문서의 대응을 본문에서 빼는 일을 코드가 하기 위해서다. 문장으로 쓰게 하면 "다루지 않는다"고 적으면서 할 일 구획에 그 문서의 항목을 옮긴 초안이 나왔다. 값으로 받으면 `APPLIES`가 아닌 문서의 항목은 모델이 써 와도 본문에 들어가지 않는다.

조건을 알 수 없을 때 확인 줄 하나만 싣는 것은, 문서의 확인 사항까지 적게 한 지침이 속도 문의에 연결 문서를 적용하는 초안을 늘렸기 때문이다([0013](0013-source-check-and-missing-evidence.md)).

접수 내용과 상태를 코드가 쓰는 것은 그 값이 이미 구조화된 자료이기 때문이다. 모델이 다시 쓰면서 직원이 말한 오류 메시지를 확인된 사실로 바꾼 사례가 있었다. 코드가 쓰면 준비한 모델 응답으로 본문 전체를 글자까지 검사할 수 있다. 잃는 것은 모델이 쓴 요약 문장이고, 본문은 양식에 가까워진다. 접수 결과 자체가 틀린 것은 이 결정으로 고쳐지지 않는다.

판정 호출에 상태를 주지 않는 것은 책임의 배치 때문이다. 판정이 답할 질문은 직원이 말한 증상과 오류가 문서의 대상에 해당하는가이고, 필요한 입력은 접수 결과와 문서다. 대응 항목은 조건을 붙인 채로 옮기므로 조건이 지금 사실인지를 모델이 풀 일이 없다. 상태는 코드가 본문에 쓴다. 쓰지 말아야 할 입력을 주고 지침으로 막는 것보다 주지 않는 편이 단순하다.

마지막 구획의 제목을 "확인되지 않은 것"에서 바꾼 것은, 코드가 쓰는 이 구획이 직원에게 더 물을 것(발생 시각 등)을 열거하는 자리가 아니기 때문이다. 그런 확인은 문서의 대응 항목에 있다.

넘겨준 문서마다 한 항목인지를 대조하는 것은 지금까지 출처 검사가 맡던 자리다. 모델이 넘겨받지 않은 문서를 돌려주거나 문서를 빠뜨리면 그 판정으로 만든 본문과 출처를 믿을 수 없다.

## 알고 있는 한계

- 모델이 조건 미확인이어야 할 문의를 적용으로 판정하면 그 문서의 항목이 본문에 들어간다. 코드는 이것을 가르지 못하고 담당자의 검토가 맡는다. 확인 실행 2의 지침에서 통합 로그인 "로그인이 안 됨"이 다섯 번 중 두 번 적용으로 판정됐다. 채택한 지침의 15번에서는 나오지 않았지만 그 횟수로 없어졌다고 말할 수 없다.
- 채택한 지침은 조건 미확인을 넓게 준다. 속도 문의에 "VPN 연결이 끊기는 경우인지 확인합니다" 한 줄이 든 초안이 나오고, 인증서 만료 문의의 초안에는 같은 줄이 하나 더 붙으며, 접속 문의에는 확인 줄이 둘이다. 그 문서들은 출처에 남고 그 서비스에 `NO_EVIDENCE`는 붙지 않는다. 알림이나 미처리 항목이 없다는 것이 적용 조건까지 확인됐다는 뜻은 아니다.
- `condition`은 모델이 쓰는 문자열이고 코드는 그것을 자르거나 문법을 검사하지 않는다. 문서의 대상만 담겼는지는 지침과 실제 출력의 대조로 본다.
- 문서 전체의 적용은 그 문서의 모든 조건이 충족됐다는 뜻이 아니다. 항목마다 붙은 조건("재연결 뒤에도 반복되면", "공통 장애가 진행 중이면")은 문장에 남아 담당자가 읽는다.
- 검색에서 낱말이 겹친 문서가 하나라도 있으면 범위를 넓히지 않는다. 걸린 문서가 맞지 않고 걸리지 않은 문서가 맞는 경우는 이 결정으로 고쳐지지 않는다.
- 접수 결과의 증상에 서비스 이름이 섞인 경우 본문의 접수 내용에 그대로 실린다.

## 다시 볼 조건

- 적용으로 잘못 판정된 초안이 담당자 검토에서 되풀이해 걸러지면, 문서의 적용을 담당자가 확인한 뒤 대응을 조립하거나 초안에는 문서의 대상 확인만 싣는 구성을 검토한다. 같은 구조에서 지침만 더 고치지 않는다.
- 필요 없는 확인 줄이 담당자의 편집 부담이 되면 판정 지침을 다시 보되, 그 글자로 실제 모델을 돌려 본 뒤에 바꾼다.
- 서비스당 문서가 늘어 모두 넘기기 어려워지면 넓히는 범위에 수를 두거나 검색 방식을 다시 본다([0012](0012-runbook-search.md)).
