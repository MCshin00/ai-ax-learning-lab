# 0015 — 담당자 화면에는 분석과 저장을 따로 공개하고, 진행 중에는 처리 단계만 보낸다

- 정한 날: 2026-10-12
- 2026-10-12: 검색어 다시 쓰기가 없어져 처리 단계는 접수, 상태 조회, 검색, 초안이고 모델 호출은 문의 하나에 최대 두 번이다. 아래의 "최대 세 번"과 "검색어 다시 쓰기"는 그 전의 설명이다([0017](0017-document-judgment-and-assembled-draft.md)).

## 상황

콘솔은 흐름을 확인하는 진입점이다. 담당자 화면이 같은 분석과 저장을 쓰려면 HTTP로 공개해야 한다. 문의 하나에 모델 호출이 최대 세 번이고 조회와 검색이 이어져 실제 모델에서는 수 초가 걸린다. 초안은 출처 검사에서 버려질 수 있다([0013](0013-source-check-and-missing-evidence.md)).

정하기 전에 JDK의 HTTP 서버로 확인했다. 이벤트를 쓰고 내보낼 때마다 받는 쪽에 하나씩 도착했다. 받는 쪽이 연결을 끊은 직후의 쓰기는 성공했고 그다음 쓰기에서 실패했다.

## 결정

| 정할 것 | 결정 |
|---|---|
| 요청의 구성 | 분석 `POST /inquiries`와 저장 `POST /requests`를 나눈다. 저장 요청은 분석 결과의 검토 ID로 검토본을 가리킨다([0014](0014-review-and-save.md)) |
| 업무 상태 | 추가 질문 필요(`NEEDS_INPUT`), 접수 실패(`FAILED`), 일부만 준비는 200 응답 안의 값이다. 일부만 준비된 것은 검토본의 미처리 목록으로 안다 |
| 요청 형식 오류 | 400이다. 분석 요청은 스트림을 시작하기 전에 확인한다 |
| 저장 거절 | 오래된 검토본, 내용 충돌, 상태 변경은 409와 원인 값이다. 서버에 연결하지 못했거나 서버가 읽기·쓰기에 실패하면 503이다 |
| 진행 중에 보내는 것 | 처리 단계(접수, 상태 조회, 검색, 검색어 다시 쓰기, 초안)의 시작. 모델이 쓰는 글자와 부분 결과는 보내지 않는다 |
| 전송 방식 | 분석 요청의 응답을 SSE로 보낸다. 단계마다 `stage`, 마지막에 `result` 하나다 |
| 화면이 연결을 끊었을 때 | 더 보내지 않고 분석은 끝까지 한다 |
| 동시에 온 요청 | 한 번에 하나씩 처리한다 |
| HTTP 서버 | JDK의 `com.sun.net.httpserver`를 쓴다. 라이브러리를 더하지 않는다 |

## 이유

분석과 저장을 나누는 것은 저장이 담당자의 확인 뒤에만 일어나야 하기 때문이다. 분석 요청은 어떤 경우에도 저장하지 않는다.

추가 질문과 일부만 준비됨은 요청이 실패한 것이 아니라 처리한 결과다. 자료에 없는 것을 정상 응답 안의 값으로 돌려주기로 한 것([0003](0003-absent-is-a-normal-result.md))과 같은 기준이다. 요청 형식 오류는 화면의 코드가 고칠 일이어서 상태 코드로 구별한다. 저장 거절은 하지 못한 것이므로 원인 값과 함께 오류로 알린다.

처리 단계만 보내는 것은 초안이 출처 검사를 통과해야 남기 때문이다. 모델이 쓰는 글자를 먼저 보내면 버려질 문장이 담당자에게 보이고 저장할 수 있는 결과로 읽힐 수 있다. 단계는 담당자에게 멈춘 것이 아니라 처리 중임을 알린다.

SSE는 문의 본문을 보낸 요청의 응답으로 단계와 결과를 이어 받을 수 있어, 작업 상태를 따로 보관하고 화면이 되풀이해 조회하는 구성이 필요 없다.

연결이 끊겨도 끝까지 하는 것은 접수 결과가 이미 대화 상태에 반영된 뒤이기 때문이다. 중간에 멈추면 대화 상태만 앞서간다. 끊긴 것을 다음 쓰기에서야 알 수 있어서 바로 멈출 수도 없다. 모델 호출은 발언 하나에 최대 세 번으로 정해져 있다([0012](0012-runbook-search.md)).

한 번에 하나씩 처리하는 것은 대화 상태, 서버 연결, 발언별 호출 수가 모두 한 번에 한 요청을 전제로 만들어졌기 때문이다.

## 알고 있는 한계

- 스트림이 시작된 뒤에는 HTTP 상태를 바꿀 수 없다. 접수 실패는 200 응답의 `result` 안에서 `FAILED`로 온다.
- 화면이 끊긴 뒤 끝난 분석의 검토 ID는 화면이 받지 못했으므로 쓸 수 없다. 화면은 같은 발언을 다시 보낸다.
- 분석이 도는 동안 온 요청은 그 분석이 끝난 뒤에 처리된다.

## 다시 볼 조건

- 여러 담당자가 동시에 써서 기다리는 시간이 문제가 되면 대화별 상태와 호출 수를 요청마다 나누고 서버 연결의 동시 호출을 정한 뒤 여러 요청을 함께 처리한다.
- 끊긴 화면이 결과를 다시 받아 가야 하면 대화의 가장 최근 검토본을 조회하는 요청을 둔다.
- 초안을 검사 없이 그대로 보여 주는 채팅형 화면이 되면 모델이 쓰는 글자를 보내는 방식을 검토한다.
