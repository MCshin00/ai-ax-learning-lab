# 0006 — 서비스 상태 조회의 입력과 자료 오류

- 정한 날: 2026-10-08
- 고친 날: 2026-10-10. 자료의 값을 확인하던 조건을 [0011](0011-each-app-owns-its-own-responsibility.md)에 따라 뺐다.

## 상황

조회 도구가 받는 입력과 읽는 자료에는 정상이 아닌 경우가 있다. 각 경우에 무엇을 돌려줄지에 따라 문의 앱의 안내가 달라진다.

## 결정

| 경우 | 결과 |
|---|---|
| 서비스 ID가 없거나 비었거나 문자열이 아님 | "없음"도 "조회하지 못함"도 아닌 별도의 결과(잘못된 입력) |
| 모르는 인수가 더 붙은 요청 | 잘못된 입력으로 거절 |
| 인수도 잘못됐고 자료도 읽을 수 없음 | 인수를 먼저 확인한다. 인수가 잘못됐으면 자료를 읽지 않고 잘못된 입력 |
| 표기가 다른 서비스 ID(예: 소문자) | 자료의 표기와 정확히 같을 때만 찾는다 |
| 자료를 파일·JSON·배열로 읽을 수 없음 | 조회하지 못함 |
| 자료의 한 행을 읽을 수 없음 | 찾는 서비스의 행에서 상태·설명·변경 번호를 읽을 수 있으면 그 결과를 돌려준다. 찾는 서비스의 행에서 읽을 수 없으면 조회하지 못함. 다른 행은 보지 않는다 |
| 조회 실패를 앱 코드에 넘기는 형태 | 예외가 아니라 그 서비스의 결과 값 |

찾는 행은 `id`가 요청한 서비스 ID와 같은 첫 행이다. 그 행에서 `state`와 `detail`을 문자열로, `revision`을 정수로 읽을 수 있으면 받은 값 그대로 돌려준다. 상태값이 아는 값인지, 설명의 내용, 변경 번호의 범위, 같은 ID가 또 있는지는 확인하지 않는다. 행에 모르는 필드가 더 있으면 무시한다.

## 이유

- 잘못된 입력은 다시 시도해도 같은 실패이고 원인이 호출한 쪽에 있다. 다른 두 결과로 안내하면 틀린 안내가 된다.
- 요청은 엄격하게 받아 호출한 쪽의 실수가 바로 드러나게 하고, 너그럽게 받는 것은 응답을 읽을 때만 한다.
- 서비스 ID는 식별자다. 느슨하게 받으면 저장과 중복 판단에서 같은 서비스가 여러 표기로 남는다. 표기를 맞추는 일은 접수 단계가 맡는다.
- 일부만 확인되어도 확인된 내용은 전달한다. 다른 서비스의 행을 읽을 수 없다는 이유로 읽을 수 있는 행의 결과를 버리지 않는다.
- 자료의 값이 옳은지는 자료를 만드는 쪽의 책임이다. 조회 서버가 상태값의 목록이나 변경 번호의 범위를 따로 가지면 자료 쪽이 바뀔 때 조회가 먼저 깨진다.
- 여러 서비스의 결과를 모을 때 한 서비스의 실패가 나머지를 버리지 않아야 한다.

## 다시 볼 조건

접수 단계가 서비스 ID의 표기를 맞추지 못하는 것으로 확인되면 표기 차이의 처리를 다시 본다.
