# 0005 — 응답을 읽는 쪽이 모르는 것을 만났을 때

- 정한 날: 2026-10-08
- [0011](0011-each-app-owns-its-own-responsibility.md)로 대체됨(2026-10-10). 아래는 대체되기 전의 결정이다.

## 상황

서버가 먼저 바뀌어, 읽는 쪽이 모르는 필드나 값을 보낼 수 있다.

## 결정

| 받은 것 | 처리 |
|---|---|
| 모르는 필드 | 무시하고 필요한 필드만 읽는다 |
| 있어야 할 필드가 없거나 타입이 다름 | 잘못된 응답으로 처리한다 |
| 구조화된 내용과 텍스트 내용이 다름 | 구조화된 내용만 읽는다. 구조화된 내용이 없으면 잘못된 응답이다 |
| 모르는 원인 값 | 받은 값을 보존한 원인 불명의 실패로 받는다. 결과 구분은 받은 대로 둔다 |
| 모르는 결과 구분 | 해석할 수 없는 응답으로 처리한다 |
| 아는 원인 값이 다른 결과 구분에 붙음 | 잘못된 응답으로 처리한다 |
| 타입은 맞지만 서버의 자료 조건에 어긋난 값(목록에 없는 상태값 등) | 받은 값 그대로 전달한다. 자료의 조건은 서버가 확인한다 |
| 그 결과 구분에 해당하지 않는 필드가 붙음 | 무시한다 |

여러 가지가 함께 어긋났으면 형식을 먼저 본다. 구조, 결과 구분, 반드시 있는 필드와 타입, 요청한 대상과의 일치를 확인하고, 어긋났으면 잘못된 응답이다. 원인 값은 그다음에 해석한다.

## 이유

원인 값을 모른다고 응답이 잘못된 것은 아니며, 응답 전체를 잘못된 응답으로 처리하면 실제 원인이 가려진다. 안내는 정확해야 한다. 결과 구분을 모르면 받은 상태 값을 사실로 써도 되는지 판단할 수 없다.

자료의 조건을 읽는 쪽에도 두면 같은 규칙이 두 곳에 생기고, 서버가 상태값을 하나 더할 때 읽는 쪽이 먼저 깨진다. 형식이 어긋난 응답은 그 안의 원인 값도 믿을 근거가 없으므로 형식을 먼저 본다.

## 다시 볼 조건

저장처럼 바꾸는 동작의 실패가 원인 불명이면 실제로 바뀌었는지 알 수 없다. 저장 도구를 더할 때 재시도 조건과 함께 다시 본다.
