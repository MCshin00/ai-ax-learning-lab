# 0016 — 라벨이 붙은 이슈가 작업을 시작하게 하고, 접수한 이슈는 다시 시작하지 않는다

- 정한 날: 2026-10-12

## 상황

지금까지는 승인된 계획을 요청문 파일로 써서 실행 관리에 직접 넘겼다. 변경을 개발 이슈로 등록하고 실행 관리가 이슈에서 작업을 시작하게 하려면, 어떤 이슈를 실행할지와 같은 이슈를 다시 만났을 때의 동작을 정해야 한다. 실행 관리는 이슈를 주기적으로 읽으므로 같은 이슈가 조회할 때마다 다시 보인다. 지금의 `start`는 끝난 작업에 다시 부르면 새 시도를 시작한다.

## 결정

| 정할 것 | 결정 |
|---|---|
| 실행 대상 | 열려 있고 `agent-ready` 라벨이 붙은 이슈. 시작 직전에 그 이슈를 다시 읽어 여전히 열려 있고 라벨이 있는지 확인한다 |
| 조회 | 실행 관리가 떠 있는 동안 60초마다 읽는다. 간격은 실행 인수로 바꿀 수 있다 |
| 한 번에 처리할 작업 | 하나. 작업이 끝난 뒤 다음 조회에서 다음 이슈를 본다 |
| 같은 이슈의 식별 | 이슈 번호. 작업 이름은 `issue-<번호>`다 |
| 다시 발견했을 때 | 그 작업의 접수 기록이 있으면 상태가 무엇이든 자동으로 시작하지 않는다 |
| 실행 관리를 다시 시작했을 때 | 접수 기록이 디스크에 남아 있으므로 위와 같다. 실행 중으로 남은 기록은 지금의 복구 순서(`stop` → 확인 → `release`)를 사람이 밟는다 |
| 다시 실행 | 사람이 `start <작업 이름> <요청문 파일>`로 명시할 때만 한다. 같은 작업 폴더에서 이어진다 |
| 막으려는 것 | 최종 검사를 통과하지 못한 결과가 검토 대기가 되는 것. 커밋을 막는 Git 훅은 두지 않는다 |
| 검사 실패의 수정 | 작업자가 자기 실행 안에서 한다. 실행 관리는 다시 실행하지 않고 실패로 기록한다 |
| 결과의 전달 | 이슈에 댓글로 상태, 브랜치 이름, 시도 번호를 남긴다. 검토 대기이면 검사 결과 요약을 함께 적는다 |
| 조회 실패 | 빈 목록과 구별해 출력하고 다음 간격에 다시 조회한다 |

## 이유

이슈는 누구나 열 수 있지만 라벨은 저장소 권한이 있는 사람만 붙인다. 라벨이 그 이슈를 실행해도 된다는 사람의 승인이다. 조회와 시작 사이에 이슈가 닫히거나 라벨이 떼어질 수 있어 시작 직전에 다시 읽는다.

번호만으로 식별하는 것은 본문을 고칠 때마다 새 작업으로 보면 오타 수정에도 작업자가 다시 돌기 때문이다. 접수 기록이 있으면 상태와 무관하게 다시 시작하지 않는 것도 같은 이유다. 검사가 실패했거나 확인이 필요한 작업을 조회할 때마다 다시 돌리면 같은 실패가 되풀이되고, 프로세스가 남았을 수 있는 작업 폴더에 새 작업자가 들어간다.

한 번에 하나인 것은 작업자 한 번이 십여 분이고 작업마다 작업 폴더를 만들기 때문이다. 동시에 돌릴 요구가 지금 없다.

Git 훅을 두지 않는 것은 작업자가 커밋하지 않고, 훅은 건너뛸 수 있기 때문이다. 막을 것은 실패한 변경이 합쳐도 되는 것처럼 보이는 일이고, 그것은 최종 검사의 결과로 상태를 정하는 지금의 구조가 맡는다.

댓글에 이유의 문장을 그대로 싣지 않는 것은 실패의 이유에 로컬 경로가 들어갈 수 있기 때문이다. 자세한 이유는 로컬의 접수 기록에서 본다.

## 알고 있는 한계

- 실행 관리가 꺼져 있는 동안에는 조회하지 않는다. 그동안 라벨이 붙은 이슈는 다음에 실행했을 때 발견된다.
- 작업이 실행되는 동안에는 조회하지 않는다. 그동안 라벨을 뗀 이슈의 작업을 멈추지 않는다.
- 이슈 본문은 그대로 작업자의 요구가 된다. 본문의 내용을 승인하는 것은 라벨을 붙이는 사람이다.
- 댓글 쓰기에 실패하면 출력만 하고 작업의 상태는 바꾸지 않는다.

## 다시 볼 조건

- 여러 이슈를 동시에 처리해야 하면 작업별 잠금과 작업 폴더는 이미 나뉘어 있으므로 동시에 시작할 수를 설정으로 둔다.
- 이슈를 고친 뒤 다시 실행하는 일이 잦으면 다시 실행을 요청하는 라벨이나 댓글 명령을 둔다.
- 외부에서 접속할 수 있는 주소에서 실행하게 되면 주기적 조회 대신 GitHub의 알림을 받는 방식을 검토한다.
