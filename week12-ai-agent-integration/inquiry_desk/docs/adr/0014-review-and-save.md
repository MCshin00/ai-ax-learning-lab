# 0014 — 문의 하나를 요청 하나로 저장하고, 가장 최근 검토본만 받는다

- 정한 날: 2026-10-12

## 상황

초안은 담당자가 읽고 고친 뒤 저장해야 운영팀의 작업 요청이 된다([0001](0001-processing-roles.md)). 일부 서비스만 확인되어도 확인된 내용은 전달해야 한다. 담당자가 초안을 본 뒤 직원이 대상을 정정할 수 있고, 저장 응답을 받지 못한 화면이 같은 저장을 다시 보낼 수 있고, 검토하는 동안 서비스 상태가 바뀔 수 있다.

지금 초안은 문의 전체에 본문 하나와 출처 목록 하나다([0013](0013-source-check-and-missing-evidence.md)). 실제 모델에서 "VPN 접속이 안 돼요"는 근거 없음으로 끝나 초안이 없었다([0012](0012-runbook-search.md)).

## 결정

| 정할 것 | 결정 |
|---|---|
| 저장의 단위 | 문의 하나가 요청 하나다. 처리하지 못한 서비스는 미처리 목록에 이유와 함께 적는다. 초안이 없는 이유가 서비스에 붙지 않으면(증상 없음, 출처 어긋남, 모델 실패) 서비스 없이 이유만 적는다 |
| 저장할 수 있는 조건 | 접수가 성립했고(`READY`) 상태 조회가 `FOUND`인 서비스가 하나 이상이다. 초안이 없어도 담당자가 본문을 써서 저장할 수 있다 |
| 검토본 | 접수에 성공한 발언마다 그 대화의 이전 검토 ID를 쓸 수 없게 하고, 저장할 수 있는 결과이면 코드가 검토 ID를 새로 만든다. 확인된 서비스와 그 변경 번호, 초안의 출처, 미처리 목록을 앱이 보관한다 |
| 오래된 검토본 | 그 대화의 가장 최근 검토 ID가 아니면 저장을 거절한다. 서버를 호출하지 않는다 |
| 화면이 보내는 것 | 검토 ID와 본문. 서비스, 출처, 미처리 목록은 앱이 보관한 검토본에서 꺼내 보낸다 |
| 재전송 | 검토 ID로 알아본다. 같은 검토 ID에 같은 내용이면 저장된 요청의 ID를 다시 돌려주고, 내용이 다르면 충돌로 거절한다 |
| 서버가 대조하는 것 | 검토 때 확인한 서비스의 변경 번호와 지금 자료의 변경 번호. 다르면 저장하지 않고 상태가 바뀌었다고 알린다 |
| 저장하는 본문 | 담당자가 보낸 본문 그대로다 |
| 저장된 요청을 읽는 길 | 같은 서버의 조회 도구. 운영 도구가 요청 ID로 읽는다 |

## 이유

요청 하나로 묶는 것은 초안이 문의 전체에 하나이기 때문이다. 서비스별로 골라 저장하려면 초안 호출이 서비스마다 본문과 출처를 나눠 돌려줘야 한다. 운영팀이 받는 쪽에서도 직원 한 명의 문의가 한 건으로 보인다.

초안이 없어도 저장할 수 있게 한 것은, 근거 없음으로 끝난 문의에도 확인된 상태와 직원이 말한 증상이 있고 그 대응은 담당자가 직접 정하기 때문이다([0013](0013-source-check-and-missing-evidence.md)). 초안이 있어야만 저장되면 이런 문의는 이 도구로 전달할 길이 없다.

가장 최근 검토본만 받는 것은 발언마다 검색과 초안을 새로 하기 때문이다. 새 발언이 접수되면 이전 검토본은 그 대화의 결과가 아니다. 접수에 실패한 발언은 대화 상태를 바꾸지 않으므로([0009](0009-conversation-state-and-missing-target.md)) 이전 검토본이 그대로 남는다.

화면이 검토 ID와 본문만 보내면 확인된 사실과 출처가 화면을 거치며 바뀔 수 없다. 담당자가 바꿀 수 있는 것은 본문이다.

재전송을 검토 ID로 알아보면 값을 하나 더 만들지 않아도 되고, 같은 검토본이 두 번 저장되지 않는다. 검토 ID를 무작위 값으로 만드는 것은 순번이면 앱을 다시 시작한 뒤 같은 ID가 다시 나와 이미 저장된 요청과 충돌하기 때문이다. 저장 응답을 받지 못한 화면은 같은 요청을 다시 보내면 되고, 앱은 스스로 다시 보내지 않는다([0011](0011-each-app-owns-its-own-responsibility.md)의 다시 볼 조건).

변경 번호만 대조하는 것은 그 값이 자료가 바뀔 때 자료를 관리하는 쪽이 올리는 값이기 때문이다([0011](0011-each-app-owns-its-own-responsibility.md)). 이미 저장된 요청의 재전송은 대조보다 먼저 확인한다. 저장이 끝난 뒤의 상태 변화가 같은 요청의 재전송을 거절로 바꾸면 화면은 저장됐는지 알 수 없다.

## 알고 있는 한계

- 검토본 하나는 한 번만 저장된다. 저장한 뒤 본문을 고쳐 다시 보내려면 다시 문의해 새 검토본을 받는다.
- 담당자가 고친 본문의 사실 여부는 코드가 확인하지 않는다. 출처는 초안의 출처 그대로여서, 담당자가 출처의 내용을 본문에서 지워도 출처 목록에는 남는다.
- 검토본은 앱의 메모리에 있다. 앱을 다시 시작하면 이전 검토 ID로는 저장할 수 없다. 저장된 요청은 서버의 파일에 남는다.
- 변경 번호의 대조와 파일 쓰기 사이에 자료가 바뀌는 경우는 다루지 않는다.

## 다시 볼 조건

- 담당자가 일부 서비스만 먼저 보내고 나머지를 보류해야 하는 일이 실제로 생기면 초안과 출처를 서비스마다 나눠 받고 저장 대상을 고르게 한다([0013](0013-source-check-and-missing-evidence.md)).
- 저장한 요청을 고쳐 다시 보내야 하면 재전송을 알아보는 값을 검토 ID와 나누거나 수정 도구를 둔다.
- 변경 번호를 올리지 않고 상태가 바뀌는 자료가 확인되면 상태와 설명도 함께 대조한다.
- 앱을 다시 시작한 뒤에도 검토를 이어야 하면 검토본의 보관 위치를 바꾼다.
