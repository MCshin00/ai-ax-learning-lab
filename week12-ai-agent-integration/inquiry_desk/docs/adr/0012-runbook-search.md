# 0012 — 운영 문서는 서비스로 거른 뒤 어휘 검색으로 찾고 코드가 호출한다

- 정한 날: 2026-10-10

## 상황

초안을 쓰려면 그 문의에 맞는 운영 문서를 모델의 입력에 넣어야 한다. 운영 문서는 네 개이고 VPN만 두 개(일반 연결 오류, 인증서 만료)다. 접수 결과에는 서비스, 문의 전체의 증상, 오류 메시지가 있다([0008](0008-intake-result-and-service-existence.md)). 검색을 코드가 호출할지 모델이 도구로 요청할지는 [0001](0001-processing-roles.md)에서 미뤄 두었다.

정하기 전에 네 문서로 어휘 검색을 돌려 보았다.

| 서비스 | 검색어 | 결과 |
|---|---|---|
| VPN | 연결이 자꾸 끊김 | RB-VPN |
| VPN | 접속이 안 됨 | 없음 |
| VPN | 접속이 안 됨 인증서 만료 | RB-VPN-CERT, RB-VPN |
| VPN | 연결이 자꾸 끊김 CERT-EXPIRED | RB-VPN-CERT, RB-VPN |
| VPN | VPN이 자꾸 끊겨요 | RB-VPN, RB-VPN-CERT |
| VPN | 터널이 올라오지 않음 | RB-VPN, RB-VPN-CERT (낱말 "않" 하나) |
| VPN | CERT-REVOKED | RB-VPN-CERT (낱말 "cert" 하나) |
| SSO | 인증서 만료 | 없음 |

## 결정

| 정할 것 | 결정 |
|---|---|
| 검색 방식 | 문서를 서비스로 거른 뒤 어휘 검색으로 찾는다. 8주차와 같은 Lucene BM25와 한국어 분석기를 쓰고 제목과 본문을 함께 색인한다 |
| 호출 주체 | 코드가 호출한다. 모델에 검색 도구를 주지 않는다 |
| 검색하는 서비스 | 접수 결과의 서비스 가운데 상태 조회가 `NOT_FOUND`가 아닌 것. 상태 조회가 실패한 서비스는 검색한다 |
| 검색어 | 접수 결과의 증상과 오류 메시지. 코드는 서비스 이름을 더하지 않는다 |
| 증상도 오류 메시지도 없을 때 | 검색하지 않는다. 상태는 돌려주고 `NO_SYMPTOM`을 남긴다 |
| 모델에 넘기는 범위 | 서비스마다 점수 순으로 최대 2개 |
| 문서를 읽는 때 | 검색할 때마다 `runbooks.json`에서 읽는다. 읽지 못하면 그 검색은 실패다 |
| 모델 호출 한도 | 발언 하나에 최대 3회(접수, 검색어 다시 쓰기, 초안) |
| 검색 결과의 값 | `FOUND`, `NONE`, `FAILED` |

## 이유

서비스로 먼저 거르면 다른 서비스의 문서가 초안에 섞일 수 없다. SSO 문의에 VPN의 인증서 문서가 걸리지 않는 것을 위의 표에서 확인했다.

어휘 검색을 고른 것은 오류 코드처럼 글자가 정확히 같아야 하는 검색어에 유리하고, 왜 그 문서가 걸렸는지를 낱말로 설명할 수 있기 때문이다. 약한 쪽은 문서와 다른 표현이다. "접속이 안 됨"은 문서의 "연결"과 낱말이 달라 0개가 된다. 이 경우는 검색어를 한 번 다시 써서 찾는다([0013](0013-source-check-and-missing-evidence.md)).

코드가 호출하는 것은 이 업무에서 초안을 쓰려면 검색이 항상 필요하기 때문이다. 검색할지 말지를 모델이 고를 일이 없고, 무엇을 찾을지는 접수 결과로 이미 정해진다. 검색어를 문서의 용어에 맞추는 일은 다시 쓰기에서 모델이 한다. 도구를 주면 검색을 건너뛰거나 반복 요청하는 경우의 처리가 늘어난다.

검색어에 서비스 이름을 넣지 않는 것은, 이미 서비스로 걸렀는데 "VPN"을 넣으면 그 서비스의 모든 문서가 걸려 근거가 0개인 경우가 생기지 않기 때문이다. 접수 결과의 증상에 서비스 이름이 들어 있어도 코드로 지우지는 않는다. 그때는 그 서비스의 문서가 모두 넘어가고 다시 찾기만 일어나지 않는다.

증상이 없으면 검색하지 않는 것은, 빈 검색어의 0개를 다시 쓰기로 넘기면 직원이 말하지 않은 증상을 모델이 지어내기 때문이다. 다음 발언에서 증상을 말하면 같은 대화로 이어진다([0009](0009-conversation-state-and-missing-target.md)).

상태 조회가 `NOT_FOUND`인 서비스를 검색하지 않는 것은 서비스가 있는지를 상태 조회가 정하기 때문이다. 상태 조회가 실패한 것은 그 서비스의 문서가 없다는 뜻이 아니므로 검색한다.

문서를 매번 읽으면 문서를 고친 것이 바로 반영되고, 네 문서에 캐시와 갱신 규칙을 둘 필요가 없다.

## 알고 있는 한계

- `FOUND`는 후보를 얻었다는 뜻이고 증상에 맞는 문서라는 보장이 아니다. "터널이 올라오지 않음"은 "않" 하나로, `CERT-REVOKED`는 "cert" 하나로 맞지 않는 문서가 걸린다. 점수 하한은 두지 않았다. 문서가 네 개라 점수의 크기가 안정된 기준이 되지 못한다. 걸린 문서가 문의에 맞는지는 담당자가 초안과 원문을 대조해 본다.
- 서비스당 문서가 한두 개라 지금은 검색이 문서를 거의 고르지 않는다. 그 서비스의 문서를 전부 넘기는 것과 결과가 거의 같다.
- 접수 결과의 증상은 문의 전체에 하나여서 여러 서비스를 함께 말한 문의는 같은 검색어로 서비스마다 찾는다.
- 다시 쓰기 모델은 문서의 용어를 모른다. 하는 일은 문서에 쓰일 법한 다른 표현을 내는 것이다. 실제 모델에서 "접속이 안 됨"은 "VPN 접속 불가 증상 오류 코드"로, "속도가 너무 느림"은 "속도 저하"로 바뀌었다. 앞의 것은 지침과 달리 서비스 이름이 들어가 그 서비스의 문서가 모두 걸렸다. 이렇게 되면 맞는 문서가 없어도 근거 없음이 나오지 않고, 걸린 문서가 맞는지는 초안과 담당자의 대조에 맡겨진다. 지침에 예를 더했고 코드로 이름을 지우지는 않았다.

## 다시 볼 조건

- 문서와 다른 표현 때문에 0개가 되는 일이 다시 쓰기로도 자주 남으면 임베딩 검색을 결합한다.
- 지침을 고친 뒤에도 다시 쓴 검색어의 서비스 이름 때문에 맞지 않는 문서가 반복해서 걸리고 초안이나 근거 없음의 판정을 해치면, 검색 대상 서비스의 ID를 검색어에서 빼는 처리를 검토한다. 대응표의 이름("메일", "통합 로그인")은 증상을 이루는 낱말이기도 해서 문자열을 통째로 지우는 방식은 쓰지 않는다. 그래도 남으면 다시 쓰기 모델에 그 서비스 문서의 제목을 주는 방식을 본다.
- 맞지 않는 문서가 걸려 틀린 초안이 실제로 나오면 그 사례에서 무엇이 효과가 있는지(분석기 조정, 관련성 판정) 확인해 정한다.
- 서비스당 문서가 늘어 2개 제한에 필요한 문서가 밀리는 사례가 나오면 넘기는 수와 오류 코드의 처리를 다시 본다. 문의의 오류 코드가 찾은 문서에 없으면 다시 찾는 규칙은 지금 자료에서 필요한 문서를 새로 얻는 경우가 없어 넣지 않았다.
- 조회 결과에 따라 다음에 볼 자료나 도구, 추가 질문을 골라야 하는 요구가 생기면 모델에 도구를 주는 구성을 검토한다.
- 여러 서비스를 함께 말한 문의에서 한쪽 증상이 검색에서 빠지면 증상을 서비스마다 나눈다([0008](0008-intake-result-and-service-existence.md)).
