# 0008 — 접수는 말한 서비스를 적고, 있는지 없는지는 조회가 판단한다

- 정한 날: 2026-10-09

## 상황

직원은 "통합 로그인이 느려요", "급여 시스템이 안 돼요"처럼 말한다. 상태 조회는 자료의 표기와 정확히 같은 서비스 ID만 찾고([0006](0006-status-lookup-inputs.md)), 자료에는 ID만 있고 직원이 부르는 이름이 없다. 자료에 없는 서비스를 말한 문의도 들어온다.

## 결정

접수 결과는 세 필드다.

| 필드 | 내용 |
|---|---|
| `services` | 직원이 말한 서비스. 대응표에 있는 이름이면 그 ID, 없으면 직원의 표현 그대로 |
| `symptom` | 문의 전체의 증상 |
| `errorMessage` | 직원이 말한 오류 메시지나 오류 코드 |

- 모델은 직원이 말한 서비스만 적는다. 증상만으로 서비스를 짐작하지 않는다.
- 코드는 `services`의 항목을 전부 조회한다. 서비스가 자료에 있는지 없는지는 조회 결과(`FOUND`, `NOT_FOUND`)가 정한다.
- 이름과 ID의 대응표(VPN, 통합 로그인 — `SSO`, 메일 — `MAIL`)는 코드의 한 곳에 두고 표기를 맞추는 데만 쓴다. 접수는 이 표로 서비스를 걸러 내지 않는다.
- 같은 서비스가 두 번 적히면 하나로 합친다.
- 질문 문장과 다음 행동은 모델에게 받지 않는다. 코드가 접수 결과를 보고 정한다.

## 이유

"어떤 서비스가 있는가"를 답하는 곳은 하나여야 한다. 조회가 이미 "없음"을 정상 결과로 돌려주므로([0003](0003-absent-is-a-normal-result.md)), 접수가 목록을 따로 두고 먼저 판단하면 같은 판단이 두 곳에 생기고 둘이 어긋날 때 자료에 있는 서비스를 없다고 안내하게 된다.

대응표가 남는 것은 자료에 이름이 없어 "통합 로그인은 SSO"를 모델에게 알려 줄 곳이 필요하기 때문이다. 표기를 맞추는 일은 접수가 맡는다([0006](0006-status-lookup-inputs.md)). 대응표가 자료와 어긋나도 있는지 없는지의 답은 자료를 따른다.

증상을 서비스마다 나누지 않은 것은 "접속이 안 돼요"처럼 서비스가 아직 없는 문의의 증상을 둘 자리가 필요해서다. 오류 메시지를 따로 둔 것은 운영 문서를 찾는 검색어로 쓰기 위해서다.

## 다시 볼 조건

- 모델이 대응표의 이름을 ID로 옮기지 못해 자료에 있는 서비스가 `NOT_FOUND`로 나오는 일이 실제 실행에서 잦으면 대응표의 이름을 늘리거나 표기 처리를 다시 본다.
- 서비스가 자주 바뀌면 자료에 이름을 넣고 서비스 목록을 돌려주는 도구를 공개해 대응표를 없앤다.
- 운영 문서 검색이 서비스별 증상을 필요로 하면 `symptom`을 서비스마다 나눈다.
