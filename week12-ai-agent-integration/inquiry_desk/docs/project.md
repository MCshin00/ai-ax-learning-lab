# IT 문의 처리 앱

직원의 자유로운 문의를 서비스 상태·운영 문서와 연결해 담당자가 검토할 작업 요청으로 만드는 프로젝트다. 현재는 개발 지침·Skill·Hook과 Hook 검사만 연결되어 있다. 앱 소스, MCP 연결, 모델 호출과 업무 검사는 아직 구현하지 않았다.

## 업무 요구

1. 직원은 자연어로 문의하고 빠진 정보를 이어서 알려 줄 수 있다.
2. 현재 서비스 상태와 관련 운영 문서를 함께 보여 주고 대응 초안을 만든다.
3. 여러 서비스 중 일부만 확인되어도 확인된 내용은 전달한다.
4. 담당자가 초안을 검토·편집한 뒤 작업 요청으로 저장하고, 운영팀의 별도 도구에서 읽을 수 있게 한다.
5. 검토 중 대상이나 서비스 상태가 바뀌면 새 사실로 다시 검토한다. 저장 응답을 놓치고 재시도해도 같은 요청이 중복 생성되지 않아야 한다.

## 합의한 처리 구조

접수(모델) → 상태 조회(코드가 MCP 호출) → 운영 문서 검색(호출 주체는 Day 3에 결정) → 초안(모델) → 출처 검사(코드) → 검토·저장(담당자 확인 뒤 코드가 MCP 호출)

모델은 문의의 서비스·증상을 해석하고 자료를 초안으로 정리한다. 반드시 필요한 상태 조회와 저장 조건은 코드가 관리한다. 문의 처리 중에는 저장하지 않으며 모델에는 저장 기능을 주지 않는다. 서비스가 불분명한 “접속이 안 돼요”에는 대상을 다시 묻는다. 서비스별 상태와 근거를 나눠 다른 서비스의 사실을 섞지 않는다.

조회에서 자료에 없는 서비스는 정상 응답 안의 “없음”이다. 조회 자체가 실패하면 호출자가 원인을 구별할 수 있는 값을 포함한 오류로 알린다. “급여 시스템이 안 돼요”에 임의의 상태나 복구 시각을 만들지 않는다. 이 의미를 표현할 구체적인 공개 입출력은 앱 구현 작업에서 정한다.

예를 들어 VPN 인증서 만료 문의에는 공통 장애 공지가 없다는 상태와 `RB-VPN-CERT`의 갱신 안내 요청을 연결할 수 있다. 이는 제공 자료에서 예상한 처리이며 앱 실행 결과가 아니다. 공통 장애가 없다는 사실만으로 개인 환경이 정상이라고 하거나, 갱신 안내 요청을 갱신 완료로 표현해서는 안 된다.

## 제공 자료와 검사 방법

| 파일 | 역할과 확인할 조건 |
|---|---|
| `data/services.json` | VPN·SSO·MAIL의 상태·설명·변경 번호 `revision`. 상태 조회 단계에서 ID별 원문을 대조한다. 저장 전 상태 변경 검사는 임시 복사본에서 revision과 상태를 바꿔 오래된 검토본의 저장이 막히는지 확인한다. |
| `data/runbooks.json` | 서비스별 문서 ID·제목·본문. 검색과 출처 검사에서 반환된 ID의 존재와 서비스 일치를 확인하고, 초안의 주장도 원문과 대조한다. |
| `data/cases.json` | 정상 조회, 추가 질문, 일부 실패, 미등록 서비스, 교정 검색, 정정, 검토·저장, 재요청, 상태 변경, HTTP 단계 전달의 입력·판단 기준. 해당 기능을 구현할 때 `turns`를 입력하고 `check`에서 기대 결과를 도출해 검사한다. `turns`가 없는 사례는 저장 재시도나 상태 변경 동작을 준비한다. |

업무 검사는 대역 모델과 임시 업무 자료로 만들며 실제 키를 읽지 않는다. 일부 실패는 조회 대역으로 재현해 다른 서비스의 성공 결과 보존을 확인한다. 출처 ID 검사는 원문과 문장의 의미 일치까지 증명하지 않으므로 대표 초안도 원문과 대조한다.

## 개발 환경과 확인

| 위치 | 사용하는 단계와 역할 |
|---|---|
| `AGENTS.md` | 변경 작업 시작 시 작업 원칙과 업무 조건 확인 |
| `.agents/skills/inquiry-change/SKILL.md` | 변경 요구를 입력·기대 결과·구현·검사·인계로 연결 |
| `src/harness/java/lab/harness/StopHook.java` | 종료 시 Gradle `test` 실행, 실행별 새 XML로 통과·실패·실행 불가 판정 |
| `src/harness/java/lab/harness/SessionStartHook.java` | 시작·재개 시 이 문서와 선택적인 인계 메모 전달 |
| `src/harnessTest/java/lab/harness/` | 두 Hook의 판정·기록·시작 문맥 검사 |
| `.codex/hooks.json` | 로컬 Hook 등록. 쓰기 제한 시 `.local/harness/hooks.proposed.json`을 메인이 옮긴다. |
| `.local/harness/checkpoint.md` | 현재 작업의 결과와 다음 행동 인계 |

Hook은 별도 소스 집합이므로 앱 배포물에 들어가지 않는다. 앱의 `test`에도 Hook 검사가 들어가지 않아 Hook 자체의 성공으로 업무 검사 부재를 가리지 않는다. `harnessTest`가 Hook을 검사하고 `check`는 두 검사 작업을 연결한다.

IDE의 Gradle 창에서 `harnessTest --offline`을 실행한다. 앱 구현 후 업무 검사는 `test --offline`로 실행한다. 자동화에서 CLI가 필요하면 Windows PowerShell은 `./gradlew.bat harnessTest --offline`, macOS·Linux·WSL은 `sh ./gradlew harnessTest --offline`을 사용한다. 결과는 `build/test-results/harnessTest`와 `build/reports/tests/harnessTest/index.html`에 남는다. 업무 검사 결과는 `build/test-results/test`다.

Stop Hook도 오프라인으로 `test --rerun-tasks`를 실행하며 `courseBuildDir`로 `.local/harness/runs/<실행 ID>/build`를 지정한다. 해당 실행의 `test-results/test`만 읽고 통과하면 `{}`를 반환한다. 실패나 실행 불가면 실패 사례 또는 실행 불가 원인과 결과 위치를 알리고 `continue:false`로 멈춘다. Hook은 수정 요청을 만들지 않는다. 실행 로그는 같은 실행 폴더의 `gradle.log`, 마지막 판정은 `.local/harness/last-hook-event.json`이다.

검사 제한 시간의 시작값은 `StopHook.TEST_TIMEOUT`의 120초이며 초과 안내도 이 값에서 만든다. 등록의 150초는 Java 시작·결과 기록까지 포함하는 바깥 제한이다. 검사 제한을 늘릴 때는 등록의 바깥 제한도 그보다 길게 맞춘다. Windows 소켓 폴더는 이 프로젝트의 `.local/sock`이며 등록 인수로 전달한다.

현재 앱 검사가 없어 Gradle `test`의 `NO-SOURCE`만으로 통과를 판단할 수 없다. Stop의 새 XML 부재는 실행 불가로 판정한다. 실제 확인 결과는 인계 메모에 남기며, 준비한 입력의 직접 실행과 실제 Codex 세션의 Hook 발동 확인을 구분한다.
