## 이번 주의 업무 — 주문 상담을 돕는 앱 만들기

쇼핑몰 상담팀의 업무를 맡았다고 생각해 봅시다. 고객은 “아직 배송 전인데 취소할 수 있나요?”라고 묻습니다. 상담원은 주문 화면에서 출고 여부를 보고, 정책 문서에서 조건과 신청 경로를 찾은 뒤, 고객의 상황에 맞춰 답변을 작성합니다. 주문 번호가 없으면 다시 물어야 하고, 고객이 번호를 정정하면 앞서 확인한 내용도 바뀝니다.

팀이 원하는 것은 **고객 문의를 넣으면 주문별 확인 사실·정책 근거·안내·남은 질문을 한곳에서 볼 수 있는 상담 앱**입니다. 상담원은 준비된 안내를 검토하거나 필요한 정보를 고객에게 묻습니다. 이 업무를 이전 주차에서 배운 모델 호출·도구·검색·상태·후속 처리로 연결해 봅니다.

이번 주에 배울 것은 **업무의 문제를 필요한 정보와 처리로 나누고, 그 책임을 맡길 구성요소와 연결 방법을 선택하는 법**입니다. 실제 결과로 선택을 검토하고, 요구가 달라지면 어느 입력·상태·처리를 바꿔야 하는지 확인합니다. 그 근거를 바탕으로 다음 포트폴리오에서도 필요한 구조를 스스로 도출합니다.

### 지금 업무에서 막히는 곳

| 상담 중 생기는 일 | 해결하려면 필요한 연결 |
|---|---|
| “A-102 취소할 수 있나요?”라는 문장만 있음 | 문장에서 주문과 문의 종류를 파악하고 실제 주문을 조회 |
| 주문 화면에는 출고 여부만 있고 취소 조건은 별도 문서에 있음 | 조회 사실과 검색한 정책을 같은 문의에 연결 |
| 취소 가능 조건은 찾았지만 신청 경로가 빠짐 | 모델에 전달한 정책 본문에 신청 경로가 포함됐는지 확인하고 빠진 부분을 추가 |
| “반품하고 싶어요”에 수령일·사용 여부가 없음 | 필요한 정보를 질문하고 답을 받으면 같은 상담을 계속 처리 |
| 여러 주문 중 하나를 찾지 못하거나 조회가 실패함 | 확인된 주문의 결과를 전달하고 남은 처리 구분 |

이 문제를 해결하는 **하나의 앱을 Day 1~5 동안 발전시킵니다.** 처음에는 주문 상태를 화면까지 전달하고, 정책 판단·대화·실패 처리를 이어 붙인 뒤 후속 요구에서 구조를 바꿉니다. 완성한 흐름이 상담원의 어떤 확인 작업을 맡고, 어느 판단을 사람에게 남기는지 실제 입력으로 확인합니다.

### 문제를 AI와 코드의 역할로 나누기

주문 번호가 주어졌을 때 상태를 조회하는 일은 기존 코드로 처리할 수 있습니다. 취소 조건이 정해져 있다면 출고 여부를 비교하는 규칙도 코드로 표현할 수 있습니다. 상담의 어려움은 고객이 필요한 항목을 정해진 순서와 형식으로 말해 주지 않는다는 데 있습니다. “아직 안 보낸 거면 취소하고 싶어요”와 “출고 전에 주문을 없앨 수 있나요?”를 같은 취소 문의로 읽고, 현재 주문 상태에 맞는 정책과 다음 질문을 연결해야 합니다.

이 앱에서는 **자유로운 문의를 처리 가능한 입력으로 바꾸고, 조회 사실과 찾아낸 정책을 고객 상황에 맞는 안내로 묶는 일**에 모델을 사용합니다. 주문 사실의 조회, 요청한 주문과 결과의 대응 검사, 실행 한도와 화면의 다음 행동은 코드가 맡습니다. 이렇게 책임을 나누면 상담원은 자료를 찾아 처음부터 답변을 작성하는 대신, 준비된 사실·근거·안내를 검토하고 부족한 정보를 확인할 수 있습니다.

| 상담원이 하던 일 | 앱에 맡길 부분 | 실습에서 확인할 설계 결과 |
|---|---|---|
| 고객 문장에서 대상과 의도를 파악 | 모델이 접수 내용을 구조화 | 표현이 달라도 대상·문의 종류가 유지되는가 |
| 주문 화면과 정책 문서를 오가며 적용 조건 확인 | 코드 조회와 정책 검색을 한 흐름으로 연결 | 같은 주문의 사실과 적용 근거가 함께 나오는가 |
| 조건·절차를 고객 상황에 맞게 설명 | 근거를 전달받은 모델이 안내 초안 작성 | 상담원이 답변에 사용할 조건·신청 경로를 확보하는가 |
| 정보가 빠졌거나 처리에 실패한 항목 추적 | 대화 상태와 결과 상태로 남은 처리 전달 | 같은 내용을 다시 묻거나 확인된 결과를 잃지 않는가 |

주문 번호와 문의 종류를 선택하는 화면만으로 업무를 충분히 처리할 수 있다면 정형 입력과 규칙 기반 안내도 적절합니다. 자유로운 문의를 그대로 받아 여러 자료를 해석해야 하는 정도, 답변을 검토하는 부담, 모델 호출 비용·대기 시간을 함께 보고 AI를 사용할 범위를 정합니다. 같은 업무에서도 입력 방식과 운영 조건에 따라 선택할 구조가 달라집니다. 위 표의 연결이 실제로 동작하는지 입력·중간 결과·최종 결과로 확인합니다.

먼저 필요한 연결을 정하고 그 역할을 맡길 기술을 고릅니다.

| 이번 업무의 필요 | 활용할 학습 | 여기서 내릴 선택 |

| 자연어를 후속 코드가 읽을 입력과 결과로 바꾸기 | 6주차 모델 호출·구조화 출력 | 모델에 맡길 해석과 코드가 검사할 조건 |

예를 들어 조회 함수를 이 앱에서만 쓴다면 직접 호출할 수 있습니다. 상담 앱과 다른 Host가 같은 업무 도구를 사용해야 한다면 MCP 도구로 제공할 기능을 정합니다. 업무 담당자가 화면에서 분기를 관리해야 한다면 9주차의 Dify Workflow도 대안입니다. 이번에는 각 단계가 주고받는 값과 저장한 정보가 바뀌는 과정을 코드에서 따라가기 위해 LangChain 기반 Python 앱을 사용합니다. 이전 기술의 사용 여부는 이런 요구와 관리 방식에서 결정합니다.

## 제공 업무와 자료

상담원은 주문 상태뿐 아니라 **어떤 조건에서 무엇을 할 수 있고 신청 경로가 어디인지** 안내해야 합니다. 원문에 없는 정책은 담당자 검토로 넘기고, 사용자 정보가 필요하면 질문합니다. 주문·정책을 확인한 사실과 모델이 작성한 설명을 결과에서 구분합니다.

| 자료·입력 | 사실과 필요한 판단 |
|---|---|
| A-102 | 배송 준비·출고 전. 취소 조건과 주문 상세의 신청 경로를 함께 확인 |
| A-103 | 배송 중·출고됨. 출고 전 취소 대신 수령 후 반품 조건 안내 |
| A-104 | 배송 완료. 수령 후 일수·사용 여부는 사용자에게 확인 |
| A-999 | 자료에 없음. 다른 주문의 확인된 결과는 보존 |
| 보증 기간 문의 | 제공 정책에 없음. 임의의 기간을 만들지 않고 검토 요청 |

`data/orders.json`과 `data/policies.json`은 가상 자료입니다. 정책은 출처 ID·제목·본문을 포함합니다. 입력 예와 원문 대조 기준은 `data/consultation_cases.json`에 있습니다. 실제 취소·반품을 실행하는 업무가 아니므로 상담 결과에는 신청 완료라고 표시하지 않습니다.

### 한 문의가 파이프라인을 통과하면

제공 문의 **“A-102를 취소할 수 있나요? 신청 경로도 알려 주세요.”**를 따라가 봅시다. 아래는 제공 자료로 도출한 예상 처리이며, 실제 모델 결과는 실습에서 대조합니다.

| 단계 | 받는 정보와 처리 | 다음으로 넘길 것 |
|---|---|---|
| 접수 | 자연어에서 대상 A-102와 취소 문의를 읽음 | 주문 번호·문의 종류 |
| 사실 조회 | 주문 자료에서 `배송 준비`, `shipped=false` 확인 | A-102의 현재 사실 |
| 정책 검색 | 출고 전 취소 조건을 찾아 `POL-CANCEL` 확보 | 정책 조건·출처와 생성에 사용할 본문 |
| 답변 준비·검사 | 출고 전 조건과 신청 경로를 설명할 근거가 있는지 확인 | 상담 초안 또는 부족한 근거에 대한 피드백 |
| 필요한 보완 | 발췌에 신청 경로가 빠졌다면 같은 정책의 전체 문맥 전달 | 보완한 근거로 다시 만든 초안과 재검사 결과 |
| 결과 사용 | 확인 사실·근거·안내를 주문별로 반환 | 상담원이 검토할 안내 또는 남은 질문·검토 사항 |

이 경우 기대하는 안내는 “배송 준비·출고 전인 A-102는 취소를 신청할 수 있고, 주문 상세에서 취소 신청을 선택한다”입니다. 조회만 연결하면 취소 조건을 모르고, 정책 검색만 연결하면 A-102에 그 조건이 적용되는지 알 수 없습니다. **문의의 대상, 현재 사실, 적용할 정책을 같은 경로로 전달해야 업무 답변이 됩니다.**

입력을 A-103으로 바꾸면 출고됐다는 사실 때문에 수령 후 반품 조건을 안내해야 합니다. A-104의 반품 문의에서는 수령 후 일수와 사용 여부를 물어야 합니다. 파이프라인은 같은 순서로 문장을 만드는 것에 더해, 확보한 정보에 따라 답변·보완·질문으로 갈라지는 처리를 연결합니다.

### 상담에 필요한 정보를 응답 항목으로 정하기

“A-102를 취소할 수 있나요? 신청 경로도 알려 주세요”에 답변 문자열 하나만 반환하면 호출 코드는 추가 질문이 필요한지 판단하기 어렵습니다. 이 업무에는 주문별 현재 사실, 근거, 안내, 남은 질문, 다음 행동이 필요합니다.

상담 결과를 다음과 같은 항목으로 나눠 반환할 수 있습니다. 아래는 응답 형식을 설명하는 예입니다.

```text
conversation_id: 상담 식별자
status: ready / partial / needs_input / needs_review / limit_reached / unavailable
items:
  - order_id: A-102
    facts: 조회한 주문 사실
    sources: 생성에 사용한 정책 원문과 ID
    answer: 조건과 신청 경로를 설명하는 문장
    question: 아직 필요한 정보
    next_action: display / ask / review
trace: 조회·검색·검사·문맥 보완의 실제 중간 결과
```

모델이 만든 안내는 초안이고, `facts`는 조회 함수의 결과입니다. `sources`에는 실제 검색·확장한 본문을 연결합니다. `next_action`은 검사 결과와 정보 부족 조건에서 앱이 결정합니다. 6주차에서 정한 응답 항목을 9주차처럼 다음 처리에 사용하는 구성입니다. 이름이나 객체 형태는 선택할 수 있지만 다음 코드가 같은 의미를 읽어야 합니다.

## 이 업무를 어떤 처리 구조로 연결할까

### 파이프라인·에이전트·혼합 구성

파이프라인은 입력을 단계별 처리와 결과로 연결합니다. 순서·분기를 코드로 정하면 반드시 거칠 검사와 후속 행동이 드러납니다. 에이전트는 모델이 현재 요청과 도구 결과를 보고 다음 도구 또는 응답을 선택하는 구성입니다. 혼합 구성에서는 바깥 흐름이 업무의 실행 조건을 지키고 일부 단계의 탐색을 에이전트에 맡깁니다.

| 구성 | 주문 상담에서의 책임 | 선택 이유와 관리할 부분 |
|---|---|---|
| 고정 흐름 | 문의 분류 → 정해진 조회·검색 → 생성 → 검사 | 업무 종류와 순서가 안정적일 때 간단함. 문의 종류·검색 경로가 늘면 분기 수정 |
| 에이전트 중심 | 모델이 주문·정책 도구를 선택하며 안내 | 문의에 따라 조회·검색 도구를 선택. 앱이 주문마다 처리를 마쳤는지, 인용한 정책이 실제 검색됐는지 검사 |
| 혼합 | 접수·대상 조회·검사·결과 전달은 앱, 정책 탐색과 안내는 에이전트 | 주문별 결과의 필수 항목과 보완 상한을 코드에서 확인하면서 검색어는 모델에 맡김 |

제공 요구에는 주문별 사실·근거·남은 처리의 구분이 있어 혼합 구성을 기본 추천합니다. 자연어 상담이라는 이유만으로 모든 단계의 순서를 모델에게 맡길 필요는 없습니다. 실제 LangChain `create_agent`를 쓰는 `consultation.py`가 혼합 구성의 참고이며, `agent.py`는 도구 선택을 중심에 둔 대안입니다. 두 앱을 모두 완성하는 과제는 아닙니다.

```text
문의 + 이전 접수
  → 모델이 접수 내용을 구조화 → 앱이 대상·입력을 확인
  → 주문별 사실 조회
  → 정책 검색 도구를 쓰는 에이전트 → 상담 초안
  → 근거·항목 검사
      ├─ 충분함 → 업무 결과와 다음 행동
      ├─ 보완 가능한 근거 → 문맥 확장 → 다시 생성·검사
      └─ 사용자 정보 필요 / 근거 없음 / 실패 → 질문·검토·부분 결과
```

## Day 1 — 상담원의 일을 나누고 처리 경로 설계하기

먼저 이 업무에서 AI를 사용할 이유와 기존 코드에 맡길 일을 구분합니다. 상담팀이 처음 맡긴 문의는 세 가지입니다. “A-102 상태가 궁금해요”, “A-102 취소는 어디서 신청하나요?”, “반품하고 싶어요”입니다. 상담원이라면 각각 무엇을 먼저 확인하고 무엇이 있어야 다음 행동을 할 수 있는지 위 자료에서 찾습니다.

상태 문의는 주문 조회로 사실을 확보할 수 있고, 취소 문의는 그 사실과 정책을 함께 읽어야 합니다. 번호 없는 반품 문의는 조회 대상을 먼저 물어야 합니다. 이 차이를 처리 경로로 옮기면서 모델이 해석할 부분과 코드로 보장할 부분을 선택합니다. 위 세 구성의 경로를 참고 코드와 대조하고 선택한 구조로 한 앱을 만듭니다. `flow_patterns.py`의 라우팅은 분류 결과를 입력받고, 병렬 예는 독립 주문 조회를 합치며, 검토 예는 검사 피드백을 수정 함수에 전달합니다. 작은 고정 함수 예를 실제 모델 평가나 다중 에이전트 실행으로 읽지 않습니다.

조회·검색 기능에 무엇을 전달하고 어떤 결과를 받을지 정합니다. 직접 함수라면 조회·검색의 입력과 결과를 앱에 전달하고, MCP로 공개하기로 했다면 기존 업무 함수를 도구로 등록해 반환된 값과 오류를 앱에서 사용하는 상담 결과 형식으로 변환합니다. 3·6주차에서 정했던 도구의 입력·출력, 9주차에서 나눴던 호출 코드와 업무 처리를 참고해 각 기능의 구현 위치를 정합니다.

개발은 10주차에서 선택한 방식을 출발점으로 합니다. AI에게 전달할 업무 요구·자료·기존 코드와 맡길 작업·검사 명령을 정하고, 구현을 나눈다면 작업 사이에 전달할 결과의 형식과 통합 담당을 정합니다. Skill은 반복되는 검토 절차를, 하네스는 실제 검사와 완료·복구를 연결할 수 있습니다.

```text
상담원이 주문 화면과 정책 문서를 오가며 답변을 준비하는 일을 돕는 앱을 만들겠습니다.
제공된 세 문의를 사람이 처리한다면 필요한 확인과 다음 행동부터 설명해주세요.
그 흐름에서 이전 주차의 도구·검색·상태·구조화 출력이 맡을 역할을 연결해주세요.
정형 입력과 코드 규칙으로 처리할 부분, 모델의 해석·생성이 유용한 부분을 구체적인 문의로 구분해주세요.
고정 흐름·에이전트 중심·혼합 구성을 같은 입력으로 비교하고 선택을 추천해주세요.
모델에 맡길 판단, 코드가 지킬 규칙, 상태·결과·오류·실행 한도를 설명해주세요.
내가 추천에 동의하는지 또는 바꾸고 싶은 점을 말하면, 그 선택에 맞춰 처리 순서와 처음 연결할 기능을 정해주세요.
기존 개발 지침·하네스에서 필요한 부분을 고르고 실제 검사에 연결할 위치를 보여주세요.
참고 클래스·노드·필드 이름을 필수 구조로 고정하지 마세요.
```

**남길 결과·완료 판단:** 세 문의의 예상 경로와 선택 이유를 기존 노트에 남깁니다. 어떤 정보가 어느 단계에서 생기며, 그 정보로 상담원의 어떤 작업을 처리할 수 있는지 설명합니다. 모델을 사용할 지점과 이유를 고르고 AI의 추천에서 받아들인 점과 바꾼 점을 이유와 함께 남깁니다.

## Day 2 — 주문 상태 문의를 앱에서 처리하기

먼저 상담원이 **“A-102 상태가 궁금해요”**를 입력하면 주문 화면을 따로 찾지 않아도 배송 준비 상태를 확인하게 만듭니다. 접수 → 주문 조회 → 상담 결과 → 화면까지 한 번 연결하면, 이후 정책과 대화를 같은 앱에 붙일 자리가 생깁니다.

6주차의 구조화 출력으로 대상과 문의 종류를 얻고, 조회 함수가 반환한 실제 값을 상담 결과에 연결합니다. 9주차에서 Workflow 결과를 후속 코드가 읽었던 것처럼 이번에는 상담 결과의 상태와 사실을 API 호출자가 읽습니다. A-103도 보내 두 주문의 상태가 실제 자료대로 달라지는지 확인합니다. 정책 근거가 필요한 취소 문의는 Day 3에서 이어 처리합니다.

참고 `consultation.py`의 `structured`는 LangChain `ToolStrategy`로 스키마를 전달합니다. 모델이 그 형식으로 결과를 요청하면 프레임워크가 검증된 객체를 반환합니다. 공개 스키마가 맞아도 다른 주문을 답하거나 잘못된 근거를 인용할 수 있으므로 앱의 대상·출처 검사가 이어집니다. SDK는 응답이 지정한 형식에 맞는지 검사하고, 앱은 그 내용을 보고 표시 가능한지(`ready`), 일부만 처리했는지(`partial`) 판단합니다.

IDE에서 `service.py`를 인수 `--port 0`으로 실행하고 출력된 로컬 주소를 브라우저에서 엽니다. 고정 응답 모드에서는 화면에 준비된 취소 문의로 완성 흐름을 살펴봅니다. 실제 상태 문의는 `--live --port 0`으로 실행해 입력합니다. 같은 앱의 `reply`를 `POST /consultations`가 호출하며 아래 두 항목을 입력으로 받습니다.

```json
{"conversation_id":"customer-1","request":"A-102 상태가 궁금해요."}
```

응답의 주문별 사실·근거·처리 상태·다음 행동을 화면과 코드에서 대조합니다. 터미널 시작이 필요한 경우 프로젝트 폴더에서 PowerShell과 macOS·Linux·WSL 모두 `python service.py --port 0`을 사용합니다. 다른 API나 작은 화면을 선택했다면 동일한 입력·응답 항목을 연결하고 그 화면이나 API에서 확인합니다.

```text
상담원이 A-102와 A-103의 상태를 화면에서 확인하는 첫 경로를 만들겠습니다.
선택한 구조로 접수→주문 조회→상담 결과→API 또는 화면을 연결해주세요.
도구 인자·조회 사실·상담 초안·앱의 후속 행동을 실제 값으로 구별해주세요.
가짜 설정과 모델로 연결을 검사하고 내가 IDE에서 실제 모델로 실행할 방법을 안내해주세요.
같은 핵심 기능을 얇은 API 또는 작은 화면에 연결하고 상태·근거·부분 결과의 전달을 확인해주세요.
현재 설계에서 새 선택이 필요하면 추천·예상과 내 의견 뒤 구현하세요.
```

**남길 결과·완료 판단:** 실제 모델과 연결된 화면 또는 API에서 A-102의 배송 준비와 A-103의 배송 중을 확인합니다. 상담원이 입력한 문장이 주문 조회와 표시할 결과로 바뀌는 경로를 코드·실제 값에 연결합니다. 대역 실행 결과는 연결을 확인한 근거로 구분합니다.

## Day 3 — 취소 조건과 신청 경로까지 안내하기

상담원이 이제 “상태는 알겠는데, 취소가 되는지와 어디서 신청하는지도 한 번에 보고 싶어요”라고 요청합니다. **“A-102를 취소할 수 있나요? 신청 경로도 알려 주세요.”**를 처리하려면 주문 조회 다음에 정책 근거를 연결해야 합니다.

8주차의 검색과 문맥 선택을 여기서 사용합니다. 고객 표현에 맞는 정책을 검색 도구로 찾고, 6주차의 Tool Calling과 7주차의 에이전트 실행으로 그 결과를 상담 초안에 전달합니다. 이어 앱이 필요한 근거를 받았는지 검사하고, 부족하면 보완한 뒤 다시 결과를 준비합니다. 상담원이 자료를 다시 찾아야 했던 상황을 앱 안의 다음 행동으로 옮기는 단계입니다.

### 발췌·전체 원문과 보완의 이유

검색 후보를 찾는 단위와 생성에 줄 문맥은 다를 수 있습니다. `PolicyEvidence`는 검색된 정책의 첫 문장을 발췌로 전달합니다. 취소 정책의 첫 문장에는 출고 전 조건이 있지만 뒤 문장의 **주문 상세에서 취소 신청**이라는 경로는 없습니다. 상담 요구가 두 내용을 모두 필요로 하므로 초기 문맥은 불충분합니다.

참고 검사는 답변이 인용한 정책 ID가 실제 검색 결과에 있는지, 해당 주문에 필요한 정책의 전체 본문을 확보했는지 봅니다. 부족하면 이미 찾은 출처의 전체 본문을 `expand`로 가져와 같은 원래 문의·사실·검사 피드백으로 다시 생성합니다. 전체 원문을 받았다는 것은 답변을 만들 자료가 준비됐다는 근거입니다. 모델이 실제 문장에 조건·신청 경로를 올바르게 사용했는지는 사람이 대조합니다.

짧은 정책 세 개라면 처음부터 전체 본문을 전달하는 구성이 더 단순할 수 있습니다. 이 비교는 좁은 문맥에서 부족함을 감지하고 보완하는 구조와 그 비용을 읽기 위한 사례입니다. 긴 매뉴얼에서는 문서 전체 대신 관련 절과 예외를 함께 가져오는 방법을 선택할 수 있습니다. 검색 근거가 전혀 없으면 같은 원문 확장으로 해결되지 않으므로 반복하지 않습니다.

제공 취소 문의로 최초 근거·초안·검사 피드백을 봅니다. 첫 문장만 제공하면 신청 경로가 없으므로 전체 원문 확인이 필요합니다. `check`가 필요한 정책의 전체 본문이 없다고 반환하면, 앱은 `expand`로 본문을 가져와 다음 모델 호출에 넣습니다. 원래 문의·주문 사실은 유지됩니다.

```python
feedback = self.check(draft, intake, result["items"], evidence)
# 보완할 근거가 있으면 같은 출처의 전체 문맥을 준비합니다.
full = self.evidence.expand(source_id)
# 다음 생성에는 원래 접수·사실과 feedback, 보완한 evidence를 전달합니다.
```

정상 상태 문의는 정책 없이 끝날 수 있습니다. 보증 기간처럼 자료에 없는 질문은 재검색 횟수로 해결되지 않습니다. 수령일이 없으면 정책을 더 읽는 대신 사용자에게 질문합니다. 8주차에서 배운 실패의 위치를 다음 실행 선택에 적용하는 것입니다.

### 요청 한 번에 모델을 몇 번까지 호출할까

사용자 요청 한 번에서 접수·검색·답변 보완에 사용한 모델 호출을 모두 합산합니다. 참고 `Budget`과 `SharedBudget.before_model`은 호출을 시작하기 전에 총 6회 상한을 확인합니다. 실패한 호출도 횟수에 포함하고, 다음 사용자 입력에서는 다시 0부터 셉니다. 문맥 보완은 최대 한 번입니다. 임베딩 호출은 모델 판단 호출과 다른 비용이며 `model_calls`에 포함되지 않습니다.

단계마다 호출 횟수를 따로 세면 접수·검색·보완에서 각각 6회씩 호출할 수 있습니다. 같은 `Budget` 객체를 각 단계에 전달해 요청 전체에서 6회를 넘지 않게 합니다. 긴 도구 실행의 시간 제한은 별도로 두며 실제 모델 연결은 요청 시간 제한과 SDK 재시도 0을 사용합니다.

기본 대역에서는 검사 후 보완 경로가 항상 보이도록 응답을 정했습니다. 실제 모델은 도구 선택과 문장을 다르게 만들 수 있습니다. `trace`에서 최초 발췌·피드백·확장 원문·최종 결과를 읽고 조건과 신청 경로를 원문에 대조합니다. 자료 범위를 충분히 전달했는데 설명이 틀렸다면 문맥 확장 성공과 생성 실패를 구별해 고칠 위치를 정합니다.

```text
A-102 취소 문의에서 출고 여부·취소 조건·신청 경로를 함께 안내하게 만들겠습니다.
현재 조회 흐름에 정책 검색과 근거 검사를 연결하고 빠진 문맥을 보완해주세요.
자료에 없는 보증 기간 문의와는 다음 행동이 어떻게 달라지는지 설명해주세요.
피드백에 무엇을 담고 보완 전후에 무엇을 보존할지 추천하고 내 의견 뒤 구현해주세요.
보완은 한 번으로 제한하고, 접수·검색·보완에서 사용한 모델 호출을 합쳐 요청 한 번에 6회를 넘지 않게 하세요.
정책 검색 함수와 모델 호출에 이 처리를 연결하고, 내가 실행할 입력과 확인할 검색 결과·피드백·답변을 안내해주세요.
실행 결과에서 보완의 효과와 여전히 해결하지 못한 내용을 함께 해석해주세요.
```

**남길 결과·완료 판단:** 실제 모델과 검색이 참여한 보완 경로, 재확인, 해결되지 않은 경우의 종료를 확인합니다. 테스트용 모델로 호출 상한과 단계별 값 전달·종료를 확인하고, 실제 답변은 원문으로 판단합니다. 참고 함수의 빈 수정 동작을 실행한 것만으로 완료하지 않습니다.

## Day 4 — 추가 답변과 주문 정정을 받아 상담 이어가기

이번에는 고객이 “반품하고 싶어요”라고만 말하고, 질문을 받은 뒤 “A-104예요”, “받은 지 이틀이고 사용하지 않았어요”라고 차례로 답합니다. 매 발언을 독립 요청으로 처리하면 마지막 문장에는 주문 번호도 반품 의사도 없어 상담을 끝낼 수 없습니다. 앞서 확인한 정보를 이어 받아야 합니다.

또 다른 상담에서는 A-102의 취소를 물었던 고객이 “A-103으로 정정할게요”라고 말합니다. 출고 전이라는 옛 사실을 계속 쓰면 잘못된 안내가 됩니다. 7주차의 상태·재개·정정을 사용해 **계속 보관할 문의와 새로 확인할 사실**을 나눕니다.

### 업무 상태와 모델 입력

여기서 **대화 상태**는 다음 발언을 처리할 때 다시 사용할 문의 종류·주문 번호·수령일·사용 여부입니다. 응답의 **처리 상태**는 `ready`, `needs_input`처럼 이번 처리를 마쳤는지 추가 정보가 필요한지를 나타냅니다. 저장해 둘 정보와 이번 처리 결과를 구분해서 읽습니다.

같은 상담에서 “취소할 수 있나요?” 뒤에 “A-102예요”가 오면 문의 종류와 번호를 합쳐야 합니다. 반면 번호가 A-103으로 정정되면 이전 조회·근거·답변은 현재 사실로 사용할 수 없습니다. 참고 앱은 접수의 문의 종류·주문 번호·주문별 보충 정보를 메모리에 보관하고, 매 요청의 사실·근거·초안은 새로 계산합니다. 7주차처럼 이어질 문의는 보관하고, 이전 주문에서 얻은 조회 결과·정책·답변은 새 주문의 판단에 쓰지 않는 선택입니다.

`Intake`는 모델에 요구한 출력 스키마이고, 앱은 실제 발언의 주문 번호를 조회 대상으로 확인합니다. 이 검사는 번호 혼동을 줄이며 자연어에서 추출한 모든 사실의 의미를 검증하지는 않습니다. 수령 후 일수·사용 여부는 실제 발언과 대조합니다. 상담 식별자는 상태를 찾는 값이며 서비스의 인증을 대신하지 않습니다.

`consultation_cases.json`의 번호 보충·반품 정보 보충·주문 정정 입력을 같은 대화 ID로 실행합니다. 다른 ID에서도 번호 없는 문의를 보내 분리 여부를 확인합니다. 정정 뒤 이전 주문의 조회·정책·답변이 남지 않는지 실제 모델 입력과 결과를 읽습니다.

실패 재시도의 범위도 선택합니다. 참고 앱은 접수만 보관하고 새 요청에서 조회부터 다시 합니다. 현재 주문 상태의 최신성이 중요하고 조회가 작은 비용이기 때문입니다. 조회 비용이 크고 사실의 유효 기간을 정할 수 있다면 7주차처럼 조회를 보존하고 생성만 재시도할 수 있습니다. 그때 보관 시점·대상·버전을 함께 관리해야 합니다.

| 상황 | 읽을 상태와 다음 행동 |
|---|---|
| 번호 없음 → 번호 보충 | 원래 문의 종류와 새 번호의 연결 |
| 수령 후 일수·사용 여부 보충 | 해당 주문의 사용자 정보만 갱신 |
| A-102 → A-103 정정 | 취소 가능 안내를 그대로 사용하지 않고 새 사실·정책 계산 |
| 주문 조회 실패 | 없는 주문과 구분하고 확인된 다른 사실 보존 |
| 검색 호출 장애 | 정책 없음과 구분해 검색 결과·검토 이유 확인 |
| 모델 오류·잘못된 구조화 결과 | 실패 상태와 확인된 사실을 함께 전달 |
| 전체 호출 상한 | 다음 모델 호출을 시작하지 않고 남은 처리 표시 |

검색·모델 장애와 한도는 대역으로 재현합니다. 자연어 보충과 정정은 실제 모델로 확인합니다. API의 오류나 보류 응답에서도 주문 사실과 질문이 사라지지 않는지 봅니다.

```text
반품 문의→A-104 번호 보충→수령 2일·미사용 답변을 같은 상담으로 처리하겠습니다.
A-102 취소 문의 뒤 A-103으로 정정하는 상담도 기존 상태·재개 설계로 연결해주세요.
이 앱에서 재시도할 때 조회를 반복할지 보존할지 요구로 추천하고 내 의견 뒤 반영해주세요.
같은 대화의 정보를 이어받는지, 다른 대화의 정보가 섞이지 않는지, 주문 정정 뒤 이전 조회·답변을 다시 쓰지 않는지 실제 입력으로 확인해주세요.
조회·모델 호출을 테스트용 함수로 바꿔 장애와 호출 상한을 재현하고, 그때까지 확인한 주문 사실이 API 응답에도 남는지 보여주세요.
```

**남길 결과·완료 판단:** 어떤 정보를 언제까지 보관하고, 실패한 요청을 어디서 다시 시작하며, 주문이 바뀌면 어떤 결과를 버리는지 실제 코드와 결과로 설명합니다. 프로그램을 껐다 켜도 상담을 이어야 한다면 파일이나 DB에 저장할 정보를 정하고 복원을 확인해야 합니다. 이 참고 앱의 메모리 상태는 실행 중 대화를 유지합니다.

## Day 5 — 여러 주문과 부분 실패를 처리하도록 확장하기

상담팀이 앱을 사용하다가 “한 고객이 여러 주문을 묻는데, 하나를 못 찾았다고 나머지까지 기다리게 하고 싶지는 않아요”라는 요구를 보냅니다. **“A-999, A-102, A-103의 상태를 각각 알려 주세요.”**를 한 번에 처리하고, 응답에서 확인된 주문의 안내와 확인하지 못한 항목을 구분합니다.

### 결과 전달과 부분 성공

모델이 세 주문 중 두 개만 답해도 호출 자체는 성공할 수 있습니다. 따라서 요청한 ID와 반환 항목을 비교하고, 주문별 사실·근거·처리 상태를 연결해야 합니다. `ready`는 필요한 응답 항목과 정책 근거가 갖춰져 표시할 수 있다는 상태입니다. 답변 내용의 정확성은 원문과 대조합니다. `partial`이면 표시할 항목과 검토할 항목이 함께 있습니다. HTTP 성공도 이 업무 상태와 별도로 읽습니다.

`finish`가 `display`, `ask`, `review`를 결정하고 API 화면은 그 결과를 표시합니다. 저장 업무를 선택한다면 3·9주차처럼 확인한 내용과 실행을 연결하고 재전달 정책을 둡니다. 이 상담 사례에서 저장은 필수 기능이 아닙니다.

A-999는 찾지 못했지만 A-102와 A-103은 조회할 수 있습니다. 세 결과를 하나의 답변 문자열로 합치면 호출 앱이 다시 확인할 주문을 구별하기 어렵습니다. 주문 ID별 사실·상태·다음 행동을 유지해 화면이 안내할 항목과 검토할 항목을 나누게 합니다.

참고 앱은 이미 주문별 결과를 반환합니다. 그 구조를 사용했다면 **조회 서비스가 한 번 실패한 주문만 같은 상담에서 재시도하되, 성공한 주문의 결과는 보존한다**는 후속 요구를 적용합니다. 성공 결과의 유효 기간과 주문 정정 시 폐기 조건을 정해야 하므로 접수만 보관하던 설계에 실제 변화가 생깁니다. 이미 같은 재시도 구조를 만들었다면 상태 표시 수준을 넘어 현재 구현에 없는 동등한 후속 요구를 제공 입력에서 선택합니다.

```text
현재 코드와 여러 주문·부분 실패 요구를 대조하고 실제로 바꿀 책임을 찾아주세요.
이미 부분 결과를 보존한다면 실패한 주문만 재시도하고 성공 결과를 유지하는 요구를 적용하겠습니다.
조회 결과를 언제까지 재사용할지, 주문 정정 시 무엇을 버릴지, 어떤 결과를 반환하고 어느 단계부터 재시도할지 추천해주세요.
내 의견 뒤 같은 앱을 수정하고 가운데 주문 실패·재시도·대상 정정·기존 정상 입력을 확인해주세요.
관련 사실과 정책이 다른 주문에 섞이지 않는지 실제 중간 결과로 설명해주세요.
```

### 같은 입력에서 전달할 본문 범위와 추가 호출 비교하기

IDE의 `compare_answers.py`에 `--structure`를 지정하면 발췌만·한 번의 보완·처음부터 전체 문맥 전달을 대역으로 볼 수 있습니다. `--structure --live`는 같은 문의·원문·모델 설정에서 실제 비교합니다. 처음부터 전체 본문을 주면 이 짧은 자료에서는 추가 보완 호출을 줄일 수 있습니다. 더 긴 문서에서는 불필요한 입력 증가와 필요한 조건 보존을 함께 판단합니다.

세 구성 모두 별도 대화 상태에서 시작합니다. 모델 출력은 매번 달라질 수 있으므로 `ready` 개수만으로 품질 순위를 정하지 않습니다. 실제 근거와 답변, 추가 호출, 실패를 해결한 위치를 대조합니다. 이미 선택한 다른 구조 변경이 있다면 자기 진입점에서 같은 입력으로 전후를 비교합니다. 프롬프트만 바꾸는 비교는 `agent.py`의 별도 참고 경로입니다.

개발 과정에서도 10주차에서 고른 검사·인계·하네스가 이번 코드의 완료 판단에 쓰였는지 봅니다. 개발 하네스의 성공과 상담 답변의 사실 정확성은 서로 다른 근거로 확인합니다.

**남길 결과·완료 판단:** 실제 요구 변경이 반영된 앱, 수정한 처리 단계와 이유, 변경 전후 결과, 기존 정상 입력이 계속 처리되는지 확인한 결과입니다. 다음 프로젝트에서도 유지할 원리와 조건에 따라 바꿀 구성을 기존 노트에 연결합니다.

### 업무 문제와 실행 결과로 설계 검토하기

Day 2~5의 실제 결과를 처음에 정리한 상담 업무와 대조합니다. 상태 문의에서는 주문 사실을, 취소 문의에서는 출고 여부와 정책 조건·신청 경로를, 반품 문의에서는 필요한 추가 질문을 얻었는지 확인합니다. 여러 주문에서 답할 수 있는 항목과 남은 처리가 구분됐는지도 봅니다. 해당 실행 결과가 있으면 그 결과를 사용합니다.

예를 들어 A-102의 취소 답변에 실제 주문 상태와 올바른 신청 경로·출처가 함께 나왔다면, 자료 조회와 안내 준비가 연결됐다는 근거가 됩니다. 정책 원문에는 있는데 답변에서 조건을 빠뜨렸다면 상담원에게 그 내용을 다시 찾고 고치는 일이 남습니다. 자연스러운 답변이 나왔다는 사실만으로 업무 부담이 줄었다고 판단할 수는 없습니다.

기존 노트에 **문제 → 선택한 역할과 연결 → 예상과 실제 결과 → 한계 → 조건이 달라지면 바꿀 선택**을 이어 설명합니다. 예를 들어 자유로운 표현을 접수하는 데 모델을 쓰고, 주문 사실은 조회 코드가 맡으며, 반품 정보가 없으면 추가 질문을 반환하고, 다음 답변을 기존 문의와 합쳐 처리하는 구성이 요구를 충족했는지 판단합니다. 결과가 기대에 못 미쳤다면 해석·검색·생성·검사 중 바꿀 곳을 실제 근거에 연결합니다. 이런 검토에서 AI가 도움이 된 부분과 기존 코드로 충분했던 부분도 드러납니다.

```text
Day 2~5의 실제 결과와 처음의 상담 업무를 대조해주세요.
선택한 모델·코드·검색·상태의 역할이 실제 결과에 어떻게 반영됐는지 짚어주세요.
예상과 다른 결과가 있다면 어느 단계에서 필요한 값이 빠지거나 잘못됐는지 짚고 고칠 방법을 설명해주세요.
입력을 정형화하거나 정책 자료·후속 업무가 달라지면 어떤 설계를 바꿀지 해설해주세요.
확인한 호출·대기·검토 부담을 포함해 내가 이 구성의 유용성과 한계를 판단하도록 도와주세요.
측정하지 않은 시간 절감이나 정확도 향상을 결론으로 만들지 마세요.
```


예를 들어 A-102가 출고됐다는 조회 결과로 바뀌면 정책 선택과 안내가 바뀌어야 하지만, 접수할 항목과 결과를 반환하는 형식은 계속 사용할 수 있습니다. 상담 기록 저장을 다음 요구로 받는다면 결과 확정 뒤에 3·9주차처럼 사람이 내용을 확인한 뒤 저장하고, 같은 저장 요청이 다시 와도 중복 생성하지 않도록 연결할 수 있습니다. 이런 식으로 **바뀐 업무 요구가 어느 단계의 입력·판단·상태를 바꾸는지** 찾는 것이 다음 포트폴리오 설계의 출발점입니다.

## 완료 기준

- 상담 업무에서 반복되는 확인과 정보 누락을 파악하고, 필요한 데이터·모델·도구·상태·후속 처리를 선택한 이유를 설명했습니다.
- 실제 LangChain과 모델·임베딩을 연결하고, 상태·취소·반품 문의를 API 또는 작은 화면에서 처리해 상담에 사용할 사실·근거·안내·질문을 확인했습니다.
- 실제 검색·생성 결과의 부족함을 검사 피드백과 제한된 보완·재확인·종료로 연결했습니다.
- 번호·정보 보충, 대상 정정, 대화 분리와 실패·상한에서 보존할 결과를 확인했습니다.
- 기존 구현에서 실제로 달라지는 후속 요구를 적용하고 변경 전후와 관련 정상 결과를 대조했습니다.
- 형식·출처 범위 검사와 답변의 의미 판단을 구분하고 원문으로 실제 결과를 해석했습니다.
- 개발에 사용한 지침·검사·하네스와 앱의 업무 품질 확인을 구분해 선택 이유를 설명했습니다.
- 실제 결과로 선택한 구성의 유용성과 한계를 설명하고, 입력·자료·후속 요구가 달라질 때 바꿀 설계를 판단했습니다.

12주차에서는 원하는 포트폴리오의 사용자·목적·범위를 정합니다. 이번에 만든 구조를 그대로 옮기기보다 필요한 사실과 다음 행동을 먼저 정하고, 어떤 기능을 코드가 직접 실행하고, 어떤 도구를 MCP로 공개하며, 흐름을 Dify에서 관리할지 모델이 도구를 선택하게 할지 정합니다.
