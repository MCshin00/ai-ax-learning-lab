### 코드와 테스트

- `ticket_demo/titles.py`의 `return title.strip()`은 앞뒤 공백만 제거한다. 입력 `"  로그인   오류  "`의 내부 연속 공백은 남는다.
- `ticket_demo/priorities.py`의 `return {"P1": "높음", "P2": "보통", "P3": "낮음"}.get(priority, priority)`는 등록되지 않은 값을 그대로 반환한다. 시작 코드에서 P0와 CUSTOM은 각각 P0와 CUSTOM으로 남는다.
- `ticket_demo/app.py`의 `return f"[{priority_label(priority)}] {normalize_title(title)}"`가 두 반환값을 합치며 대괄호를 붙인다. 우선순위 함수의 반환값에는 대괄호를 넣지 않는다.
- `ticket_demo/tests/test_ticket.py`는 `render_ticket(" 로그인 오류 ", "P1")`의 `[높음] 로그인 오류`와 `render_ticket("요청", "CUSTOM")`의 `[CUSTOM] 요청`을 검사한다. 내부 연속 공백과 P0는 이 테스트가 확인하지 않는다.

제목 정리와 우선순위 매핑은 서로의 계산 결과 없이 수정할 수 있으므로 독립 작업으로 나눌 수 있다. 두 함수가 문자열을 반환하는 약속과 app.py가 대괄호를 붙이는 규칙은 함께 유지해야 한다. 개별 테스트 통과와 Git 적용 성공만으로 통합 출력이 올바르다고 판단할 수 없다.

## Day 2 — 구현자·QA 관점으로 검토 맡기기

### 역할 지시와 실제 위임 구분하기

역할은 맡길 책임이고, 페르소나는 그 일을 수행할 때 중점적으로 볼 관점과 행동 성향이다. QA(Quality Assurance, 품질 보증)에는 요구를 충족하는지 확인할 책임을 맡기고, 빠진 입력과 실패 조건을 살피도록 관점을 정했다. 여기에 읽을 파일·확인할 입력·반환할 근거를 붙여 실제 작업 지시를 만들었다.

이번에는 이 지시를 서로 다른 두 하위 에이전트에 전달하고 각각 결과를 받았다. 역할을 붙이는 일, 별도 에이전트에 실행을 맡기는 일, 수정할 파일 상태를 Worktree로 나누는 일은 각각 따로 정한다. 파일을 수정하지 말라는 지시는 작업 범위를 정하며, 환경의 도구·샌드박스 권한 자체를 바꾸지는 않는다.

## Day 3 — Worktree 두 개에서 작은 변경 만들기

Day 2의 두 보고와 검사 계획을 확인하고, 정한 담당 범위대로 제목과 우선순위를 나눠 구현했다.

### Worktree와 브랜치 구분하기

작업 트리(working tree)는 IDE에서 열고 수정하는 실제 프로젝트 파일들이다. 원본 학습 저장소도 하나의 작업 트리이며, `git worktree`는 같은 저장소에 작업 폴더를 추가로 연결한다. 커밋은 기록된 파일 상태이고, 브랜치는 이어지는 커밋 흐름을 가리키는 이름이다. 브랜치만 만들면 폴더가 늘어나지는 않는다. Worktree를 두면 서로 다른 브랜치의 파일을 각각 열어 수정하고 실행할 수 있다.

Worktree에는 담당 파일만 가져오는 것이 아니라 선택한 커밋의 프로젝트 파일을 준비한다. 제목 작업 폴더에도 `app.py`와 `priorities.py`가 있어 전체 실행 경로 안에서 제목 변경을 검사할 수 있었다. 커밋하지 않은 요구사항이나 Git에서 제외한 자료는 따라오지 않으므로, 추가 조건을 적은 README를 먼저 커밋하고 두 작업을 시작했다.

일반 폴더 복사와 달리 Worktree는 같은 저장소의 커밋·브랜치 정보를 공유한다. 각 폴더의 현재 버전·수정 중인 파일·다음 커밋에 넣을 변경을 준비하는 staging은 따로 유지한다. 한쪽에서 커밋해도 원본 파일이 자동으로 갱신되지는 않으며, 원본에 반영하려면 변경을 가져오는 단계가 필요하다. 이번에는 Day 4에서 `cherry-pick`으로 두 커밋의 변경을 적용했다.

### 같은 시작 코드에서 작업 나누기

추가 조건을 적은 프로젝트 README를 `docs(ticket): 공백 제목 처리 요구사항 기록`으로 커밋했다. 시작 코드는 이미 Git에 등록되어 있어 그대로 사용했다. 시작 커밋은 `1872463b74cb784a52c42ac94f855889ce36202c`이며 두 Worktree 모두 이 커밋에서 만들었다.

| 작업 | Worktree 루트 | 브랜치 | 변경한 파일 |
|---|---|---|---|
| 제목 | `C:/Users/Administrator/Desktop/ai-ax-w04-title` | `w04-title` | `titles.py`, 새 `tests/test_titles.py` |
| 우선순위 | `C:/Users/Administrator/Desktop/ai-ax-w04-priority` | `w04-priority` | `priorities.py`, 새 `tests/test_priorities.py` |

각 작업의 실행 위치는 위 루트 아래 `week04-multi-agent-worktrees/ticket_demo`다. 제목 하위 작업 `/root/day3_title`과 우선순위 하위 작업 `/root/day3_priority`에 Day 2에서 정한 요구·담당 파일·입력·기대 결과를 전달했다. 두 작업은 자신의 Worktree에서 구현하고 검사했다.

### 바꾼 위치와 이유

제목은 `titles.py`의 `normalize_title`을 바꿨다.

```python
normalized = " ".join(title.split())
return normalized or "(제목 없음)"
```

인자 없는 `split()`은 공백·탭·줄바꿈을 기준으로 단어를 나누고 빈 조각을 남기지 않는다. 이를 한 칸으로 합치므로 앞뒤 공백과 내부 연속 공백을 함께 정리한다. 공백뿐인 제목은 합친 결과가 빈 문자열이어서 `(제목 없음)`을 반환한다. 이 구현은 빈 문자열도 같은 값으로 처리하지만, 이번에는 선택한 공백 제목 사례를 검사했다.

우선순위는 `priorities.py`의 `priority_label` 매핑에 `"P0": "긴급"`을 추가했다. 기존 P1·P2·P3 항목과 `.get(priority, priority)`를 유지해 미등록 값은 원문 그대로 반환한다. 두 함수의 이름·인자·문자열 반환을 유지했고, 대괄호를 붙이는 `app.py`는 바꾸지 않았다.

### 단독 검사와 실제 출력

각 Worktree의 실행 위치에서 아래 명령을 사용했다.

```powershell
python -X utf8 -B -m unittest discover -s tests -v
python -X utf8 -B app.py
```

다른 환경에서 다시 실행할 때 macOS·Linux·WSL은 같은 위치에서 `python` 대신 `python3`를 사용한다.

| 작업 | 실제 테스트 결과 | 새 테스트에서 확인한 입력 |
|---|---|---|
| 제목 | 7개 통과: 기존 2개 + 제목 5개 | 정상 제목, 앞뒤·연속 공백, 탭·줄바꿈, 공백뿐인 제목, 공백 문자만 섞인 제목 |
| 우선순위 | 7개 통과: 기존 2개 + 우선순위 5개 | P0 → 긴급, P1 → 높음, P2 → 보통, P3 → 낮음, CUSTOM → CUSTOM |

새 제목 검사는 Day 2에서 고른 다섯 입력을 각각 기대 문자열과 비교한다. 새 우선순위 검사는 `"긴급"`을 정확히 비교하므로 반환값에 대괄호가 들어가는 오류도 잡는다. 기존 두 통합 검사도 각 Worktree에서 함께 통과했다.

기본 입력 `("  로그인   오류  ", "P0")`으로 실행한 결과는 다음과 같다.

| 실행 위치 | 예상 출력 | 실제 출력 |
|---|---|---|
| 제목 Worktree | `[P0] 로그인 오류` | `[P0] 로그인 오류` |
| 우선순위 Worktree | `[긴급] 로그인   오류` | `[긴급] 로그인   오류` |
| 원본 `ai-ax-learning-lab` | `[P0] 로그인   오류` | `[P0] 로그인   오류` |

제목 Worktree에서는 `render_ticket("   ", "P0")`도 실행했다. 예상한 `[P0] (제목 없음)`이 나와 추가 조건이 최종 표시로 이어지는 것까지 확인했다.

### 변경이 분리된 상태 확인하기

두 Worktree에는 같은 이름의 파일이 있지만 수정 상태는 따로 유지된다. 제목 Worktree는 제목만 바뀌어 P0가 남고, 우선순위 Worktree는 우선순위만 바뀌어 제목의 연속 공백이 남는다. 두 변경을 아직 가져오지 않은 원본은 시작 출력을 유지한다.

각 Worktree의 `.git` 파일은 원본 저장소의 `.git/worktrees/ai-ax-w04-title`과 `.git/worktrees/ai-ax-w04-priority`를 가리킨다. 커밋·브랜치 정보는 같은 저장소에 연결되어 있고, 작업 파일은 각 폴더에 따로 있다는 것을 실제 경로로 확인했다.

각 변경의 diff와 새 테스트를 읽어 정한 두 파일만 바뀌었는지 확인했다. 원본 프로젝트의 파일 내용과 Day 1~2 노트는 보존했다. 두 Worktree의 구현 변경은 아직 커밋하지 않았다.

Day 4에는 각 변경을 커밋한 뒤 원본에 합치고 전체 테스트와 실제 출력을 확인한다. 통합 후 기대값은 기본 입력의 `[긴급] 로그인 오류`, 공백 제목의 `[긴급] (제목 없음)`이다. 현재 통과한 것은 각 Worktree의 단독 검사이며, 이 두 통합 결과는 아직 예상값이다.

다음으로 두 변경의 코드와 새 테스트를 대조해 Day 2에서 고른 입력을 확인하는지 살펴본 뒤 통합 단계로 넘어간다.

## Day 5 — 작업을 나눌 상황과 다음에 쓸 기준

### 이번 실습에서 확인한 것

이번 변경은 두 함수와 각 테스트를 고치는 작은 작업이었다. 같은 크기의 일은 다음에 한 작업으로 구현하고 필요한 부분만 검토를 맡기기로 했다. 이 선택을 규모가 크거나 여러 요구가 얽힌 프로젝트에도 그대로 적용하지는 않는다.

제목 작업이 공백 정리와 `(제목 없음)` 처리를 전담하고, 우선순위 작업은 P0 표시를 추가했다. 문자열 반환과 `app.py`의 대괄호 조립을 유지한 것으로 충분했다. Day 4에는 Git 충돌 해결이나 공통 코드의 추가 수정 없이 합쳤고, 전체 테스트 12개와 최종 표시 입력 6개가 기대값과 일치했다.

구현자 보고에서는 수정 위치와 반환 규칙을, QA 보고에서는 빠진 입력과 단독·통합 검사의 구분을 채택했다. 두 보고가 같은 코드를 읽고 대괄호 책임을 반복해서 짚었지만, 하나는 구현 범위로, 다른 하나는 확인할 출력으로 연결됐다. 관점별 검토가 무엇을 남길 수 있는지는 확인했지만, 역할 지시가 정확도나 속도를 높였다고 비교 검증한 것은 아니다.

작업을 나누면서 각 요청에 범위와 기대 결과를 전달하고, 두 보고를 대조하고, 커밋을 가져와 다시 검사하는 절차도 거쳤다. 작은 변경에서는 이 준비와 통합 부담까지 고려한다. 더 큰 작업에서는 독립적으로 맡길 일의 양과 맥락을 나누는 효과를 함께 판단한다.

### 무엇을 나누려는지에 따라 도구 고르기

하위 에이전트는 부모 작업이 일부 일을 맡기고 결과를 모으는 데 쓴다. 독립적인 코드 조사나 검토를 나눠 상세 탐색을 맡기고, 판단에 필요한 근거를 돌려받는 방식이다. [공식 하위 에이전트 안내](https://learn.chatgpt.com/docs/agent-configuration/subagents)

Worktree는 같은 Git 저장소의 파일 상태를 별도 작업 폴더로 나눈다. 서로 다른 변경이나 대안을 유지할 때 쓰며, 대화를 나누는 것과 파일을 나누는 것은 별도로 결정한다. [공식 Worktree 안내](https://learn.chatgpt.com/docs/environments/git-worktrees)

| 방식 | 나누는 것 | 내가 사용할 상황 | 맡길 때 정할 내용 |
|---|---|---|---|
| Worktree | 수정할 파일과 브랜치의 상태 | 독립 기능, 대안 구현, 서로 다른 버전의 수정 상태를 따로 유지할 때 | 시작 커밋, 담당 파일, 공통 파일 담당, 가져올 변경과 통합 검사 |
| 역할·페르소나 | 무엇을 중점적으로 볼지 | 같은 변경을 구현·QA·보안·운영 등 다른 판단 기준으로 살펴야 할 때 | 직함에 더해 검토 대상, 중요한 실패 조건, 반환할 코드 근거와 결과 형식 |
| 여러 하위 에이전트 | 한 요청 안에서 맡길 일 | 독립적인 조사·검토·구현 일부를 맡기고 부모 작업에서 결과를 회수할 때 | 각 질문과 범위, 공통 요구, 언제 결과를 모을지, 어떤 근거를 받을지 |
| 여러 세션·작업 | 계속 이어갈 대화와 작업 맥락 | 기능별 수정이 오래 이어지거나 운영 버그와 새 기능을 따로 추적할 때 | 각 작업의 목적·상태·결정 사항, 공유할 변경, 통합을 맡을 작업 |

역할 지시는 무엇을 중요하게 볼지 정하는 방법이다. 역할을 붙이는 것만으로 전문성이나 정답이 보장되지는 않는다. 역할별로 다른 근거를 얻을 이유가 있으면 같은 대상을 보게 하고, 읽어야 할 모듈이나 자료 자체가 많으면 대상별로 나눈다.

다음 사례는 이번 티켓 예제에서 실행한 결과가 아니라, 위 구분을 실제 프로젝트에 적용할 때 쓸 판단이다.

### 실전에서 유용할 상황

#### 1. 여러 기능을 함께 만드는 프로젝트

문의 관리 서비스에서 접수 API, 담당자 화면, CSV 가져오기를 개발한다면 기능별 작업으로 나눌 수 있다. 각 부분에 구현할 일이 충분하고 서로의 세부 구현을 기다리지 않고 진행할 수 있을 때 분할할 이유가 생긴다.

먼저 요청·응답 형식, 필수 필드, 권한과 오류 표현을 정한다. API 구현과 화면 구현을 각각의 작업에 맡기고 Worktree로 변경 상태를 분리한다. QA에는 공통 요구를 기준으로 정상·누락·실패 입력을 정리하게 한다. 기능별 후속 요구가 계속 이어지면 별도 세션에서 이어 간다.

공통 타입이나 DB 스키마처럼 함께 쓰는 부분은 담당을 한곳에 두고 먼저 반영한다. 기능별 검사가 끝나면 실제 문의 접수 → 목록 표시 → 담당자 변경 흐름으로 합친 결과를 확인한다. 파일이 다르더라도 입출력 규칙이 계속 바뀌는 구간은 먼저 합의해야 한다.

#### 2. 같은 변경을 여러 관점으로 검토해야 할 때

문의의 외부 전송 기능이라면 구현 관점은 변경 위치와 호환성, QA 관점은 실패·재시도·중복 전송, 개인정보 관점은 전송 필드와 로그에 남는 정보를 살필 수 있다. 같은 요구와 같은 커밋의 코드를 읽히되 질문과 반환할 근거를 다르게 정한다.

읽기 전용 검토라면 이를 위해 Worktree까지 만들 필요는 없다. 하위 에이전트들의 보고를 모아 실제 코드와 대조하고, 수정은 담당을 정해 진행한다. 서로 다른 결론이나 버그를 억지로 찾게 하지 않고, 겹친 지적도 근거가 맞으면 하나의 수정과 검사로 연결한다.

예를 들어 역할 지시는 “꼼꼼한 QA처럼 검토”에서 끝내지 않고 다음처럼 맡길 일을 구체화한다.

```text
QA 관점에서 전송 요구와 현재 코드를 읽고, 실패 후 재시도와 중복 요청의 동작을 검토한다.
각 사례의 입력·기대 상태·관련 코드 위치·기존 테스트의 확인 범위를 반환한다.
파일은 수정하지 않고, 실행하지 않은 검사는 예상 결과로 구분한다.
```

여러 의견의 다수결로 결정하지 않는다. 허용된 전송 대상·데이터·실패 처리 요구와 실제 코드가 채택 기준이다. 코드 확인과 실제 전송 실행도 구분하고, 실행은 정한 범위에서 검증한다.

#### 3. 같은 요구의 대안 구현을 비교할 때

대용량 CSV 가져오기를 한 번에 처리하는 방식과 나눠 처리하는 방식으로 비교한다면 같은 파일을 서로 다르게 고칠 수 있다. 이때 대안마다 Worktree와 하위 작업 또는 세션을 두면 각 구현을 유지하며 같은 입력을 시험할 수 있다.

비교 전에 입력 자료, 오류 허용 범위, 결과 형식과 선택 기준을 맞춘다. 같은 자료를 넣어 결과 일치, 중간 실패 처리, 필요한 자원 사용을 확인한 뒤 적합한 구현을 고른다. 성능이 선택 기준이면 실제 측정값으로 판단한다.

이 경우에는 두 구현을 모두 합치는 것이 목표가 아니다. 채택할 구현이나 필요한 변경만 원본에 가져오고 기존 흐름과 함께 다시 확인한다. 처음부터 한 대안으로 충분한 요구라면 비교 작업 자체를 만들지 않는다.

#### 4. 기능 개발 중 운영 버그를 함께 고칠 때

새 검색 기능을 만드는 동안 운영 버전의 문의 저장 오류를 고쳐야 한다면, 기능 개발의 파일 상태와 대화를 유지하고 운영 버전을 기준으로 별도 버그 수정 Worktree와 작업을 시작한다.

두 작업의 시작 버전과 목적을 구분한다. 운영 버그는 재현 입력과 수정 범위를 좁혀 확인하고, 필요한 수정만 기능 개발 쪽에도 적용한다. 같은 저장 로직을 건드려야 한다면 그 부분은 수정·적용 순서를 정한다. 두 작업이 항상 같은 커밋에서 시작해야 하는 것은 아니다. 이번 실습은 같은 기능의 두 변경을 비교하려고 시작 커밋을 맞춘 경우였다.

버그 수정은 운영 기준에서 확인하고, 기능 개발 쪽에 가져온 뒤에는 기존 저장 동작과 새 검색 기능을 함께 검사한다. 별도 세션에는 해당 작업의 요구와 상태를 유지하고, 다른 세션에 필요한 결정과 변경은 명시적으로 전달한다.

### 실제 프로젝트에서 적용할 순서

먼저 독립적으로 끝낼 수 있는 일과 앞선 결정이 필요한 일을 구분한다. 예를 들어 CSV 필드·누락값 조사와 기존 표시 코드·테스트 조사는 병렬로 읽을 수 있다. 두 결과를 모아 입력·반환 형식을 정한 다음 파서 구현 → 표시 코드 연결 → 실제 목록 출력 검사는 순서대로 진행한다.

한 기능 안에서도 조사에는 하위 에이전트, 구현 상태 유지에는 Worktree, 오래 이어갈 기능에는 별도 세션을 함께 쓸 수 있다. 개수를 먼저 늘리기보다 각 작업이 어떤 결과를 독립적으로 반환할지 정한다. 공통 규칙이 달라지면 영향을 받는 작업에 같은 결정을 전달한다.

파일 상태가 분리되어도 공통 설정·스키마·외부 실행 환경까지 자동으로 분리되는 것은 아니다. DB·포트·외부 서비스 상태를 함께 쓰는 실행은 그 범위도 따로 맞춘다. 실제 동시 실행과 쓰기 순서는 프로젝트의 작업 규칙을 따른다.

결과를 모으는 작업에서는 담당 범위대로 수정됐는지 diff와 커밋을 확인하고, 같은 코드 상태에서 실제 사용자 흐름을 검사한다. 공유 코드를 계속 함께 고치거나 매 단계 서로의 결정을 기다려야 한다면 그 구간은 한곳에 모아 순서대로 처리한다.

### 이번 Worktree와 브랜치 정리

정리 전에 `git worktree list`로 대상 경로와 브랜치를 확인했다. 두 Worktree 모두 미커밋 변경, 새 파일, Git 제외 파일이 없었고, 각 구현 파일과 테스트가 원본 main의 통합 결과와 같았다.

일반 `git worktree remove`로 아래 실습 폴더를 제거했다. Worktree 제거에 강제 삭제는 사용하지 않았다.

| 정리한 Worktree | 폴더 정리 당시 남긴 브랜치와 커밋 |
|---|---|
| `C:/Users/Administrator/Desktop/ai-ax-w04-title` | `w04-title` · `3c772799afeabd2ee797f9144b7c02295ada902b` |
| `C:/Users/Administrator/Desktop/ai-ax-w04-priority` | `w04-priority` · `a51ba239b5f238135ae87a131a8857fcd22c7a03` |

폴더 정리 후 Worktree 목록에는 원본 `C:/Users/Administrator/Desktop/ai-ax-learning-lab`만 남았다. 이때는 작업별 브랜치도 남겨 두었고, 원본 main은 통합 커밋 `14c2900e13db30c4f11a9fc62189a39a157ac5b1`을 가리켰다.

학습 기록을 점검한 뒤 `w04-title`과 `w04-priority` 브랜치도 정리했다. 먼저 `git cherry`로 두 패치가 main에 반영됐는지 확인하고, 각 작업의 구현 파일과 테스트를 main과 비교해 차이가 없음을 확인했다. cherry-pick으로 작업 커밋과 통합 커밋의 ID가 달라졌으므로, 이 확인을 거친 두 브랜치만 `git branch -D`로 삭제했다. 원격에는 두 실습 브랜치가 없었다. 이제 로컬 브랜치와 Worktree는 main과 원본 작업 폴더만 남아 있으며, 구현·테스트는 Day 4에 적은 두 통합 커밋으로 main에 보존되어 있다.


## 보충 — 후속 요구에서 공통 처리의 책임 정하기

### 새 요구와 처리 위치

기존 구현은 제목의 공백을 정리하고 P0를 긴급으로 표시했다. 공백뿐인 제목도 `(제목 없음)`으로 바꾸는 일이어서 제목 함수 안에서 처리할 수 있었다. 제목 정리와 우선순위 매핑은 서로의 입력을 몰라도 구현할 수 있었다.

후속 요구는 제목이 없고 우선순위가 P0인 티켓을 `[긴급] 담당자 확인 필요`로 표시하는 것이다. 같은 공백 제목이라도 P1은 기존 `[높음] (제목 없음)`을 유지한다. 이 조건은 제목의 누락 여부와 우선순위를 함께 알아야 판단할 수 있다.

공통 변경은 기존 통합 코드를 다루는 한 작업에서 `app.py`와 `tests/test_ticket.py`를 함께 담당했다. 조건의 처리 위치는 두 입력을 모두 받고 최종 표시를 조립하는 `render_ticket`으로 정했다. 기존 두 기능이 통합된 코드에서 처리 위치와 P0·P1의 기대값을 정한 뒤, 공통 조건과 통합 테스트를 구현하고 전체 출력을 확인하는 순서로 진행했다.

### 원래 입력과 표시 문자열의 차이

현재 제목 함수는 `return normalized or "(제목 없음)"`으로 표시할 문자열을 반환한다. 따라서 공백 제목 `"   "`과 실제 제목 `"(제목 없음)"`의 반환값이 같다. 반환값이 비어 있는지만 검사하면 제목 누락을 발견하지 못하고, 대체 문구와 같은지만 검사하면 실제 제목도 누락으로 판단한다.

`render_ticket`에서는 원래 입력의 `not title.strip()`으로 공백뿐인 제목을 구분하고, P0일 때 표시할 제목을 바꾼다. 일반 제목의 공백 정리는 기존 `normalize_title`이 처리하며 우선순위 표시도 기존 `priority_label`을 사용한다.

```python
def render_ticket(title: str, priority: str) -> str:
    display_title = normalize_title(title)
    if priority == "P0" and not title.strip():
        display_title = "담당자 확인 필요"
    return f"[{priority_label(priority)}] {display_title}"
```

입력 제목은 먼저 기존 제목 함수를 거쳐 표시 문자열이 된다. 이어 원래 제목과 우선순위로 긴급 전용 문구를 적용할지 판단한다. 마지막에 우선순위 표시와 대괄호를 붙여 반환한다. 공백 제목의 P0는 표시 문자열이 바뀌지만 P1과 실제 제목 `"(제목 없음)"`은 기존 표시를 사용한다.

### 실제 실행 결과

실행 위치: `week04-multi-agent-worktrees/ticket_demo/`.

```powershell
python -X utf8 -B -m unittest discover -s tests -v
python -X utf8 -B app.py
```

전체 테스트는 기존 12개와 새 통합 검사 4개를 합쳐 **16개 통과**했다. 새 검사는 기본 P0의 최종 표시, 공백 제목의 P0, 공백 제목의 P1·P2·P3·CUSTOM, 실제 제목 `"(제목 없음)"`인 P0를 확인한다. 공백 제목의 P0 검사에는 공백 문자만 있는 입력과 탭·줄바꿈이 섞인 입력을 포함했다. 앱의 기본 출력은 `[긴급] 로그인 오류`였다.

아래 여섯 입력도 `render_ticket`에 직접 전달해 반환값과 기대 문자열을 비교했고 모두 일치했다.

| 제목 입력 | 우선순위 | 기대값과 일치한 실제 출력 |
|---|---|---|
| `"  로그인   오류  "` | `P0` | `[긴급] 로그인 오류` |
| `"   "` | `P0` | `[긴급] 담당자 확인 필요` |
| `" \t\n "` | `P0` | `[긴급] 담당자 확인 필요` |
| `"   "` | `P1` | `[높음] (제목 없음)` |
| `"요청"` | `CUSTOM` | `[CUSTOM] 요청` |

### 작업 분할에서 확인한 점

기본 두 변경에서는 제목과 우선순위 작업이 표시 문자열을 반환하고 조립부가 이를 합치는 것으로 충분했다. 후속 요구에서는 두 입력을 함께 판단하는 규칙이 생겨 조립부의 책임이 늘었다. 이미 통합된 두 기능을 재사용하면서 공통 조건의 담당을 한곳에 두고 수정한 결과, P0의 새 표시와 P1의 기존 표시를 함께 확인할 수 있었다.

작업을 나눌 때는 파일 위치뿐 아니라 새 요구에 필요한 정보가 어디에 있는지도 살펴야 한다. 기존 독립 구현을 진행할 때 정했던 범위가 후속 요구에서도 충분한지 다시 판단하고, 함께 결정할 조건은 담당과 적용 순서를 정해 최종 출력에서 확인한다.
