# 4주차 작업 위임과 통합

제목 정리와 우선순위 이름은 각각 처리할 수 있지만, 두 값으로 만드는 최종 표시에는 공통 약속이 필요하다. 분할 기준은 파일 개수가 아니라 독립적으로 판단할 수 있는 정보와 반환 계약이다. 후속 요구에서 두 입력을 함께 판단해야 하면 처리 책임과 순서를 다시 정한다.

위임·Worktree·통합과 후속 조건의 실습을 마쳤다.

## Day 1 — 시작 동작과 작업 범위

### 시작 입력에서 빠진 요구 찾기

최초 제공본은 앞뒤 공백만 정리하고 P1·P2·P3의 이름만 변환했다. 입력 `"  로그인   오류  ", "P0"`의 결과는 `[P0] 로그인   오류`였다. 기존 P1 입력의 `[높음] 로그인 오류`, 미등록 우선순위의 `[CUSTOM] 요청`을 검사했지만, 그 두 입력에는 내부 연속 공백과 P0가 없었다. 기존 검사 통과가 새 요구의 확인을 뜻하지 않는 이유다.

현재 구현의 역할은 다음 위치에 이어진다.

| 대상 | 실제 파일·메서드 | 반환 계약 |
|---|---|---|
| 제목 정리 | `ticket_demo/src/main/java/lab/week04/Titles.java`의 `normalizeTitle` | 연속 공백·탭·줄바꿈을 한 칸으로 정리한 문자열, 공백뿐이면 `(제목 없음)` |
| 우선순위 표시 | `ticket_demo/src/main/java/lab/week04/Priorities.java`의 `priorityLabel` | 대괄호 없는 이름, 미등록 값은 원문 유지 |
| 최종 조립 | `ticket_demo/src/main/java/lab/week04/App.java`의 `renderTicket` | 대괄호를 한 번 붙인 최종 표시와 긴급·빈 제목 공동 조건 |
| 검사 | `ticket_demo/src/test/java/lab/week04/` | 개별 처리와 두 결과가 합쳐진 동작을 기대값과 비교 |

대괄호는 조립부에서 붙인다. 우선순위 구성에서 `[긴급]`을 반환하면 문자열이라는 형식은 맞아도 최종 표시가 `[[긴급]] 로그인 오류`가 된다. 소유 파일뿐 아니라 반환값의 의미까지 합의해야 한다.

### 추가 조건의 선택

공백뿐인 제목을 거부하는 방법과 `(제목 없음)`으로 표시하는 방법을 비교했다. 목록 행을 유지하고 누락을 표시하는 방향을 선택했다. 이 단계의 제목 처리는 우선순위를 알 필요가 없어 제목 구성에 모을 수 있었다. 단, 이후 P0에 별도 안내를 표시하는 요구는 두 입력을 함께 판단해야 한다.

## Day 2 — 구현자·QA 관점으로 검토 맡기기

### 역할 지시와 실제 위임

구현자·QA라는 역할은 검토 관점을 정한다. 같은 답변에 역할 이름을 붙이는 것과, 별도 하위 에이전트가 요구·코드를 읽고 결과를 돌려주는 것은 실행 방식이 다르다. 이 활동에서는 같은 시작 요구와 코드를 두 하위 에이전트에 읽히고, 파일 수정 없이 근거를 받아 비교했다.

| 관점 | 확인한 근거 | 다음 구현에 반영한 판단 |
|---|---|---|
| 구현자 | 제목과 우선순위가 서로의 계산 결과를 사용하지 않음 | 개별 구성과 검사를 나누어 맡김 |
| 구현자 | 조립부가 이미 대괄호를 붙임 | 우선순위는 표시 이름만 반환 |
| QA | 기존 검사는 P1·미등록 값만 확인 | P0·P2·P3와 내부 공백·공백뿐인 제목 검사 추가 |
| QA | 개별 함수가 맞아도 조합이 틀릴 수 있음 | 통합 뒤 실제 최종 표시를 정확히 비교 |

보고의 수나 역할 이름이 채택 기준은 아니다. 요구와 실제 처리 위치를 대조해 같은 지적은 한 변경으로 묶고, 아직 실행하지 않은 결과는 예상으로 두었다.

### 담당과 처리 순서

제목 작업은 제목 구성과 제목 검사를, 우선순위 작업은 이름 매핑과 우선순위 검사를 맡았다. 대괄호 조립 규칙과 문자열 반환은 두 작업에 공통으로 전달했다. 공통 조립부는 별도 통합 담당의 범위로 두었다. 독립 변경을 마친 뒤 두 기능을 함께 검증하는 순서였다.

| 입력 | 기대 결과 | 확인 이유 |
|---|---|---|
| `"  로그인   오류  "` | `로그인 오류` | 앞뒤·내부 공백 정리 |
| 탭·줄바꿈이 섞인 제목 | 단어 사이 한 칸 | 여러 공백 표현을 같은 표시 규칙으로 처리 |
| 공백뿐인 제목 | `(제목 없음)` | 빈 내용을 목록에서 드러냄 |
| P0 | `긴급` | 새 매핑, 대괄호 없음 |
| P1·P2·P3 | 높음·보통·낮음 | 기존 표시 유지 |
| CUSTOM | `CUSTOM` | 미등록 값을 숨기지 않음 |

## Day 3 — Worktree 두 개에서 작은 변경 만들기

### 브랜치와 작업 폴더

브랜치는 커밋 흐름을 가리키고 Worktree는 실제 파일 상태를 펼쳐 편집하는 공간이다. Worktree는 담당 파일만 가져오지 않고 선택한 커밋의 프로젝트를 준비한다. 제목 작업에서도 우선순위·조립 코드가 있어 전체 실행 경로 안에서 변경을 확인할 수 있었다.

추가 요구를 기록한 README를 먼저 커밋한 뒤 같은 시작 코드에서 `w04-title`, `w04-priority` 작업을 나눴다. 커밋하지 않은 요구나 Git에서 제외한 개인 자료가 새 Worktree에 자동으로 따라오는 것은 아니다.

당시 제목 변경만 있는 결과는 `[P0] 로그인 오류`, 우선순위 변경만 있는 결과는 `[긴급] 로그인   오류`였다. 원본 작업에는 아직 두 변경이 들어오지 않았다. 한 Worktree의 저장·커밋이 다른 작업 폴더의 파일까지 즉시 바꾸지 않는 관계를 이 출력으로 확인했다.

### 처리 책임이 실제 변경에 이어지는 방식

제목 구성은 공백 표현을 정규화하고 결과가 비면 대체 제목을 반환한다. 표시 이름 구성은 P0의 매핑을 추가하고 기존 이름과 미등록 값 처리를 유지한다. 두 결과는 모두 표시할 문자열이라는 공통 계약을 따르므로 조립부가 같은 방식으로 사용한다.

현재 `Titles.normalizeTitle`의 공백 처리는 정해 둔 공백 집합을 한 칸으로 치환하는 코드로 구현되어 있다. 중요한 이유는 특정 문자열 API의 특성이 아니라, 탭·줄바꿈·연속 공백이 있어도 같은 제목을 일정한 방식으로 표시한다는 요구다.

## Day 4 — 두 변경 합치고 실제 출력 확인하기

### 변경 적용과 통합 확인

당시 두 작업의 변경을 각각 `cherry-pick`해 충돌 없이 통합했다. 소스 변경의 출처를 남긴 커밋은 다음과 같다.

| 변경 | 작업 커밋 | 원본에 적용된 커밋 |
|---|---|---|
| 제목 | `3c772799afeabd2ee797f9144b7c02295ada902b` | `a5666e175ce522b10f86bdcdb4e2b201cb417062` |
| 우선순위 | `a51ba239b5f238135ae87a131a8857fcd22c7a03` | `14c2900e13db30c4f11a9fc62189a39a157ac5b1` |

통합 뒤의 최종 표시는 `[긴급] 로그인 오류`였고, 당시 기존·개별 검사 12개와 최종 표시 입력 6개가 기대와 일치했다. Git 적용 성공은 변경이 들어왔다는 근거이고 실행 결과는 함께 동작한다는 근거다. 둘 중 하나만으로 통합 완료를 판단하지 않았다.

| 적용 상태 | 제목 결과 | 우선순위 결과 | 최종 표시 |
|---|---|---|---|
| 시작 | `로그인   오류` | P0 | `[P0] 로그인   오류` |
| 제목만 | `로그인 오류` | P0 | `[P0] 로그인 오류` |
| 우선순위만 | `로그인   오류` | 긴급 | `[긴급] 로그인   오류` |
| 통합 | `로그인 오류` | 긴급 | `[긴급] 로그인 오류` |

이 표는 반환값의 변화로 최종 결과를 해석한다. 통합했다고 생각했는데 P0가 그대로라면 우선순위 변경의 적용 여부부터 확인한다. 대괄호가 중복되면 조립 책임이 겹친 지점을 살핀다.

## Day 5 — 작업을 나눌 상황과 다음 기준

이번처럼 작은 변경은 한 작업으로 처리해도 충분하다. 위임 맥락 전달·작업 폴더 준비·결과 비교·통합 비용을 감수한 이유는 분리와 연결을 관찰하기 위해서였다. 실제 속도나 비용이 항상 개선된다고 판단하지 않는다.

| 방식 | 나누는 대상 | 사용 판단 |
|---|---|---|
| 역할·페르소나 | 검토 관점 | 같은 변경에서 다른 실패 조건과 근거를 얻을 필요가 있음 |
| 하위 에이전트 | 맡길 일 | 독립 조사·검토·구현 결과를 부모 작업에서 회수 가능 |
| Worktree | 수정 중인 파일 상태 | 독립 기능·대안·서로 다른 버전을 동시에 유지 |
| 여러 작업·세션 | 이어 갈 대화와 맥락 | 기능별 후속 요구나 운영 문제를 계속 추적 |

공통 타입·저장 구조·입출력 규칙처럼 다른 작업에 영향을 주는 결정은 담당과 적용 순서를 먼저 정한다. 모든 단계가 서로의 결정을 기다리면 그 구간은 한곳에 모으는 편이 자연스럽다.

### 실전에서 유용할 상황


#### 1. 여러 기능을 함께 만드는 프로젝트

문의 관리 서비스에서 접수 API, 담당자 화면, CSV 가져오기를 개발한다면 기능별 작업으로 나눌 수 있다. 각 부분에 구현할 일이 충분하고 서로의 세부 구현을 기다리지 않고 진행할 수 있을 때 분할할 이유가 생긴다.

먼저 요청·응답 형식, 필수 필드, 권한과 오류 표현을 정한다. API 구현과 화면 구현을 각각의 작업에 맡기고 Worktree로 변경 상태를 분리한다. QA에는 공통 요구를 기준으로 정상·누락·실패 입력을 정리하게 한다. 기능별 후속 요구가 계속 이어지면 별도 세션에서 이어 간다.

공통 타입이나 DB 스키마처럼 함께 쓰는 부분은 담당을 한곳에 두고 먼저 반영한다. 기능별 검사가 끝나면 실제 문의 접수 → 목록 표시 → 담당자 변경 흐름으로 합친 결과를 확인한다. 파일이 다르더라도 입출력 규칙이 계속 바뀌는 구간은 먼저 합의해야 한다.

#### 2. 같은 변경을 여러 관점으로 검토해야 할 때

문의의 외부 전송 기능이라면 구현 관점은 변경 위치와 호환성, QA 관점은 실패·재시도·중복 전송, 개인정보 관점은 전송 필드와 로그에 남는 정보를 살필 수 있다. 같은 요구와 같은 커밋의 코드를 읽히되 질문과 반환할 근거를 다르게 정한다.

읽기 전용 검토라면 이를 위해 Worktree까지 만들 필요는 없다. 하위 에이전트들의 보고를 모아 실제 코드와 대조하고, 수정은 담당을 정해 진행한다. 서로 다른 결론이나 버그를 억지로 찾게 하지 않고, 겹친 지적도 근거가 맞으면 하나의 수정과 검사로 연결한다.

예를 들어 역할 지시는 “꼼꼼한 QA처럼 검토”에서 끝내지 않고 다음처럼 맡길 일을 구체화한다.

```text
QA 관점에서 전송 요구와 현재 코드를 읽고, 실패 후 재시도와 중복 요청의 동작을 검토한다.
각 사례의 입력·기대 상태·관련 코드 위치·기존 테스트의 확인 범위를 반환한다.
파일은 수정하지 않고, 실행하지 않은 검사는 예상 결과로 구분한다.
```

여러 의견의 다수결로 결정하지 않는다. 허용된 전송 대상·데이터·실패 처리 요구와 실제 코드가 채택 기준이다. 코드 확인과 실제 전송 실행도 구분하고, 실행은 정한 범위에서 검증한다.

#### 3. 같은 요구의 대안 구현을 비교할 때

대용량 CSV 가져오기를 한 번에 처리하는 방식과 나눠 처리하는 방식으로 비교한다면 같은 파일을 서로 다르게 고칠 수 있다. 이때 대안마다 Worktree와 하위 작업 또는 세션을 두면 각 구현을 유지하며 같은 입력을 시험할 수 있다.

비교 전에 입력 자료, 오류 허용 범위, 결과 형식과 선택 기준을 맞춘다. 같은 자료를 넣어 결과 일치, 중간 실패 처리, 필요한 자원 사용을 확인한 뒤 적합한 구현을 고른다. 성능이 선택 기준이면 실제 측정값으로 판단한다.

이 경우에는 두 구현을 모두 합치는 것이 목표가 아니다. 채택할 구현이나 필요한 변경만 원본에 가져오고 기존 흐름과 함께 다시 확인한다. 처음부터 한 대안으로 충분한 요구라면 비교 작업 자체를 만들지 않는다.

#### 4. 기능 개발 중 운영 버그를 함께 고칠 때

새 검색 기능을 만드는 동안 운영 버전의 문의 저장 오류를 고쳐야 한다면, 기능 개발의 파일 상태와 대화를 유지하고 운영 버전을 기준으로 별도 버그 수정 Worktree와 작업을 시작한다.

두 작업의 시작 버전과 목적을 구분한다. 운영 버그는 재현 입력과 수정 범위를 좁혀 확인하고, 필요한 수정만 기능 개발 쪽에도 적용한다. 같은 저장 로직을 건드려야 한다면 그 부분은 수정·적용 순서를 정한다. 두 작업이 항상 같은 커밋에서 시작해야 하는 것은 아니다. 이번 실습은 같은 기능의 두 변경을 비교하려고 시작 커밋을 맞춘 경우였다.

버그 수정은 운영 기준에서 확인하고, 기능 개발 쪽에 가져온 뒤에는 기존 저장 동작과 새 검색 기능을 함께 검사한다. 별도 세션에는 해당 작업의 요구와 상태를 유지하고, 다른 세션에 필요한 결정과 변경은 명시적으로 전달한다.

### 실제 프로젝트에서 적용할 순서

먼저 독립적으로 끝낼 수 있는 일과 앞선 결정이 필요한 일을 구분한다. 예를 들어 CSV 필드·누락값 조사와 기존 표시 코드·테스트 조사는 병렬로 읽을 수 있다. 두 결과를 모아 입력·반환 형식을 정한 다음 파서 구현 → 표시 코드 연결 → 실제 목록 출력 검사는 순서대로 진행한다.

한 기능 안에서도 조사에는 하위 에이전트, 구현 상태 유지에는 Worktree, 오래 이어갈 기능에는 별도 세션을 함께 쓸 수 있다. 개수를 먼저 늘리기보다 각 작업이 어떤 결과를 독립적으로 반환할지 정한다. 공통 규칙이 달라지면 영향을 받는 작업에 같은 결정을 전달한다.

파일 상태가 분리되어도 공통 설정·스키마·외부 실행 환경까지 자동으로 분리되는 것은 아니다. DB·포트·외부 서비스 상태를 함께 쓰는 실행은 그 범위도 따로 맞춘다. 실제 동시 실행과 쓰기 순서는 프로젝트의 작업 규칙을 따른다.

결과를 모으는 작업에서는 담당 범위대로 수정됐는지 diff와 커밋을 확인하고, 같은 코드 상태에서 실제 사용자 흐름을 검사한다. 공유 코드를 계속 함께 고치거나 매 단계 서로의 결정을 기다려야 한다면 그 구간은 한곳에 모아 순서대로 처리한다.


### Worktree 활동의 정리

당시 `git worktree list`와 파일 상태를 확인한 뒤 작업 폴더 `ai-ax-w04-title`, `ai-ax-w04-priority`를 일반 Worktree 제거 명령으로 정리했다. 이후 두 패치가 main에 반영되었음을 확인하고 실습 브랜치도 정리했다. 위 표의 통합 커밋에 구현과 검사가 보존되어 있다.

## 보충 — 두 입력을 함께 판단하는 후속 요구

원래 제목이 공백뿐이고 P0이면 `[긴급] 담당자 확인 필요`를 표시한다. 같은 제목의 P1은 `[높음] (제목 없음)`이다. 이 조건은 제목 누락과 우선순위를 함께 알아야 하므로 두 입력을 받는 `App.renderTicket`에 둔다.

```java
String displayTitle = Titles.normalizeTitle(title);
if ("P0".equals(priority) && Titles.isBlank(title)) {
    displayTitle = "담당자 확인 필요";
}
return "[" + Priorities.priorityLabel(priority) + "] " + displayTitle;
```

표시 문자열과 원래 입력의 의미는 다르다. 공백 제목도 실제 제목 `(제목 없음)`도 정리 후에는 같은 표시가 된다. 표시값만 보고 누락을 추정하면 실제 제목까지 바꾸게 된다. 원래 입력에서 공백뿐인지 확인하고 두 입력을 가진 조립부에서 공동 규칙을 판단하는 이유다.

당시 후속 조건의 검사까지 추가한 결과는 16개 통과였다.
