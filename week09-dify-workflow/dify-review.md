# Dify 회의 후속 작업 추출 학습 기록

회의 메모의 추출값을 후속 행동에 사용할 때는 어떤 사실을 보존할지, 누가 판단할지, 무엇을 확인한 뒤 저장할지를 정해야 한다. 이 기록은 정상·누락·상충·부분 보완 메모의 차이를 따라 그 판단을 입력 계약, 업무 검사, Workflow 분기와 저장 조건에 연결한다. 모델 호출의 성공뿐 아니라 원문 정보와 다음 행동의 일치가 비교 기준이다.

## Day 1 — 메모 추출과 객체·문자열의 경계

회의 메모에서 작업·담당자·기한·원문 근거·상충을 추출하는 Workflow를 Dify Cloud에서 `gpt-5.2` 모델로 실행했다. 입력 자료와 추출 규칙은 [제공 사례](workflow_materials/cases.json), [추출 지침](workflow_materials/extraction-prompt.txt), [출력 스키마](workflow_materials/extraction-schema.json)에 있다. 상세 구성 순서는 [주차 README](README.md)의 Day 1을 따른다.

### Workflow와 변수 연결: 처리 규칙에 실행마다 다른 메모 전달하기

Workflow는 입력을 받아 정해진 단계들을 거쳐 결과를 반환하는 실행 흐름이다. 처음에는 `회의 입력 → 회의 추출 → 결과 출력`으로 실제 모델 응답을 확인했고, 이후 같은 흐름에 `추출 직렬화`를 추가했다. Day 1에서 구성한 각 노드가 맡는 일과 전달값은 다음과 같다.

| 노드 | 입력·설정 | 출력과 역할 |
|---|---|---|
| 회의 입력 | 필수 문단 필드 `memo`, 표시 이름 `회의 메모` | 실행할 때 받은 원문을 후속 노드에 전달 |
| 회의 추출 | SYSTEM 추출 규칙, USER의 `memo` 참조, 제공 JSON Schema | 자연어 메모를 작업별 필드가 있는 `structured_output` 객체로 변환 |
| 추출 직렬화 | `extraction`에 LLM의 `structured_output` 전체 객체 연결 | 같은 내용을 JSON 문자열 `extraction_json`으로 변환 |
| 결과 출력 | `extraction`에 Code의 `extraction_json` 연결 | 선택한 문자열을 Workflow의 최종 결과로 반환 |

노드를 선으로 잇는 것과 사용할 변수를 지정하는 것은 서로 다른 설정이다. 연결선은 다음 실행 단계를 정하고, 변수 참조는 그 단계에 어떤 값을 넣을지 정한다. LLM 다음에 Code를 연결했더라도 Code의 입력에는 LLM의 여러 출력 중 사용할 값을 따로 지정해야 한다.

추출 규칙은 SYSTEM에 두고, USER에는 `회의 메모:`와 입력 노드의 `memo` 참조를 넣었다. `memo`는 매 실행의 자료가 들어오는 자리다. 정상 메모와 누락 메모가 같은 처리 규칙을 거치면서 서로 다른 담당자·기한 결과를 낸 것은 이 연결에서 확인한 동작이다. USER에 정상 사례 문장을 고정해서 적었다면 Test Run의 입력만 바꿔도 모델에 전달되는 자료는 바뀌지 않는다.

제공 추출 지침의 마지막 대괄호 문구는 변수 연결 위치를 설명하는 안내다. 실제 설정에서는 그 안내를 원문으로 보내는 대신 변수 선택기로 `회의 입력.memo`를 연결한다. 학습 폴더의 파일은 지침과 스키마의 원본이며, Dify가 사용할 내용은 노드 설정에 반영된다. 이후 파일 내용을 수정한다면 실제 노드 설정에도 반영했는지 확인해야 한다.

### 첫 실행: 입력 메모에서 최종 출력까지

입력:

```text
민수가 금요일에 초안을 공유한다.
```

첫 실행의 최종 출력:

```json
{
  "extraction": "{\"tasks\":[{\"title\":\"초안 공유\",\"owners\":[\"민수\"],\"due\":\"금요일\",\"evidence\":[\"민수가 금요일에 초안을 공유한다.\"],\"conflicts\":[]}]}"
}
```

작업은 `초안 공유`, 담당자는 `민수`, 기한은 `금요일`로 추출됐다. 근거에는 원문 문장이 들어갔다. 기준 날짜가 없는 입력에서 기한을 특정 날짜로 바꾸지 않고 원문의 표현을 보존했다.

`extraction`의 값은 JSON 모양의 텍스트를 담은 문자열이다. 바깥 JSON에서 내부 따옴표가 `\"`로 표시되는 것은 문자열을 표현하기 위한 이스케이프다. JSON처럼 보이는 텍스트를 받는 것과 다음 노드가 필드를 읽을 수 있는 객체를 받는 것은 구분해야 한다.

### 프롬프트와 JSON Schema: 의미 규칙과 데이터 모양

[추출 지침](workflow_materials/extraction-prompt.txt)은 다음처럼 빈값과 원문 보존의 의미를 정한다.

> 담당자가 미정이면 owners는 [], 기한이 미정이면 due는 ""입니다.
> evidence는 원문에서 그대로 인용한 문장입니다. 작업·담당자·기한과 상충을 판단할 근거를 함께 보존하세요.
> 금요일 같은 표현을 임의의 날짜로 환산하지 마세요. 없는 사실은 채우지 마세요.

이 규칙은 어떤 내용을 추출할지 설명한다. 반면 [출력 스키마](workflow_materials/extraction-schema.json)는 다음 단계가 읽을 필드의 모양을 정한다. 실제 스키마의 작업 항목 정의에서 일부를 발췌하면 다음과 같다.

```json
{
  "owners": {"type": "array", "items": {"type": "string"}},
  "due": {"type": "string"}
}
```

이 발췌는 전체 스키마의 `properties` 일부이며, 독립적으로 설정하는 전체 스키마는 아니다. 전체 구조에서 `tasks`는 작업 객체의 배열이고 각 작업은 `title`, `owners`, `due`, `evidence`, `conflicts`를 가진다. 배열은 여러 항목을 담는 값이고 객체는 필드 이름으로 값을 구분하는 구조다. 이번 결과에는 작업 하나만 있지만 `tasks` 배열 안에 담기므로 후속 단계는 작업 수와 관계없이 같은 위치에서 항목을 읽을 수 있다.

작업 객체의 `required`에는 다섯 필드가 지정돼 있다. 따라서 담당자가 없어도 `owners` 필드 자체는 있어야 한다. `additionalProperties: false`는 정의하지 않은 필드를 추가하지 않도록 제한한다. 하지만 `owners`에 문자열 하나가 들어 있다는 조건만으로 그 사람이 원문에 있었는지는 알 수 없다. 예를 들어 누락 메모에서 `owners: ["민수"]`가 나왔다면 타입은 맞지만 내용은 틀린 결과다. 이는 검사 기준을 설명하는 가정이며 이번 실제 누락 결과는 빈 배열이었다.

첫 실행에서도 JSON 형태의 텍스트가 나왔지만, 그것만으로 스키마를 설정한 객체 경로가 확인되는 것은 아니다. 구조화 출력 설정 이후에는 실제 LLM 응답의 `structured_output`에 객체가 있었고 Code 입력에도 그 객체가 전달됐다. 두 실행의 차이는 최종 글자 모양보다 다음 단계가 어떤 타입의 값을 받는지에서 드러난다.

### 구조화 출력: 필드의 존재와 정보의 유무

구조화 출력 연결 이후 정상 사례의 결과 내용은 다음과 같다. 아래는 내용 비교를 위해 펼친 JSON이며 바깥 응답의 문자열 포장과 공백은 생략했다.

```json
{
  "tasks": [
    {
      "title": "초안 공유",
      "owners": ["민수"],
      "due": "금요일",
      "evidence": ["민수가 금요일에 초안을 공유한다."],
      "conflicts": []
    }
  ]
}
```

누락 사례 입력:

```text
초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.
```

실제 LLM의 `structured_output`:

```json
{
  "tasks": [
    {
      "conflicts": [],
      "due": "",
      "evidence": [
        "초안을 공유하기로 했다.",
        "담당자와 기한은 정하지 않았다."
      ],
      "owners": [],
      "title": "초안 공유"
    }
  ]
}
```

작업 자체는 추출됐지만 담당자는 빈 배열, 기한은 빈 문자열로 남았다. 필드가 필수라는 조건은 값을 지어내라는 뜻이 아니다. 제공 스키마는 `owners`를 문자열 배열, `due`를 문자열로 정의하며 정보가 없으면 각각 `[]`, `""`로 표현할 수 있다.

근거에는 작업 합의와 담당자·기한 미정이라는 두 문장이 보존됐다. 정보의 누락과 상충은 다른 상태다. 이 메모에는 서로 다른 담당자나 기한이 충돌하는 내용이 없으므로 `conflicts`가 빈 배열인 결과도 원문과 맞는다. 스키마는 필드와 타입을 정하지만 원문 의미까지 보장하지 않으므로, 정상·누락 사례 모두 실제 문장과 결과를 대조해야 한다.

두 사례를 함께 보면 같은 필드가 서로 다른 사실 상태를 표현한다.

| 필드 | 정상 메모의 실제 결과 | 누락 메모의 실제 결과 | 의미 |
|---|---|---|---|
| `title` | `초안 공유` | `초안 공유` | 담당자·기한이 없어도 작업 합의는 보존 |
| `owners` | `["민수"]` | `[]` | 확인된 담당자와 미정 구분 |
| `due` | `금요일` | 빈 문자열 | 원문 기한과 미정 구분 |
| `evidence` | 정상 메모 한 문장 | 작업 합의·미정에 관한 두 문장 | 결과를 원문과 다시 대조할 근거 |
| `conflicts` | `[]` | `[]` | 두 입력 모두 미해결 상충을 서술하지 않음 |

누락 사례의 제공 예상 추출은 두 문장을 하나의 근거 문자열에 담고 있지만 실제 결과는 두 문자열로 나눴다. 두 문장이 모두 원문에서 보존됐으므로 이 차이만으로 추출 실패라고 판단하지 않는다. 중요한 비교 대상은 배열의 문장 수를 똑같이 맞추는지가 아니라 작업·담당자·기한의 관계와 근거가 유지되는지다.

이 결과에서 빈값은 없애야 할 잡음이 아니라 다음 단계에 전달할 정보다. 기한을 임의로 채우면 형식상 완성된 결과처럼 보여도 사람이 보완해야 할 사실이 숨겨진다. 반대로 빈값을 보존하면 후속 검사에서 무엇이 아직 정해지지 않았는지 명시적으로 다룰 수 있다.

### Code 입력과 출력: 내용을 유지하며 전달 형식 바꾸기

누락 사례의 Code 입력 `extraction`에는 위 `structured_output`과 같은 `tasks` 객체가 전달됐다. LLM 출력에는 `text`와 `structured_output`이 함께 있었으며, Code 입력에서 확인된 값은 문자열이 아닌 객체였다.

실제 Code 출력:

```json
{
  "extraction_json": "{\"tasks\": [{\"title\": \"초안 공유\", \"owners\": [], \"due\": \"\", \"evidence\": [\"초안을 공유하기로 했다.\", \"담당자와 기한은 정하지 않았다.\"], \"conflicts\": []}]}"
}
```

담당자·기한의 빈값과 원문 근거는 변환 후에도 유지됐다. 객체의 필드 순서와 공백은 달라졌지만 같은 정보를 담고 있다.

Code 노드의 변환 코드는 다음과 같다.

```python
import json

def main(extraction: dict) -> dict:
    return {"extraction_json": json.dumps(extraction, ensure_ascii=False)}
```

Code 입력 변수 이름 `extraction`은 함수의 인자 이름과 일치한다. 변수 선택기에서는 LLM의 `structured_output` 전체를 연결했으므로 함수는 `tasks` 필드가 있는 객체를 받는다. 그 안의 `tasks`만 선택하면 배열만 전달돼 바깥 구조가 달라지고, `text`를 선택하면 이미 문자열인 값을 받게 된다. 모두 LLM의 결과와 관련된 값이지만 같은 입력 계약은 아니다.

`json.dumps`는 입력 객체를 JSON 문자열로 바꾸고, `ensure_ascii=False`는 한글을 읽기 쉬운 문자로 남긴다. 반환 객체의 키 `extraction_json`은 Code 노드의 String 출력 선언과 이름이 같아야 한다. 최종 Output은 이 변수를 참조하되 외부에 반환할 이름을 `extraction`으로 정했다. Code의 입력 이름과 최종 출력 이름이 같아도 서로 다른 노드에 속한 값이다.

화면에서 문자열 안쪽 따옴표가 이스케이프돼 보이는 것과 이미 문자열인 값을 다시 직렬화하는 것은 구분해야 한다. 후자는 한 번 해석해도 객체가 아니라 문자열이 남는 형태를 만들 수 있다. 이번에는 실제 Code 입력이 객체였고 출력이 그 내용을 담은 JSON 문자열이어서, 입력과 출력의 타입을 따라 변환 경계를 확인할 수 있었다.

직렬화는 객체를 전달·저장할 문자열 표현으로 바꾸는 일이다. 이 경계에서는 LLM이 추출한 내용을 다시 판단하지 않고, 이후 제공 Tool이 받는 문자열 계약에 맞춘다. 받는 쪽이 객체를 받을 수 있다면 객체를 그대로 전달할 수 있다. 문자열이 필요하다는 이유로 변환하는 것이며 모든 노드 사이에서 필요한 절차는 아니다.

최종 연결은 `회의 입력.memo → LLM structured_output 객체 → Code extraction 객체 → extraction_json 문자열 → 최종 Output extraction`이다. 정상 메모의 담당자·기한과 누락 메모의 빈값이 결과에 보존됐다. LLM은 원문에서 정보를 추출하고, Code는 전달 형식을 변환하며, Output은 그 문자열을 앱의 결과로 반환한다.

## Day 2 — 항목별로 검사하고 메모 전체의 다음 행동 정하기

### 요구와 선택한 처리 단위

회의 후속 작업은 담당자·기한이 확인되면 초안으로 보여 주고, 미정이거나 상충한 정보가 있으면 원문과 보완할 내용을 함께 보여 줘야 한다. Day 1의 정상 결과에는 민수·금요일이 있었고, 누락 결과에는 `owners=[]`, `due=""`가 남았다. 두 결과는 모두 읽을 수 있는 추출 데이터지만 다음 행동은 다르다. 누락 메모에 단순히 “초안 공유”만 표시하면 무엇을 보완해야 하는지 드러나지 않는다.

구성은 **항목별로 검사하되 하나라도 보완이 필요하면 메모 전체를 검토하는 방식**으로 정했다. 확정 항목과 미정 항목을 함께 보존하고, 전체 상태와 각 항목의 검토 이유를 반환한다. 작은 회의 메모를 한 번에 확인하고 보완하는 제공 요구에 맞으며, 확정 항목과 보완 항목을 별도 화면이나 결과 묶음으로 관리하는 부담을 줄인다. 대신 이미 확정된 작업도 검토 화면에 함께 나타난다.

[제공 사례](workflow_materials/cases.json)의 `mixed` 메모는 두 방식의 차이를 드러낸다.

> 민수가 금요일에 초안을 공유한다. 검토 회의 준비 담당자와 기한은 정하지 않았다.

제공 예상 추출과 [업무 함수](meeting_plugin/business.py)에 따른 예상 판단은 다음과 같다. 이 표는 설계 비교이며 실제 모델·Plugin 실행 결과는 아니다.

| 항목 | 항목별 판단 | 메모 전체 검토 | 항목별 결과 분리 |
|---|---|---|---|
| 초안 공유 | 담당자 민수·기한 금요일, `ready` | 확정 정보를 보존해 전체 검토 결과에 포함 | 확정 작업 묶음에 포함 |
| 검토 회의 준비 | 담당자·기한 미정, `review` | 두 누락 이유와 함께 전체 검토 결과에 포함 | 보완 작업 묶음에 포함 |
| 메모 전체 | 항목의 준비 상태가 다름 | 전체 `review`, 두 작업을 함께 확인 | 확정 작업과 보완 작업을 나눠 표시 |

이미 준비된 작업을 즉시 별도로 활용해야 하는 요구가 생기면 항목별 결과 분리가 더 적합할 수 있다. 그 경우에도 항목별 검사를 다시 만들기보다 검사 결과를 나누고 원래 작업과의 대응을 유지하면 된다. 전체 처리 단위는 데이터 타입이 자동으로 정하는 것이 아니라 결과를 어떻게 사용할지에 따라 선택한다.

### 자연어 해석과 필드 검사 분리

LLM은 원문에서 작업·담당자·기한·근거·상충을 추출하고, Plugin은 추출된 필드에 업무 규칙을 적용하며, Workflow는 검사 결과에 맞는 안내로 연결한다. 모델에 추출과 확정 판단을 모두 맡기면 연결은 짧아지지만, 추출이 잘못된 것인지 검토 규칙이 잘못된 것인지 구분하기 어렵다. 이번에는 각 단계의 중간값을 따로 확인할 수 있도록 분리한다.

제공 `business.py`의 핵심 검토 조건은 다음과 같다.

```python
if len(owners) != 1:
    reasons.append("담당자 미정" if not owners else "담당자 상충 확인")
if not due:
    reasons.append("기한 미정")
if conflicts:
    reasons.append("미해결 상충: " + "; ".join(conflicts))
```

Day 1의 누락 값을 이 규칙에 넣으면 담당자 미정과 기한 미정이 검토 이유로 남을 것으로 예상된다. 한 명의 담당자를 요구하는 것은 이번 사례의 업무 규칙이다. 공동 담당을 허용하는 업무에서는 이름이 둘이라는 이유만으로 상충으로 판단할 수 없으며, 그에 맞게 규칙과 필요한 정보를 바꿔야 한다.

함수는 근거 문장이 원문에 포함되는지, 담당자·기한 표현이 근거에 있는지도 검사한다. 그러나 이름이 근거에 등장하는 것과 그 사람이 해당 작업의 담당자라는 것은 다른 판단이다. 필드 검사를 통과한 `ready`는 실제 업무 등록이나 원문 의미 전체의 정확성을 보장하지 않는다.

메모 전체의 상태는 제공 함수의 다음 조건과 맞는다.

```python
status = "ready" if checked and all(task["status"] == "ready" for task in checked) else "review"
```

항목이 하나 이상이고 모든 항목이 준비됐을 때만 전체가 `ready`다. 작업이 하나도 없거나 일부 항목에 검토 이유가 있으면 `review`가 된다. 전체 상태와 항목별 상태를 함께 남기므로 메모가 검토 경로로 가더라도 이미 확정된 정보는 유지된다.

### Tool 입출력과 후속 행동

Tool 입력은 원문 `memo`와 Day 1에서 직렬화한 `extraction_json`으로 정했다. 추출값만 있으면 빈 필드는 검사할 수 있지만 근거가 원문에 있는지 대조할 수 없다. 원문과 추출 근거를 함께 전달하면 검사와 사람의 재확인에 같은 자료를 사용할 수 있다.

| 경계 | 선택한 값과 타입 | 역할 |
|---|---|---|
| Tool 입력 | `memo`: 문자열 | 회의 입력의 원문 |
| Tool 입력 | `extraction_json`: 문자열 | LLM 구조화 결과를 Code에서 직렬화한 값 |
| Tool 출력 | `status`: 문자열 | 메모 전체의 후속 경로 선택 |
| Tool 출력 | `summary`: 문자열 | 항목별 내용과 검토 이유를 화면에 표시 |
| 상세 JSON | `tasks`: 항목별 결과 배열 | 추출 정보, 항목별 `status`, `reasons` 보존 |

상세 JSON은 전체 결과를 담고, `status`와 `summary`는 후속 노드가 직접 참조할 변수로 공개하는 구성이다. 제공 함수의 결과에는 이 세 필드가 들어 있다. `tasks`를 상세 JSON에 포함하는 것과 같은 이름의 별도 출력 변수를 등록하는 것은 구분한다.

| 전체 결과 | 연결할 후속 행동 |
|---|---|
| `ready` | 필드 검사를 통과한 초안을 표시하고 사람이 확인 |
| `review` | 원문·작업·검토 이유를 함께 표시하고 필요한 사실 보완 |
| `invalid` | JSON이나 입력 계약을 확인하도록 안내 |

`invalid`는 “담당자를 아직 정하지 않았다”와 달리 추출 데이터를 읽거나 계약에 맞춰 처리할 수 없는 경우다. 오류를 빈 작업 목록으로 바꾸면 읽기 실패와 작업 없음이 섞인다. Plugin 자체를 호출하지 못한 실행 실패도 업무 결과인 `review`와 구분해야 한다.

SDK의 등록 선언·실행 연결·결과 메시지 형식은 Dify와 연결하기 위한 규약이다. `memo`, `extraction_json`, `status` 같은 업무 필드명과 메모 전체 처리 정책은 이번 구성의 선택이다. 구현에서는 선택한 이름과 타입이 선언·함수 전달·반환·Workflow 변수 참조에서 일치하도록 맞춘다.

### 보완은 원문에 추가해 같은 흐름으로 재처리

보완은 기존 메모에 명시적인 정정 내용을 덧붙여 같은 Workflow를 다시 실행하는 방식으로 정했다. 제공 `partial` 사례처럼 담당자만 확정하는 입력을 사용할 수 있다.

```text
초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.
사람의 보완: 담당자는 민수로 확정했다. 기한은 아직 정하지 않았다.
```

예상 결과는 `owners=["민수"]`, `due=""`이며, 담당자 미정은 해소돼도 기한 미정은 남아 전체 `review`가 유지되는 것이다. 이는 다음 실행에서 확인할 예상이다. 보완이 들어왔다는 이유만으로 모든 누락이 해결됐다고 처리하지 않고 실제 갱신된 필드에 따라 남은 이유를 계산한다.

Day 2에서 정한 구현 경계는 원문·추출값 입력, 항목별 검사, 메모 전체 상태와 상세 결과 반환이다. 다음 단계에서는 이 계약을 실제 Tool Plugin으로 노출하고 Day 1의 Workflow에서 호출해 정상 입력의 반환값부터 확인한다.

## Day 3 — 업무 검사와 SDK 연결부 구현

### 항목별 검사와 전체 처리 정책의 위치

제작 Plugin은 [meeting_tool](meeting_tool/README.md)에 구성했다. [business.py](meeting_tool/business.py)의 제공 항목별 검사 `check_tasks`를 재사용하고, [meeting_review.py](meeting_tool/meeting_review.py)에 원문·JSON 문자열 입력 확인, 전체 상태와 요약 구성을 두었다. 혼합 메모에서 일부 항목이 준비되어 있어도 전체를 검토하는 정책은 이 파일의 `all(...)` 조건에 드러난다.

제공 `check_tasks`는 내부에서 참고 `review`를 호출하고 그 결과 중 항목별 배열만 반환하는 재사용 접점이다. 제작 연결부는 이 배열에서 전체 상태와 표시할 요약을 구성한다. 이렇게 하면 필드 검사 규칙을 복제하지 않고 전체 결과를 사용하는 방식을 바꿀 수 있다.

이 분리에서 변경 위치는 요구에 따라 정해진다. 공동 담당을 허용한다면 항목별 업무 규칙과 추출에 필요한 정보를 검토해야 하고, 준비된 항목만 따로 표시한다면 `meeting_review.py`의 결과 구성과 이를 받는 Workflow를 바꾼다. `tools/review_tasks.py`의 SDK 메시지 연결은 반환 계약이 달라지는 부분을 맞춘다. 같은 함수의 재사용 여부보다 어떤 판단이 어느 경계에 있는지가 변경 범위를 결정한다.

[Tool 연결 코드](meeting_tool/tools/review_tasks.py)의 `_invoke`는 `memo`와 `extraction_json`을 제작 함수에 넘긴다. 상세 JSON 메시지에는 전체 상태와 항목별 결과가 담기고, `status`·`summary`는 Workflow에서 직접 참조할 변수로 반환된다. 참고 연결의 `payload` 문자열도 유지하며 상세 JSON과 같은 내용을 담는다.

등록 경로는 `manifest.yaml → provider/meeting.yaml → tools/review_tasks.yaml → tools/review_tasks.py`다. 제공자 이름은 참고 예제와 구분되는 `Meeting Review Lab`, Tool 표시 이름은 `Review meeting tasks`로 정했다. 선언은 SDK가 실행할 코드를 찾게 하고, 실행 코드는 업무 결과를 SDK 메시지로 전달한다.

### 로컬에서 확인한 계약

Python 3.12.12와 `dify-plugin==0.10.2` 환경에서 [기존 검사를 재사용한 테스트](meeting_tool/test_plugin.py)로 등록 파일·아이콘 로딩과 결과 메시지의 일치를 확인했다. 제공 예상 추출을 입력으로 사용한 오프라인 검사다.

혼합 사례에서는 전체 `review`와 항목별 `ready`, `review`가 함께 반환됐고, 첫 작업의 담당자 민수와 두 번째 작업의 담당자·기한 미정 이유가 유지됐다. 빈 작업 배열은 원문을 검토할 `review`, 읽을 수 없는 JSON이나 잘못된 작업 항목은 형식을 고칠 `invalid`로 구분됐다. 출력 변수의 `status`·`summary`와 `payload`에 담긴 상세 결과도 업무 함수 결과와 일치했다.

### Dify Cloud에서 실제 Tool 호출과 최종 출력 확인

PC에서 실행한 Plugin이 Cloud 작업공간의 `Meeting Review Lab`으로 표시됐고, Workflow에서 `Review meeting tasks`를 호출했다. 실행 경로는 `회의 입력 → 회의 추출 → 추출 직렬화 → 업무 검사 → 결과 출력`이다. Tool의 `memo`에는 회의 입력 원문을, `extraction_json`에는 Code에서 직렬화한 추출값을 연결하는 구성이다.

정상 사례의 기준 문장:

```text
민수가 금요일에 초안을 공유한다.
```

실제 Tool 출력 중 `json` 배열에 담긴 상세 결과는 다음과 같다.

```json
{
  "status": "ready",
  "summary": "초안 공유 | 민수 | 금요일 | 필드 검사 통과",
  "tasks": [
    {
      "conflicts": [],
      "due": "금요일",
      "evidence": ["민수가 금요일에 초안을 공유한다."],
      "owners": ["민수"],
      "reasons": [],
      "status": "ready",
      "title": "초안 공유"
    }
  ]
}
```

작업·담당자·기한·근거는 추출값에서 유지됐고, 검사 결과인 항목별 `status`와 `reasons`가 더해졌다. 담당자 한 명과 기한이 있고 근거가 보존된 이 사례에서는 검토 이유가 비어 있었으며, 유일한 항목이 준비돼 메모 전체도 `ready`가 됐다.

같은 실행의 최종 Output:

```json
{
  "extraction": "{\"tasks\": [{\"title\": \"초안 공유\", \"owners\": [\"민수\"], \"due\": \"금요일\", \"evidence\": [\"민수가 금요일에 초안을 공유한다.\"], \"conflicts\": []}]}",
  "status": "ready",
  "summary": "초안 공유 | 민수 | 금요일 | 필드 검사 통과"
}
```

최종 Output에는 검사 전 추출 문자열과 검사 후 상태·요약이 함께 반환됐다. 두 결과를 대조하면 Plugin이 원문의 사실을 새로 추출하는 대신 전달받은 필드에 검사 결과를 덧붙였다는 구조를 확인할 수 있다.

Tool 응답의 `json` 배열은 SDK의 상세 JSON 메시지를 담고, 최상위 `status`·`summary`는 별도로 공개한 변수다. `payload`는 같은 상세 결과를 직렬화한 문자열로 반환됐다. `text`가 빈 문자열이고 `files`가 빈 배열이어도, 이 Tool이 사용하는 JSON 메시지와 변수 출력이 전달됐다면 결과가 없는 것은 아니다. 최종 Output이 어떤 종류의 값을 참조하는지가 중요하다.

정상 메모에서 실제 Plugin 호출, 원문 근거 보존, 검사 결과의 최종 출력 전달을 확인했다.

## Day 4 — 검사 결과로 후속 행동을 나누고 원문의 상충 보존하기

### 상태 표시에서 서로 다른 안내로 연결

Day 3의 Workflow는 검사 결과를 그대로 출력했다. Day 4에서는 정상 결과는 작업 초안으로, 검토 결과는 원문과 보완할 내용으로 보여 주도록 후속 경로를 구성했다. 앞부분의 입력·LLM 추출·직렬화·Tool 검사는 이어 사용하고, `업무 검사` 다음에 `결과 분기`를 두었다.

```text
회의 입력 → 회의 추출 → 추출 직렬화 → 업무 검사 → 결과 분기
  IF status == ready  → 작업 초안 → 초안 출력
  ELIF status == review → 검토 안내 → 검토 출력
  ELSE → 형식 오류 출력
```

분기에서 비교하는 변수는 `업무 검사.status`이고 비교값은 직접 입력한 문자열 `ready`, `review`다. IF/ELSE는 이 값을 비교해 다음 실행 단계를 고른다. 원문을 다시 읽어 담당자를 결정하거나 추출 내용을 수정하는 역할은 아니다.

[정상 Template](workflow_materials/ready-template.jinja)은 `summary`를 받아 초안 안내에 배치하고, [검토 Template](workflow_materials/review-template.jinja)은 `memo`와 `summary`를 받아 원문과 검토 이유를 함께 보여 준다. 정상 경로와 검토 경로에서 사람이 얻는 정보와 다음 행동이 달라지기 때문에 분기할 이유가 있다. 상태값만 보여 주는 요구라면 Output 하나로도 충분하다.

Template의 `{{ summary }}`는 입력 변수 `summary`의 값을 넣는 자리다. 연결선은 실행 순서를 정하고, Template 입력 변수의 `업무 검사.summary` 참조는 실제 전달할 값을 정한다. 검토 경로의 `memo`는 `회의 입력.memo`를 참조한다. 이미 검사한 내용을 표시하는 작업이므로 추가 LLM 호출 없이 Template으로 구성했다.

아래 경로 이름과 결과는 Day 4 실행 당시의 기록이다. 최종 Workflow의 변수 집계기와 공통 Output 연결은 Day 5의 「분기 결과를 공통 Output으로 모으기」와 내보낸 DSL에서 확인할 수 있다.

정상·누락·상충의 실제 실행은 아래와 같다. 형식 오류 경로는 구성 안내에 포함됐지만 이번 실제 실행 사례에는 포함되지 않았다.

### 정상 메모: 검사 요약을 작업 초안으로 표시

입력:

```text
민수가 금요일에 초안을 공유한다.
```

실제 최종 출력의 `status`는 `ready`였고 실행 경로는 `작업 초안 → 초안 출력`이었다. `result`의 실제 내용:

```text
확정 가능한 작업 초안
초안을 공유 | 민수 | 금요일 | 필드 검사 통과
```

최종 `extraction` 문자열을 내용 비교를 위해 객체로 펼치면 다음과 같다.

```json
{
  "tasks": [{
    "title": "초안을 공유",
    "owners": ["민수"],
    "due": "금요일",
    "evidence": ["민수가 금요일에 초안을 공유한다."],
    "conflicts": []
  }]
}
```

Day 3의 `초안 공유`와 달리 제목은 `초안을 공유`로 반환됐지만 작업 의미와 담당자·기한의 관계는 유지됐다. 표현을 문자 단위로 같게 만드는 것보다 원문 사실의 보존이 이번 비교 기준이다. Template은 검사 요약 앞에 초안 안내를 붙였으며 새 담당자나 기한을 만들지 않았다. 필드 검사 통과는 사람이 확인할 초안을 얻었다는 뜻이며 실제 업무 등록을 뜻하지 않는다.

### 누락 메모: 없는 정보를 유지하고 보완 이유 표시

입력:

```text
초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.
```

실제 추출의 `owners`는 `[]`, `due`는 `""`였고, 근거에는 입력의 두 문장이 보존됐다. Tool 상세 결과의 작업 항목은 다음과 같다.

```json
{
  "title": "초안 공유",
  "owners": [],
  "due": "",
  "evidence": [
    "초안을 공유하기로 했다.",
    "담당자와 기한은 정하지 않았다."
  ],
  "conflicts": [],
  "status": "review",
  "reasons": ["담당자 미정", "기한 미정"]
}
```

전체 상태도 `review`였고 실행 경로는 `검토 안내 → 검토 출력`이었다. 최종 `result`:

```text
원문과 남은 질문을 함께 확인하세요.

회의 메모
초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.

검토할 항목
초안 공유 | 담당자 미정 | 기한 미정 | 담당자 미정; 기한 미정
```

LLM은 작업 합의와 미정 상태를 추출했고, 업무 함수는 빈 필드를 검토 이유로 바꿨으며, 분기는 그 결과를 검토 안내로 연결했다. 담당자·기한 칸의 미정 표시와 마지막 검사 이유에 같은 문구가 반복되는 것은 요약이 필드값과 검토 이유를 함께 표시하기 때문이다. 실제 결과의 의미는 담당자와 기한 두 정보를 보완해야 한다는 것이다.

### 상충 메모: 두 이름과 최종 결정의 부재를 함께 보존

입력:

```text
민수가 금요일에 초안을 공유한다. 지수도 초안 공유 담당자라고 기록됐다. 최종 담당자는 확인하지 않았다.
```

실제 추출은 민수와 지수를 모두 `owners`에 담고, 최종 담당자가 확정되지 않았다는 설명을 `conflicts`에 남겼다. Tool 상세 결과의 작업 항목:

```json
{
  "title": "초안 공유",
  "owners": ["민수", "지수"],
  "due": "금요일",
  "evidence": [
    "민수가 금요일에 초안을 공유한다.",
    "지수도 초안 공유 담당자라고 기록됐다.",
    "최종 담당자는 확인하지 않았다."
  ],
  "conflicts": [
    "초안 공유 담당자가 민수와 지수로 모두 기록되어 있으나 공동 담당/최종 담당자 확정이 명시되지 않음"
  ],
  "status": "review",
  "reasons": [
    "담당자 상충 확인",
    "미해결 상충: 초안 공유 담당자가 민수와 지수로 모두 기록되어 있으나 공동 담당/최종 담당자 확정이 명시되지 않음"
  ]
}
```

전체 상태는 `review`, 실행 경로는 `검토 안내 → 검토 출력`이었다. 최종 `result`:

```text
원문과 남은 질문을 함께 확인하세요.

회의 메모
민수가 금요일에 초안을 공유한다. 지수도 초안 공유 담당자라고 기록됐다. 최종 담당자는 확인하지 않았다.

검토할 항목
초안 공유 | 민수, 지수 | 금요일 | 담당자 상충 확인; 미해결 상충: 초안 공유 담당자가 민수와 지수로 모두 기록되어 있으나 공동 담당/최종 담당자 확정이 명시되지 않음
```

누락 사례와 같은 검토 경로이지만 보완할 사실은 다르다. 누락 사례는 담당자·기한이 없고, 상충 사례는 기한이 있으며 담당자로 기록된 두 사람 중 최종 결정이 확인되지 않았다. 상충 결과에서 기한까지 지우거나 담당자 한 명을 임의로 선택하지 않아, 확인된 정보와 결정이 필요한 정보가 함께 남았다.

### 추출·검사·분기의 판단 범위

[업무 검사](meeting_tool/business.py)는 담당자가 한 명인지, 기한이 비어 있는지, 전달된 상충이 있는지와 근거의 원문 포함 여부를 확인한다. 이번 상충 사례에서는 추출 단계가 두 이름과 세 근거 문장을 보존했기 때문에 검사도 담당자 상충과 미해결 문제를 드러낼 수 있었다.

교재가 설명하는 반례는 모델이 지수를 누락하고 민수·금요일과 첫 문장만 반환하는 경우다. 이 경우 남아 있는 이름·기한·근거는 필드 검사를 통과할 수 있고 분기도 받은 `ready` 값에 맞게 실행될 수 있다. 하지만 원문의 상충을 놓친 결과이므로 업무 요구를 만족하지 못한다. 이는 이번 실제 실행 결과가 아니라 제공 코드에서 설명할 수 있는 판단의 한계다.

문제가 생겼을 때는 원문 → LLM 추출 → Tool 입력·결과 → Template 입력·출력 순서로 값을 대조해야 한다. 추출에서 사라진 의미를 분기 조건의 문자열 비교로 복구할 수는 없다. 반대로 Tool이 `review`를 반환했는데 초안 화면이 나왔다면 후속 조건이나 연결을 확인해야 한다. 정상·누락·상충의 실제 결과에서는 추출 정보, 검사 이유, 선택한 경로, 최종 안내가 서로 일치했다.

## Day 5 — 부분 보완을 반영하고 남은 검토 이유 유지하기

### 원문과 보완을 함께 새 실행에 전달

Day 4의 누락 메모에 담당자만 확정하는 보완 문장을 추가해 같은 Workflow로 처리했다. 입력:

```text
초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.
사람의 보완: 담당자는 민수로 확정했다. 기한은 아직 정하지 않았다.
```

제공 [partial 사례](workflow_materials/cases.json)는 담당자 조건은 해결하고 기한은 미정으로 남긴다. 기존 추출 지침은 명시적인 보완·정정이 있으면 해당 값만 갱신하도록 한다. 이번 실행에서는 원문과 보완 문장을 함께 전달했으며, 이전 실행의 중간 상태를 복원하는 방식이 아니라 같은 입력 계약으로 새 실행을 시작했다.

### 실제 추출과 검사 결과

최종 `extraction`에는 `owners=["민수"]`, `due=""`가 반환됐다. 근거에는 원래 메모와 담당자 확정 문장이 함께 보존됐고 `conflicts`는 빈 배열이었다. Tool의 상세 결과에 담긴 작업 항목:

```json
{
  "title": "초안 공유",
  "owners": ["민수"],
  "due": "",
  "evidence": [
    "초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.",
    "사람의 보완: 담당자는 민수로 확정했다. 기한은 아직 정하지 않았다."
  ],
  "conflicts": [],
  "status": "review",
  "reasons": ["기한 미정"]
}
```

원래의 담당자 미정과 뒤의 명시적인 확정을 미해결 상충으로 남기지 않고 보완된 담당자를 반영했다. 동시에 기한을 임의로 채우지 않아 `reasons`에는 기한 미정만 남았다.

| 비교 항목 | Day 4 누락 메모의 실제 결과 | 부분 보완 후 실제 결과 |
|---|---|---|
| 담당자 | `[]` | `["민수"]` |
| 기한 | 빈 문자열 | 빈 문자열 |
| 검토 이유 | 담당자 미정·기한 미정 | 기한 미정 |
| 전체 상태 | `review` | `review` |
| 실행 경로 | 검토 안내 → 검토 출력 | 검토 안내 → 검토 출력 |

전체 상태와 실행 경로는 같지만, 해결된 조건과 남은 조건은 달라졌다. 상태값만 보면 보완 효과를 놓칠 수 있으므로 항목별 값과 검토 이유까지 대조해야 한다. 이미 해결된 담당자 문제를 계속 묻지 않으면서 아직 필요한 기한은 확인하도록 하는 것이 이번 재처리의 효과다.

### 검토 화면에 반영된 보완 내용

실제 최종 Output의 `status`는 `review`, 실행 경로는 `검토 안내 → 검토 출력`이었다. `result`의 실제 내용:

```text
원문과 남은 질문을 함께 확인하세요.

회의 메모
초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.
사람의 보완: 담당자는 민수로 확정했다. 기한은 아직 정하지 않았다.

검토할 항목
초안 공유 | 민수 | 기한 미정 | 기한 미정
```

LLM은 보완을 반영한 필드를 만들고, 업무 함수는 현재 필드에 남은 문제를 계산하며, 분기와 Template은 그 결과를 표시했다. 보완이 들어왔다는 사실 자체를 완료 조건으로 삼지 않고, 기한이 실제로 채워졌는지에 따라 검토 상태가 유지됐다.

이 방식에서 다음 실행에 필요한 맥락은 입력 메모 자체에 담긴다. 중단된 실행을 그대로 이어야 하는 요구라면 별도의 상태 보관과 재개 설계가 필요하다. 이번 결과는 원문과 보완을 함께 다시 전달하는 처리에서 확인한 동작이다.

### 저장 전 사람 확인과 재전달 정책

후속 요구는 확인한 회의 초안을 저장하되 정보가 부족한 메모는 보류하고, 같은 결과의 재전달로 초안을 중복 생성하지 않는 것이다. 전체 메모를 검토하는 기존 선택을 이어 사용하고, 전체 `ready`인 초안도 원문과 작업을 사람이 확인한 뒤 `save`를 입력할 때 저장하는 정책으로 정했다. 필드 검사가 원문의 모든 의미를 보장하지 못하므로 검사 통과와 저장 확인을 분리한다.

같은 회의 ID와 같은 저장 내용이면 기존 결과를 유지하고 `already_saved`를 반환한다. 같은 ID의 내용이 달라졌다면 `revision_required`로 보류한다. 기존 초안을 자동으로 덮어쓰지 않아 재전달과 내용 변경을 구분할 수 있다. 메모들이 서로 독립된 이번 입력에서는 한 호출이 실패해도 다음 메모를 계속 처리한다. 앞 결과에 의존하는 순차 업무라면 실패 후 계속 진행하는 정책을 다시 검토해야 한다.

HTTP 요청은 `User-Agent: MeetingReviewLab/1.0`으로 호출 프로그램의 이름·버전을 명시한다. `Content-Type: application/json`은 요청 본문의 형식, `Accept: application/json`은 받을 응답의 형식을 나타낸다. 이 값들은 `workflow_client.py`의 요청 헤더에 있으며 Dify 화면의 앱 이름이나 API 키와는 별개다.

[workflow_client.py](meeting_tool/workflow_client.py)는 제공 호출 프로그램을 재사용하며, 재검사 함수는 제작 Plugin과 같은 `meeting_review.review`로 연결했다. 호출자의 `process`는 API 응답의 `data.status`로 실행 성공을 확인한 뒤 `data.outputs.payload`에서 상세 업무 결과를 읽는다. 실행이 성공했어도 업무 결과가 `review`면 저장을 보류한다. 원문과 반환된 작업을 다시 검사하고, 반환 상태와 재검사 상태도 대조한다.

`DraftStore.save`는 원문과 검사된 작업을 직렬화해 내용 비교값을 만들고, 회의 ID를 기본 키로 사용한다. 같은 ID의 재전달에서는 새 행을 추가하지 않고 기존 내용과 비교한다. 이 저장 경계에서의 멱등성은 같은 결과를 반복 전달해도 초안이 중복 생성되지 않는 성질이다. 모델 호출 자체를 생략하는 캐시는 아니다. 실제 호출 프로그램은 두 번째 처리에서도 모델을 다시 호출하므로 같은 원문이라도 제목이나 근거 표현이 달라지면 내용 변경으로 보류될 수 있다.

### 대역 응답으로 확인한 저장 경계

실제 API 대신 제공 추출을 반환하는 대역, 메모리 DB, 확인 입력 대역으로 호출 프로그램의 후속 처리를 실행했다. 정상 메모는 처음에 `saved`, 같은 결과의 두 번째 전달에서는 `already_saved`가 됐다. 누락 메모는 담당자·기한 미정, 부분 보완 메모는 기한 미정으로 두 처리 모두 `review`를 유지했다. 이 결과는 저장·보류 로직에 대한 확인이며 실제 모델 호출과 사람의 저장 확인은 포함하지 않는다.

[기존 저장 검사](meeting_tool/test_workflow_client.py)에서는 같은 ID의 작업 제목이 달라지면 `revision_required`가 반환되고 기존 저장 건수가 유지됐다. 확인 대역이 거부한 경우에는 모델 결과에 `approved=true`가 있어도 저장되지 않았다. 저장 결정은 모델이 만든 승인 필드가 아니라 호출 프로그램의 확인 입력에 달려 있다.

중간 API 호출의 시간 초과를 대역으로 발생시킨 경우에는 해당 메모를 `workflow_unavailable`로 구분하고 뒤의 독립된 정상 메모를 처리했다. 잘못된 응답 구조는 `invalid_workflow_output`으로 구분됐다. 정상 저장, 업무 검토, 호출 실패는 원인과 다음 행동이 달라 같은 상태로 합치지 않는다.

### 분기 결과를 공통 Output으로 모으기

분기별 안내문은 Variable Aggregator로 모으고 최종 Output 하나에서 `status`, `result`, `extraction`, `payload`를 반환한다. 호출자는 분기와 관계없이 같은 `payload` 필드에서 상세 검사 결과를 읽는다. 분기마다 다른 안내를 보여 주면서 후속 처리에는 공통 입력 계약을 제공하는 구성이다.

정상·검토 경로의 Template과 ELSE의 형식 오류 안내 Template은 각 경로에서 만들어진 문자열을 집계기로 전달한다. 집계기는 여러 안내문을 이어 붙이는 것이 아니라, 실행된 분기의 결과를 공통 출력으로 연결한다. 업무 판단과 안내문 작성은 기존 단계가 담당하고 집계기는 분기 뒤의 전달 경계를 맡는다.

정상 메모의 실제 최종 출력에서 `status=ready`였고, `result`는 다음 객체였다.

```json
{
  "output": "확정 가능한 작업 초안\n초안 공유 | 민수 | 금요일 | 필드 검사 통과"
}
```

누락 메모는 `status=review`였고, `result`는 다음 객체였다.

```json
{
  "output": "원문과 남은 질문을 함께 확인하세요.\n\n회의 메모\n초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.\n\n검토할 항목\n초안 공유 | 담당자 미정 | 기한 미정 | 담당자 미정; 기한 미정"
}
```

안내 문자열은 `result.output`에 있다. 안내문을 사용하는 소비자는 객체 안의 이 필드를 읽는다. 초안 저장 호출자는 `result` 대신 `payload`를 읽으므로 이 표시 구조에 의존하지 않는다.

정상 메모의 `payload`에는 담당자 민수·기한 금요일·원문 근거와 빈 검토 이유, 전체 `ready`가 보존됐다. 누락 메모의 `payload`에는 담당자 빈 배열·기한 빈 문자열과 두 미정 이유, 전체 `review`가 보존됐다. 두 경우 모두 `payload`는 검사 결과 객체를 담은 JSON 문자열로 반환돼 호출 프로그램의 입력 계약과 맞았다. 공통 Output의 Test Run 결과는 아래 실제 API 호출에서 소비하는 입력 계약의 근거다.

### 실제 API 호출과 사람 확인 후 저장

Dify Cloud의 게시된 Workflow를 `workflow_client.py --live`로 호출한 결과, 정상·누락·부분 보완 메모의 구조화 결과가 호출자의 재검사와 저장 판단까지 이어졌다. 제공 세 메모를 두 차례 처리한 터미널 결과는 다음과 같다.

| 입력 ID | 검사 결과와 근거 | 첫 번째 처리 | 두 번째 처리 |
|---|---|---|---|
| `normal` | 작업 `초안 공유`, 담당자 `민수`, 기한 `금요일`, 원문 근거 보존, 검토 이유 없음 | `save` 입력 후 `saved` | `save` 입력 후 `already_saved` |
| `missing` | 담당자 `[]`, 기한 `""`, 검토 이유 `담당자 미정`, `기한 미정` | `review`로 보류 | `review`로 보류 |
| `partial` | 작업 `초안을 공유`, 담당자 `민수`, 기한 `""`, 검토 이유 `기한 미정` | `review`로 보류 | `review`로 보류 |

정상 입력은 `민수가 금요일에 초안을 공유한다.`였다. 두 차례 모두 `checked.status=ready`와 같은 문장의 근거가 표시됐으며, 원문과 작업을 표시한 뒤의 확인 프롬프트에 실제 `save` 입력이 있었다. 첫 번째 `saved`는 [호출 코드](meeting_tool/workflow_client.py)의 `DraftStore.save`에서 로컬 SQLite 초안 저장을 마친 결과다. 저장 위치는 실행 폴더 `meeting_tool/` 아래의 `.local/meeting-drafts.sqlite`다. 두 번째 `already_saved`는 같은 ID의 원문과 검사된 작업이 기존 저장 내용과 일치해 새 초안을 추가하지 않았다는 뜻이다.

`ready`는 필드 검사 통과를 나타내고 `saved`는 사람의 확인 뒤 저장까지 완료됐음을 나타낸다. 두 상태를 분리하므로 모델이 작업을 추출했다는 사실만으로 저장 권한을 얻지 않는다. 누락·부분 보완 메모는 재검사 뒤 `review` 분기에서 반환되므로 저장 확인과 DB 저장으로 진행하지 않았다. 부분 보완에서는 담당자 미정 이유만 해소되고 기한 미정 이유가 남아, 보완된 정보만 반영하는 정책과 실제 결과가 일치했다.

누락 메모의 `evidence`는 첫 번째에 `초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.`라는 한 문자열, 두 번째에 두 문장으로 나뉜 배열이었다. 원문 근거와 담당자·기한의 누락 상태는 같아 검토 판단도 유지됐다. 이는 반복 호출에서 표현 구조가 달라질 수 있음을 보여 준다. 정상 메모는 이번 두 호출에서 저장 내용이 같아 `already_saved`였지만, 저장 가능한 작업의 제목이나 근거 배열이 달라지면 같은 원문이라도 내용 비교 결과가 달라질 수 있다. 현재 저장 정책은 의미의 유사성을 다시 추론하지 않고 원문과 검사된 작업의 저장 내용을 비교한다.

실제 노드·변수 연결은 [내보낸 Workflow DSL](회의%20후속%20작업%20추출.yml)에 보존했다. 다른 작업공간에서 실행하려면 [제작 Plugin](meeting_tool/)을 별도로 연결해야 한다.
