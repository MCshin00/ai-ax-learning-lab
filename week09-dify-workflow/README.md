이번 주의 질문은 **“같은 처리 흐름을 노코드로 만들면 무엇이 달라지는가?”**입니다. 회의 후속 작업 요구에서 필요한 정보·판단·다음 행동을 도출하고, 모델·업무 함수·Workflow가 맡을 책임과 입출력 경계를 설계합니다. 작은 Tool Plugin으로 제공 업무 함수를 공개하고 실제 Workflow에서 사용합니다. 핵심 결과는 선택한 구조로 작동하는 Workflow와 Tool Plugin입니다.

제공 메모·업무 함수·SDK 예제로 진행합니다. Python은 Dify Plugin의 구현에 사용하고 다른 Java 실습을 옮기지 않습니다. AI가 구성을 제안하고 구현을 돕되 학습자가 모델·업무 함수·Workflow가 맡는 책임과 예상 출력을 판단합니다.

## Dify와 AI 애플리케이션 이해하기

### Dify — 모델과 도구를 연결해 앱을 만들고 실행하는 플랫폼

Dify는 언어 모델을 사용하는 애플리케이션을 만들고 운영하는 플랫폼입니다. 브라우저의 편집 화면에서 입력 폼, 모델 요청, 데이터 가공, 도구 호출과 조건 분기를 구성하고, 실행 결과를 단계별로 확인합니다. 완성한 앱은 웹 화면이나 API를 통해 사용할 수 있습니다. 여기서 **앱**은 특정 입력을 받아 정해진 처리를 수행하고 결과를 돌려주는 하나의 프로그램입니다. [Dify 기본 개념](https://docs.dify.ai/en/learn/key-concepts)

예를 들어 문서 요약 앱을 만든다면 문서를 받을 곳, 요약을 요청할 모델과 지침, 사용자에게 돌려줄 결과를 정합니다. Dify는 이 구성을 저장하고 실행하며, LLM은 그중 문서를 읽고 요약하는 일을 맡습니다. 따라서 모델을 바꾸어도 입력 폼과 결과 전달 방식은 유지할 수 있고, 반대로 같은 모델을 쓰면서 처리 순서를 바꿀 수도 있습니다.

채팅 화면에서 매번 요청문을 입력하는 사용법과 비교하면, 앱 제작에서는 **어떤 입력에도 반복 적용할 처리와 연결을 미리 정한다**는 점이 중요합니다. Dify를 사용해도 입력·출력과 실패 시 행동은 제작자가 결정합니다. 화면에 노드를 배치하면 연결 코드 일부를 줄일 수 있지만, 어떤 정보를 어디로 보낼지에 대한 설계는 남습니다.

### 화면으로 구성하는 개발과 코드로 구성하는 개발

6주차의 직접 API 호출이나 7주차의 프레임워크에서는 호출 순서·함수 인자·반환값을 코드로 표현했습니다. Dify에서는 그중 많은 부분을 노드와 변수 설정으로 표현합니다. **오케스트레이션**은 이처럼 여러 처리의 순서와 데이터 전달을 조직하는 일입니다.

화면으로 구성하면 중간 결과와 분기를 같은 캔버스에서 살펴보기 쉽습니다. 코드로 구성하면 복잡한 자료 구조나 실행 정책을 프로그래밍 언어와 테스트 도구로 다루기 쉽습니다. 어느 쪽이든 모델 입력을 잘못 전달하면 결과가 어긋납니다. 요구가 자주 바뀌는 짧은 흐름에는 화면 구성이 편할 수 있고, 세밀한 상태 관리나 기존 코드 통합이 커지면 코드와의 경계를 더 신중하게 정해야 합니다.

노코드는 준비된 기능을 설정해 구성하는 방식이고, 로우코드는 필요한 곳에 코드를 더하는 방식입니다. 이번 주에는 기본 노드를 사용하고 Python Tool Plugin도 만들므로 두 방식을 함께 경험합니다. 비교의 기준은 코드 줄 수보다 책임·입출력·변경 위치가 얼마나 분명해지는가입니다.

### Dify Cloud와 직접 설치 — 누가 실행 환경을 운영하는가

Dify를 이용하려면 편집 화면과 앱을 실행하는 서버가 필요합니다. **Dify 환경**은 이 서버와 접속 주소, 계정·설정이 준비된 상태를 뜻합니다. 학습 폴더의 파일만으로 Dify 서버가 실행되는 것은 아닙니다.

| 방식 | 접속 방법 | 준비와 운영 책임 |
|---|---|---|
| Dify Cloud | 브라우저에서 [cloud.dify.ai](https://cloud.dify.ai)에 가입·로그인 | Dify가 서버를 운영하고, 사용자는 작업공간·모델·앱을 설정 |
| 조직이나 교육자가 제공한 환경 | 안내받은 웹 주소에 해당 계정으로 로그인 | 운영자가 서버를 관리하고, 사용자는 허용된 작업공간에서 앱을 구성 |
| 직접 설치(Self-hosting) | 자신의 PC나 서버에 Dify를 실행한 뒤 그 웹 주소로 접속 | 설치·업데이트·저장소·네트워크 등을 직접 관리 |

이번 학습을 처음 시작하고 제공받은 환경이 없다면 **Dify Cloud를 기본 경로로 사용합니다.** 별도의 서버 설치 없이 Workflow 제작을 시작할 수 있기 때문입니다. 직접 설치는 운영 위치와 설정을 관리해야 할 때 선택할 수 있으며, [공식 Docker Compose 설치 안내](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose)를 따릅니다. Docker Compose는 Dify를 구성하는 여러 서버 프로그램을 함께 실행하는 도구입니다. 직접 설치하더라도 외부 모델을 선택하면 모델 요청은 그 제공자로 전달됩니다.

### 작업공간·Studio·앱 — 설정을 어디에 두는가

**작업공간(Workspace)**은 앱과 모델·도구 설정을 관리하는 단위입니다. **Studio**는 그 작업공간에서 앱을 만들고 편집하는 곳입니다. **캔버스(Canvas)**는 한 앱의 처리 흐름을 노드로 배치하는 편집 화면입니다.

작업공간에서 모델을 사용할 수 있도록 준비한 뒤, 앱 안의 LLM 노드에서 실제로 호출할 모델을 선택합니다. 이 구분은 연결 문제를 찾는 데 도움이 됩니다. 모델 목록 자체가 비어 있으면 제공자 설정을 확인하고, 모델을 선택했는데 메모가 전달되지 않으면 해당 앱의 프롬프트와 변수를 확인합니다.

### 모델 제공자·모델·인증 — 누가 문장을 처리하는가

**모델 제공자(Model Provider)**는 모델을 호출할 연결을 제공하는 서비스 또는 시스템입니다. **모델**은 그 연결을 통해 실제로 요청을 처리하는 대상입니다. Dify의 제공자 설정은 모델에 접근하는 방법을 준비하고, LLM 노드는 사용할 모델과 요청 내용을 정합니다.

모델 연결에는 제공자별 인증 정보가 필요할 수 있습니다. API 키는 프로그램이 해당 서비스를 사용할 권한을 증명하는 값입니다. Dify 로그인은 작업공간에 들어가는 권한이고, 모델 인증은 그 작업공간에서 모델을 호출할 권한이므로 각각 준비해야 할 수 있습니다. Cloud에서 제공되는 크레딧으로 지원 모델을 사용하는 경로도 있습니다. 현재 제공 모델·사용량·과금 조건을 계정 화면에서 확인하며, 키가 필요한 경우 본인이 제공자의 발급 화면에서 받아 Dify 설정에 입력합니다. [모델 준비와 첫 접속](https://docs.dify.ai/en/quick-start)

## 흐름과 데이터의 기본 개념

### Workflow와 Chatflow — 한 번의 처리와 이어지는 대화

**Workflow**는 입력을 받아 여러 단계를 거쳐 결과를 만드는 실행 흐름입니다. Dify의 Workflow 앱은 문서 한 건 요약이나 입력 자료 변환처럼 한 번의 요청에서 결과를 얻는 작업에 적합합니다. **Chatflow**는 대화의 매 차례에 실행되며, 대화 변수나 모델의 대화 기억을 활용할 수 있는 앱 유형입니다. [앱 유형](https://docs.dify.ai/en/learn/key-concepts)

예를 들어 같은 문서를 한 번 요약하는 요구는 Workflow로 구성할 수 있습니다. 사용자가 “그중 두 번째 내용을 더 설명해 줘”라고 이어 물을 때 이전 대화를 활용하려면 Chatflow의 대화 기능을 검토할 수 있습니다. 선택 기준은 화면 모양보다 **이전 대화의 무엇을 다음 요청에 유지해야 하는가**입니다. 이번 회의 메모 사례는 원문과 보완을 입력 한 건에 담아 처리하므로 Workflow를 사용합니다.

### 노드·연결·실행 — 무엇이 언제 작동하는가

**노드(Node)**는 입력 수집, 모델 호출, 코드 실행처럼 한 종류의 처리를 맡는 단위입니다. 노드 사이의 연결은 실행 순서와 가능한 경로를 표현합니다. **실행(Run)**은 현재 구성에 특정 입력을 넣어 실제 처리가 진행되는 한 번의 과정입니다. 같은 구성도 입력과 모델 응답에 따라 다른 결과를 낼 수 있습니다.

`입력 → 모델 → 출력`을 구성했다면 입력 노드가 값을 받고, 모델 노드가 요청을 보내고, 출력 노드가 선택된 결과를 반환합니다. 각 노드의 실행 상세에는 그 단계가 받은 입력과 만든 출력이 나타납니다. 최종 결과만 보면 알기 어려운 누락도 처음 값이 달라진 단계를 찾으면 원인을 좁힐 수 있습니다.

### 변수·참조·타입 — 어떤 값을 전달하는가

**변수**는 이름으로 값을 가리킬 수 있게 한 것입니다. **참조**는 그 이름을 통해 실제 값을 가져오는 연결입니다. 변수 이름이 `memo`이고 이번 값이 “민수가 금요일에 초안을 공유한다”라면, 일반 글자 `memo`와 변수 참조는 서로 다른 입력입니다. 참조를 넣었을 때만 실행 시점의 문장이 프롬프트에 들어갑니다.

**타입(Type)**은 값의 종류입니다. 문자열은 텍스트, 배열은 여러 값의 목록, 객체는 이름 붙은 필드의 묶음입니다. 같은 내용을 담아도 객체와 문자열은 후속 단계에서 사용하는 방법이 다릅니다. 객체에서는 `tasks` 필드를 바로 읽을 수 있지만 JSON 문자열에서는 먼저 문자열을 해석해 객체로 바꾸어야 합니다.

노드 연결은 실행 순서를, 변수 설정은 값의 전달을 정합니다. 따라서 앞 노드에서 여러 출력이 나올 때 어떤 출력을 받을지 명시해야 합니다. 이 원리는 코드에서 함수를 호출할 순서와 인자로 넘길 값을 각각 정하는 것과 같습니다.

### 프롬프트와 LLM 추출 — 처리 규칙과 이번 자료

**프롬프트**는 모델에 보내는 지침과 입력 내용입니다. 채팅형 모델에서는 SYSTEM 메시지에 지속적으로 적용할 처리 규칙을, USER 메시지에 이번 자료를 둘 수 있습니다. 예를 들어 “원문에 없는 날짜를 만들지 마세요”는 규칙이고 “금요일에 공유한다”는 해석할 자료입니다. [LLM 노드](https://docs.dify.ai/en/cloud/use-dify/nodes/llm)

**추출(Extraction)**은 문장의 정보를 정해진 필드로 옮기는 처리입니다. 요약이 읽기 쉬운 짧은 설명을 만드는 데 초점을 둔다면, 추출은 후속 단계가 작업·담당자·기한을 각각 사용할 수 있게 합니다. 다만 LLM은 문장의 의미를 해석하므로 누락이나 잘못된 연결이 생길 수 있습니다. 형식이 일정하다는 것만으로 정확성을 판단하지 않고 원문과 대조합니다.

### 구조화 출력·JSON Schema — 결과의 형식을 약속하기

**구조화 출력(Structured Outputs)**은 모델 응답을 미리 정한 데이터 구조로 받도록 설정하는 기능입니다. **JSON Schema**는 필드 이름, 타입, 필수 여부와 허용 범위를 표현하는 규칙입니다. 프롬프트가 작업의 의미와 추출 원칙을 설명한다면 스키마는 다음 단계가 읽을 모양을 정합니다. Dify의 LLM 노드에서 스키마를 지정할 수 있으며 지원 방식은 모델에 따라 다릅니다. [구조화 출력 설정](https://docs.dify.ai/en/cloud/use-dify/nodes/llm)

예를 들어 `owners`를 문자열 배열로 선언하면 `["민수"]`나 `[]`가 그 타입에 맞습니다. 필수 필드로 지정하는 것은 `owners`라는 항목을 결과에 포함하라는 뜻입니다. 담당자가 알려져 있다는 뜻은 아닙니다. `due`가 필수 문자열이어도 기한을 모르면 빈 문자열을 보낼 수 있습니다.

스키마가 `owners`의 타입을 확인해도 민수가 실제 담당자인지는 원문을 보아야 합니다. **형식의 유효성**과 **내용의 정확성**은 별도 판단입니다. Day 1은 스키마와 실제 응답을 확인하고, Day 4는 형식을 지킨 응답에서도 상충이 누락될 수 있음을 살펴봅니다.

### 직렬화·파싱·입출력 계약 — 서로 다른 처리 사이를 연결하기

**직렬화(Serialization)**는 객체 같은 데이터를 전송·저장 가능한 표현으로 바꾸는 일입니다. 이 주차에서는 객체를 JSON 문자열로 바꿉니다. **파싱(Parsing)**은 그 문자열의 문법을 읽고 구조를 해석하는 일입니다. JSON 파싱 결과를 객체로 받아 필드를 사용할 수 있습니다.

```text
작업 객체 {tasks: …} → JSON 직렬화 → 문자열 → JSON 파싱 → 작업 객체
```

직렬화는 추출된 담당자나 기한을 다시 판단하지 않습니다. 객체를 받는 단계끼리는 그대로 전달할 수 있지만, 받는 쪽이 문자열을 요구한다면 경계에서 변환해야 합니다. Day 1의 `json.dumps`는 LLM의 `structured_output`을 제공 Tool이 받는 문자열로 바꿉니다. 이미 JSON인 문자열을 다시 직렬화하면 따옴표로 감싼 문자열이 한 겹 더 생기므로 입력 타입을 확인합니다.

**입출력 계약**은 보내는 쪽과 받는 쪽이 합의한 이름·타입·의미·실패 시 결과입니다. 예를 들어 원문과 추출 결과를 함께 받는 함수에는 두 값 모두 전달해야 합니다. 이름만 맞고 타입이 다르거나, 타입만 맞고 의미가 달라도 연결은 올바르지 않습니다. 이 계약은 언어나 Dify에 한정되지 않는 프로그램 간 연결의 원리입니다.

## 도구 실행과 결과 처리의 기본 개념

### Tool·Plugin·SDK — 호출할 기능을 확장하기

**Tool**은 이름과 입력·출력으로 호출할 수 있는 기능입니다. **Plugin**은 Dify에 기능을 추가하기 위한 코드와 선언의 묶음이며, 그중 Tool을 제공하는 종류가 **Tool Plugin**입니다. 하나의 Tool Provider는 여러 Tool을 묶어 제공할 수 있습니다. 여기서 Tool Provider는 도구 묶음의 제공자이며, 앞서 모델 연결을 준비한 Model Provider와 역할이 다릅니다. [Tool Plugin 구조](https://docs.dify.ai/en/develop-plugin/dev-guides-and-walkthroughs/tool-plugin)

**SDK(Software Development Kit)**는 플랫폼과 연결하는 프로그램을 만들 때 사용하는 라이브러리와 개발 수단입니다. Dify Plugin SDK는 입력을 받는 실행 지점과 결과 메시지를 만드는 방법을 제공합니다. 업무 함수가 데이터의 의미를 판단하고, SDK 연결 코드는 그 함수의 입력과 결과를 Dify가 이해하는 형식으로 주고받게 합니다.

예를 들어 회의 검사 함수가 `{status: "review"}`를 반환해도 그 함수가 자동으로 Dify의 도구 목록에 나타나지는 않습니다. 이름·입력 선언·실행 코드의 위치를 등록하고, 실행 결과를 SDK 메시지로 반환해야 합니다. **등록 가능한 구조를 갖추는 일**과 **업무에 맞는 판단을 구현하는 일**은 각각 확인해야 합니다. Day 3에서 실제 선언 파일과 연결 코드를 읽습니다.

### 기본 노드·Code·Tool — 기능을 둘 위치 선택하기

| 기능 | 하는 일 | 사용하는 이유 |
|---|---|---|
| LLM | 프롬프트를 모델에 보내 해석·생성 | 자연어의 의미를 다루기 위해 |
| Code | 입력값을 코드로 가공하고 반환 | 직렬화처럼 명확한 변환이 필요할 때 |
| Tool | 등록된 기능을 지정한 입력으로 호출 | 별도로 관리하는 업무 함수나 외부 기능을 사용하기 위해 |
| IF/ELSE | 조건에 맞는 다음 경로 선택 | 결과에 따라 후속 행동이 달라질 때 |
| Template | 정해진 형식에 값을 넣어 텍스트 생성 | 추가 모델 호출 없이 표시 문구를 만들 때 |
| Output | 선택한 값을 앱의 최종 결과로 반환 | 호출한 사용자나 프로그램에 결과를 전달하기 위해 |

앱 한 곳에서만 쓰는 짧은 변환은 Code 노드에 둘 수 있습니다. 여러 앱에서 같은 계약으로 쓸 기능을 별도의 코드·의존성과 함께 관리하려면 Tool Plugin을 검토할 수 있습니다. Plugin에는 등록과 실행 환경 관리라는 부담이 따릅니다. 기능이 어디에 있는가보다 재사용·변경·실패 처리를 어느 단위로 관리할 것인가가 선택 기준입니다.

**Template**은 값과 표시 형식을 분리합니다. 예를 들어 `담당자: {{ owner }}`에 `owner="민수"`를 넣으면 `담당자: 민수`가 됩니다. 이때 민수를 담당자로 추론하는 처리는 없습니다. Dify의 Template 노드는 Jinja2라는 템플릿 문법을 사용하며, Day 4에서는 이미 검사된 값을 화면 문구로 배치합니다. [Template 노드](https://docs.dify.ai/en/cloud/use-dify/nodes/template)

### 조건 분기·업무 상태·실행 실패 — 결과에 따른 다음 행동

**조건 분기**는 값이 조건을 만족하는지에 따라 실행 경로를 고르는 처리입니다. IF는 첫 조건, ELIF는 추가 조건, ELSE는 앞의 조건에 맞지 않는 경우입니다. 분기는 입력받은 값을 사용하므로 그 값에 없는 사실까지 찾아내지는 못합니다. [IF/ELSE 노드](https://docs.dify.ai/en/cloud/use-dify/nodes/ifelse)

**업무 상태**는 처리한 자료가 업무 기준을 얼마나 만족하는지 나타냅니다. **실행 상태**는 프로그램이 처리 자체를 수행했는지 나타냅니다. 검사가 정상 실행된 결과가 “보완 필요”일 수 있습니다. 반대로 연결 실패로 함수를 호출하지 못했다면 보완 여부를 판단한 결과 자체가 없습니다.

이번 예제의 `ready`, `review`, `invalid`는 우리가 정한 결과 이름입니다. `ready`는 제공 필드 검사를 통과한 경우, `review`는 누락·상충 등을 사람이 보완할 경우, `invalid`는 JSON이나 계약을 해석할 수 없는 경우입니다. 이 이름들은 Dify의 실행 성공·실패 상태와 다릅니다. `ready`여도 원문 의미의 정확성이나 실제 업무 등록까지 증명되지는 않습니다.

### 사람 확인·재처리·멱등성 — 결과를 행동으로 옮기는 조건

**사람 확인**은 실행할 대상과 내용을 사람이 검토하고 허용하는 단계입니다. 모델이 만든 `approved=true` 같은 값만으로 사람의 확인이 생기지는 않습니다. **재처리**는 자료를 다시 입력해 처리하는 것입니다. 보완한 자료로 새 실행을 시작하는 방식과, 중단된 실행의 상태를 저장했다가 이어가는 방식은 필요한 상태 관리가 다릅니다.

**멱등성(Idempotency)**은 같은 작업을 반복 요청해도 효과가 한 번 적용한 것과 같도록 만드는 성질입니다. 예를 들어 저장 응답을 받지 못해 같은 초안을 다시 전달했을 때 중복 행이 생기지 않아야 한다면 작업 식별자와 기존 저장 내용을 비교할 방법이 필요합니다. 내용이 달라진 재요청까지 무조건 무시하면 수정 요구를 잃습니다. Day 5의 작은 저장 예제로 같은 요청·내용 변경·독립된 항목 실패를 구분합니다.

### 시험 실행·게시·API·DSL — 만든 앱을 사용하고 보관하기

**시험 실행(Test Run)**은 편집 중인 구성을 입력값으로 확인하는 과정입니다. **게시(Publish)**는 외부 호출에서 사용할 앱 구성을 반영하는 과정입니다. **API**는 다른 프로그램이 정해진 요청 형식으로 앱을 호출하는 접점입니다. 외부 프로그램은 요청을 보낼 주소와 인증, 입력 필드와 결과 형식을 알아야 합니다. 게시 후 누가 사용할 수 있는지는 제공 방식과 접근 설정에 따릅니다. [앱 게시와 제공 방식](https://docs.dify.ai/en/cloud/use-dify/publish/README)

**DSL(Domain-Specific Language)**은 특정 목적의 구성을 표현하는 언어입니다. Dify에서는 앱 구성을 YAML 파일로 내보내고 가져올 수 있습니다. **YAML**은 이름과 값을 계층적으로 적는 데이터 표현 형식이며, DSL은 그 형식에 Dify의 노드·연결·설정을 담은 것입니다. 앱 구성을 보관하는 파일과 특정 입력의 실제 실행 기록은 역할이 다릅니다. 다른 환경에 가져왔을 때는 모델과 Plugin 연결도 그 환경에서 확인해야 합니다. [Dify DSL](https://docs.dify.ai/en/learn/key-concepts)

## 회의 메모 사례에 개념 연결하기

이번 요구는 회의 메모에서 후속 작업을 추출하고, 담당자·기한·상충을 검사해 사용할 초안과 보완할 정보를 보여 주는 것입니다. LLM은 문장 해석을, 업무 함수는 정해진 조건 검사를, Workflow는 값의 전달과 다음 경로를 맡습니다. 정상 메모의 **예상 추출**은 다음과 같습니다.

```json
{"tasks":[{"title":"초안 공유","owners":["민수"],"due":"금요일","evidence":["민수가 금요일에 초안을 공유한다."],"conflicts":[]}]}
```

`owners`는 여러 이름을 보존하는 배열입니다. 담당자가 둘로 기록됐는데 최종 결정이 없다면 한 사람을 임의로 고르지 않도록 합니다. `due`는 원문의 기한 표현입니다. 기준 날짜 없이 “금요일”을 특정 날짜로 바꾸면 원문에 없는 사실을 더하게 됩니다. `evidence`는 원문에서 인용한 근거이고 `conflicts`는 미해결 상충입니다. 이 필드명은 제공 함수가 읽는 계약이며 모든 추출 앱의 표준은 아닙니다.

제공 `business.py`는 이 필드를 검사합니다. `tools/review_tasks.py`는 Dify 입력을 함수에 연결하고, YAML 선언은 Dify 화면에 입력·출력을 알려 줍니다. 예를 들어 근거에 이름이 포함되는지를 코드로 확인할 수 있지만 그 이름이 정말 해당 작업의 담당자인지는 문장 의미의 문제입니다. 이 차이를 Day 2의 책임 선택과 Day 4의 상충 사례에서 다시 확인합니다.

### Cloud 무료 플랜으로 어느 정도 진행할 수 있는가

이번 주의 기본 시작 경로는 **Dify Cloud의 무료 Sandbox 플랜**입니다. 하나의 Workflow를 단계적으로 수정하고 짧은 제공 메모를 실행하므로, 공개된 무료 플랜의 규모로 학습을 시작하기에 적합합니다. 유료 구독이나 Dify 서버 설치를 먼저 할 필요는 없습니다.

2026년 9월 15일 공식 안내 기준으로 Sandbox는 작업공간 1개·사용자 1명·앱 5개, 모델 메시지 크레딧 200, 월 API 호출 한도 5,000회와 실행 로그 30일 보관을 제공합니다. 한도와 요금은 바뀔 수 있으므로 시작 시 [공식 Cloud 요금표](https://dify.ai/pricing/dify-cloud)에서 확인합니다. 한 작업공간을 여러 학습자가 공유하기보다 각자 무료 계정으로 자신의 Workflow를 구성합니다.

**200크레딧은 가입 시 한 번 제공되며 매월 다시 채워지지 않습니다.** 모델별 차감량이 달라 200번의 실행을 뜻하지도 않습니다. 제공 크레딧으로 쓸 수 있고 구조화 출력을 지원하는 모델을 선택해 정상·누락 사례부터 확인합니다. 같은 Workflow 안의 LLM 호출이 늘어나거나 재실행이 많아지면 더 빨리 소진됩니다. 따라서 작은 사례를 중심으로 진행하기에는 적합하지만 모든 학습자의 무료 완주를 보장하는 양은 아닙니다. [크레딧 제공 방식](https://docs.dify.ai/en/quick-start)

예를 들어 호출당 1크레딧인 모델이면 남은 200크레딧으로 약 200번, 10크레딧인 모델이면 약 20번의 모델 응답을 받을 수 있다는 계산입니다. 이것은 Workflow 전체 실행 횟수가 아니라 **모델 호출량의 예상**입니다. 현재 요금표의 모델별 차감량을 보고 선택하며, 이번 작은 추출 실습은 적은 크레딧을 쓰는 모델부터 결과를 확인합니다.

크레딧이 부족하면 무료 작업공간에 본인의 모델 API 연결을 설정해 이어갈 수 있습니다. 이 경우 모델 제공자의 사용료가 별도로 발생할 수 있으며, Dify 구독료와 모델 호출 비용은 구분합니다. 로컬에 Dify를 설치해도 외부 모델의 비용이 없어지지는 않습니다.

Cloud를 사용하면 Dify 서버와 Docker를 PC에 설치하지 않아도 됩니다. Day 3에서는 직접 만든 Tool Plugin을 시험하기 위해 **Python 3.12와 Plugin 의존성을 PC에 준비**하고, 실행 중인 Plugin을 Cloud 작업공간에 개발 연결합니다. 공식 디버그 안내는 Cloud와 자체 설치 환경을 모두 다룹니다. 실제 연결은 해당 작업공간의 Plugins 화면에서 주소와 키를 받아 확인합니다. [Plugin 개발 연결](https://docs.dify.ai/en/develop-plugin/features-and-specs/plugin-types/remote-debug-a-plugin)

### 기본 경로 — Cloud 첫 접속과 모델 준비

브라우저와 IDE를 함께 사용합니다. 브라우저는 Dify 앱의 구성·시험 실행에, IDE는 제공 자료를 읽고 Day 3부터 Plugin 코드를 편집·실행하는 데 사용합니다. PC의 학습 폴더는 브라우저의 Dify 작업공간에 자동으로 올라가지 않습니다. 필요한 프롬프트와 스키마를 직접 복사하고 변수 연결은 Dify 화면에서 설정합니다.

1. 제공받은 환경이 있으면 그 주소로 접속합니다. 없다면 브라우저 주소창에 `https://cloud.dify.ai`를 입력해 Dify Cloud를 열고 가입·로그인합니다.
2. 사용할 작업공간을 선택하거나 화면 안내에 따라 준비합니다. Studio에서 앱을 만들 수 있는지 확인합니다.
3. **Integrations → Model Provider**에서 사용할 모델 제공자를 준비합니다. 설치 버튼이 표시되면 해당 제공자 연결을 설치하고 설정합니다. 이미 연결된 제공자는 이어 사용합니다.
4. Cloud의 지원 크레딧이나 본인의 모델 인증 중 사용할 경로와 비용·사용 가능량을 확인합니다. API 키가 필요한 경로에서는 제공자에서 발급한 값을 본인이 Dify의 해당 인증 입력란에 넣습니다. 모델 키와 이후 Plugin 개발 연결 키는 용도가 다르므로 서로 대신 넣지 않습니다.
5. IDE에서 학습 저장소의 `week09-dify-workflow/`를 열고 `extraction-prompt.txt`, `extraction-schema.json`, `cases.json`을 확인합니다. 다음 Day 1에서 앱을 만들고 LLM 노드의 모델 목록이 표시되는지 확인합니다.

이 경로는 Dify Cloud의 현재 공식 안내를 기준으로 합니다. 자체 설치 버전이나 화면 언어에 따라 메뉴 위치가 다르면 모델 제공자 설정·앱 제작이라는 역할로 찾습니다. 메뉴가 없거나 편집할 수 없으면 해당 작업공간의 권한을 확인합니다. [공식 첫 접속과 모델 설정](https://docs.dify.ai/en/quick-start)

Day 1의 Code 노드는 Dify가 실행합니다. PC의 Python 3.12와 Plugin 개발 연결은 Day 3에서 준비합니다. `dify-review.md`는 첫 실제 결과를 남길 때 주차 폴더에 만들고 이후 같은 노트에 이어 씁니다.

### 선택 경로 — PC에 Dify를 설치해서 진행하기

Cloud로 진행한다면 바로 아래 실습 순서와 Day 1로 이동합니다. 로컬 설치를 선택할 때는 다음 준비를 마친 뒤 **같은 Day 1의 Workflow 만들기**로 합류합니다. 학습 목표와 입력 자료는 같고 Dify 서버를 운영하는 위치만 달라집니다.

#### 1. Docker 실행 환경 준비

Docker는 필요한 서버 프로그램을 컨테이너라는 실행 단위로 구동하는 도구입니다. Docker Compose는 Dify의 웹 화면·API·DB·Plugin 실행 서비스 등 여러 컨테이너를 설정에 따라 함께 시작합니다. 로컬 설치는 브라우저만 여는 것에 더해 이 서버들을 PC에서 실행하는 준비입니다.

| 운영체제 | 준비 방법 | 이후 명령을 실행할 곳 |
|---|---|---|
| Windows | WSL 2와 [Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/)을 준비하고 Linux 컨테이너·사용할 WSL 배포판의 통합을 켬 | PowerShell에서 Docker를 사용할 수 있음. 이 교재의 권장 설치 위치는 WSL의 Linux 파일시스템이며 이 경로를 선택하면 WSL 터미널 사용 |
| macOS | [Docker Desktop](https://docs.docker.com/desktop/setup/install/mac-install/) 설치·실행 | 터미널 |
| Linux | [Docker Engine](https://docs.docker.com/engine/install/)과 Docker Compose 플러그인 준비 | 터미널 |

공식 Dify 설치 안내의 최소 자원은 CPU 2코어·메모리 4GiB이며, macOS의 Docker 가상머신에는 메모리 8GiB 설정을 안내합니다. 운영체제와 IDE가 쓸 여유도 확보합니다. Windows에서 WSL을 사용하는 경우 컨테이너에 연결할 소스·데이터를 Linux 파일시스템에 두라는 공식 권장에 따라, WSL 안에서 선택한 작업 폴더에 설치합니다. [운영체제별 설치 조건](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose)

#### 2. Dify 소스와 설정 준비

과정 원본·학습 저장소 바깥에 Dify 서버용 작업 폴더를 선택합니다. Git이 설치되어 있어야 합니다. [Dify 릴리스](https://github.com/langgenius/dify/releases)에서 사용할 정식 릴리스의 태그를 확인하고 아래 `<릴리스 태그>`를 그 값으로 바꿉니다. 서버의 여러 구성요소를 같은 릴리스로 준비하기 위해 태그를 지정합니다.

다음 명령은 **Windows PowerShell과 macOS·Linux·WSL 터미널에서 동일**합니다. 선택한 작업 폴더에서 실행하며, WSL 경로를 선택했다면 전체 과정을 WSL 터미널에서 진행합니다.

```text
git clone --branch "<릴리스 태그>" --depth 1 https://github.com/langgenius/dify.git dify-local
cd dify-local/docker
docker compose version
```

공식 안내 기준으로 Compose 2.24.0 이상이 필요합니다. `docker` 명령을 찾을 수 없거나 서버에 연결할 수 없으면 Docker 설치·실행 상태를 먼저 확인합니다. 이미 `dify-local` 폴더가 있으면 새 설치와 기존 설치를 구분해 작업 위치를 정합니다.

IDE에서 방금 받은 `dify-local/docker/`를 엽니다. 학습자가 파일 탐색기에서 `.env.example`을 복사해 `.env`라는 이름으로 저장합니다. 이것은 Dify 서버가 시작할 때 사용하는 로컬 설정입니다. 기존 `.env`가 있으면 그대로 보존하고, 내용이나 인증 값을 AI·학습 노트에 보내지 않습니다. Day 3의 `meeting_tool/` 설정 파일은 Plugin 실행용이므로 위치와 용도가 다릅니다.

#### 3. 서버 실행과 첫 로그인

같은 `dify-local/docker/` 위치에서 실행합니다. 아래 명령도 **Windows PowerShell과 macOS·Linux·WSL에서 동일**합니다. Compose는 여러 서버를 함께 기동·확인하는 데 사용합니다.

```text
docker compose up -d
docker compose ps
```

첫 실행은 필요한 이미지를 내려받으므로 시간이 걸릴 수 있습니다. `-d`는 컨테이너를 백그라운드로 실행하는 옵션입니다. 웹·API·DB 등 지속 실행 서비스가 실행 또는 정상 상태인지 확인합니다. 초기 준비용 일회성 서비스는 작업 후 종료될 수 있으므로 종료 표시만으로 전체 실패라고 판단하지 않습니다. Docker Desktop의 Containers 화면에서도 상태와 개별 서비스 로그를 볼 수 있습니다.

기본 포트 설정이면 브라우저 주소창에 `http://localhost/install`을 입력해 관리자 계정을 만들고, 이후 `http://localhost`에서 로그인합니다. 웹 포트를 바꿨다면 주소에도 해당 포트를 넣습니다. 접속되지 않으면 컨테이너 상태와 웹 포트 충돌부터 확인합니다. [서버 실행과 접속](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose)

#### 4. 모델 연결 후 Day 1로 합류

로컬 Dify의 모델 제공자 설정에서 사용할 모델을 연결합니다. 가장 단순한 구성은 **로컬 Dify + 외부 모델 API**입니다. Cloud의 무료 메시지 크레딧이 로컬 설치에 이전되지는 않으므로 외부 모델을 사용한다면 해당 제공자의 인증과 사용 가능량을 준비합니다. 로컬 모델도 연결할 수 있지만 별도의 모델 서버·PC 사양·구조화 출력 지원을 확인해야 합니다.

Studio에서 Workflow를 만들 수 있고 LLM 노드에서 모델을 선택할 수 있으면 준비가 끝납니다. 아래 Day 1을 그대로 진행합니다. 이후 다시 사용할 때도 Dify 컨테이너가 실행 중이어야 합니다. 실습을 마치고 서버만 멈출 때는 같은 `docker/` 폴더에서 `docker compose stop`, 다시 시작할 때는 `docker compose start`를 사용합니다. 이 명령은 PowerShell과 macOS·Linux·WSL에서 같으며 저장 데이터용 볼륨은 유지합니다.

Day 3의 로컬 Plugin 개발 연결에서는 브라우저 웹 주소와 디버그 주소를 구분합니다. Plugins의 디버그 화면에 표시된 주소·키를 사용하고, PC의 Plugin 프로세스가 그 주소에 접근할 수 있어야 합니다. 자체 설치의 기본 디버그 포트는 `5003`이며 Docker에서 이 포트의 공개와 개발 연결 활성화가 필요할 수 있습니다. 연결이 거부되면 선택한 릴리스의 설정과 [공식 Plugin 디버그 안내](https://docs.dify.ai/en/develop-plugin/features-and-specs/plugin-types/remote-debug-a-plugin)를 확인합니다. Day 5의 API 호출에는 해당 로컬 앱의 API 안내에 표시된 기본 주소와 키를 사용합니다.

각 실습은 설계 판단을 드러내는 작은 비교입니다. 예를 들어 정상 메모만 실행하면 빈값의 의미를 볼 수 없고, 부분 보완의 최종 `review`만 보면 담당자 문제가 해결됐다는 사실을 놓칩니다. 그래서 같은 처리에 필요한 차이만 넣고 중간 필드와 다음 행동을 함께 읽습니다. 실행 성공 표시는 연결의 근거이고, 설계 판단은 그 결과가 요구를 만족하는 이유와 조건이 달라질 때 바꿀 위치에서 확인합니다. 예상·선택·실제 결과의 해석은 기존 노트에 이어 쓰며 별도 답안이나 반복 실습을 만들지 않습니다.

## 구조화 결과가 업무로 이어지는 경계

이 주차는 회의 메모에서 작업을 추출해 검사하고, 보완이 필요한 결과와 사용할 수 있는 초안을 나눕니다. **추출 → 검사 → 분기 → 사람 확인 → 초안 저장**까지 같은 자료로 연결합니다. 저장된 초안은 실제 협업 서비스에 업무를 등록한 결과가 아닙니다.

`workflow_materials/extraction-schema.json`은 LLM 노드의 구조화 출력에 지정할 스키마입니다. `meeting_plugin/workflow_client.py`는 실행된 Workflow의 `payload`를 읽고 같은 `business.review`로 원문을 대조한 뒤 로컬 초안을 저장하는 참고 호출자입니다. Plugin 내부 SQLite 강의나 서버 구축이 목적이 아니라, 불확실한 모델 출력이 다음 처리에 들어가는 조건을 고르는 활동입니다.

### Day 1 — 메모가 모델에 전달되는 첫 흐름 만들기

오늘은 **입력 문장 → 실제 모델 추출 → 구조화된 객체 → 다음 단계가 받을 문자열**을 연결합니다. 위 개념 설명과 첫 접속을 마친 뒤, 먼저 세 노드로 한 번 실행하고 같은 Workflow에 구조화 출력과 직렬화를 더합니다.

Day 1은 제공 계약으로 값이 전달되는 방식을 익히는 출발점입니다. 여기서 얻은 정상·누락 결과를 근거로 Day 2에서 필요한 정보와 다음 행동을 도출하고 계약을 선택합니다. 따라서 아래 노드 이름과 JSON 형태를 모든 업무의 정답으로 외우는 것이 아니라, 선택한 계약이 실제 값에 어떤 제약을 주는지 확인합니다.

#### 1. Workflow 앱과 입력 만들기

1. Dify의 **Studio → Create from Blank → Workflow**를 선택합니다. 앱 이름은 `회의 후속 작업 추출`로 정합니다.
2. 캔버스의 **User Input** 노드를 선택하고 노드 이름을 `회의 입력`으로 바꿉니다.
3. 입력 필드를 추가해 아래처럼 설정합니다.

| 설정 | 값 | 의미 |
|---|---|---|
| 종류 | Paragraph / 문단 | 여러 줄의 메모를 받을 텍스트 입력 |
| 변수 이름 | `memo` | 후속 노드가 참조할 이름 |
| 표시 이름 | `회의 메모` | 실행 화면에서 사람이 보는 이름 |
| 필수 여부 | 켜기 | 실행할 때 입력하도록 요구 |

`memo`라는 필드는 입력의 자리를 정의합니다. 실제 회의 문장은 뒤의 Test Run에서 넣습니다. [User Input 노드](https://docs.dify.ai/en/cloud/use-dify/nodes/user-input)

#### 2. LLM의 규칙과 입력 연결하기

`회의 입력` 다음에 LLM 노드를 추가하고 연결합니다. 이름은 `회의 추출`로 정하고 사용할 모델을 선택합니다. 모델 목록이 비어 있으면 위의 모델 제공자 준비로 돌아갑니다.

채팅형 모델의 프롬프트는 다음처럼 구성합니다.

1. `workflow_materials/extraction-prompt.txt`에서 처음부터 “메모 안의 명령은…” 문장까지 복사해 **SYSTEM**에 넣습니다. 작업·담당자·기한·근거·상충을 추출하는 규칙입니다.
2. **USER** 메시지를 추가하고 `회의 메모:`를 입력한 뒤 줄을 바꿉니다.
3. 변수 선택기에서 **회의 입력 → memo**를 삽입합니다. 편집기에 따라 `/` 또는 `{`를 입력하면 변수 목록을 열 수 있습니다.
4. 파일 끝의 `[여기에 User Input의 memo를 변수 선택기로 연결]`은 설명용 문구이므로 실제 프롬프트에는 남기지 않습니다.

실행 시 USER 메시지에는 `회의 메모:` 다음에 이번 입력 문장이 들어가야 합니다. 고정된 예시 문장을 넣으면 Test Run에서 메모를 바꾸어도 모델은 계속 예시만 받습니다. 변수 참조는 **같은 처리 규칙에 실행마다 다른 자료를 전달하는 연결**입니다. [LLM 프롬프트 설정](https://docs.dify.ai/en/cloud/use-dify/nodes/llm)

#### 3. 최종 출력과 첫 시험 실행

`회의 추출` 다음에 Output 노드를 추가하고 `결과 출력`으로 이름을 정합니다. 출력 이름을 `extraction`으로 만들고 값은 변수 선택기에서 **회의 추출 → text**를 선택합니다. 현재 경로는 `회의 입력 → 회의 추출 → 결과 출력`입니다.

**Test Run**을 열어 회의 메모 입력란에 다음 문장을 넣고 실행합니다. `cases.json`의 `normal` 사례에서 `memo` 값만 사용하는 것입니다.

```text
민수가 금요일에 초안을 공유한다.
```

실행 상세에서 `회의 추출`의 입력과 출력을 엽니다. 입력에는 실제 메모가 있어야 하고, 출력에는 작업 `초안 공유`, 담당자 `민수`, 기한 `금요일`과 원문 근거가 있어야 합니다. 앞의 예상 JSON과 필드별 의미를 대조합니다. 필드 순서·공백보다 없는 정보를 추가했는지, 원문의 관계를 보존했는지가 중요합니다. JSON 앞에 설명문이나 코드 블록이 붙었다면 다음 함수가 바로 읽기 어려운 응답입니다.

**이 단계에서 확인할 결과:** 실제 메모가 모델까지 전달되고 모델의 `text`가 최종 `extraction`으로 반환됩니다. 노드가 성공했어도 메모 대신 안내 문구가 들어갔다면 변수 연결부터 고칩니다. Output은 선택한 값을 앱 밖으로 반환하는 접점입니다. [Output 노드](https://docs.dify.ai/en/cloud/use-dify/nodes/output)

#### 4. LLM 노드에 실제 스키마 지정하기

`회의 추출`의 **Structured Outputs / 구조화 출력**을 켜고 JSON Schema 편집 방식에서 `workflow_materials/extraction-schema.json` 전체 내용을 넣어 저장합니다. 앞서 만든 SYSTEM 지침과 USER의 `회의 입력.memo` 참조는 유지합니다.

스키마에서 `tasks`는 배열이고 각 항목은 `title`, `owners`, `due`, `evidence`, `conflicts`를 갖는 객체입니다. `owners`, `evidence`, `conflicts`는 문자열 배열이고 나머지는 문자열입니다. `required`는 필드 존재를 요구하고 `additionalProperties: false`는 선언하지 않은 추가 필드를 허용하지 않는다는 뜻입니다. 담당자·기한의 필드가 필수여도 모르는 값은 각각 `[]`, `""`로 남겨야 합니다.

이 설정으로 실제 `structured_output` 객체를 받는지 다음 실행에서 확인합니다. Dify와 모델에 따라 지원 방식이 다르므로 구조화 출력을 사용할 수 있는 모델을 선택합니다. 프롬프트로 JSON만 요청한 첫 실행과 스키마 기능을 설정해 얻은 실제 결과는 구분합니다. [구조화 출력](https://docs.dify.ai/en/cloud/use-dify/nodes/llm)

#### 5. Code 노드에서 객체를 문자열로 바꾸기

`회의 추출 → 결과 출력`의 직접 연결을 해제하고 그 사이에 **Code** 노드를 추가합니다. 이름은 `추출 직렬화`, 언어는 Python으로 정합니다. 다음 계약으로 설정합니다.

| 위치 | 이름 | 타입·연결 |
|---|---|---|
| Code 입력 | `extraction` | `회의 추출 → structured_output` 객체 |
| Code 출력 | `extraction_json` | String |
| 최종 Output | `extraction` | `추출 직렬화 → extraction_json` |

기본 예제 입력·출력이 있으면 위 이름으로 정리하고 다음 코드로 교체합니다.

```python
import json

def main(extraction: dict) -> dict:
    return {"extraction_json": json.dumps(extraction, ensure_ascii=False)}
```

입력 변수 `extraction`은 같은 이름의 함수 인자로 전달됩니다. 반환한 `extraction_json`은 출력 선언과 이름이 같아야 후속 노드가 참조할 수 있습니다. `json.dumps`는 객체를 JSON 문자열로 바꾸며 `ensure_ascii=False`는 한글을 읽기 쉬운 형태로 유지합니다. 업무 내용에 대한 판단을 추가하는 코드는 아닙니다. [Code 노드](https://docs.dify.ai/en/cloud/use-dify/nodes/code)

현재 경로는 `회의 입력 → 회의 추출 → 추출 직렬화 → 결과 출력`입니다. 코드와 전체 주차의 변수 대응을 다시 볼 때는 `workflow_materials/workflow-setup.md`를 참고합니다. 이 파일은 설정 해설이며 Dify에 가져오기할 DSL 파일은 아닙니다.

#### 6. 정상·누락 입력의 실제 값 따라가기

같은 정상 메모를 실행하고 **LLM의 `structured_output` → Code의 입력 객체 → Code의 출력 문자열 → 최종 `extraction`**을 순서대로 확인합니다. 표현 형태만 바뀌고 담당자·기한·근거는 유지되어야 합니다. 문자열이 JSON 응답 안에 표시되면 내부 따옴표가 `\"`로 보일 수 있습니다. 화면의 이스케이프 표시와 실제로 한 번 더 직렬화된 문자열은 구분하고, Code 입력이 객체였는지부터 확인합니다.

이어서 `cases.json`의 `missing` 메모를 넣습니다.

```text
초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.
```

예상 핵심 값은 `owners=[]`, `due=""`입니다. `evidence`는 실제 원문의 문장을 인용해야 합니다. 두 사례는 **알려진 정보의 보존**과 **모르는 정보의 표현**을 각각 확인합니다. 담당자가 “미정”이라는 사람 이름으로 들어가거나 기한을 만들어 냈다면 스키마의 타입이 맞아도 의미는 틀렸습니다. 직렬화 이전에 이미 잘못됐다면 추출 지침과 실제 모델 입력을 고쳐야 합니다.

| 막힌 곳 | 먼저 확인할 내용 |
|---|---|
| 모델 목록·호출 실패 | 제공자 연결, 인증·사용 가능량과 실행 오류 메시지 |
| 메모와 무관한 응답 | USER의 `회의 입력.memo` 참조와 실제 전달된 문장 |
| `structured_output`이 없음 | 구조화 출력 설정·스키마 저장·모델 지원 상태 |
| Code 입력·출력 오류 | 입력 이름 `extraction`, 객체 참조, 반환·출력 선언 `extraction_json` |
| 최종 결과가 비어 있음 | Output의 변수 참조와 네 노드의 실행 연결 |

#### 7. 실행 결과와 해석 남기기

`dify-review.md`에 앱 이름·사용 모델, 실제 스키마 설정과 노드 값의 위치, 정상·누락 입력의 실제 결과를 연결합니다. 원문 보존 여부와 객체를 문자열로 바꾼 이유를 결과에 근거해 설명하고, 예상과 달랐다면 처음 어긋난 단계와 수정 결과를 이어 씁니다. 예시 JSON을 실제 모델 응답으로 기록하지 않습니다.

아래 요청은 내용을 읽고 대화형 도구에 직접 복사해 사용할 수 있습니다.

```text
9주차 README의 개념 설명과 Day 1 순서로 Dify Workflow를 구성하겠습니다.
현재 단계에서 필요한 화면 설정과 이유를 설명하고, 제공 추출 지침·스키마로 진행을 도와 주세요.
회의 입력.memo가 LLM 프롬프트로, structured_output이 Code 입력으로,
extraction_json이 최종 Output으로 연결되는 값을 실제 설정에 근거해 설명하세요.
정상·누락 메모를 직접 실행한 결과에서 작업·담당자·기한·근거를 원문과 대조하겠습니다.
없는 값을 채우거나 예시 출력을 실제 실행으로 기록하지 마세요.
실제 결과와 해석은 dify-review.md 한 곳에 이어 주세요.
```

**Day 1 완료 확인:** 실제 메모가 모델에 전달되고, 스키마를 설정한 객체가 JSON 문자열로 최종 출력까지 이어집니다. 정상·누락 결과를 근거로 필수 필드에도 빈값이 필요한 이유와 직렬화가 내용 판단을 바꾸지 않는 이유를 설명합니다. 모델이나 환경이 지원하지 않아 실행하지 못한 부분은 그 결과와 이유를 남기며 실제 연결 완료로 표시하지 않습니다.

### Day 2 — 요구에서 노드·입출력·검토 기준 도출하기

> 회의 메모를 받아 후속 작업을 정리한다. 담당자·기한이 확정된 작업은 사용할 수 있는 초안으로 보여 준다. 미정이거나 상충한 사실은 원문과 남은 질문을 함께 보여 주고 사람이 보완할 수 있게 한다. 일부만 보완됐으면 남은 질문을 유지한다.

이 요구에는 특정 노드 이름이나 JSON 필드가 없습니다. 처음부터 “LLM 노드 하나, Tool 하나, IF 하나”를 정하기보다 어떤 정보가 다음 판단을 가능하게 하는지 먼저 정합니다. 아래는 제공 자료를 사용해 하나의 설계가 완성되는 과정입니다. 이어지는 실습에서는 그 근거를 바탕으로 선택한 구성을 구현합니다.

#### 1. 사용자가 얻을 결과와 다음 행동에서 구분을 만듭니다

정상 메모 “민수가 금요일에 초안을 공유한다”는 작업·담당자·기한을 함께 보여 주면 바로 읽을 수 있는 초안입니다. 반면 “초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다”는 초안만 표시하면 사람이 무엇을 채워야 하는지 모릅니다. 따라서 결과에는 **확정된 값과 아직 필요한 정보**가 함께 있어야 합니다.

| 원문의 조건 | 결과에 남길 사실 | 사용자의 다음 행동 |
|---|---|---|
| 담당자·기한이 확인됨 | 작업·담당자·기한 | 초안 확인·사용 |
| 담당자가 없고 기한도 미정 | 작업과 두 누락 이유 | 필요한 사실 보완 |
| 같은 일의 최종 담당자가 불명확 | 두 이름과 상충 근거 | 최종 결정 확인 |
| 담당자만 보완됨 | 새 담당자, 아직 없는 기한 | 기한만 추가 확인 |

결과 종류를 `ready/review`로 구분할 수도 있고 `confirmed_tasks/pending_tasks`처럼 항목 묶음을 반환할 수도 있습니다. 필드 이름이 아니라 다음 행동을 결정할 정보가 보존되는지가 기준입니다. 추출 자체가 읽을 수 없는 형식이면 업무의 “미정”과 다른 결과가 필요합니다. 이름을 못 정한 회의와 JSON을 파싱하지 못한 실행은 고칠 사람이 확인할 위치부터 다르기 때문입니다.

#### 2. 모델이 판단할 것과 코드가 판단할 것을 나눕니다

원문에서 “누가 어떤 일을 맡았는가”는 의미 해석입니다. 단어의 위치만으로 항상 알 수 없으므로 이 예제는 LLM이 추출하도록 합니다. 담당자가 한 명인지, 기한이 비어 있는지, 미해결 상충이 전달됐는지는 정해진 자료 형식에 대한 판단이므로 함수로 표현합니다.

대안은 모델에게 정리와 확정 판단을 한 번에 맡기는 것입니다. 설정은 짧지만 왜 검토가 필요한지 코드가 일관되게 읽기 어렵고, 누락이 생긴 위치를 분리하기도 어렵습니다. 추출과 검사를 나누면 모델이 반환한 값과 규칙의 판단을 각각 볼 수 있습니다. 대신 두 단계 사이에 데이터 계약을 관리해야 합니다. 이 비용이 불필요한 단순 요약이면 한 번의 LLM 호출을 선택할 수 있지만, 이번 요구는 원문 근거·미정·상충에 따른 다음 행동이 있어 분리할 이유가 있습니다.

제공 검사는 담당자를 한 명 확정하는 사례 규칙을 사용합니다. 공동 담당을 허용하는 업무라면 이름 둘을 자동으로 충돌이라고 할 수 없고 공동 담당 여부를 나타낼 정보가 더 필요합니다. **도메인의 판단을 먼저 정하고 그 판단에 필요한 필드를 만드는 순서**가 중요합니다. 타입이나 배열 개수가 업무 의미를 대신 정하지 않습니다.

`business.py`는 다음 조건으로 검토 이유를 남깁니다. `evidence`가 원문에 포함되는지와 담당자·기한의 표현이 근거에 있는지도 검사합니다.

```python
if len(owners) != 1:
    reasons.append("담당자 미정" if not owners else "담당자 상충 확인")
if not due:
    reasons.append("기한 미정")
if conflicts:
    reasons.append("미해결 상충: " + "; ".join(conflicts))
```

근거에 이름이 나타나는 사실만으로 그 사람이 해당 작업의 담당자라는 의미까지 증명되지는 않습니다. 이 한계는 Day 4에서 실제 추출과 원문을 대조해 확인합니다.

#### 3. 왜 원문과 근거를 다음 단계까지 전달하는지 정합니다

추출 결과만 Tool에 보내면 담당자·기한의 빈값은 검사할 수 있지만 근거 문장이 원문에 있었는지 볼 수 없습니다. 이번 요구는 사람이 상충을 확인하고 보완해야 하므로 원문과 추출된 근거를 함께 보존합니다. 그래서 참고 Plugin은 원문 `memo`와 추출 JSON `extraction_json` 두 입력을 받습니다.

`owners`는 상충 시 이름 둘을 보존할 배열이고 `conflicts`는 해석 단계에서 발견한 미해결 문제입니다. `evidence`는 사람이 판단을 다시 살펴볼 자료입니다. 이것을 모두 하나의 요약 문자열에 섞으면 기한이 비었는지나 이름이 둘인지 다음 단계가 다시 추론해야 합니다. 별도 필드로 두면 후속 처리를 명확히 할 수 있으나, 필드가 많다는 사실 자체가 더 좋은 설계는 아닙니다.

형식 선택에도 경계가 있습니다. 제공 Tool의 입력 선언은 문자열이고 내부에서 JSON을 읽습니다. 이는 현재 Tool 매개변수로 추출 결과를 전달하기 위해 선택한 어댑터입니다. 업무 객체를 문자열에 담는 것과 업무가 본질적으로 문자열 하나인 것은 다릅니다. 애플리케이션 안에서는 객체를 다루고 SDK 경계에서 직렬화할 수 있습니다. `memo`, `status` 같은 필드명은 SDK가 강제하는 예약어가 아닙니다. 선택한 이름·타입이 선언, 실제 반환, 변수 참조에서 일치하면 됩니다.

#### 4. 검사 단위와 전체 결과를 별도로 선택합니다

제공 `mixed` 자료에는 확정된 “초안 공유”와 담당자·기한이 없는 “검토 회의 준비”가 함께 있습니다. 항목별 판단은 각각 `ready`, `review`입니다. 여기서 메모 전체의 결과는 아직 정해지지 않았습니다.

| 후보 구성 | mixed 입력의 결과 | 선택 이유와 부담 |
|---|---|---|
| 전체 메모 검토 | 두 항목을 보존한 채 전체를 검토 경로로 보냄 | 한 메모를 한 번에 확인하기 단순함. 확정 항목도 검토 화면에 함께 나타남 |
| 항목별 결과 분리 | 확정 초안과 보완할 항목을 함께 반환 | 이미 쓸 수 있는 일을 빨리 구분함. 항목의 대응과 출력 합성을 관리해야 함 |

참고 `review` 함수는 첫 번째 선택입니다. 다음 실제 코드는 **모든 항목이 준비되어 있고 빈 목록이 아닐 때만** 전체를 `ready`로 만듭니다.

```python
status = "ready" if checked and all(task["status"] == "ready" for task in checked) else "review"
```

두 번째 선택을 하려면 같은 업무 검사를 다시 구현할 필요가 없습니다. `business.check_tasks(memo, tasks)`가 반환한 항목별 결과를 나눌 수 있습니다.

```python
checked = check_tasks(memo, tasks)
confirmed = [task for task in checked if task["status"] == "ready"]
pending = [task for task in checked if task["status"] == "review"]
```

이 코드는 새로운 정답 형태를 지정하는 것이 아니라 검사 결과를 어떤 단위로 사용하느냐에 따라 전체 구조가 달라진다는 설명입니다. 항목을 분리할 경우 작업 제목만으로 다시 합치지 않도록 원문의 항목과 대응되는 위치나 식별자를 유지할지도 판단합니다. 제공 작은 사례는 배열 순서를 보존하며, 장기 편집·합치기 요구가 없으므로 별도 식별 시스템을 만들지 않습니다.

#### 구현할 구성 선택하기

해설의 참고 구성은 메모 전체를 검토하고 결과에 따라 다른 안내를 제공합니다. 실습에서는 같은 제공 요구를 바탕으로 전체 메모 또는 항목별 결과, Tool에 전달할 정보, 다음 단계에 공개할 출력, 보완의 입력 방식을 고릅니다. LLM은 자연어를 필드로, Plugin은 필드를 검사 결과로 바꾸고, Workflow는 그 결과에 필요한 후속 행동을 연결합니다. 이 책임을 실제 노드·변수·결과에 반영합니다.

```text
제공 회의 요구와 교재 설계 해설, business.py의 항목별 검사 부품을 읽어 주세요.
먼저 필요한 사실·판단·사용자 다음 행동을 구분하고, 전체 메모 처리와 항목별 처리의 후보를 비교하세요.
정상·누락·상충 또는 혼합 메모에서 각 후보의 중간값과 결과가 어떻게 다른지 설명하세요.
원문과 추출값을 어디까지 전달할지, Tool의 출력과 Workflow의 후속 행동을 추천해 주세요.
SDK가 요구하는 선언·메시지 형식과 우리가 정할 업무 필드·처리 단위를 구분하세요.
예제의 이름·노드 수를 고정하지 말고 선택할 구성의 이유와 부담을 설명하세요.
내 짧은 수용·수정 의견을 기다린 뒤 구성을 진행하세요.
```

**완료 확인:** 기능을 추가하기 전에 필요한 판단·중간값·분기가 요구에서 나오는 이유를 이해하고 구성안을 선택합니다. 선택한 책임·입출력·결과 단위를 코드나 설정에 반영할 수 있게 정합니다.

### Day 3 — 업무 함수를 실제 Tool Plugin으로 노출하기

#### Code 노드와 Tool Plugin 중 기능의 위치를 정합니다

앱 안에서만 쓰는 짧은 가공이면 Code 노드로 가까이 둘 수 있습니다. 같은 검사 함수를 코드·의존성·버전과 함께 관리하고 Dify에 명명된 기능으로 노출하려면 Tool Plugin을 선택할 수 있습니다. Plugin은 이름만 등록하는 일이 아니라 입력을 받고 함수를 실행해 SDK 메시지로 결과를 돌려주는 별도 실행 경계이므로 환경 연결도 필요합니다.

이번 주는 그 경계를 직접 제작합니다. `business.py`를 제공하는 이유는 회의 규칙을 다시 코딩하는 데 시간을 쓰기보다, **그 함수를 어떤 입력·출력·오류 계약으로 공개할지** 선택하기 위해서입니다. 모델 추출을 Plugin 안에서도 다시 수행하면 호출 비용과 추출 위치가 늘어납니다. 현재 구조는 Workflow의 LLM이 한 번 추출하고 Plugin은 제공 함수를 실행합니다.

SDK는 manifest의 provider 경로, provider의 tool 경로, 실행 클래스와 메시지 형식을 요구합니다. 반면 메모 전체를 검토할지, 출력에 `status`를 둘지, 결과를 항목별로 나눌지는 학습자가 정하는 업무 설계입니다. 두 종류의 결정을 섞으면 SDK 예제를 복사했을 때 업무 구조도 유일한 답처럼 보이게 됩니다.

#### SDK 선언과 실행 코드 연결하기

**Manifest**는 Plugin의 이름·버전·등록할 기능·실행 자원 등을 적는 진입 선언입니다. **Provider 선언**은 도구 묶음과 그 안의 Tool을 가리키고, **Tool 선언**은 각 기능의 입력·출력과 실행 코드 위치를 정합니다. SDK는 이 선언을 읽어 호출할 코드를 찾습니다. 선언만 추가하면 코드가 구현되는 것은 아니고, Python 함수만 만들면 도구가 등록되는 것도 아닙니다.

제공 코드의 `_invoke`는 SDK가 Tool 실행을 요청할 때 들어오는 메서드입니다. `tool_parameters`에는 Workflow에서 연결한 입력값이 들어옵니다. 업무 함수가 반환한 객체를 `create_json_message`로 감싸면 SDK의 JSON 결과 메시지가 되고, `create_variable_message`는 후속 노드가 이름으로 참조할 출력을 만듭니다. **메시지**는 여기서 사람 간 채팅이 아니라 Plugin과 Dify 사이에 전달하는 결과 단위입니다.

```python
result = review(tool_parameters.get("memo"), tool_parameters.get("extraction_json"))
yield self.create_json_message(result)
yield self.create_variable_message("status", result["status"])
yield self.create_variable_message("summary", result["summary"])
```

첫 메시지는 상세 결과를 JSON으로 반환하고, 뒤의 두 메시지는 Workflow에서 직접 참조할 변수를 만듭니다. `output_schema`에도 `status`, `summary`를 같은 이름으로 선언합니다. `yield`는 SDK에 결과 메시지를 차례로 넘기는 Python 표기입니다. 출력 이름·값·타입을 일치시키는 것이 연결의 원리입니다. [공식 Tool Plugin 제작](https://docs.dify.ai/en/develop-plugin/dev-guides-and-walkthroughs/tool-plugin), [Tool 반환값과 출력 스키마](https://docs.dify.ai/en/develop-plugin/features-and-specs/plugin-types/tool)

`manifest.yaml`의 `plugins.tools`는 공개할 provider 경로를 가리킵니다. `resource.permission`은 Plugin이 Dify의 모델·다른 도구·저장소 등을 역으로 사용하는 권한입니다. **Tool을 공개하는 선언과 다른 Tool을 호출하는 권한은 다릅니다.** 제공 업무 함수는 로컬 계산만 하므로 추가 역호출 권한은 비어 있습니다. 외부 API를 부르는 기능이라면 그 API의 인증·실패 처리를 별도로 설계해야 합니다. [Plugin Manifest](https://docs.dify.ai/en/develop-plugin/features-and-specs/plugin-types/plugin-info-by-manifest)

#### Plugin 실행 환경 준비하기

**가상환경**은 이 프로젝트에서 사용할 Python과 설치 라이브러리를 구분해 관리하는 환경입니다. `requirements.txt`는 필요한 라이브러리와 버전을 적고, `pip`는 이를 설치하는 도구입니다. **개발 연결**은 PC에서 실행 중인 Plugin을 Dify 작업공간에 연결해 실제 Tool 호출을 시험하는 방식입니다. 브라우저에서 만든 Workflow의 호출이 연결된 Plugin 실행 프로세스까지 도달해야 하므로, 로컬 함수 검사와 실제 개발 연결 검사는 확인 범위가 다릅니다.

참고 코드는 `meeting_plugin/`에서 읽고, 제작·실행은 선택한 Plugin 폴더인 `meeting_tool/`에서 진행합니다. 아래 구현 단계에서 준비할 `requirements.txt`를 사용해 IDE에서 Python 3.12 가상환경을 선택하고 의존성을 설치합니다. 명령이 필요하면 제작 Plugin 폴더에서 실행합니다.

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

macOS·Linux·WSL:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

이후 명령의 `python`은 선택한 가상환경을 뜻합니다. 실제 터미널에서는 위 운영체제별 실행 파일을 사용합니다. Plugin SDK는 `dify-plugin==0.10.2`로 고정합니다.

#### 선택한 업무 계약으로 구현하고 연결하기

`meeting_plugin/`은 완성된 참고 예제입니다. 같은 주차에서 선택한 Plugin 폴더에 **업무 함수의 공개 계약과 그 결과를 사용하는 Workflow 구조**를 AI와 만듭니다. 기본 작업 이름은 `meeting_tool/`로 사용할 수 있습니다. `business.py`와 환경·실행 준비 파일은 제공 예제에서 가져오고, 항목별 검사 결과를 어떻게 묶고 어떤 입력·결과를 SDK에 넘길지는 Day 2의 결정으로 구현합니다. 업무 함수를 다시 만들거나 모든 필드·노드를 제공 예제와 같게 할 필요는 없습니다.

등록 경로는 `manifest.yaml → provider/meeting.yaml → tools/review_tasks.yaml → tools/review_tasks.py`입니다. 마지막 Python 파일의 `review(...)`가 업무 함수 접점입니다. 파일이 있다는 것만으로 Dify에 보이는 것은 아니므로 실제 SDK가 이 경로와 클래스를 읽을 수 있어야 합니다. 복잡한 검사 로직을 다시 구현하지 않습니다.

```text
meeting_plugin은 참고 예제이고, 같은 주차의 meeting_tool에 작은 Plugin 연결부를 만들겠습니다.
예제의 business.py와 requirements·실행 준비·제외 설정·아이콘을 가져와 사용하세요.
Day 2에서 선택한 계약으로 입력·결과 포장, manifest, provider, Tool YAML, _invoke와 Workflow를 구성해 주세요.
check_tasks의 항목별 판단을 재사용하고, 선택한 전체 결과·오류·후속 행동이 실제 코드와 노드에 드러나게 하세요.
provider·tool 등록과 SDK 메시지 규칙을 지키면서 업무 필드명·반환 구조는 선택한 계약으로 맞추세요.
각 경계에 어떤 값이 들어가고 나오는지 정상 메모를 따라 설명하세요.
새로 바꿀 책임이나 계약은 이유·예상 결과를 설명하고 내 의견을 반영한 뒤 구현하세요.
같은 계약을 유지하는 설정 오류는 바로 고치고, 기존 SDK 등록·메시지 검사를 필요한 범위에서 실행하세요.
이어서 Dify 개발 연결과 Workflow의 Tool 노드 설정을 도와 주세요.
```

제공 예제의 필드를 다르게 만드는 것 자체가 목표는 아닙니다. 같은 선택을 하더라도 왜 그 정보를 보존하고 어떤 책임을 코드·Workflow에 두었는지 판단합니다. 예를 들어 항목별 결과를 골랐다면 전체 메모를 `ready/review` 하나로 압축하지 않고 확정 항목과 검토 이유가 출력에 살아 있어야 합니다. AI가 작성한 파일의 존재보다 선택한 의미가 실제 입력에서 이어지는지를 봅니다.

연결 전에는 제공 `test_plugin.py`를 새 Plugin에 맞춰 재사용할 수 있습니다. `python -B -m unittest -v`는 실제 SDK가 manifest·provider·tool을 읽고 Tool 메시지를 만드는지 확인합니다. 등록 이름·인자·결과 포장에 관한 기대값은 선택한 계약에 맞춥니다. 담당자·기한의 누락과 상충을 확정된 사실로 사용하지 않는 업무 원리는 유지하되, 전체 상태를 고르는 검사로 항목별 결과 구조를 강제하지 않습니다. 기존 작은 사례로 변경한 계약을 확인하고, 다루지 못한 동작이 있을 때 필요한 검사를 보완합니다.

Dify Plugin 관리의 개발/디버그 화면에서 주소와 키를 얻습니다. IDE에서 만든 `meeting_tool/`을 실행 위치로 지정하고, 제공 `.env.example`을 `.env`로 복사해 `REMOTE_INSTALL_URL`, `REMOTE_INSTALL_KEY`에 현재 작업공간의 값을 넣습니다. `INSTALL_METHOD=remote`로 두고 앞서 준비한 가상환경의 모듈 실행 설정에서 `main`을 실행합니다. 터미널에서 연결을 유지할 때는 같은 환경·작업 폴더의 `python -B -m main`을 사용할 수 있습니다. 이 폴더에도 `.gitignore`·`.difyignore`가 있어 `.env`를 제외하는지 확인합니다. 디버그 주소와 키를 노트·채팅에 남기지 않습니다. [공식 개발 환경 연결](https://docs.dify.ai/en/develop-plugin/getting-started/cli)

Plugin이 표시되면 Workflow의 Tool 노드에서 직접 등록한 제공자와 Tool을 고릅니다. 제공 예제와 같은 이름과 계약을 사용했다면 Meeting Review의 Review meeting tasks에서 `memo`에 User Input의 메모, `extraction_json`에 `추출 직렬화.extraction_json`을 연결합니다. 이 문자열은 Day 1에서 LLM의 실제 `structured_output` 객체를 직렬화한 결과입니다. 다른 계약이면 직접 선언한 각 인자의 이름·타입에 맞는 선행 노드 변수를 선택하고 객체·문자열 사이에 필요한 변환을 연결합니다. `workflow-setup.md`는 참고 계약의 대응표이며 실제 선택한 매핑으로 정상 메모를 한 번 호출합니다. 이미 작동하는 본인 연결부가 있다면 그것을 이어 사용하며 같은 Plugin을 또 만들지 않습니다.

**완료 확인:** Dify가 실제 Plugin을 호출하고 선택한 계약의 정상 결과와 다음 단계에 필요한 값을 받습니다. 참고 계약이면 `status=ready`와 `summary`·상세 JSON입니다. 로컬 SDK 검사만 통과했다면 Plugin 코드는 보존하되 `Dify Tool 연결: NOT_VERIFIED`로 남기고 실제 연결을 확인한 것으로 표시하지 않습니다.

#### 후속 처리가 받을 결과 계약

참고 Plugin의 `payload`는 검사 결과 전체를 JSON 문자열로 반환합니다. `status`·`summary`는 화면 분기와 표시, `payload`는 호출 앱의 후속 처리를 위한 값입니다. 사람이 읽을 요약만 반환하면 호출 앱이 담당자·기한을 다시 추론해야 합니다. SDK 변수 선언·반환·Workflow Output의 참조가 같은 이름과 타입인지 확인합니다. `test_plugin.py`의 SDK 호출 검사는 이 계약을 확인하고 실제 모델 추출 품질은 확인하지 않습니다.

### Day 4 — 검사 결과로 분기하고 상충의 보존 여부 판단하기

#### 서로 다른 후속 행동이 필요한 곳에 분기를 둡니다

값에 `ready`라는 글자를 붙여 한 번 반환하는 요구라면 Output 하나로도 충분합니다. 분기 노드를 배운다는 이유로 같은 내용을 반환하는 경로를 여러 개 만드는 것은 효과가 적습니다. 참고 구성은 **정상일 때 작업 초안을 보여 주고, 검토일 때 원문과 남은 질문을 함께 보여 주기**로 선택했습니다. 따라서 후속 단계가 실제로 달라집니다.

`workflow-setup.md`의 정상 경로는 `ready-template.jinja`가 Tool의 `summary`를 받아 초안으로 표시합니다. 검토 경로는 `review-template.jinja`가 `memo`와 `summary`를 받아 원문과 질문을 함께 표시합니다. 형식 오류 경로의 Template은 Tool의 `summary`를 그대로 표시합니다. Template은 이미 있는 값을 배치하며 새 사실을 만들지 않습니다. 이 작업을 위해 모델을 한 번 더 호출할 필요는 없습니다. 세 경로의 안내문은 변수 집계기를 거쳐 최종 Output 하나로 반환합니다. [Dify Template 노드](https://docs.dify.ai/en/cloud/use-dify/nodes/template)

순서 연결과 변수 연결도 다른 선택입니다. Tool 다음에 Template을 연결하는 선은 실행 순서를 정하고, `summary=업무 검사.summary`는 전달할 값을 정합니다. `output_schema`의 이름과 `_invoke`가 반환하는 변수 이름이 같아야 선택한 값이 도착합니다. 최종 화면이 틀렸을 때는 원문→추출값→Tool 입력→반환값→Template 입력 순으로 **처음 어긋난 값**을 찾아야 합니다.

형식 오류를 빈 작업 목록으로 바꾸면 “회의에 일이 없었다”와 “작업을 읽지 못했다”가 섞입니다. 제공 Plugin은 `invalid`로 반환해 형식 확인 경로로 보냅니다. 도구가 시작되지 못했거나 프로세스가 실패한 것은 이 결과조차 만들지 못한 실행 실패이며 Dify 실행 화면에서 따로 확인합니다.

#### 실제 추출에서 분기까지 확인하기

Day 2에서 선택한 후속 행동을 실제로 연결합니다. `업무 검사` 다음에 IF/ELSE 노드를 추가하고 이름을 `결과 분기`로 정합니다. IF의 비교 변수는 `업무 검사.status`, 조건은 같음(Is/Equals), 비교값은 직접 입력한 문자열 `ready`입니다. ELIF에는 같은 변수와 조건에 비교값 `review`를 넣습니다. 비교값에는 따옴표나 중괄호를 넣지 않습니다. ELSE는 나머지 결과를 받습니다.

각 경로에 다음 Template을 연결합니다. 노드 입력의 연결값은 변수 선택기에서 지정하고, Template 본문의 중괄호는 그 입력 변수의 값을 넣는 자리입니다.

| 분기 | Template 이름 | 입력 변수 | 본문 |
|---|---|---|---|
| IF `ready` | `작업 초안` | `summary=업무 검사.summary` | `workflow_materials/ready-template.jinja` 전체 내용 |
| ELIF `review` | `검토 안내` | `memo=회의 입력.memo`, `summary=업무 검사.summary` | `workflow_materials/review-template.jinja` 전체 내용 |
| ELSE | `형식 오류 안내` | `summary=업무 검사.summary` | `{{ summary }}` |

**Variable Aggregator(변수 집계기)**는 서로 배타적인 분기에서 실행된 경로의 값을 공통 출력으로 연결하는 노드입니다. 예를 들어 정상 경로만 실행되면 작업 초안의 문자열이, 검토 경로만 실행되면 검토 안내의 문자열이 전달됩니다. 여러 경로를 동시에 실행해 결과를 이어 붙이는 처리와는 다릅니다. [변수 집계기](https://docs.dify.ai/en/cloud/use-dify/nodes/variable-aggregator)

1. 세 Template 뒤에 Variable Aggregator 노드를 하나 추가하고 이름을 `안내문 통합`으로 정합니다. 각 Template의 연결선을 모두 이 노드에 연결합니다.
2. 집계할 변수에 `작업 초안.output`, `검토 안내.output`, `형식 오류 안내.output`을 선택합니다. 세 값은 모두 문자열이며 집계 타입은 **String (`string`)**으로 설정합니다. 분기 전에 항상 값이 생기는 `업무 검사.summary` 대신 각 분기의 Template 출력을 집계합니다.
3. 안내문 하나를 모으므로 기본 단일 집계를 사용하면 됩니다. 그룹 기능을 사용하는 설정에서도 같은 집계 그룹에 세 문자열을 넣고 타입을 String으로 지정합니다. 실행 상세에 표시되는 실제 출력 이름과 타입을 최종 Output의 참조에 맞춥니다.
4. `안내문 통합` 다음에는 **`최종 출력` Output 노드 하나**를 둡니다. 기존 Output을 재사용할 수 있으며, 경로별 Template은 이 공통 출력 앞에서 합류합니다.

```text
회의 입력 → 회의 추출 → 추출 직렬화 → 업무 검사 → 결과 분기
  IF ready  → 작업 초안 ──────┐
  ELIF review → 검토 안내 ────┼→ 안내문 통합 → 최종 출력
  ELSE → 형식 오류 안내 ──────┘
```

최종 Output에는 아래 필드를 한 번씩 선언합니다. Output 변수 이름은 API 응답의 키가 되며 Workflow 전체에서 고유하게 정합니다. [Output 노드](https://docs.dify.ai/en/cloud/use-dify/nodes/output)

| 출력 이름 | 연결할 값 | 역할 |
|---|---|---|
| `status` | `업무 검사.status` | 업무 결과 종류 |
| `result` | `안내문 통합`의 실제 집계 출력 | 실행된 경로의 안내문 |
| `extraction` | `추출 직렬화.extraction_json` | 검사 전 추출값과 결과 비교 |
| `payload` | `업무 검사.payload` | 호출 앱이 읽을 상세 검사 결과의 JSON 문자열 |

기본 집계의 문자열 출력을 선택하면 `result`가 안내 문자열입니다. 그룹 전체를 선택해 `result={"output":"안내문"}`처럼 객체를 반환하는 구성에서는 안내문 위치가 `result.output`입니다. 선택한 변수의 이름만이 아니라 실제 반환 타입과 소비자가 읽을 위치도 확인합니다. 초안 저장 호출자는 `payload`를 사용하므로 표시용 결과의 그룹 구조에 의존하지 않습니다.

항목별 구조를 선택했다면 검토 항목 유무에 따라 필요한 안내를 달리 연결할 수 있습니다. 분기는 요구에 필요한 다음 행동을 정하고, 집계기와 공통 Output은 선택된 결과를 일관된 계약으로 반환합니다.

Day 3의 정상 결과를 재사용하고 `missing`, `conflict`의 메모를 실행합니다. 입력의 모든 값을 바꾸면서 모델도 함께 교체하지 않습니다. 같은 구성에서 입력 때문에 경로가 어떻게 달라지는지 확인합니다.

상충 사례의 원문은 다음과 같습니다.

```text
민수가 금요일에 초안을 공유한다. 지수도 초안 공유 담당자라고 기록됐다.
최종 담당자는 확인하지 않았다.
```

예상 추출은 두 이름과 미해결 상충을 보존하며 Tool은 `review`를 반환합니다. 하지만 모델이 첫 문장만 근거로 골라 `owners=["민수"]`, `conflicts=[]`로 반환했다면 제공 검사를 통과할 수 있습니다. 이름과 기한이 실제 인용문에 있기 때문입니다. 이때 IF/ELSE는 주어진 검사값으로 올바르게 분기했어도 최종 초안은 업무 요구를 만족하지 못합니다.

이 반례처럼 실제 추출에서 상충이 누락됐다면 고칠 위치는 추출 단계입니다. 원문 전체와 실제 추출을 대조해 누락된 문장을 확인하고 지침이나 추출 형태를 보완합니다. 추출이 상충을 보존했다면 해당 결과를 그대로 근거로 사용하고, 반례는 제공 검사 코드의 한계를 설명하는 가정으로 구분합니다. 같은 필드 검사를 반복해도 추출에서 사라진 의미를 복원할 수는 없습니다.

```text
선택한 결과 계약을 읽어 서로 다른 후속 행동을 수행하는 실제 조건 분기를 연결해 주세요.
작업 초안 표시와 원문·남은 질문 표시처럼 요구에 필요한 행동이 값에 따라 달라지게 하세요.
분기별 Template 출력을 String 타입의 변수 집계기로 모아 최종 Output 하나에 연결해 주세요.
status·result·extraction·payload를 한 번씩 반환하고 실제 집계 출력의 이름·타입을 참조에 맞추세요.
제공 정상 결과를 재사용하고 누락·상충 메모의 원문, LLM 추출, Tool 결과, 실행 경로를 함께 읽겠습니다.
원문의 지수가 추출에서 빠졌다면 분기 성공을 업무 성공으로 판단하지 마세요.
처음 사실이 사라진 위치와 수정 이유를 설명하고, 필요한 부분을 바꾼 뒤 같은 메모로 확인하세요.
실제 결과와 추출·검사의 한계를 dify-review.md 한 곳에 이어 주세요.
```

**완료 확인:** 필드 검사와 원문 해석의 차이를 실제 노드 입력·출력으로 설명하고, 정상과 검토가 요구에 맞게 다른 경로를 사용함을 확인합니다. 오류가 없다면 일부러 여러 실패를 새로 만들 필요는 없습니다.

### Day 5 — 부분 보완과 사람 확인을 거쳐 초안 저장하기

오늘은 앞에서 정의한 재처리·사람 확인·멱등성을 실제 결과에 연결합니다. **상태 보관**은 다음 처리에 필요한 입력·판단·실행 위치 등을 남기는 일이고, **재개**는 그 상태에서 실행을 잇는 일입니다. 단순히 원문에 보완 문장을 덧붙여 다시 보내면 새로운 실행이므로 이전 실행의 중간 지점이 자동으로 복원되지는 않습니다.

이번에는 Workflow를 한 번 끝낸 뒤 원문과 사람의 보완을 함께 새 실행에 보내는 구성을 확인합니다. 중단된 실행 자체를 이어야 한다면 사람 응답 대기, 요청 식별, 상태 보관과 재개를 추가로 설계해야 합니다.

정보가 부족했던 메모에 사람이 다음을 보완했다고 가정한 제공 `partial` 입력을 사용합니다.

```text
초안을 공유하기로 했다. 담당자와 기한은 정하지 않았다.
사람의 보완: 담당자는 민수로 확정했다. 기한은 아직 정하지 않았다.
```

담당자 조건은 해결됐지만 기한은 남아 있습니다. 원문과 보완을 함께 새 실행에 전달하면 이미 확인한 작업을 유지하면서 남은 이유로 검토 경로를 계속 사용해야 합니다. “보완이 있었다”는 사실만 보고 모든 검토를 완료시키지 않습니다. 이 재처리 방식은 기존 노드를 같은 입력 계약으로 다시 사용합니다.

```text
현재 회의 Workflow에 제공 partial 메모를 넣어 보완 전후를 비교해 주세요.
담당자만 바뀌고 기한은 미정인 상태에서 예상 추출·검사·경로를 먼저 설명하세요.
이미 선택한 계약과 지침을 사용해 실행하고 남은 기한 질문이 유지되는지 읽겠습니다.
결과가 다르면 먼저 어긋난 단계만 고치고 같은 입력으로 확인해 주세요.
부분 보완 전후의 실제 필드·검토 이유와 재처리 방식의 의미를 기존 노트에 연결하세요.
```

아래 초안 저장까지 연결한 최종 Workflow를 Dify의 export 기능으로 주차 폴더에 저장합니다. `workflow-setup.md`는 구성표이고 DSL은 실제 선택한 모델·프롬프트·노드·변수 연결을 보관해 나중에 확인하거나 가져오기할 산출물입니다. Plugin 구현은 소스에, 특정 입력의 결과와 선택 이유는 학습 노트에 남으므로 세 자료를 연결합니다. DSL을 가져왔다고 Plugin 실행 환경이나 모델 인증까지 준비되는 것은 아닙니다. 공유할 사본에서 비밀값과 작업공간 전용 식별 정보도 확인해 제거합니다. [앱 관리와 가져오기·내보내기](https://docs.dify.ai/en/cloud/use-dify/workspace/app-management)

Plugin 소스와 실제 Dify 사용으로 기본 결과가 완성됩니다. **패키징**은 Plugin 코드·선언·필요 자산을 설치 가능한 `.difypkg` 파일로 묶는 일입니다. Workflow의 노드 구성을 담는 DSL과 달리 호출할 기능의 구현을 담습니다. 파일이 필요하면 공식 Plugin CLI를 설치하고 주차 폴더에서 `dify plugin package ./meeting_tool`을 실행합니다. 이 명령은 Windows PowerShell과 macOS·Linux·WSL에서 같으며 Plugin 배포 파일을 만들 때 사용합니다. 패키지 생성은 배포·공개를 뜻하지 않으며 Marketplace 등록은 이 주차의 완료 조건이 아닙니다.

**보완 결과 확인:** 전체가 계속 `review`여도 담당자 미정 이유가 사라지고 기한 미정만 남았는지 비교합니다. 같은 상태값 안에서 어떤 정보가 바뀌었는지가 재처리의 효과입니다. 이어서 확인된 초안을 저장하는 조건을 연결합니다.

#### 실제 Workflow 결과를 받아 초안 저장하기

제공 후속 요구는 “확인한 회의 초안을 저장하되 정보가 부족한 메모는 보류하고 같은 결과의 재전달로 초안을 중복 생성하지 않는다”입니다. 전체 메모를 보류할지 확정 가능한 항목만 처리할지는 AI의 추천·이유를 검토해 정합니다. 참고 구현은 전체 메모 검토를 선택합니다.

**호출자(Client)**는 API 요청을 보내고 결과를 받는 프로그램입니다. **엔드포인트(Endpoint)**는 요청을 보낼 구체적인 주소입니다. 제공 `workflow_client.py`는 기본 주소에 `/workflows/run`을 붙이고 `inputs.memo`에 원문을 담아 요청합니다. 응답에서 `data.status`는 Workflow 실행 상태, `data.outputs.payload`는 우리가 Output에 연결한 업무 결과입니다. 따라서 실행이 `succeeded`여도 업무 결과는 `review`일 수 있습니다. API 요청·응답을 담은 바깥 구조와 그 안의 업무 데이터를 나누어 읽습니다.

Dify의 공통 `최종 출력`에서 `payload=업무 검사.payload`가 String으로 반환되는지 확인하고 Workflow를 실행 가능한 상태로 게시합니다. 앱의 API Access에서 확인한 API 기본 주소와 키를 IDE의 비공유 설정 `DIFY_API_URL`, `DIFY_API_KEY`에 넣습니다. 주소는 보통 `/v1`까지이며 호출자가 `/workflows/run`을 붙입니다. API 키가 들어 있는 설정은 AI에 공유하지 않습니다.

호출 코드는 HTTP 요청의 `User-Agent` 헤더에 학습용 앱 식별자 `MeetingReviewLab/1.0`을 명시합니다. `User-Agent`는 요청을 보내는 프로그램의 이름·버전을 설명하는 값이며, Dify 화면의 앱 이름이나 API 키와는 별개입니다. `Content-Type: application/json`은 요청 본문의 형식, `Accept: application/json`은 받을 응답의 형식을 나타냅니다. 이 헤더들은 `workflow_client.py`에 지정하므로 IDE의 환경변수에 추가할 필요는 없습니다.

여기의 키는 **만든 Dify 앱을 호출하는 키**입니다. Dify가 LLM에 접근할 때 쓰는 모델 제공자 키나, PC의 Plugin을 연결할 때 쓰는 개발 키와는 호출 대상이 다릅니다. 현재 앱의 API 안내에서 발급·설정합니다. [Dify 앱 API 시작하기](https://docs.dify.ai/en/api-reference/guides/get-started)

**대역**은 실제 외부 호출 대신 정해진 결과를 반환하는 시험용 구현입니다. **메모리 DB**는 실행 중 메모리에만 데이터를 유지하고, 제공 예제의 **SQLite**는 별도 DB 서버 없이 파일에도 데이터를 저장할 수 있는 데이터베이스입니다. 먼저 대역으로 후속 처리 규칙을 확인하고 실제 호출에서는 모델 추출부터 사람 확인까지 연결합니다.

참고 `meeting_plugin/workflow_client.py`와 기존 검사를 제작 Plugin 폴더에서 재사용하고, 재검사 함수를 Day 2~3에서 구현한 계약에 맞춥니다. IDE에서 제작한 `meeting_tool/workflow_client.py`를 기본 실행하면 제공 추출 대역과 메모리 DB로 저장·보류·재전달을 봅니다. `--live`로 실행하면 실제 Dify Workflow를 호출하고 원문과 작업을 표시합니다. 내용을 확인해 `save`를 입력한 초안만 `.local/meeting-drafts.sqlite`에 저장합니다. 같은 ID·같은 내용이면 `already_saved`, 같은 ID의 다른 내용이면 `revision_required`로 보류합니다. 이 ID는 저장 중복 방지에 쓰며 모델 호출 자체를 캐시하지는 않습니다.

여기서 저장을 더하는 이유는 추출 결과가 실제 행동으로 넘어가는 조건을 설계하기 위해서입니다. `ready`만 보고 저장하면 필드 검사 통과와 사람의 허용이 섞이고, 매번 새 초안을 만들면 같은 결과의 재전달이 중복 작업이 됩니다. 그래서 확인 입력은 저장 직전에, 같은 ID·내용의 비교는 `DraftStore.save` 안에 둡니다. 누락 메모의 `review`와 정상 메모의 `save` 후 `saved`를 대조하면 업무 판단과 실행 허용의 경계가 드러납니다. 재전달 결과는 저장 경계의 반복 처리 정책을 확인합니다.

필드 검사가 통과해도 원문에서 누락된 상충을 복원할 수는 없으므로 저장 전 사람이 내용까지 봅니다. 프롬프트에서 `approved=true`를 받는 것으로 사람의 확인을 대신하지 않습니다. 호출 실패는 근거 부족·검토 보류와 별도로 남고 독립된 다음 메모는 계속 처리합니다. 앞 메모 결과에 의존하는 작업이라면 같은 부분 성공 정책을 그대로 적용할 수 없습니다.


## 완료 기준

완료의 근거는 선택한 계약의 구현과 실제 결과, 그 결과를 요구에 비추어 해석한 기록입니다. 실행 성공이나 AI가 작성한 설명만으로 이해·설계 역량을 확인했다고 판단하지 않습니다. 이미 진행한 선택과 결과를 아래 기준에 연결하며 별도 답안이나 같은 실행을 다시 요구하지 않습니다.

- [ ] 제공 메모로 실제 Dify의 입력→LLM 추출→출력 연결을 만들었습니다.
- [ ] 제공 요구의 사실·판단·다음 행동에서 결과 단위·책임·입출력·오류·보완 방식을 도출하고 가능한 구성을 비교했습니다.
- [ ] 기본 노드·모델·외부 Tool의 책임과 선택한 처리 단위를 실제 코드·변수·분기에 반영했습니다.
- [ ] SDK의 등록·메시지 규약과 학습자가 정한 업무 계약을 구분하고 실제 Plugin·Workflow를 제작해 호출했습니다.
- [ ] 정상·검토·형식 오류와 실행 실패를 구분하고, 실제 검사 결과에서 필요한 후속 행동으로 분기했습니다.
- [ ] 정상·누락·상충 메모에서 원문→추출→검사→경로를 확인하고 필드 검사의 의미적 한계를 설명했습니다.
- [ ] 부분 보완 뒤 해결된 값과 남은 문제를 구분했으며 실제 Workflow export·Plugin 소스·노트를 연결했습니다.

오프라인 업무 함수·SDK 검사만 진행했다면 그 결과는 보존하고 실제 Dify·모델 연결 항목은 미완료로 남깁니다. 다른 프로젝트나 추가 기능을 완료했다는 이유로 이 연결을 완료 처리하지 않습니다.
