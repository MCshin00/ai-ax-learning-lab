> 이 README가 이번 주차의 상세 학습 본문입니다. 루트 `CURRENT_WEEK.md`는 여기로 돌아오는 짧은 대시보드입니다.

- 기본 작업 폴더: [`lab/ticket-title-normalizer`](lab/ticket-title-normalizer/)
- 전체 과정: [루트 README](../README.md)
- 현재 위치와 다음 명령: [CURRENT_WEEK](../CURRENT_WEEK.md)

## 시작 준비

실습 전에 루트 `LEARNING_GUIDE.md`의 공통 안내에서 작업 폴더, Git·비밀값, 필요한 런타임과 외부 비용을 확인하세요. 대표 사례는 대화형 표면에서 먼저 실행하고 실제 결과를 확인합니다.


이번 주에는 작은 코드 변경을 요청하고 결과를 확인합니다. 익숙한 개인 프로젝트의 작은 버그를 사용해도 되고, 준비된 티켓 제목 정규화 과제를 써도 됩니다.

## 시작 전에 알아둘 개념

Codex는 요청과 프로젝트 자료를 읽고 코드 수정이나 명령 실행을 돕는 AI 개발 도구입니다. 프롬프트는 이번에 맡길 요청이며, 작업 폴더와 파일은 그 요청을 해석할 맥락입니다. 예를 들어 “제목 공백을 정리해 줘”라는 요청에 README의 요구사항과 기존 테스트가 함께 있어야 무엇을 바꾸고 유지할지 판단하기 쉽습니다.

`diff`는 실제 파일의 변경 내역이고, 테스트는 특정 입력에서 기대한 동작을 검사합니다. 완료 보고를 읽을 때 이 두 가지를 함께 확인하면 무엇이 바뀌고 무엇까지 검증됐는지 알 수 있습니다. 이번에는 **요청 → 코드 변경 → 테스트 → 후속 수정**을 한 작은 기능에서 확인합니다.

AI 도구의 답변에는 설명과 실제 작업에 관한 보고가 함께 들어갈 수 있습니다. “빈 제목을 거부하도록 고쳤습니다”라는 문장을 읽는 것만으로 파일이 바뀌었는지는 알 수 없습니다. 변경된 코드는 diff에서, 빈 입력의 처리 결과는 실행·테스트에서 확인합니다. 이 구분 덕분에 요청을 잘못 이해한 문제, 구현한 코드의 문제, 검증하지 않은 내용을 완료했다고 보고한 문제를 따로 찾을 수 있습니다.

## 실습 순서

| 단계 | 할 일 | 확인할 것 |
|---|---|---|

| Day 2 | 요구·코드·테스트의 연결을 읽고 새 입력 확인 | 처리 경로와 예상·실제 결과의 일치 |
| Day 3 | 후속 요청으로 수정하거나 경계 동작 확인 | 같은 입력의 수정 전후 또는 처리 결과 |
| Day 4 | 저장소 규칙 하나를 읽고 필요한 경우 조정 | 이번 요청과 계속 적용할 규칙의 차이 |
| Day 5 | 다른 작은 변경에 다시 사용 | 무엇을 맡기고 무엇을 직접 확인했는가 |

### Day 1 — 작은 기능을 요청하고 실행 결과 확인하기

IDE와 Codex에서 `week01-codex-prompt-comparison/lab/ticket-title-normalizer/`를 엽니다. 이 폴더의 README에 요구사항과 테스트 방법이 있습니다. JDK 17 이상이 필요합니다. 첫 실행에서 Gradle·JUnit을 내려받을 수 있습니다. IDE의 Gradle 테스트 실행 버튼을 사용하거나 다음 명령을 사용합니다.

Windows PowerShell:

```powershell
.\gradlew.bat test
```

macOS·Linux·WSL:

```bash
./gradlew test
```

처음에는 `normalize`가 미구현이라 테스트가 실패합니다. 이 과제에서 코드를 만드는 도구는 Codex입니다. 다음 요청을 대화창에 직접 보냅니다.

```text
README의 요구사항대로 티켓 제목 정규화를 구현해 주세요.
기존 테스트를 삭제하거나 약화하지 말고, 테스트를 실행해 결과를 알려 주세요.
내가 확인할 핵심 변경과 아직 확인하지 못한 사항을 짧게 설명해 주세요.
```

끝나면 IDE의 변경 목록에서 코드 한 곳을 열고 테스트 결과를 봅니다. 실행하지 못했다는 보고를 테스트 통과로 읽지 않습니다.

### Day 2 — 요구·코드·테스트 구조를 따라가며 입력 확인하기

#### 해설 — 요청의 문구가 코드의 조건이 되기까지

“제목 공백을 정리해 줘”에는 앞뒤 공백만 지울지, 내부의 연속 공백도 합칠지, 공백뿐인 제목을 빈 문자열로 돌려줄지가 정해져 있지 않습니다. 준비된 README는 이 선택을 구체화합니다. 아래는 README의 요구에서 도출한 예상 동작이며, 아직 자신의 구현을 실행한 결과는 아닙니다.

```text
입력: "  로그인   오류  "
앞뒤 공백 제거: "로그인   오류"
연속 공백 정리: "로그인 오류"
빈 제목·길이 조건 확인을 거친 반환값: "로그인 오류"

입력: "   "
요구되는 결과: IllegalArgumentException
```

이렇게 입력과 기대 결과를 연결하면 “공백 처리”라는 말이 실제 동작의 조건이 됩니다. 다만 위 흐름은 이해를 돕는 설명이며 특정한 코드 순서 하나만 정답으로 요구하지 않습니다. 구현이 처음부터 공백뿐인 입력을 검사하든 정규화 후 검사하든 README가 정한 결과를 만족해야 합니다. 처음 받은 코드가 `trim()`만 호출한다면 내부 공백이 남고, 공백 입력에서 빈 문자열을 반환한다면 요구한 예외가 없습니다. 어디가 틀렸는지 알려면 프롬프트 항목 수보다 이런 구체적인 차이가 필요합니다.

이번 요청은 바꿀 일을 지정하고, README는 이 예제의 동작 조건을 제공하며, 코드는 그 조건을 실행합니다. 테스트는 대표 입력과 기대 결과를 짝지어 실제 구현을 검사합니다. 조건과 구현을 구분해 두면 구현 방법을 바꿔도 같은 기대 결과로 확인할 수 있습니다. 반대로 잘못된 코드에 맞춰 기대값까지 바꾸면 요구를 지켰는지 검사할 기준이 사라집니다.

테스트가 모두 통과해도 검사에 없는 입력까지 확인한 것은 아닙니다. 예를 들어 앞뒤 공백 사례만 확인했다면 내부 공백이나 빈 제목에 대해서는 별도 근거가 없습니다. 이 주차에서 다른 입력을 확인하는 이유가 여기에 있습니다. 요청과 결과 사이에서 어떤 가정이 빠졌는지 찾고, 관련된 조건과 검사만 보완합니다.

README의 요구사항을 보고 공백뿐인 제목이나 이모지가 긴 제목 중 한 입력의 기대 결과를 정합니다. Codex에게 그 입력을 실행하게 하고 실제 출력 또는 예외를 예상과 대조합니다. 기대 결과가 불명확하면 요구사항의 관련 문장과 구체적인 예를 함께 설명해 달라고 요청합니다.

Day 1에서 완성한 코드를 열어 제목 입력이 결과로 바뀌는 경로를 따라갑니다. 준비된 예제에서는 다음 위치를 사용하고, 자기 프로젝트를 골랐다면 같은 역할의 파일을 찾습니다.

| 대상 | 따라가며 확인할 것 |
|---|---|
| 이번 요청과 `README.md` | 제목의 공백·빈 값·길이에 어떤 동작을 요구하는가 |
| `src/main/java/lab/week01/TicketTitleNormalizer.java` | 입력을 검사하고 바꿔 반환하는 순서와 각 분기의 역할 |
| `src/test/java/lab/week01/TicketTitleNormalizerTest.java` | 어떤 입력으로 그 요구를 확인하며 무엇은 아직 검사하지 않는가 |
| 적용되는 `AGENTS.md`와 diff | 반복 규칙과 이번 요청을 구분하고 실제 변경이 이를 지켰는가 |

Codex에게 “공백뿐인 제목이 들어왔을 때 README의 요구가 어느 코드와 테스트에 연결되는지 설명해 줘”라고 요청해도 됩니다. 구현과 테스트를 나누면 동작을 고칠 곳과 기대를 확인할 곳을 구분할 수 있습니다. 코드의 검사 순서가 결과에 영향을 주는지도 봅니다. 작성자의 의도는 확인된 설명이 있을 때만 인용합니다.

원하는 동작이 달라진다면 바꿔야 할 구현과 관련 테스트를 가리켜 봅니다. 작은 예제 전체를 읽어도 되며 파일 수를 맞춘 분석표는 필요하지 않습니다.

### Day 3 — 후속 요청으로 고치고 다시 확인하기

Day 2에서 차이가 발견됐다면 바꿀 코드와 수정 후 예상 결과를 먼저 짚습니다. AI에게 후보와 설명을 받아 검토해도 됩니다. 다음 요청에 실제 입력과 결과를 함께 보냅니다.

```text
Day 2에서 예상과 달랐던 입력, 기대 결과, 실제 결과를 확인해 주세요.
이 차이를 만드는 코드 위치와 최소 수정안을 설명하고 수정해 주세요.
수정 후 같은 입력을 다시 실행하고 관련 테스트도 확인해 주세요.
```

결과가 이미 맞다면 실제로 필요한 조건 하나를 바꾸거나 잘못된 입력을 거부하는 동작을 확인해도 됩니다. 발견하지 않은 오류를 꾸미거나 테스트를 약화하지 않습니다.

### Day 4 — 반복해서 적용할 규칙 확인하기

#### 해설 — 이번 요청과 계속 적용할 지침을 구분하는 이유

“이번에는 제목의 앞뒤 공백을 없앤다”는 이번 변경의 요구입니다. “테스트를 삭제해 통과시키지 않는다”는 다음 변경에서도 유지할 작업 규칙입니다. 후자를 `AGENTS.md`에 두면 매번 같은 규칙을 대화에 다시 적는 일을 줄일 수 있습니다. 반면 지나간 작업의 세부 요구를 계속 쌓으면 다음 요청에도 적용해야 하는지 혼동하기 쉽습니다. 공식 안내도 `AGENTS.md`를 반복해서 적용할 프로젝트 지침으로 설명합니다. [OpenAI 프로젝트 맞춤 설정](https://learn.chatgpt.com/docs/customization/overview)

지침은 위치에 따라 적용되는 범위도 달라집니다. 일반적인 설정에서는 전역 지침에 프로젝트 루트부터 현재 작업 폴더까지의 지침을 이어 읽고, 더 가까운 지침이 앞선 내용과 충돌하는 부분을 구체화하거나 덮어씁니다. 예를 들어 루트에는 공통 테스트 원칙을 두고 특정 하위 작업에는 그곳의 테스트 명령을 둘 수 있습니다. 하위 지침이 있다는 사실만으로 다른 폴더에도 그 규칙이 적용되거나 상위의 모든 규칙이 사라지는 것은 아닙니다. 실제로 적용된 파일과 현재 작업 위치를 함께 확인해야 합니다. [OpenAI 지침 탐색 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

또한 지침에 “반드시 테스트한다”고 적는 것과 테스트가 실행되는 것은 다릅니다. 지침은 도구의 작업을 안내하고, 테스트 명령과 그 출력은 실제 확인 근거를 만듭니다. 규칙이 있는데 검증을 빠뜨렸다면 새 규칙을 더 쓰기 전에 어떤 파일을 읽었고 무엇을 실행했는지부터 봅니다.

현재 작업에 적용되는 `AGENTS.md`를 열어 요청·README와 맡는 역할이 어떻게 다른지 봅니다. `../../prompts/agents-audit.md`로 설명을 요청해도 됩니다. 예를 들어 테스트 실행 규칙이 있다면 실제 명령과 결과가 보고됐는지 대조합니다. 매번 유지할 규칙을 이 파일에 두면 어떤 반복 설명을 줄이는지 생각하고 일회성 요구는 대화에 남깁니다. 계속 필요한 규칙이 빠졌을 때만 AI와 함께 수정하며 새 규칙 파일을 만들 의무는 없습니다.

### Day 5 — 다른 작은 작업에 다시 사용하기

자기 프로젝트의 작은 변경 하나를 골라 Codex에 요청하고 diff와 관련 테스트 또는 실제 출력을 확인합니다. 당장 사용할 프로젝트가 없다면 같은 예제의 README에 실제 입력·출력 예시 하나를 추가하도록 요청하고 구현 결과와 대조합니다. 결과를 수용한 이유와 다음에 요청을 보완할 점만 짧게 남깁니다.

## 완료 기준

- [ ] 작은 작업을 Codex에 요청하고 실제 결과를 확인했습니다.
- [ ] 요청·규칙·코드·테스트의 역할과 입력의 처리 경로를 실제 위치에서 설명했습니다.
- [ ] 원하는 동작을 바꿀 위치와 예상 결과를 짚고 수정 또는 경계 입력의 실제 결과와 대조했습니다.
- [ ] 후속 요청으로 고친 결과 또는 경계 입력의 동작을 확인했습니다.
- [ ] 다른 작은 작업에 적용하고 수용 여부를 직접 판단했습니다.

두 프롬프트의 통제 실험, 별도 채점표, 반복 실행은 이 주차 과제가 아닙니다. 요청이 모호해서 문제가 생겼을 때 필요한 정보만 보완해 봅니다.

## 이 폴더의 자료

- `lab/`: 시작 코드, 설정, 평가 자료와 이번 주 구현
- `prompts/`: 과정이 제공하고 `sync`가 갱신할 수 있는 요청 자료
- `runs/`: 짧은 메모와 다시 확인할 결과. 외부 공개는 선택
- `references/`: 실습 뒤 `reference` 명령으로 공개하는 비교용 참고 구현
- `.local/notes/`: 개인 메모, `.local/raw/`: 정제 전 로그, `.local/scratch/`: 임시 작업. `.local/` 전체는 Git에서 제외

`runs/`와 `lab/`은 학습자가 관리합니다. `sync`는 이 두 폴더를 덮어쓰지 않습니다.
