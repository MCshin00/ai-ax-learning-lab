# 2주차 학습 노트 — Skills

## Day 1 — Skill Creator로 만들고 처음 호출하기

### 학습 목표와 개념

버그 제보를 정리하는 `issue-summary` Skill을 만들고, 이름을 지정해 호출한 결과가 요청에 맞는지 확인한다.

- **Skill**은 같은 종류의 작업에 재사용할 지침과 필요한 자료의 묶음이다. 이번 Skill은 버그 제보의 정리 형식과 사실 보존 규칙을 담는다.
- **Skill Creator**는 Skill을 생성하거나 수정하는 데 사용하는 Skill이다.
- **명시 호출**은 `$issue-summary`처럼 사용할 Skill의 이름을 직접 지정하는 것이다.
- **자동 선택**은 Skill 이름 없이 요청했을 때 Codex가 적용할 Skill을 고르는 것이다. Day 3에서 확인한다.

### 작업 대상과 기록 근거

- 작업 폴더: [2주차 작업 폴더](./)
- 생성된 Skill: [issue-summary/SKILL.md](.agents/skills/issue-summary/SKILL.md)
- 학습 안내: [2주차 README](README.md)

현재 Skill 원문과 학습자가 이 대화에 공유한 실제 응답을 확인했다. 아래 생성 요청과 호출 요청은 학습 안내에서 제시한 문구이며, 응답은 학습자가 공유한 내용을 그대로 기록했다. Creator의 생성 과정이나 보조 검사 결과를 별도로 확인한 기록은 포함하지 않는다.

### Creator에 안내한 생성 요청

```text
$skill-creator를 사용해 issue-summary Skill을 만들어 주세요.
위치는 현재 폴더의 .agents/skills/issue-summary/입니다.

버그 제보를 증상, 재현 순서, 기대 동작, 확인이 필요한 정보로 정리하고 싶습니다.
입력에 없는 원인·버전·재현 단계를 지어내지 않아야 합니다.
단순 번역이나 일반적인 개념 질문에는 자동으로 선택되지 않게 해 주세요.

먼저 지침만 있는 작은 Skill로 만들어 주세요.
내가 검토할 대표 결과도 보여 주세요.
```

현재 `SKILL.md`에는 이름과 적용 범위, 정리 원칙, 네 항목의 출력 형식이 들어 있다. 특히 입력에 없는 사실을 채우지 않고, 제공되지 않은 항목은 `입력에 없음`으로 표시하도록 되어 있다.

### 첫 명시 호출에 안내한 요청

같은 lab 폴더를 선택한 새 작업에서 보내도록 안내한 요청이다.

```text
$issue-summary를 사용해 다음 제보를 정리해 주세요.
Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.
```

### 학습자가 공유한 실제 응답

```markdown
### 증상

- Android 앱에서 로그인 버튼을 누르면 로딩이 계속됨.
- 어제까지는 로그인됐으나 현재 문제가 발생함.
- 앱을 다시 켜도 같은 증상이 나타남.
- 웹에서는 로그인됨.

### 재현 순서

1. Android 앱에서 로그인 버튼을 누름.
2. 문제가 발생한 뒤 앱을 다시 켬. 같은 증상이 나타남.

### 기대 동작

입력에 없음.

### 확인이 필요한 정보

- 사용 중인 기기 모델, Android 버전, 앱 버전은 무엇인가요?
- 어떤 로그인 방식을 사용했나요?
- 로딩은 얼마나 기다려 봤으며, 오류 메시지가 표시됐나요?
- 정상이라면 로그인 버튼을 누른 뒤 어떤 화면이나 동작을 기대하나요?
```

### 입력·지침·결과를 대조한 검토

| 확인한 부분 | 실제 근거 | 검토 내용 |
|---|---|---|
| 사실 보존 | Android 앱의 로그인 로딩 지속, 어제까지 정상, 재실행 후 동일, 웹 로그인 가능이 출력에 모두 남아 있다. | 제보의 주요 사실을 보존했다. |
| 원인과 환경 정보 | 원인을 단정하지 않았고 기기·버전·로그인 방식은 질문으로 남겼다. | 서버 장애나 특정 버전을 만들어 내지 않았다. |
| 재현 순서 | 로그인 버튼 누르기와 앱 다시 켜기만 적었다. | 입력에 없는 준비 단계나 중간 행동을 추가하지 않았다. |
| 기대 동작 | `기대 동작`에 `입력에 없음`을 적고, 마지막 항목에서 기대하는 화면이나 동작을 물었다. | 로그인 성공을 기대한다고 추론할 수는 있지만, 원문에 명시된 사실과 구분했다. |
| 정보 부족 처리 | 정리 결과를 먼저 제공하고 필요한 질문을 뒤에 배치했다. | 누락된 정보를 모두 답해야만 초안을 받을 수 있는 흐름이 아니었다. |

현재 Skill의 “입력에 있는 사실만 사용한다”는 지침은 원인을 단정하지 않은 출력과 연결된다. “제공되지 않은 항목은 `입력에 없음`으로 표시한다”는 지침은 기대 동작 항목에서 확인된다. 버전 등을 묻는 문장은 확인된 사실이 아니라 다음에 수집할 정보다.

**검토 결론:** 공유된 첫 출력은 Day 1의 사실 보존과 미확인 정보 구분 기준에 맞는 수용 가능한 결과다. 이 검토에서 즉시 수정할 내용은 발견하지 못했다. 다만 한 번의 결과만으로 다른 제보의 품질이나 자동 선택 동작까지 확인한 것은 아니다.

### Day 1 당시의 다음 행동

- **Day 1:** 생성된 Skill 원문과 공유된 첫 출력의 검토를 기록했다.
- **Day 2:** 학습자가 이미 수행했다고 알려 준 활동으로, 이번 진행에서는 건너뛴다. 기존 분석 내용을 이 노트에서 새로 수행한 것으로 기록하지 않는다.
- **다음은 Day 3:** 정상·비발동·정보 부족 요청을 각각 새 작업에서 확인한다.

먼저 같은 lab 폴더의 새 작업에서 Skill 이름 없이 다음 정상 요청을 보낸다.

```text
다음 제보를 개발자에게 전달할 이슈로 정리해 주세요.

Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.
```

Skill의 선택 여부와 출력 품질을 따로 기록한다. `issue-summary/SKILL.md`를 읽은 기록 등 사용 근거를 확인하고, 근거가 보이지 않으면 선택 여부는 `NOT_VERIFIED`로 남긴다. 출력 모양만으로 자동 선택을 판단하지 않는다.

## Day 3 — 정상·비발동·정보 부족 요청 확인하기

### 목적과 기록 근거

Skill 이름을 지정하지 않은 요청에서 적용 범위와 출력 품질을 확인한다. 같은 lab 폴더를 선택한 새 작업에서 사례별로 실행하도록 안내했고, 학습자가 이 대화에 공유한 세 응답과 사용 여부에 대한 관찰을 기록했다. 아래 요청은 각 실습에서 보내도록 안내한 문구다.

정상·정보 부족 사례에는 `issue-summary` 사용 선언과 `Loaded a tool, read files, ran a command`라는 도구 활동 요약이 있었다. 펼쳐진 파일 경로는 공유되지 않았으므로 실제 `issue-summary/SKILL.md`를 읽었는지는 확인하지 못했다. 출력 품질과 Skill 선택 여부는 구분해서 기록한다.

### 1. 정상 요청

**요청**

```text
다음 제보를 개발자에게 전달할 이슈로 정리해 주세요.

Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.
```

**공유된 사용 선언**

> `issue-summary` 스킬을 사용해 확인된 증상과 추가 확인이 필요한 정보를 나눠 정리하겠습니다.

**공유된 실제 응답**

```markdown
**증상**

- Android 앱에서 로그인 버튼을 누르면 로딩이 계속됨.
- 어제까지는 로그인할 수 있었음.
- 앱을 다시 켜도 같은 증상이 나타남.
- 웹에서는 로그인됨.

**재현 순서**

1. Android 앱에서 로그인 버튼을 누름 → 로딩이 계속됨.
2. 앱을 다시 켬 → 같은 증상이 나타남.

**기대 동작**

입력에 없음.

**확인이 필요한 정보**

- 앱 이름·버전, 기기 모델과 Android 버전은 무엇인가요?
- 로딩 상태에서 얼마나 기다렸으며, 오류 메시지가 표시되나요?
- 정상일 때 로그인 버튼을 누르면 어떤 화면으로 이동하나요?
```

**검토**

- 로그인 로딩 지속, 어제까지 정상, 앱 재실행 후 동일, 웹 로그인 가능이라는 사실을 보존했다.
- 서버 장애 등 원인을 단정하거나 앱·운영체제 버전을 만들어 내지 않았다.
- 기대 동작은 입력에 없는 정보로 표시하고, 필요한 환경 정보와 정상 동작을 질문했다.
- **출력 품질: 수용.**
- **자동 선택: `NOT_VERIFIED`.** 사용 선언과 도구 활동 요약은 있으나, 실제로 읽은 Skill 파일 경로는 이 기록에서 확인되지 않았다.

### 2. 비발동 요청

**요청**

```text
HTTP 404가 무엇인지 설명해 주세요.
```

**공유된 실제 응답**

```markdown
**HTTP 404(Not Found)**는 서버가 요청한 페이지나 파일을 찾지 못했을 때 보내는 응답 상태 코드입니다. 서버와 통신은 됐지만, 요청한 주소에 해당하는 내용을 찾을 수 없다는 뜻입니다.

예를 들어 `example.com/about`에 접속했는데 해당 페이지가 없다면 서버가 404를 반환할 수 있습니다.

주로 다음과 같은 경우에 발생합니다.

- URL을 잘못 입력한 경우
- 페이지나 파일이 삭제되거나 주소가 바뀐 경우
- 서버에서 주소와 페이지를 연결하는 설정이 잘못된 경우

방문자라면 **주소의 오타를 확인하거나 사이트의 홈·검색에서 페이지를 다시 찾아보세요.** 개발자라면 요청 URL, 파일 위치, 경로 연결 설정을 확인하면 됩니다.
```

**학습자의 관찰**

> 스킬은 사용하지 않았네요.

**검토**

- HTTP 404에 대한 일반적인 개념 설명으로 답했다.
- 증상·재현 순서·기대 동작·확인 정보라는 버그 제보 양식을 적용하지 않았다.
- **출력 품질: 수용.**
- **비발동: 학습자의 미사용 관찰을 근거로 기대 동작에 부합한다고 기록한다.** 이 노트를 작성하는 과정에서 해당 작업의 도구 기록을 별도로 조회한 것은 아니다.

### 3. 정보 부족 요청

**요청**

```text
앱이 안 돼요. 이슈로 정리해 주세요.
```

**공유된 사용 선언**

> `issue-summary` 스킬을 사용해 이슈 초안을 정리하겠습니다. 지금 확인된 내용은 “앱이 안 된다”는 증상뿐이라, 구체적인 증상과 재현 방법은 확인이 필요한 항목으로 남기겠습니다.

**공유된 실제 응답**

```markdown
**증상:** “앱이 안 돼요.”라는 제보. 구체적인 증상은 입력에 없음.

**재현 순서:** 입력에 없음.

**기대 동작:** 입력에 없음.

**확인이 필요한 정보:**

- 어떤 앱이며, 어떤 기기·운영체제에서 사용 중인가요?
- 어떤 조작을 했을 때 문제가 발생하며, 화면 반응이나 오류 메시지는 무엇인가요?
- 해당 조작을 하면 원래 어떤 결과가 나와야 하나요?
```

**학습자의 관찰**

> 스킬 사용한거같네.

**검토**

- 확인된 사실을 “앱이 안 된다”로 제한했다.
- 앞선 정상 사례의 Android나 로그인 문제를 이번 제보에 섞지 않았다.
- 재현 순서와 기대 동작을 지어내지 않고 `입력에 없음`으로 표시했다.
- 초안을 먼저 제공한 뒤 앱·환경, 조작·증상, 기대 동작을 질문했다.
- **출력 품질: 수용.**
- **자동 선택: `NOT_VERIFIED`.** 사용 선언은 있으나 실제 Skill 파일을 읽은 경로는 공유된 내용에서 확인되지 않았다.

### 세 사례의 비교와 판단

아래 수용 판단은 이 대화에서 실제 응답을 대조한 검토 결과다.

| 사례 | 출력 품질 | Skill 선택에 대해 확인한 범위 |
|---|---|---|
| 정상 | 사실 보존과 미확인 정보 구분 — 수용 | 사용 선언·도구 활동 요약 확인. 실제 Skill 읽기 여부는 `NOT_VERIFIED` |
| 비발동 | 일반 개념 설명 유지 — 수용 | 학습자가 Skill 미사용을 관찰했다고 보고함 |
| 정보 부족 | 사실을 추가하지 않고 초안·질문 제공 — 수용 | 사용 선언·도구 활동 요약 확인. 실제 Skill 읽기 여부는 `NOT_VERIFIED` |

정상 사례는 주어진 사실을 네 항목으로 정리했고, 정보 부족 사례는 같은 형식을 사용하면서 모르는 내용을 채우지 않았다. 비발동 사례는 이슈 정리 형식 대신 개념을 설명했다. 세 응답에서 기대한 출력 차이는 확인됐다.

다만 출력 형식과 모델의 사용 선언만으로 실제 Skill 선택을 확정할 수는 없다. 정상·정보 부족 사례에서 `read files`를 펼쳐 해당 `SKILL.md` 경로를 확인하면 이 노트의 선택 상태를 갱신할 수 있다. 경로 확인 전에는 미확인 상태를 유지한다. 이번 세 사례로 일반적인 자동 선택 성공률을 계산하지 않는다.

- **Day 2:** 학습자가 이미 수행했다고 알려 준 활동으로 건너뛴다.
- **Day 3:** 세 사례의 실제 응답과 출력 검토를 기록했고, 선택 근거의 확인 범위를 구분했다.
- **다음은 Day 4:** 현재 세 출력에서 뚜렷한 오류는 발견하지 못했다. 필요한 변경 한 가지를 정하고, 수정할 지침과 예상 결과를 짚은 뒤 Creator로 수정한다. 같은 요청과 새 요청으로 결과를 확인한다. 구체적인 변경 항목은 아직 정하지 않았다.

## Day 4 — 이슈 제목 추가와 수정 전후 확인

### 바꿀 내용과 예상

Day 3의 세 출력에서 뚜렷한 오류는 발견하지 못했다. 개발자가 목록에서 핵심 문제를 파악할 수 있도록, 기존 네 항목 앞에 **이슈 제목 한 줄을 추가하는 변경**을 정했다.

- 수정 대상: [issue-summary/SKILL.md](.agents/skills/issue-summary/SKILL.md)
- 변경 위치: 소개 문장, 새 `제목 작성` 절, `출력 형식` 첫 줄
- 제목에는 입력에 명시된 대상과 증상만 사용한다.
- 상세 증상이 없으면 `상세 증상 미확인`을 표시한다.
- 기존 사실 보존 규칙과 증상·재현 순서·기대 동작·확인 정보 항목을 유지한다.

수정 전에는 결과가 `증상`부터 시작했다. 수정 후에는 정상 제보에 로그인 로딩 문제를 요약한 제목이, 정보 부족 제보에는 상세 증상이 미확인이라는 제목이 붙을 것으로 예상했다. 예상 예시는 실제 검증 결과와 구분해 다뤘다.

### Creator 수정과 원문 확인

학습자가 공유한 Creator의 보고에서는 `SKILL.md`만 수정했고, `quick_validate.py` 형식 검사가 `Skill is valid!`로 통과했다고 했다. 이 검사는 형식에 대한 보고이며 실제 제목의 품질은 이후 호출 결과로 확인했다.

현재 파일을 직접 읽어 아래 변경을 확인했다. 다음은 대화에서 확인한 수정 전후 원문의 관련 부분이다.

```diff
-제공된 버그 제보를 아래 네 항목으로 간결하게 정리한다.
+제공된 버그 제보를 한 줄의 이슈 제목과 아래 네 항목으로 간결하게 정리한다.
```

추가된 `제목 작성` 절에는 다음 규칙이 있다.

> 입력에 명시된 대상과 증상만으로 핵심 문제가 드러나는 짧은 제목 한 줄을 쓴다. 원인이나 입력에 없는 정보를 덧붙이지 않으며, 기존 사실 보존 규칙을 제목에도 적용한다.

> 증상이 모호하거나 없으면 제목에 `상세 증상 미확인`을 명시한다.

출력 형식의 첫 줄에는 `이슈 제목: 한 줄 제목`이 추가됐다. 제목 작성 규칙은 제목에 담을 정보의 범위를 정하고, 출력 형식은 그 제목이 놓일 위치를 정한다. 기존 정리 원칙과 네 항목은 현재 파일에도 유지돼 있다.

### 정상 제보 재확인

같은 실습 폴더의 새 작업에서 다음 명시 호출을 보내도록 안내했고, 학습자가 실제 결과를 공유했다.

```text
$issue-summary를 사용해 다음 제보를 정리해 주세요.
Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.
```

**실제 제목**

> 이슈 제목: Android 앱에서 로그인 버튼을 누르면 로딩이 계속됨

본문은 기존 네 항목으로 나왔다. 로그인 버튼을 누르면 로딩이 계속되고, 어제까지는 로그인할 수 있었으며, 앱을 다시 켜도 동일하고 웹에서는 로그인된다는 사실이 유지됐다. 기대 동작은 `입력에 없음`으로 표시됐다.

| 확인 항목 | 예상과 실제의 대조 |
|---|---|
| 제목 추가 | 출력 맨 앞에 한 줄 제목이 실제로 추가됐다. |
| 제목의 사실 보존 | Android 앱·로그인 버튼·로딩 지속만 사용했고 원인을 추가하지 않았다. |
| 기존 내용 유지 | 네 항목과 주요 사실, 미확인 정보 구분이 유지됐다. |
| 질문의 변화 | 대기 시간·오류 메시지 대신 로그인 방식을 묻는 등 질문 구성이 달라졌다. 질문 목록을 고정하도록 지시한 것은 아니며, 모두 입력에 없는 정보를 묻는 질문이다. |

**검토 판단: 수용.** 제목의 문구가 예상 예시와 완전히 같지는 않아도, 의도한 의미와 위치가 확인됐다.

### 정보 부족 제보 재확인

```text
$issue-summary를 사용해 다음 제보를 정리해 주세요.
앱이 안 돼요.
```

공유된 화면에는 `Read Issue Summary skill`이라는 읽기 활동 표시가 있었다.

**공유된 실제 응답**

```markdown
이슈 제목: 앱 — 상세 증상 미확인

### 증상

“앱이 안 돼요.”라고 제보됨. 상세 증상은 미확인.

### 재현 순서

입력에 없음

### 기대 동작

입력에 없음

### 확인이 필요한 정보

- 어떤 앱인가요?
- 문제가 발생하기까지 어떤 행동을 어떤 순서로 했나요?
- 실제로 어떤 현상이 나타나나요? 오류 메시지가 있다면 알려 주세요.
- 기대했던 정상 동작은 무엇인가요?
```

**검토 판단: 수용.** 제목에 입력의 대상인 앱과 `상세 증상 미확인`이 표시됐다. Android·로그인 등의 정보를 추가하지 않았고, 재현 순서·기대 동작을 미확인으로 남긴 뒤 필요한 질문을 제공했다.

**Day 4 결과:** 정상·정보 부족 제보 모두에서 제목 추가와 사실 보존을 확인했다. 변경 위치, 수정 전후 차이, 예상과 실제 결과의 대조까지 기록했다.

## Day 5 — 새 장바구니 제보에 재사용하기

### 새 요청과 실행 근거

제목 규칙을 수정할 때 사용하지 않은 장바구니 제보를 선택했다. 같은 실습 폴더의 새 작업에서 다음 요청을 명시 호출하도록 안내했고, 학습자가 실제 응답을 공유했다.

```text
$issue-summary를 사용해 다음 제보를 정리해 주세요.
상품을 장바구니에서 삭제하면 합계가 그대로예요.
화면을 새로 열면 합계가 맞습니다.
```

공유된 화면에는 사용 선언과 `Read Issue Summary skill`이라는 읽기 활동 표시가 있었다. 이번 확인은 이름을 지정한 호출이며, Day 3의 자동 선택 여부를 대신 검증하는 기록은 아니다.

### 공유된 실제 응답

```markdown
이슈 제목: 장바구니에서 상품 삭제 후 합계가 그대로 표시됨

### 증상

상품을 장바구니에서 삭제하면 합계가 그대로이며, 화면을 새로 열면 합계가 맞게 표시됨.

### 재현 순서

1. 장바구니에서 상품을 삭제한다.
2. 화면을 새로 연다.

### 기대 동작

입력에 없음.

### 확인이 필요한 정보

- 상품 삭제 후 합계가 어떻게 바뀌기를 기대하나요?
- “화면을 새로 연다”는 구체적으로 어떤 동작인가요?
```

### 새 결과의 검토와 적용 범위

| 확인 항목 | 실제 결과와 판단 |
|---|---|
| 수정 의도 유지 | 맨 앞에 새 제보의 핵심을 요약한 제목이 있다. |
| 사실 보존 | 상품 삭제 후 합계가 그대로라는 증상과, 화면을 새로 열면 합계가 맞는다는 사실을 모두 보존했다. |
| 원인 추측 방지 | 캐시 문제 등 확인되지 않은 원인을 단정하지 않았다. |
| 재현 순서 | 입력에 명시된 두 행동만 적었고, “화면을 새로 연다”의 구체적인 의미는 질문했다. |
| 기대 동작 구분 | 상품 삭제 후 합계가 즉시 달라져야 한다고 추론할 수는 있지만, 제보자가 명시한 기대 동작은 없어 미확인으로 남겼다. |

**검토 판단: 수용.** 새로운 제보에서도 제목 추가와 기존 사실 보존 규칙이 유지됐다. 이번 결과에서 즉시 수정할 문제는 발견하지 못했다.

재사용할 수 있는 작업은 버그 제보를 개발자에게 전달할 이슈 초안으로 정리하는 일이다. 이 Skill은 제보의 사실과 추가 질문을 정리하며, 원인 진단이나 버그 수정 자체를 수행하는 범위로 확대해 해석하지 않는다.

### 이번 주 진행 정리

- **Day 1:** 첫 명시 호출 결과를 검토하고 기록했다.
- **Day 2:** 학습자가 이미 수행했다고 알려 준 활동으로 건너뛰었다.
- **Day 3:** 정상·비발동·정보 부족 사례의 결과와 선택 근거를 구분해 기록했다.
- **Day 4:** 제목 규칙을 추가하고 정상·정보 부족 제보에서 수정 전후를 확인했다.
- **Day 5:** 새로운 장바구니 제보에 재사용해 제목과 사실 보존이 유지되는지 확인했다.

Day 4·5의 출력 검토는 완료했다. Day 3 정상·정보 부족 사례의 실제 Skill 읽기 경로는 추가로 공유되지 않았으므로 자동 선택 상태는 기존의 `NOT_VERIFIED`를 유지한다.
