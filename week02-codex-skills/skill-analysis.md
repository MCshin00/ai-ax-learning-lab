# 2주차 학습 노트 — Skills

작성일: 2026-09-07

## Day 1 — Skill Creator로 만들고 처음 호출하기

### 학습 목표와 개념

버그 제보를 정리하는 `issue-summary` Skill을 만들고, 이름을 지정해 호출한 결과가 요청에 맞는지 확인한다.

- **Skill**은 같은 종류의 작업에 재사용할 지침과 필요한 자료의 묶음이다. 이번 Skill은 버그 제보의 정리 형식과 사실 보존 규칙을 담는다.
- **Skill Creator**는 Skill을 생성하거나 수정하는 데 사용하는 Skill이다.
- **명시 호출**은 `$issue-summary`처럼 사용할 Skill의 이름을 직접 지정하는 것이다.
- **자동 선택**은 Skill 이름 없이 요청했을 때 Codex가 적용할 Skill을 고르는 것이다. Day 3에서 확인한다.

### 작업 대상

- 작업 폴더: [2주차 작업 폴더](./)
- 생성된 Skill: [issue-summary/SKILL.md](.agents/skills/issue-summary/SKILL.md)
- 학습 안내: [2주차 README](README.md)

요청문의 Skill 이름은 입력창에서 선택한 Skill을 나타낸다.

### Creator에 보낸 생성 요청

```text
$skill-creator를 사용해 issue-summary Skill을 만들어 주세요.
위치는 현재 폴더의 .agents/skills/issue-summary/입니다.

버그 제보를 증상, 재현 순서, 기대 동작, 확인이 필요한 정보로 정리하고 싶습니다.
입력에 없는 원인·버전·재현 단계를 지어내지 않아야 합니다.
단순 번역이나 일반적인 개념 질문에는 자동으로 선택되지 않게 해 주세요.

먼저 지침만 있는 작은 Skill로 만들어 주세요.
내가 검토할 대표 결과도 보여 주세요.
```

초기 생성본에는 이름과 적용 범위, 정리 원칙, 네 항목의 출력 형식이 들어 있었다. 특히 입력에 없는 사실을 채우지 않고, 제공되지 않은 항목은 `입력에 없음`으로 표시하도록 되어 있다.

### 첫 명시 호출 요청

생성 후 같은 실습 폴더의 새 작업에서 보낸 명시 호출 요청이다.

```text
$issue-summary를 사용해 다음 제보를 정리해 주세요.
Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.
```

### 실제 응답

```markdown
### 증상

- Android 앱에서 로그인 버튼을 누르면 로딩이 계속됨.
- 어제까지는 로그인됐으나 현재 문제가 발생함.
- 앱을 다시 켜도 같은 증상이 나타남.
- 웹에서는 로그인됨.

### 재현 순서

1. Android 앱에서 로그인 버튼을 누름.
2. 문제가 발생한 뒤 앱을 다시 켬. 같은 증상이 나타남.

### 기대 동작

입력에 없음.

### 확인이 필요한 정보

- 사용 중인 기기 모델, Android 버전, 앱 버전은 무엇인가요?
- 어떤 로그인 방식을 사용했나요?
- 로딩은 얼마나 기다려 봤으며, 오류 메시지가 표시됐나요?
- 정상이라면 로그인 버튼을 누른 뒤 어떤 화면이나 동작을 기대하나요?
```

### 입력·지침·결과를 대조한 검토

| 확인한 부분 | 실제 근거 | 검토 내용 |
|---|---|---|
| 사실 보존 | Android 앱의 로그인 로딩 지속, 어제까지 정상, 재실행 후 동일, 웹 로그인 가능이 출력에 모두 남아 있다. | 제보의 주요 사실을 보존했다. |
| 원인과 환경 정보 | 원인을 단정하지 않았고 기기·버전·로그인 방식은 질문으로 남겼다. | 서버 장애나 특정 버전을 만들어 내지 않았다. |
| 재현 순서 | 로그인 버튼 누르기와 앱 다시 켜기만 적었다. | 입력에 없는 준비 단계나 중간 행동을 추가하지 않았다. |
| 기대 동작 | `기대 동작`에 `입력에 없음`을 적고, 마지막 항목에서 기대하는 화면이나 동작을 물었다. | 로그인 성공을 기대한다고 추론할 수는 있지만, 원문에 명시된 사실과 구분했다. |
| 정보 부족 처리 | 정리 결과를 먼저 제공하고 필요한 질문을 뒤에 배치했다. | 누락된 정보를 모두 답해야만 초안을 받을 수 있는 흐름이 아니었다. |

현재 Skill의 “입력에 있는 사실만 사용한다”는 지침은 원인을 단정하지 않은 출력과 연결된다. “제공되지 않은 항목은 `입력에 없음`으로 표시한다”는 지침은 기대 동작 항목에서 확인된다. 버전 등을 묻는 문장은 확인된 사실이 아니라 다음에 수집할 정보다.

**검토 결론:** 입력의 네 가지 사실은 초안에 남고, 기대 동작·버전·로그인 방식은 미확인 정보로 구분됐다.

### 이름 없이 보낸 요청

같은 실습 폴더의 새 작업에서 Skill 이름을 뺀 요청을 보냈다.

```text
다음 제보를 개발자에게 전달할 이슈로 정리해 주세요.

Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.
```

이 요청의 응답과 Skill 선택 결과는 Day 3의 정상 사례에 있다.

## Day 2 — 생성된 Skill의 구조 분석

초기 생성본과 제목을 추가한 버전의 구성은 다음과 같다.

- `SKILL.md` 한 파일에 메타데이터·정리 원칙·제목 작성·출력 형식이 들어 있다. 별도 참고 자료·템플릿·실행 스크립트는 없다.
- `name`·`description`은 이름과 적용 범위를 설명하고, 본문은 선택한 뒤 수행할 방법을 정한다.
- 정리 원칙은 사실·추정·순서·누락 정보를 처리하고, 제목 절은 대상·증상 또는 미확인 상태를 표현한다.
- 출력 틀은 배치를 제공하며, 특정 제보의 내용을 미리 채운 결과와 구분된다.
- 정보 부족·장바구니 출력의 각 항목을 관련 원문과 대조해 규칙과 실제 결과를 연결했다.
- 질문의 위치를 옮기려면 출력 틀뿐 아니라 정리 원칙의 ‘마지막 항목’도 함께 고쳐야 한다. 이 위치 변경은 예상으로 분석했고, 실제 수정은 제목 추가였다.

## Day 3 — 정상·비발동·정보 부족 요청 확인하기

### 비교할 요청

정상 제보·일반 개념 질문·정보 부족 제보를 각각 새 작업에서 보냈다. 세 요청 모두 Skill 이름을 지정하지 않았다.

### 1. 정상 요청

**요청**

```text
다음 제보를 개발자에게 전달할 이슈로 정리해 주세요.

Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.
```

**응답 시작 문장**

> `issue-summary` 스킬을 사용해 확인된 증상과 추가 확인이 필요한 정보를 나눠 정리하겠습니다.

**실제 응답**

```markdown
**증상**

- Android 앱에서 로그인 버튼을 누르면 로딩이 계속됨.
- 어제까지는 로그인할 수 있었음.
- 앱을 다시 켜도 같은 증상이 나타남.
- 웹에서는 로그인됨.

**재현 순서**

1. Android 앱에서 로그인 버튼을 누름 → 로딩이 계속됨.
2. 앱을 다시 켬 → 같은 증상이 나타남.

**기대 동작**

입력에 없음.

**확인이 필요한 정보**

- 앱 이름·버전, 기기 모델과 Android 버전은 무엇인가요?
- 로딩 상태에서 얼마나 기다렸으며, 오류 메시지가 표시되나요?
- 정상일 때 로그인 버튼을 누르면 어떤 화면으로 이동하나요?
```

**검토**

- 로그인 로딩 지속, 어제까지 정상, 앱 재실행 후 동일, 웹 로그인 가능이라는 사실을 보존했다.
- 서버 장애 등 원인을 단정하거나 앱·운영체제 버전을 만들어 내지 않았다.
- 기대 동작은 입력에 없는 정보로 표시하고, 필요한 환경 정보와 정상 동작을 질문했다.
- **출력 품질: 수용.**

### 2. 비발동 요청

**요청**

```text
HTTP 404가 무엇인지 설명해주세요.
```

**실제 응답**

```markdown
**HTTP 404(Not Found)**는 서버가 요청한 페이지나 파일을 찾지 못했을 때 보내는 응답 상태 코드입니다. 서버와 통신은 됐지만, 요청한 주소에 해당하는 내용을 찾을 수 없다는 뜻입니다.

예를 들어 `example.com/about`에 접속했는데 해당 페이지가 없다면 서버가 404를 반환할 수 있습니다.

주로 다음과 같은 경우에 발생합니다.

- URL을 잘못 입력한 경우
- 페이지나 파일이 삭제되거나 주소가 바뀐 경우
- 서버에서 주소와 페이지를 연결하는 설정이 잘못된 경우

방문자라면 **주소의 오타를 확인하거나 사이트의 홈·검색에서 페이지를 다시 찾아보세요.** 개발자라면 요청 URL, 파일 위치, 경로 연결 설정을 확인하면 됩니다.
```

**당시 관찰**

> 스킬은 사용하지 않았네요.

**검토**

- HTTP 404에 대한 일반적인 개념 설명으로 답했다.
- 증상·재현 순서·기대 동작·확인 정보라는 버그 제보 양식을 적용하지 않았다.
- **출력 품질: 수용.**

### 3. 정보 부족 요청

**요청**

```text
앱이 안 돼요. 이슈로 정리해 주세요.
```

**응답 시작 문장**

> `issue-summary` 스킬을 사용해 이슈 초안을 정리하겠습니다. 지금 확인된 내용은 “앱이 안 된다”는 증상뿐이라, 구체적인 증상과 재현 방법은 확인이 필요한 항목으로 남기겠습니다.

**실제 응답**

```markdown
**증상:** “앱이 안 돼요.”라는 제보. 구체적인 증상은 입력에 없음.

**재현 순서:** 입력에 없음.

**기대 동작:** 입력에 없음.

**확인이 필요한 정보:**

- 어떤 앱이며, 어떤 기기·운영체제에서 사용 중인가요?
- 어떤 조작을 했을 때 문제가 발생하며, 화면 반응이나 오류 메시지는 무엇인가요?
- 해당 조작을 하면 원래 어떤 결과가 나와야 하나요?
```

**당시 관찰**

> 스킬 사용한거같네.

**검토**

- 확인된 사실을 “앱이 안 된다”로 제한했다.
- 앞선 정상 사례의 Android나 로그인 문제를 이번 제보에 섞지 않았다.
- 재현 순서와 기대 동작을 지어내지 않고 `입력에 없음`으로 표시했다.
- 초안을 먼저 제공한 뒤 앱·환경, 조작·증상, 기대 동작을 질문했다.
- **출력 품질: 수용.**

### 세 사례의 비교와 판단

| 사례 | 출력과 판단 | Skill 사용 근거 |
|---|---|---|
| 정상 | 사실 보존과 미확인 정보 구분 — 수용 | 이름 없는 요청에서 `.agents/skills/issue-summary/SKILL.md`를 읽은 기록이 있다. |
| 비발동 | 일반 개념 설명 — 수용 | 해당 요청의 전체 턴에 Skill 읽기나 도구 실행이 없다. |
| 정보 부족 | 사실을 추가하지 않고 초안·질문 제공 — 수용 | 이름 없는 요청에서 `.agents/skills/issue-summary/SKILL.md`를 읽은 기록이 있다. |

정상 사례는 주어진 사실을 네 항목으로 정리했고, 정보 부족 사례는 같은 형식을 사용하면서 모르는 내용을 채우지 않았다. 비발동 사례는 이슈 정리 형식 대신 개념을 설명했다. 세 응답에서 기대한 출력 차이는 확인됐다.

## Day 4 — 이슈 제목 추가와 수정 전후 확인

### 바꿀 내용과 예상

개발자가 목록에서 핵심 문제를 파악할 수 있도록, 기존 네 항목 앞에 **이슈 제목 한 줄을 추가하는 변경**을 정했다.

- 수정 대상: [issue-summary/SKILL.md](.agents/skills/issue-summary/SKILL.md)
- 변경 위치: 소개 문장, 새 `제목 작성` 절, `출력 형식` 첫 줄
- 제목에는 입력에 명시된 대상과 증상만 사용한다.
- 상세 증상이 없으면 `상세 증상 미확인`을 표시한다.

수정 전에는 결과가 `증상`부터 시작했다. 수정 후에는 정상 제보에 로그인 로딩 문제를 요약한 제목이, 정보 부족 제보에는 상세 증상이 미확인이라는 제목이 붙을 것으로 예상했다.

### 변경한 지침

변경한 곳은 소개 문장·제목 작성 절·출력 첫 줄이다. 소개 문장의 수정 전후는 다음과 같다.

```diff
-제공된 버그 제보를 아래 네 항목으로 간결하게 정리한다.
+제공된 버그 제보를 한 줄의 이슈 제목과 아래 네 항목으로 간결하게 정리한다.
```

추가된 `제목 작성` 절에는 다음 규칙이 있다.

> 입력에 명시된 대상과 증상만으로 핵심 문제가 드러나는 짧은 제목 한 줄을 쓴다. 원인이나 입력에 없는 정보를 덧붙이지 않으며, 기존 사실 보존 규칙을 제목에도 적용한다.

> 증상이 모호하거나 없으면 제목에 `상세 증상 미확인`을 명시한다.

출력 형식의 첫 줄에는 `이슈 제목: 한 줄 제목`이 추가됐다. 제목 작성 규칙은 제목에 담을 정보의 범위를 정하고, 출력 형식은 그 제목이 놓일 위치를 정한다.

### 정상 제보 재확인

제목 추가 후 같은 실습 폴더의 새 작업에서 보낸 요청이다.

```text
$issue-summary를 사용해 다음 제보를 정리해 주세요.
Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.
```

**실제 제목**

> 이슈 제목: Android 앱에서 로그인 버튼을 누르면 로딩이 계속됨

본문은 기존 네 항목으로 나왔다. 로그인 버튼을 누르면 로딩이 계속되고, 어제까지는 로그인할 수 있었으며, 앱을 다시 켜도 동일하고 웹에서는 로그인된다는 사실이 유지됐다. 기대 동작은 `입력에 없음`으로 표시됐다.

| 확인 항목 | 예상과 실제의 대조 |
|---|---|
| 제목 추가 | 출력 맨 앞에 한 줄 제목이 실제로 추가됐다. |
| 제목의 사실 보존 | Android 앱·로그인 버튼·로딩 지속만 사용했고 원인을 추가하지 않았다. |
| 기존 내용 유지 | 네 항목과 주요 사실, 미확인 정보 구분이 유지됐다. |
| 질문의 변화 | 대기 시간·오류 메시지 대신 로그인 방식을 묻는 등 질문 구성이 달라졌다. 질문 목록을 고정하도록 지시한 것은 아니며, 모두 입력에 없는 정보를 묻는 질문이다. |

**검토 판단: 수용.** 제목의 문구가 예상 예시와 완전히 같지는 않아도, 의도한 의미와 위치가 확인됐다.

### 정보 부족 제보 재확인

```text
$issue-summary를 사용해 다음 제보를 정리해 주세요.
앱이 안 돼요.
```

**실제 응답**

```markdown
이슈 제목: 앱 — 상세 증상 미확인

### 증상

“앱이 안 돼요.”라고 제보됨. 상세 증상은 미확인.

### 재현 순서

입력에 없음

### 기대 동작

입력에 없음

### 확인이 필요한 정보

- 어떤 앱인가요?
- 문제가 발생하기까지 어떤 행동을 어떤 순서로 했나요?
- 실제로 어떤 현상이 나타나나요? 오류 메시지가 있다면 알려 주세요.
- 기대했던 정상 동작은 무엇인가요?
```

**검토 판단: 수용.** 제목에 입력의 대상인 앱과 `상세 증상 미확인`이 표시됐다. Android·로그인 등의 정보를 추가하지 않았고, 재현 순서·기대 동작을 미확인으로 남긴 뒤 필요한 질문을 제공했다.

**Day 4 결과:** 로그인 제보에는 대상·증상을 요약한 제목이, 정보 부족 제보에는 `앱 — 상세 증상 미확인`이라는 제목이 추가됐다.

## Day 5 — 새 장바구니 제보에 재사용하기

### 새 제보에 보낸 요청

제목 수정에 사용하지 않은 장바구니 제보를 같은 실습 폴더의 새 작업에서 명시 호출했다.

```text
$issue-summary를 사용해 다음 제보를 정리해 주세요.
상품을 장바구니에서 삭제하면 합계가 그대로예요.
화면을 새로 열면 합계가 맞습니다.
```

### 실제 응답

```markdown
이슈 제목: 장바구니에서 상품 삭제 후 합계가 그대로 표시됨

### 증상

상품을 장바구니에서 삭제하면 합계가 그대로이며, 화면을 새로 열면 합계가 맞게 표시됨.

### 재현 순서

1. 장바구니에서 상품을 삭제한다.
2. 화면을 새로 연다.

### 기대 동작

입력에 없음.

### 확인이 필요한 정보

- 상품 삭제 후 합계가 어떻게 바뀌기를 기대하나요?
- “화면을 새로 연다”는 구체적으로 어떤 동작인가요?
```

### 원문과 결과의 대조

| 확인 항목 | 실제 결과와 판단 |
|---|---|
| 수정 의도 유지 | 맨 앞에 새 제보의 핵심을 요약한 제목이 있다. |
| 사실 보존 | 상품 삭제 후 합계가 그대로라는 증상과, 화면을 새로 열면 합계가 맞는다는 사실을 모두 보존했다. |
| 원인 추측 방지 | 캐시 문제 등 확인되지 않은 원인을 단정하지 않았다. |
| 재현 순서 | 입력에 명시된 두 행동만 적었고, “화면을 새로 연다”의 구체적인 의미는 질문했다. |
| 기대 동작 구분 | 상품 삭제 후 합계가 즉시 달라져야 한다고 추론할 수는 있지만, 제보자가 명시한 기대 동작은 없어 미확인으로 남겼다. |

**검토 판단: 수용.** 제목에 상품 삭제 후 합계가 그대로인 문제가 드러났고, 화면을 새로 열면 합계가 맞는다는 관찰과 추가 질문도 함께 남았다.

자동 선택 사례는 제목 추가 전 버전이며, 제목 추가 후의 로그인·정보 부족·장바구니 사례는 명시 호출 결과다.


## 개편된 Day 4 — 다중 제보의 중복·출처·관찰 차이 처리

재실습일: 2026-09-09

다중 제보 규칙은 앞선 수정에서 이미 추가돼 있다. 이번에는 제목 추가까지만 포함된 수정 전 버전과 현재 수정본에 같은 제보를 보내 결과를 다시 비교했다. 아래 요청과 응답은 이번 재실습의 실제 내용이다.

### 비교할 Skill과 기존 변경

수정 전 대상은 Git에 보관된 단일 제보용 Skill의 임시 사본이다. 현재 대상은 [.agents/skills/issue-summary/SKILL.md](.agents/skills/issue-summary/SKILL.md)다. 임시 경로는 아래 요청을 보낼 당시의 위치다. 두 버전을 각각 별도 대화에서 한 번씩 사용했다.

| 위치 | 앞선 수정에서 추가한 내용 |
|---|---|
| `description` | 한 건·여러 건의 제보 정리를 적용 범위에 명시하고 중복·출처·관찰 차이 보존을 설명했다. |
| 본문 소개 | 여러 제보의 공통 사실을 묶되 각 사실의 출처와 차이를 남기도록 연결했다. |
| `여러 제보를 함께 정리할 때` 절 | 출처 ID, 공통·개별 사실, 다른 관찰, 재현 순서, 정보 부족·확인 질문과 원문 대조를 처리하는 규칙을 추가했다. |

단일·다중 제보는 사실을 이슈 초안으로 정리하는 목적과 공통 규칙을 공유한다. 다중 입력의 처리 기준을 기존 `SKILL.md`에 함께 두면 공통 규칙을 한곳에서 관리할 수 있어 한 파일 구성을 선택했다.

공통 사실을 묶는 기준은 다음 원문에 들어 있다.

> 공통 문장 옆에 해당 사실을 뒷받침하는 모든 제보 ID를 붙인다. 일부 제보에만 있는 행동·조건은 그 출처만 붙여 별도로 남긴다.

R-01·R-02의 로그인 관련 로딩 지속과 재시작 후 동일한 현상은 함께 설명할 수 있다. 버튼을 눌렀다는 행동은 R-01에만 있으므로 그 출처로 구분해야 한다. R-03의 웹·새로고침 결과와 R-04의 재시도 성공도 각각의 관찰로 남겨야 한다. 같은 환경·시점이라는 근거가 없어 이 차이만으로 같은 장애나 직접적인 모순이라고 확정할 수는 없다.

이번 비교에서 예상한 결과는 현재 수정본이 공통 설명을 줄이면서 각 제보의 행동과 다른 관찰을 되짚을 수 있는 출력이다.

| 개별 행동 | 현재 수정본의 재현 순서에서 버튼 조작은 R-01에 연결됐다. R-02에는 재시작 행동과 최초 행동 미확인이 기록돼 있다. 공통 증상을 묶어도 서로 다른 행동을 같은 순서로 합치지 않았다. |
| 플랫폼·관찰 차이 | 두 버전 모두 R-03의 웹·새로고침 후 로그인과 R-04의 한 번 실패 후 성공을 보존했다. 현재 수정본에서도 각각의 출처로 구분돼 있다. |
| 버전 미확인 | 두 응답 모두 R-04의 버전을 모른다는 내용을 남겼다. 이번 재실습에서 버전 표현이 개선됐다고 판단할 차이는 없었다. |
| 확인 질문 | 수정 전에는 앱·Android 버전을 각 이슈에서 따로 물었다. 현재 수정본은 `[R-01, R-02] 각각의 Android 버전과 앱 버전`으로 묶었다. 공통 질문을 사용하면서 두 제보의 버전이 같다고 가정하지 않았다. |
| 기대 동작 | 두 버전 모두 `입력에 없음`으로 작성했다. 재시도·새로고침 후 성공이라는 관찰과 제보자가 명시한 기대 동작을 구분한 결과다. |

현재 수정본은 R-01·R-02의 공통 설명과 질문을 묶고, 네 제보의 출처·개별 행동·관찰 차이를 확인할 수 있는 결과를 냈다.


## 개편된 Day 5 — 새 제보 묶음과 기존 요청에 재사용

실습일: 2026-09-09

Day 4에서 다중 제보 규칙을 추가한 [issue-summary](.agents/skills/issue-summary/SKILL.md)에 새 장바구니 제보 묶음과 기존 단일 제보를 명시 호출했다. 적용 제외 사례는 Skill 이름 없이 HTTP 404의 의미를 물었다. 세 요청은 모두 `week02-codex-skills/`를 실행 위치로 삼은 각각의 새 대화에서 사용했다.

### 새 제보 묶음

**보낸 요청**

```text
$issue-summary로 다음 제보를 정리해 주세요.

[S-01] 웹 장바구니에서 상품을 삭제해도 합계가 그대로입니다. 새로고침하면 맞습니다.
[S-02] 웹 장바구니 합계가 상품 삭제 뒤 바뀌지 않습니다. 새로고침하면 맞습니다.
[S-03] Android 앱 장바구니에서는 삭제하자마자 합계가 맞았습니다.
[S-04] 합계가 이상합니다. 어떤 화면이었는지는 기억나지 않습니다.
```

**받은 최종 답변**

```markdown
이슈 제목: 웹 장바구니에서 상품 삭제 후 합계가 갱신되지 않음 [S-01][S-02]

### 증상

- [S-01][S-02] 웹 장바구니에서 상품을 삭제해도 합계가 그대로이며, 새로고침하면 올바르게 표시됨.
- [S-03] Android 앱 장바구니에서는 삭제 직후 합계가 올바르게 표시됨.
- [S-04] “합계가 이상합니다.”라는 제보이며, 어떤 화면이었는지는 기억하지 못함. 환경·상세 증상과 위 제보와의 관련성은 미확인.

### 재현 순서

[S-01][S-02]

1. 웹 장바구니에서 상품을 삭제한다. 합계가 바뀌지 않는다.
2. 새로고침한다. 합계가 올바르게 표시된다.

[S-03]

1. Android 앱 장바구니에서 삭제한다. 즉시 합계가 올바르게 표시된다.

[S-04] 입력에 없음.

### 기대 동작

입력에 없음. [S-03]은 기대 동작이 아닌 실제 정상 동작 관찰임.

### 확인이 필요한 정보

- [S-01][S-02] 발생한 브라우저와 버전은 무엇인가요?
- [S-04] 합계가 구체적으로 어떻게 이상했나요? 사용 환경이나 직전 행동 중 기억나는 정보가 있나요?
```

**원문과 결과의 대조**

| 원문에서 구별할 내용 | 실제 결과와 판단 |
|---|---|
| S-01·S-02의 중복 | 웹 장바구니에서 삭제 후 합계가 그대로이고 새로고침하면 맞는다는 공통 설명을 한 문장으로 묶었다. 문장과 재현 순서에 `[S-01][S-02]`가 함께 남아 두 원문을 되짚을 수 있다. |
| S-03의 플랫폼·관찰 차이 | Android 앱에서 삭제 직후 합계가 맞았다는 관찰을 별도 줄과 재현 순서로 남겼다. 웹의 갱신 실패를 Android에서도 발생한 일로 바꾸지 않았다. |
| S-04의 정보 부족 | 합계가 이상하다는 말과 화면을 기억하지 못한다는 내용을 남겼다. 장바구니·웹·Android 중 어느 것에도 배정하지 않고, 다른 제보와의 관련성도 미확인으로 표시했다. |
| 기대 동작과 실제 관찰 | S-03의 정상 관찰을 다른 제보의 기대 동작으로 옮기지 않았다. 기대 동작은 `입력에 없음`으로 구분했다. |
| 확인 질문 | S-01·S-02에는 브라우저와 버전을 묻고, S-04에는 구체적인 이상 현상과 기억나는 환경·직전 행동을 물었다. 질문마다 대상 제보를 구별할 수 있다. |

새 입력에서도 반복 설명을 줄이면서 네 제보의 출처와 관찰 차이를 보존했다. S-04의 정보가 적어도 나머지 제보의 초안을 먼저 제공하고, 부족한 부분은 해당 제보의 질문으로 남겼다.

### 기존 단일 제보

**보낸 요청**

```text
$issue-summary로 다음 제보를 정리해 주세요.
상품을 장바구니에서 삭제하면 합계가 그대로예요.
화면을 새로 열면 합계가 맞습니다.
```

**받은 최종 답변**

```markdown
이슈 제목: 장바구니에서 상품 삭제 후 합계가 그대로 표시됨

### 증상

- 상품을 장바구니에서 삭제해도 합계가 그대로임.
- 화면을 새로 열면 합계가 맞게 표시됨.

### 재현 순서

1. 장바구니에서 상품을 삭제한다.
2. 화면을 새로 연다.

### 기대 동작

입력에 없음.

### 확인이 필요한 정보

- 어떤 서비스와 사용 환경(앱 또는 웹, 기기·버전)에서 발생했나요?
- “화면을 새로 연다”는 구체적으로 어떤 동작인가요?
- 상품 삭제 직후 합계가 어떻게 표시되기를 기대하나요?
```

상품 삭제 뒤 합계가 그대로인 현상과 화면을 새로 열면 맞는다는 관찰이 모두 남았다. 재현 순서도 입력의 두 행동으로 구성됐다. 다중 입력의 “새로고침”을 가져와 단일 제보의 “화면을 새로 연다”를 같은 행동으로 확정하지 않고, 그 의미를 확인 질문으로 남겼다.

제목과 네 항목을 바로 작성했으며 제보 ID나 추가 제보를 요구하지 않았다. 사용 환경과 기대 동작은 원문에 없으므로 질문으로 구분했다.

### 적용 제외 요청

**보낸 요청**

```text
HTTP 404가 무엇인지 설명해 주세요.
```

**받은 최종 답변**

```markdown
**HTTP 404(Not Found)**는 서버가 요청한 주소에 해당하는 페이지나 파일을 찾을 수 없다는 뜻의 **HTTP 상태 코드**입니다. HTTP 상태 코드는 서버가 요청을 처리한 결과를 숫자로 알려 주는 방식입니다.

예를 들어 `https://example.com/posts/123`에 접속했는데 해당 게시글이 없으면 서버가 `404 Not Found`를 반환할 수 있습니다.

주요 원인은 다음과 같습니다.

- **주소 오타**: URL 경로를 잘못 입력한 경우
- **페이지 삭제·이동**: 예전 링크가 더 이상 유효하지 않은 경우
- **서버 설정 문제**: 해당 주소를 처리하도록 연결해 두지 않은 경우

방문자라면 주소를 확인하거나 사이트의 홈·검색에서 페이지를 다시 찾아보세요. 개발자라면 요청 URL, 경로 연결 설정(라우팅), 해당 자료의 존재 여부를 확인하면 됩니다.
```

이 응답은 404의 의미·예시·가능한 원인을 설명했다. 이슈 초안의 제목·증상·재현 순서 형식을 적용하지 않았다. 이 요청의 전체 실행에는 도구 호출이 없어 `issue-summary/SKILL.md` 읽기도 없었다. 같은 폴더에서 실행한 앞의 두 정리 요청에는 해당 파일을 읽은 기록이 있다. 출력 모양과 실제 읽기 여부가 모두 이번 개념 질문의 비발동과 맞는다.

### 결과를 Skill의 구조와 연결하기

`description`은 한 건·여러 건의 버그 제보 정리를 적용 대상으로 설명하고 일반 개념 질문을 제외한다. 두 정리 요청의 Skill 읽기와 404 질문의 비발동은 이 적용 범위에 맞는 결과다.

본문의 `여러 제보를 함께 정리할 때` 절은 공통 사실에 모든 출처를 붙이고, 다른 관찰과 빠진 정보를 분리하도록 정한다. S-01·S-02의 묶음, S-03의 별도 정상 관찰, S-04의 미확인 처리가 각각 그 규칙에 대응한다. `정리 원칙`의 사실 보존·누락 정보 처리와 `제목 작성`·`출력 형식`은 단일 제보에도 적용됐다.

공통 규칙과 다중 제보 규칙을 한 파일에 둔 구성이 두 종류의 입력을 처리했다. 이번 세 결과에서 추가로 고칠 문제는 발견되지 않아 Skill의 변경은 없다. 다음 요구에서 적용할 작업 종류가 달라지면 `description`을, 제보를 묶는 기준이 달라지면 `여러 제보를 함께 정리할 때` 절을, 결과 항목이 달라지면 `출력 형식`을 먼저 살펴볼 수 있다.
