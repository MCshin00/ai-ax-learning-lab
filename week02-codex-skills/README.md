# 2주차 — Skill Creator로 만들고 사용하며 고치기

> 이 README가 이번 주차의 상세 학습 본문입니다. 루트 `CURRENT_WEEK.md`는 여기로 돌아오는 짧은 대시보드입니다.

- 기본 작업 폴더: [`lab`](lab/)
- 전체 과정: [루트 README](../README.md)
- 현재 위치와 다음 명령: [CURRENT_WEEK](../CURRENT_WEEK.md)


이번 주에는 Skill의 역할을 이해하고 Skill Creator로 익숙한 작업의 초안을 만들어 사용합니다. 기본 예제는 버그 제보를 개발자가 읽기 쉬운 요약으로 바꾸는 `issue-summary`입니다. 이미 잘 아는 다른 반복 작업으로 바꿔도 됩니다. 좋은 결과를 알아볼 수 있는 일이 첫 Skill에 적합합니다.

## 시작 전에 알아둘 개념

**Skill은 특정 작업에 반복해서 사용할 지침과 필요한 자료를 묶은 폴더**입니다. 예를 들어 이슈 정리에 매번 요구하는 항목과 사실 확인 규칙을 저장해 두면 새 제보에도 다시 사용할 수 있습니다. 한 번의 프롬프트가 이번 요청을 전달한다면, Skill은 같은 종류의 요청에 재사용할 방법을 담습니다.

**Skill Creator는 Skill의 생성·수정을 돕는 기본 제공 Skill**입니다. Codex에 `$skill-creator`와 함께 원하는 작업을 설명하면 지침 초안과 필요한 파일을 만드는 데 도움을 받을 수 있습니다. 학습자는 제안한 범위와 실제 결과를 검토합니다. Creator로 만들었다고 원하는 결과가 보장되는 것은 아닙니다.

중심 파일인 `SKILL.md`에는 이름, 적용 상황을 설명하는 `description`, 수행 지침이 있습니다. 이름을 지정하는 **명시 호출**과 요청에 맞는 Skill을 Codex가 고르는 **자동 선택**을 구분합니다. 일반 질문에까지 자동 선택되거나 필요한 작업에서 빠지는 문제는 적용 설명과 실제 선택 기록을 함께 봅니다. [공식 Skill 안내](https://learn.chatgpt.com/ko-KR/docs/build-skills)

### Day 1 — Creator로 만들고 처음 호출하기

Codex 앱이나 IDE에서 `week02-codex-skills/lab/`를 작업 폴더로 엽니다. CLI를 사용한다면 학습 저장소 루트에서 다음과 같이 시작합니다.

```text
codex -C ./week02-codex-skills/lab
```

Skill 목록에서 Skill Creator를 선택하거나 아래 요청을 직접 보냅니다. CLI·IDE에서는 `$skill-creator`로 지정할 수 있습니다. 목록에 없다면 현재 설치의 Skill 목록과 공식 안내를 확인하고, 생성이 가능해진 뒤 이어갑니다. 이름을 적었다는 사실만으로 실제 사용했다고 판단하지 않습니다.

```text
$skill-creator를 사용해 issue-summary Skill을 만들어 주세요.
위치는 현재 폴더의 .agents/skills/issue-summary/입니다.
버그 제보를 증상, 재현 순서, 기대 동작, 확인이 필요한 정보로 정리하고 싶습니다.
입력에 없는 원인·버전·재현 단계를 지어내지 않아야 합니다.
단순 번역이나 일반적인 개념 질문에는 자동으로 선택되지 않게 해 주세요.
먼저 지침만 있는 작은 Skill로 만들어 주세요. 내가 검토할 대표 결과도 보여 주세요.
```

Creator의 질문에 답하거나 제안한 범위를 수정합니다. 기준 문장과 구조를 미리 혼자 작성할 필요는 없습니다. 생성된 Skill의 위치와 이름을 확인한 뒤 **새 작업**에서 호출합니다.

```text
$issue-summary를 사용해 다음 제보를 정리해 주세요.
Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.
```

입력에 있던 사실과 아직 모르는 정보를 구분했는지 봅니다. 원인을 서버 장애라고 단정했다면 그 부분이 수정할 대상입니다. Skill이 발견되지 않으면 CWD와 `.agents/skills/` 위치를 확인하고, 변경이 표시되지 않으면 새 작업 또는 앱 재시작으로 다시 확인합니다.

### Day 2 — Skill의 구성과 설계 이유 살펴보기

이 단계의 해설은 Creator로 만든 파일을 이해하는 기준입니다. 기존 Skill을 분석해 아래 관계를 이미 설명할 수 있다면 그 학습을 인정하고, 새 Skill의 실제 출력과 연결할 부분만 확인해도 됩니다. 분석을 다시 수행하거나 같은 내용의 글을 새로 쓸 필요는 없습니다.

Day 1에서 사용한 Skill 폴더를 IDE 탐색기로 열고 실제로 생성된 파일을 봅니다. 구조 확인은 이번 주의 기본 실습입니다. 다음 표와 대조하되 선택 파일이 없는 것은 정상입니다.

| 파일·폴더 | 역할 |
|---|---|
| `SKILL.md` | 이름·적용 설명과 작업 지침. 필수 파일 |
| `assets/` | 결과를 만들 때 쓸 템플릿 등. 필요한 경우에만 포함 |
| `references/` | 작업 중 참고할 상세 자료. 필요한 경우에만 포함 |
| `scripts/` | 반복 실행할 코드. 필요한 경우에만 포함 |
| `agents/openai.yaml` | 화면 표시나 호출 정책 등의 설정. 있을 때 역할 확인 |

`SKILL.md` 위쪽의 `---` 사이가 YAML 메타데이터이고 `name`과 `description`이 있습니다. 그 아래 Markdown 본문은 실제 수행 지침입니다. Codex는 선택할 때 이름·설명을 참고하고, Skill을 사용할 때 본문의 지침을 읽습니다. 부속 자료는 필요한 작업에서 읽거나 실행합니다.

#### 해설 — 적용 설명과 수행 지침을 따로 두는 이유

여러 Skill 중 이번 요청에 쓸 것을 고를 때는 각 Skill의 긴 절차를 모두 읽기보다 이름과 적용 설명으로 먼저 범위를 좁힙니다. 선택한 뒤에는 본문을 읽고 작업에 필요한 자료를 따라갑니다. 이런 단계적 읽기 방식 때문에 `description`은 “언제 쓸 것인가”, 본문은 “사용할 때 무엇을 할 것인가”를 맡습니다. 이는 공식 문서가 설명하는 점진적 공개 방식입니다. [OpenAI Skill 구성과 사용 방식](https://learn.chatgpt.com/ko-KR/docs/build-skills)

예를 들어 이슈 요약 Skill의 설명이 “개발 관련 요청을 처리한다”라면 “버그 제보를 정리해 줘”와 “HTTP 404를 설명해 줘”를 구분하기 어렵습니다. “버그 제보를 이슈 초안으로 정리한다”는 설명에는 대상과 작업이 함께 드러납니다. 반대로 “Android 로그인 제보만 정리한다”로 한정하면 다른 앱의 장바구니 제보를 처리할 수 있어도 선택 범위에서 빠질 수 있습니다. 이들은 설명 문구로부터 예상하는 선택 문제이며, 실제 누락이나 오선택은 Day 3에서 관찰해야 합니다.

본문에 비발동 조건을 적으면 선택 후 작업 범위를 판단하는 데 도움이 됩니다. 선택 단계부터 구분해야 할 중요한 경계는 적용 설명에도 나타나야 합니다. 단, 경계를 문장으로 적었다고 잘못된 실행을 항상 막는 것은 아닙니다. 선택을 돕는 설명, 선택 후의 지침 준수, 실제 결과 품질은 각각 확인할 대상입니다.

#### 해설 — 같은 제보가 지침·참고 자료·템플릿을 거치는 과정

`practice/skill-example/issue-brief-example/`은 역할을 나눠 보여 주는 작은 비교 자료입니다. 아래는 그 파일에 적힌 지침을 제보에 적용해 설명한 흐름입니다. 경로로 읽어 사용하는 이 자료는 자동 선택 위치에 설치된 Skill이 아닙니다.

```text
제보: Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다.
      어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다.

SKILL.md: 관찰된 증상·행동·환경을 구분하고 입력에 없는 원인을 만들지 않음
references/writing-rules.md: 미확인 버전과 상대 날짜의 처리 규칙 확인
assets/issue-template.md: 증상 → 재현 정보 → 환경 → 확인할 질문의 형식 제공
이번 출력: Android 앱의 로그인 버튼 뒤 로딩 지속, 재시도 결과, 미확인 환경과 질문
```

본문에는 정보 누락·불일치·상대 날짜가 있을 때 작성 규칙을 읽도록 연결돼 있습니다. 이 입력에서는 앱 버전이 없고 “어제”가 있으므로 그 자료를 읽을 이유가 있습니다. 제보 시점이 없는데 오늘을 기준으로 날짜를 계산하면 원문에 없는 사실을 더하게 됩니다. 그래서 규칙은 상대 표현임을 유지하게 합니다. 환경에는 이미 주어진 Android 정보를 쓰고, 버전 등 빠진 내용은 미확인으로 남깁니다.

템플릿은 이 판단을 대신하지 않습니다. `## 환경`이라는 제목만으로 어떤 버전이 사실인지 알 수 없고, “미확인 정보를 지어내지 말라”는 지침만으로 출력 항목의 순서가 고정되지는 않습니다. 지침은 판단 방법, 템플릿은 반복할 형식, 이번 출력은 특정 제보에 대한 결과를 맡습니다.

따라서 환경을 맨 위에 보이게 하려면 템플릿의 순서를 바꾸는 것이 직접적입니다. 버전이 없을 때마다 임의의 최신 버전을 쓰는 문제가 있다면 판단 지침과 작성 규칙을 먼저 봅니다. 실제 수정은 Creator에게 맡겨도 되며, 이렇게 수정 이유를 구분할 수 있으면 생성된 변경을 검토할 기준이 생깁니다.

#### 해설 — 파일을 나누는 효과와 스크립트가 필요한 경계

이 예제 정도의 내용은 한 파일에 넣어도 됩니다. 분리하면 출력 형식만 고칠 때 템플릿을, 특별한 입력 처리만 고칠 때 참고 규칙을 찾기 쉽습니다. 필요한 규칙을 조건에 맞춰 읽게 할 수도 있습니다. 대신 파일 사이의 연결을 유지해야 하고, 같은 규칙을 여러 곳에 중복하면 수정 후 내용이 어긋날 수 있습니다. 폴더가 많다는 사실 자체가 품질의 근거가 되지는 않습니다.

스크립트도 특정한 일이 있을 때 추가합니다. “결과에 정해진 항목이 모두 있는가”는 명시적인 규칙으로 검사할 수 있습니다. 반면 “제보의 뜻을 유지했는가”, “다음 확인에 유용한 질문인가”는 원문과 문맥을 해석해야 합니다. 검사 코드가 모든 항목의 존재를 확인해도, 항목 안에 지어낸 원인이 들어 있는 문제까지 자동으로 판정했다고 볼 수 없습니다.

현재 이슈 초안은 모델 지침과 사람이 결과를 읽는 방식으로 시작하기에 충분합니다. 같은 형식 검사를 자주 반복해야 할 때 검사 도구를 쓸 이유가 생깁니다. 이 설명을 이해하기 위해 검사기를 직접 구현할 필요는 없습니다. 필요한 경우 기존 도구나 Creator가 제안한 코드를 사용하되, 무엇을 검사하고 무엇은 검사하지 않는지 확인합니다.

#### 해설 — 관찰한 사실에서 어디까지 결론 낼 수 있는가

Skill의 이름을 지정해 좋은 결과를 얻었다면 그 요청에서 명시 호출과 출력 품질을 확인한 것입니다. 같은 요청에 이름을 빼도 자동 선택될지는 별도 확인이 필요합니다. 또 Skill을 읽은 기록이 있어도 사실을 지어냈다면 선택은 됐지만 결과는 수용할 수 없습니다. 반대로 출력이 좋아 보여도 선택 기록이 없다면 어느 Skill 덕분인지 단정할 수 없습니다.

분석 글에서도 이 구분을 유지합니다. “본문에는 제보 정리 절차가 있는데 설명은 특정 앱으로 한정돼 있다”는 파일에서 확인한 사실입니다. “다른 앱 제보에서 선택되지 않을 수 있다”는 그 사실에 근거한 가설입니다. “해당 요청에서 선택되지 않았다”는 실행 기록이 있어야 하는 관찰입니다. 구조를 읽어 얻은 통찰과 실제 검증을 연결하되, 하지 않은 실험을 근거로 쓰지 않습니다.

`../prompts/skill-audit.md`로 설명을 요청해도 됩니다. 자신의 파일에서 `name`, `description`, 본문 지침을 찾아 Day 1의 요청이 결과로 이어지는 경로를 따라갑니다. 본문이 부속 파일을 가리킨다면 언제 읽거나 실행하는지 확인하고 템플릿이 있다면 빈 형식과 채워진 결과를 비교합니다.

| 대상 | 역할 | 이슈 요약 예 |
|---|---|---|
| `SKILL.md` | 반복 작업의 지침 | 입력에 없는 원인을 지어내지 않는다 |
| 템플릿이 있다면 | 매번 사용할 빈 출력 형식 | 증상 / 재현 순서 / 기대 동작 / 미확인 정보 |
| 이번 출력 | 특정 요청을 처리한 결과 | Android 로그인에서 로딩이 끝나지 않음 |

다음 질문을 자신의 Skill에 연결해 봅니다.

- 적용 상황은 왜 `description`에서 설명하고 작업 순서는 본문에 두는가?
- 본문에 있는 내용과 템플릿·참고 자료로 나뉜 내용은 각각 어떤 필요를 해결하는가? 합쳤을 때와 나눴을 때 수정할 곳은 어떻게 달라지는가?
- 요청에 없던 원인을 만들어 내는 문제와 제목 형식을 바꾸는 요구는 각각 어디를 고쳐야 하는가?

생성된 Skill이 지침만 있어 구성 차이를 보기 어렵다면 `practice/skill-example/study-example.md`와 그 옆 `issue-brief-example/`을 엽니다. 이 작은 비교 예제에는 작업 순서를 담은 본문, 출력 형식을 담은 템플릿, 필요한 경우 읽는 작성 규칙이 있습니다. 예제의 입력과 출력으로 각 파일이 맡는 부분을 대조합니다. 실습용으로 제공한 자료이며 자동 선택 위치에 설치되지 않습니다. 경로를 지정해 읽는 것과 이름으로 자동 선택되는 것은 구분합니다.

예제를 사용할 때는 `practice/skill-example/issue-brief-example/SKILL.md`를 읽고 그 지침으로 제보를 요약해 달라고 요청할 수 있습니다. 비교를 위해 두 번째 Skill을 새로 제작하거나 기존 Skill의 모든 폴더를 복제할 필요는 없습니다. 스크립트가 없는 예제에서는 왜 모델 지침으로 충분한지도 생각해 봅니다.

읽을 파일 수를 제한하지 않고 필요한 관계를 충분히 살펴봅니다. 자료에 적힌 설계 이유와 현재 구조에서 추론한 효과를 구분하고 **각 구성의 역할·읽는 순서·원하는 동작을 바꿀 위치**를 짚을 수 있으면 Day 3으로 갑니다.

### Day 3 — 세 가지 요청으로 확인하기

각 사례는 앞선 Skill 호출이 영향을 주지 않도록 새 작업에서 보냅니다. 새 작업도 같은 `week02-codex-skills/lab/` 폴더를 선택합니다. 자동 선택을 볼 때는 Skill 이름을 빼고 요청합니다. 아래는 `issue-summary`의 예입니다. 다른 Skill을 골랐다면 그 목적에 맞는 사례를 AI와 함께 정합니다.

| 사례 | 요청 | 기대 결과 |
|---|---|---|
| 정상 | 다음 제보를 개발자에게 전달할 이슈로 정리해 줘. Android 앱에서 로그인 버튼을 누르면 로딩이 계속됩니다. 어제까지는 됐고 앱을 다시 켜도 같습니다. 웹에서는 로그인됩니다. | 사실과 미확인 정보를 구분 |
| 비발동 | HTTP 404가 무엇인지 설명해 줘 | 이슈 작성 Skill이 필요하지 않음 |
| 정보 부족 | 앱이 안 돼요. 이슈로 정리해 줘 | 아는 사실만 정리하고 필요한 질문을 남김 |

결과의 품질과 Skill 선택 여부는 따로 봅니다. 출력 모양만으로 발동을 추정하지 않고 도구가 `SKILL.md`를 읽은 기록 등 화면에 보이는 근거를 확인합니다. 근거가 보이지 않으면 선택 여부는 `NOT_VERIFIED`로 둡니다. 세 사례는 일반적인 발동 성공률을 측정하는 표본이 아닙니다.

### Day 4 — 구체적 문제를 보여 주고 수정하기

Day 3의 실제 요청·출력에서 문제 한 곳을 고릅니다. 문제가 없다면 필요한 변경 하나를 정합니다. 예를 들어 이슈 요약의 미확인 정보를 질문 형태로 바꿀 수 있습니다. Day 2에서 살펴본 본문·템플릿 중 어디를 바꿀지와 수정 후 예상 결과를 먼저 짚습니다. 아래 예시의 문제와 경로는 자신의 관찰과 선택한 Skill에 맞게 바꿉니다.

```text
$skill-creator로 .agents/skills/issue-summary/를 수정해 주세요.
이 요청과 출력에서 입력에 없던 원인을 사실처럼 쓴 부분이 문제입니다.
[실제로 보낸 요청과 문제가 있는 결과를 붙이기]
이 문제가 관련된 지침을 찾아 최소한으로 고치고 변경 이유를 설명해 주세요.
```

같은 요청으로 다시 확인하고 예상한 변화와 실제 출력을 대조합니다. 관련 없는 내용까지 바뀌었다면 어느 지침이 영향을 줬는지 다시 읽습니다. 실패가 그대로면 출력의 문제를 더 구체적으로 전달합니다. description 문제라면 발동 조건을, 출력 문제라면 절차나 템플릿을 바꿉니다.

### Day 5 — 다른 요청에 다시 사용하기

수정할 때 쓰지 않은 요청 하나를 골라 새 작업에서 선택한 Skill을 명시 호출합니다. `issue-summary`라면 `practice/issue-examples.md`의 장바구니 제보를 써도 됩니다.

새 결과에서도 입력의 사실과 미확인 정보가 구분되고 Day 4의 수정 의도가 유지되는지 확인합니다. 받아들일 부분과 남은 문제, 다시 쓸 작업을 짧게 남깁니다. 문제가 발견되면 관련 지침만 고치고 같은 요청으로 재확인합니다.

## 완료 기준

- [ ] Skill Creator로 Skill을 생성하고, 결과를 직접 검토했습니다.
- [ ] 실제 요청에 명시 호출해 결과를 확인했습니다.
- [ ] 실제 Skill의 메타데이터·본문·부속 파일 역할과 읽는 순서를 결과에 연결해 설명했습니다. 필요한 경우 작은 비교 예제를 함께 봤습니다.
- [ ] 구성을 나눈 효과를 설명하고 원하는 동작을 바꿀 위치와 예상 결과를 실제 변경 후 결과와 대조했습니다.
- [ ] 정상·비발동·정보 부족 사례를 확인하고 선택 근거가 없으면 미확인으로 남겼습니다.
- [ ] 실제 문제 또는 필요한 변경 한 곳을 수정하고 같은 요청과 새 요청에 다시 사용했습니다.

도구 안내 근거: [OpenAI의 Skill 제작·호출 안내](https://learn.chatgpt.com/docs/build-skills). Creator는 지침만 있는 Skill부터 시작할 수 있으며, 생성·명시 호출·자동 선택·수정은 서로 다른 확인 단계입니다.

## 이 폴더의 자료

- `lab/`: 시작 코드, 설정, 평가 자료와 이번 주 구현
- `prompts/`: 과정이 제공하고 `sync`가 갱신할 수 있는 요청 자료
- `runs/`: 짧은 메모와 다시 확인할 결과. 외부 공개는 선택
- `references/`: 실습 뒤 `reference` 명령으로 공개하는 비교용 참고 구현
- `.local/notes/`: 개인 메모, `.local/raw/`: 정제 전 로그, `.local/scratch/`: 임시 작업. `.local/` 전체는 Git에서 제외

`runs/`와 `lab/`은 학습자가 관리합니다. `sync`는 이 두 폴더를 덮어쓰지 않습니다.
