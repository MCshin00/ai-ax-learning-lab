# 작업 계약의 두 가지 예

작업 계약은 **다음 수행자가 할 본 작업**을 정리한 문서입니다. Skill을 채점하는 양식이 아닙니다. 빈 템플릿은 재사용하고 채운 계약은 요청마다 바꿉니다. 아래 경로·명령은 예제 프로젝트의 조건입니다. 명령은 그 프로젝트 루트에서 실행하며, macOS·Linux·WSL에서는 `python` 대신 `python3`를 사용합니다. IDE의 같은 테스트 실행 기능을 사용해도 됩니다.

## 파일을 수정하는 작업

요청: “제목 정규화에서 앞뒤·연속 공백을 처리해 줘. 이 프로젝트에는 src/title.py와 tests/test_title.py가 있고 unittest를 쓴다. 빈 값 처리와 길이 제한은 바꾸지 마.”

```markdown
# 제목 공백 정규화

## Goal
제목의 앞뒤 공백을 없애고 연속 공백을 한 칸으로 만든다.

## Context
제목 표시가 입력된 공백에 따라 들쭉날쭉하다. 기존 빈 값 처리와 길이 제한은 유지한다.

## Allowed paths
- src/title.py
- tests/test_title.py

## Forbidden changes
- 빈 값 처리, 길이 제한과 외부 의존성을 바꾸지 않는다.

## Acceptance criteria
- "  결제   오류  "를 넣으면 "결제 오류"가 나온다.
- "결제 오류"를 넣으면 그대로 나온다.
- 기존 빈 값과 길이 제한 테스트가 통과한다.

## Required verification
- `python -B -m unittest discover -s tests -v`를 실행한다.
- 두 예시 입력의 실제 출력과 변경 diff를 확인한다.

## Stop conditions
- 지정된 파일이 없거나 공백 수정이 기존 요구와 충돌하면 내용을 확인한다.

## Handoff
구현자가 공백 처리만 수정하고 변경 요약과 테스트 결과를 요청자에게 돌려준다.
검증하지 못했다면 이유와 남은 확인을 알린다.
```

Acceptance criteria는 **제목 정규화 기능**의 조건입니다. “여덟 항목이 모두 있다”는 계약 문서의 형식 품질이므로 이 칸에 넣지 않습니다. Handoff는 계약 이후의 작업과 전달 내용입니다.

## 파일을 수정하지 않는 작업

요청: “아래 두 장애 보고서의 공통 원인과 차이를 채팅으로 정리해 줘. 원문에 없는 원인은 추정하지 마.”

| 항목 | 이번 계약 |
|---|---|
| Goal | 두 보고서의 원인과 대응을 비교한다 |
| Context | 함께 개선할 항목을 찾으려 한다 |
| Allowed paths | 해당 없음 — 제공된 보고서만 사용하며 파일을 수정하지 않는다 |
| Forbidden changes | 원인·수치·대응을 만들어 내지 않는다 |
| Acceptance criteria | 공통점·차이점을 나누고 각 주장에 원문 근거를 연결한다 |
| Required verification | 원문과 대조하고 원인이 명시되지 않은 부분은 미확인으로 남긴다 |
| Stop conditions | 보고서 누락이나 사건 구분 불가 시 필요한 정보를 요청한다 |
| Handoff | 분석 담당자가 비교 결과와 남은 질문을 요청자에게 채팅으로 돌려준다 |

경로와 셸 명령은 필수가 아닙니다. 작업에 맞는 범위와 확인 방법이 필요합니다. 중단 조건은 개수를 채우지 말고 계속하면 결과가 틀리거나 권한을 넘는 구체적인 경우만 적습니다.
