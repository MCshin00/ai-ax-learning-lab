이번 주에는 **같은 작은 개발 요구를 M1~M5로 각각 한 번 수행**하고, 책임 분담·실행 과정·결과를 근거로 하네스 v1을 개선합니다. 실습에는 `comparison_task/`의 제공 Java 과제와 공개 검사를 사용합니다.

핵심 결과물은 **M1~M5 비교와 하네스 v2**입니다. 한 번의 실행에서 관찰한 수치와 실패·인계·사람의 판단을 해석합니다. 통계적 순위나 특정 도구의 우열을 확정하지 않습니다.

이번 주의 질문은 **“이 요구를 AI와 개발할 때 어떤 절차와 역할이 필요하고, 완료는 무엇으로 판단할까?”**입니다. 같은 표시 기능을 만드는 동안 절차를 요청에 쓰는 것, 별도 역할에 검토를 맡기는 것, 구현을 병렬로 나누는 것, 검사 결과로 실행을 제어하는 것의 차이를 경험합니다. 그 결과를 바탕으로 현재 요구에 사용할 방식과 구성을 바꿀 조건을 설명하고, 발견한 문제를 하네스의 실제 변경으로 연결하는 것이 학습 목표입니다.

최종 코드가 같아도 역할과 실행 제어가 어떻게 달랐는지는 배울 수 있습니다. 다만 방식을 구성해 본 경험과 그 방식의 품질 향상을 확인한 경험은 구분합니다. 이 과제는 책임과 요구가 이미 제시된 작은 작업이므로, 복잡한 설계를 처음 도출하는 능력이나 큰 프로젝트에서의 생산성까지 평가하지는 않습니다.

## 먼저 구분할 개념

### 실행 방식과 구현 기술

이번 M1~M5는 같은 코드를 만드는 **개발 작업의 운영 방식**입니다. 같은 요구와 코드에서 작업을 누가 나누고 어떤 순서로 실행하며 어디서 완료를 판단하는지를 바꿉니다.

| 방식 | 유지할 의미 | 바뀌는 책임 |
|---|---|---|
| M1 | 절차를 별도로 지정하지 않은 단일 Codex 실행 | 모델이 주어진 요구에서 진행 방법을 선택 |
| M2 | 계획·구현·테스트·자기검토 순서를 준 단일 실행 | 진행 순서를 요청에 명시, 같은 실행이 단계들을 수행 |
| M3 | 계획·구현·검사·보안 검토·통합의 역할 분리 | Planner·Implementer·Tester·Security Reviewer·Integrator가 별도 역할로 인계 |
| M4 | 학습자가 아키텍처를 판단하고 Worktree에서 병렬 구현 | 인터페이스·파일 소유·통합 기준은 학습자가 판단, 구현은 병렬 작업에 배분 |
| M5 | 개발 하네스와 필요한 사람 개입을 결합 | 외부 실행 제어가 검사·복구·종료를 연결, 요구·권한·해결 불가 판단은 사람에게 전달 |

M4에서는 AI의 설계안을 읽고 요구에 비춰 책임과 연결을 판단한 뒤 구현을 진행합니다. M3는 여러 관점의 분리, M4는 사람이 판단한 구조와 격리된 병렬 구현이 중심입니다. M3의 역할은 순차로 인계할 수 있습니다.

### 같은 조건과 비교할 차이

코드 시작 상태·업무 요구·입력·검사·가능한 모델 설정을 같게 유지합니다. M1 이후의 수정 코드를 M2에 넘기면 절차의 효과와 이미 구현된 코드의 효과가 섞입니다. 따라서 각 방식은 제공 시작 코드의 별도 복사본과 새 작업에서 시작합니다. 사용하는 공통 프로젝트 지침도 같게 유지하고, 이와 충돌하는 방식별 지침이 있으면 실행 전에 정리합니다.

M3의 역할 호출, M4의 병렬 작업, M5의 허용된 복구는 각 방식의 한 번 수행 안에 포함합니다. 결과가 좋지 않다는 이유로 처음부터 반복해 유리한 결과만 고르지 않습니다. 환경 문제로 중단한 경우도 발생 조건을 남깁니다.

### 수치와 해석

수치는 같은 의미로 셀 수 있어야 비교할 수 있습니다. 이번에는 제공된 요구 확인 사례 통과 수, 작업 실행 수, 통합에서 발견한 불일치, 필요한 사람 개입을 사용합니다. 실제 도구가 제공하는 시간·토큰·사용량이 있으면 보조로 남길 수 있지만 값이 없으면 미제공으로 씁니다. 여러 작업의 합계와 한 작업의 값, 모델 토큰과 API 결제액을 섞지 않습니다.

예를 들어 M1과 M3가 모두 5개 사례를 통과하고 M3에 인계가 더 많았다면, 이 작은 과제에서 역할 분리가 추가 품질 차이를 드러내지 못했을 수 있습니다. 이것으로 복잡한 업무에서도 역할 분리가 쓸모없다고 결론내릴 수는 없습니다. 반대로 M4에서 빈 제목 처리가 빠졌다면 Worktree 자체의 결함보다 인터페이스와 통합 책임을 먼저 봐야 합니다.

## 제공 과제와 파일

지원 목록에 서로 다른 시스템의 우선순위와 제목이 들어옵니다. 같은 표시 규칙을 적용하되 빈 제목에는 우선순위보다 정보 보충 안내가 먼저 나와야 합니다.

| 입력 | 기대 출력 |
|---|---|
| `" Urgent "`, `"  결제   오류  "` | `[P0] 결제 오류` |
| `"normal"`, `"상품\n문의"` | `[P1] 상품 문의` |
| `"LOW"`, `"화면 개선"` | `[P2] 화면 개선` |
| 알 수 없는 우선순위, `"문의"` | `[P1] 문의` |
| `"urgent"`, 공백뿐인 제목 | `확인 필요` |

`P0/urgent`, `P1/normal`, `P2/low`는 대소문자·앞뒤 공백을 정리해 같은 우선순위로 취급합니다. 없는 우선순위는 `P1`, 없는 제목은 `확인 필요`입니다. 자세한 입력 범위는 프로젝트 README에 고정되어 있습니다.

이 과제는 업무 구현의 규모를 작게 제한해서 실행 방식의 차이를 읽기 위한 것입니다. 두 함수의 구현을 병렬로 할 수 있지만, 작업을 나누고 합치는 비용이 절감 시간보다 클 수도 있습니다. 그 사실도 비교 결과입니다.

### 프로젝트 구조와 입력에서 결과까지의 경로

`comparison_task/`는 명령행으로 지원 요청 한 건을 표시하는 작은 Gradle 프로젝트입니다. `runs/M1`~`runs/M5`에는 같은 프로젝트를 복사하며, 각 복사본을 독립적으로 수정합니다.

```text
comparison_task/
├── README.md                 요구와 실행 안내
├── build.gradle              컴파일·검사·앱 실행 설정, JUnit 의존성
├── settings.gradle           Gradle 프로젝트 이름
├── gradlew / gradlew.bat     지정된 Gradle 버전을 실행하는 Wrapper
├── gradle/wrapper/           Wrapper 실행 파일과 버전·배포 위치 설정
└── src/
    ├── main/java/lab/week10/
    │   ├── Priority.java    우선순위 입력 정리
    │   ├── Title.java       제목 입력 정리
    │   └── Summary.java     전체 표시 조합과 명령행 진입점
    └── test/java/lab/week10/
        ├── SummaryTest.java      기존 표시 검사
        └── RequirementTest.java  새 요구를 확인하는 검사
```

앱을 실행하면 `Summary.main()`이 명령행 인자 두 개를 받아 `Summary.render(priority, title)`에 전달하고 반환 문자열을 출력합니다. `render()`는 `Priority.normalize()`와 `Title.normalize()`의 결과를 조합합니다. 시작 코드의 두 정리 함수는 입력을 그대로 반환하므로 `LOW`를 넣으면 `[LOW]`가 표시됩니다. 구현 후에는 같은 입력이 `[P2]`로 표시되어야 합니다.

테스트는 `Summary.render()`를 직접 호출해 반환값이 표시 규칙과 맞는지 비교합니다. 명령행 입력에서 출력까지의 연결은 프로젝트 README의 앱 실행 예로 확인합니다. 실행 중 생성되는 `build/`에는 컴파일 결과와 검사 보고서가, `.gradle/`에는 Gradle 작업용 캐시가 들어갑니다.

주차 폴더의 `m5-execution.md`와 `m5-task.md`는 Day 4에서 같은 과제를 자기 엔진의 입력과 실행 명령에 연결할 때 사용합니다.

### test와 acceptance: 무엇을 실행하고 판단하는가

**수용 테스트(acceptance test, 인수 테스트)**는 결과물이 업무 요구를 만족해 받아들일 수 있는지 확인하는 검사입니다. 이 프로젝트의 `test`와 `acceptance`는 모두 JUnit 테스트를 실행하는 Gradle 작업입니다. 검사 목적을 구분하려고 `build.gradle`에서 실행할 클래스를 나누었습니다.

| Gradle 작업 | 실행 대상 | 확인하는 질문 | 시작 상태의 예상 |
|---|---|---|---|
| `test` | `SummaryTest`의 기존 표시 검사 1개 | 이미 정리된 입력의 표시가 유지되는가? | 통과 |
| `acceptance` | `RequirementTest`의 제공된 요구 확인 검사 5개 | 별칭·공백·기본값·빈 제목 등 새 요구를 만족하는가? | 실패 |

`test`는 `RequirementTest`를 제외하고, 별도로 등록한 `acceptance`는 그 클래스만 포함합니다. `acceptance`는 이 프로젝트에서 정의한 작업 이름입니다. 다른 프로젝트에서는 빌드 설정에 따라 검사 대상과 작업 이름이 달라집니다.

IDE의 Gradle 화면에서 작업을 실행하면 필요한 앱 코드 컴파일(`compileJava`) → 테스트 코드 컴파일(`compileTestJava`) → 선택한 검사 실행으로 이어집니다. 검사는 입력과 기대값을 코드 안에 가지고 있으므로 실행할 때 별도 입력을 타이핑하지 않습니다. `acceptance`만 실행하면 `test`까지 자동 실행되지는 않습니다. 둘을 함께 요청하면 설정된 순서에 따라 `test` 다음 `acceptance`를 실행합니다.

예를 들어 기존 검사는 `Summary.render("P1", "결제 오류")`의 반환값이 `[P1] 결제 오류`인지 확인합니다. 새 검사는 `Summary.render("LOW", "화면 개선")`이 `[P2] 화면 개선`인지 확인합니다. 시작 코드에서 두 번째 검사를 실행하면 다음과 같은 차이가 예상됩니다.

```text
Expected :[P2] 화면 개선
Actual   :[LOW] 화면 개선
```

`Expected`는 요구를 표현한 기대값, `Actual`은 현재 코드가 반환한 값입니다. 컴파일 뒤 이런 차이로 `acceptance`가 실패했다면 아직 구현하지 않은 요구가 드러난 것입니다. 컴파일 오류나 의존성 다운로드 실패는 검사 자체를 실행하지 못한 경우이므로 구분합니다. 구현 후의 완료 기준은 기존 검사와 새 요구 확인 검사 모두의 통과입니다.

실행 로그의 `PASSED`와 `FAILED`는 개별 검사 결과입니다. `BUILD SUCCESSFUL`은 요청한 Gradle 작업이 성공했다는 뜻이므로 `test`만 실행한 성공으로 새 요구까지 완료했다고 판단하지 않습니다. `UP-TO-DATE`는 변경이 없어 해당 작업을 다시 수행하지 않았다는 뜻이며, `NO-SOURCE`는 처리할 소스가 없는 단계라는 뜻입니다. 자세한 검사 결과는 각 복사본의 `build/reports/tests/test/index.html`과 `build/reports/tests/acceptance/index.html`에서 확인할 수 있습니다.

Gradle이 검사 전에 `Unable to establish loopback connection`으로 중단되면 [실습 프로젝트의 소켓 설정 안내](comparison_task/README.md#windows-codex의-소켓-오류)에 따라 Java 소켓용 임시 폴더를 지정합니다. M1~M5에서 같은 설정을 사용하고, M4의 Worktree에도 적용합니다.

## Day 1 — 공통 조건과 시작 상태 준비하기

IDE나 파일 탐색기에서 `comparison_task/`의 소스·Wrapper·README를 주차의 `runs/M1`~`runs/M5`에 각각 복사합니다. `build/`, `.gradle/`, `.local/`은 제외합니다. 각 복사본의 README에서 주차 본문 링크는 `../../README.md`로 맞춥니다. 다섯 개 복사본은 비교 조건을 맞추기 위한 제공 실습 작업 공간입니다.

시작 코드의 중요한 연결은 다음입니다.

```java
return "[" + Priority.normalize(priority) + "] " + Title.normalize(title);
```

제목 정리 함수가 빈 문자열을 반환해도 이 코드가 그대로라면 `[P0] `가 남습니다. 우선순위와 제목을 각자 정리하는 책임 외에 **제목이 비면 전체 표시를 바꾸는 통합 책임**이 있습니다. 이 지점은 어느 실행 방식에서도 충족해야 하는 공통 요구입니다.

한 복사본에서 IDE의 `test`와 `acceptance`를 실행합니다. Windows는 `.\gradlew.bat test acceptance`, macOS·Linux·WSL은 `./gradlew test acceptance`입니다. 기존 표시는 통과하고 새 요구는 아직 실패합니다. 이 시작 확인을 다섯 복사본에서 반복할 필요는 없습니다. 새 요구의 실패가 비교할 출발점입니다.

```text
제공 comparison_task의 요구, 시작 코드, 기존 검사와 새 요구 확인 사례를 읽어 주세요.
어느 코드가 입력 정리와 전체 표시를 맡고, 빈 제목 요구 때문에 어떤 연결이 필요한지 설명해 주세요.
아직 구현하지 말고 M1~M5에서 같게 유지할 조건과 달라질 작업 책임을 짚어 주세요.
내가 비교하려는 차이에 대한 짧은 의견을 받은 뒤 주차 노트 한 곳에 공통 조건을 남겨 주세요.
```

**남길 결과·완료 판단:** 같은 요구·시작 상태·검사로 비교할 준비와 무엇이 방식별 변수인지 남깁니다. 비교 기록은 `tool-choice.md` 한 곳을 사용하며 새로운 측정 시스템을 만들지 않습니다.

## Day 2 — 단일 실행의 M1과 M2 비교하기

각 복사본에서 새 Codex 작업을 시작합니다. Day 1의 구현 답이나 다른 방식의 결과를 복사해 넘기지 않습니다. 두 방식은 같은 모델과 공통 요구를 사용합니다.

각 실행이 끝나면 다음 방식으로 넘어가기 전에 `tool-choice.md`에 변경한 책임과 실제 입출력, 검사 근거, 관찰한 진행 방식을 기록합니다. Day 5에는 누적한 M1~M5 기록을 비교하고 하네스 개선을 선택합니다.

### M1: 절차를 추가하지 않은 단일 실행

`runs/M1/`에서 아래 요청을 한 번 보냅니다. 프로젝트에 이미 있는 공통 지침은 다른 방식과 같게 둡니다.

```text
이 프로젝트 README의 지원 요청 표시 규칙을 구현해 주세요.
기존 표시와 새 요구를 만족하도록 수정하고 실제 결과를 확인해 주세요.
완료되면 변경 동작, 확인한 결과, 남은 문제를 짧게 알려 주세요.
```

M1이 스스로 계획·검사·검토를 한다면 그대로 관찰합니다. 절차를 지정하지 않았다는 것이 무계획·무검사로 강제한다는 뜻은 아닙니다. 모델이 선택한 실제 진행을 기록합니다.

### M2: 순서를 준 단일 실행

`runs/M2/`에서 다음 요청을 한 번 보냅니다.

```text
이 프로젝트 README의 지원 요청 표시 규칙을 구현해 주세요.
한 실행 안에서 계획 → 구현 → 테스트 → 자기검토 순서로 진행해 주세요.
계획에는 바꿀 책임과 빈 제목의 전체 표시 규칙을, 테스트에는 기존 표시와 새 요구 확인 사례를 포함해 주세요.
자기검토에서는 요구와 현재 변경을 대조하고 필요한 수정만 이어가세요.
완료되면 변경 동작, 확인한 결과, 남은 문제를 짧게 알려 주세요.
```

각 방식의 같은 `test acceptance` 결과를 확인합니다. 이미 실제로 수행한 같은 검사가 있으면 그 결과를 사용합니다. AI가 “검사 완료”라고 쓴 문장만 있고 실행 근거가 없을 때는 검사를 실행합니다. 실패가 남았다면 후속 대화로 계속 보완하기 전에 첫 결과로 남겨, 단일 요청에서 무엇이 해결됐는지 구분합니다.

M2의 계획이 빈 제목의 통합 책임을 실제 수정으로 연결했는지, M1도 같은 점을 스스로 발견했는지 봅니다. 두 코드가 같아도 결과와 진행 방식이 같은 근거로 확인됐다면 의미 있는 관찰입니다.

예를 들어 두 방식 모두 빈 제목에서 `확인 필요`를 반환하고 실제 검사까지 수행했다면, 이번 요구에서는 절차를 명시한 추가 효과가 드러나지 않은 것입니다. M2가 계획을 문장으로 남겼다는 사실만으로 결함을 줄였다고 볼 수는 없습니다. 계획에 적힌 책임이 빠진 구현을 바로잡는 데 쓰였거나, 자기검토에서 실제 누락을 찾아 수정했다면 그 연결이 절차의 효과를 설명하는 근거가 됩니다. 검사 전에 고친 오타는 구현 중 수정이며 테스트가 발견한 문제와 구분합니다.

**남길 결과·완료 판단:** 각 방식의 실제 요구 확인 검사 결과와 다른 진행 지점 한두 개를 코드·실행 근거에 연결합니다. 요청문 한 번의 결과를 모델 전체의 고정된 성질로 설명하지 않습니다.

## Day 3 — M3: 역할을 나누고 근거를 인계하기

`runs/M3/`에서 Planner → Implementer → Tester → Security Reviewer → Integrator의 역할을 나눕니다. 별도 에이전트 또는 역할별 새 작업을 사용합니다. 동시 실행 자원이 적다면 순차로 인계합니다. 같은 대화에서 역할 이름만 붙인 다섯 문단을 작성한 것을 다섯 역할의 독립 확인으로 기록하지 않습니다.

- Planner는 요구와 변경 책임·완료 판단 기준을 정리합니다.
- Implementer는 그 요구와 현재 코드로 구현합니다.
- Tester는 구현 결과를 공통 입력·검사로 대조합니다.
- Security Reviewer는 실제 변경에서 외부 입력이 실행이나 예상 밖 동작으로 이어지는지 봅니다.
- Integrator는 미해결 사항을 처리하고 최종 상태와 결과를 연결합니다.

인계에는 **현재 코드·확정된 함수의 입력·출력과 처리 규칙·남은 문제·검사 결과 위치**를 전달합니다. 예를 들어 “Title은 공백뿐인 입력에서 빈 문자열을 반환하고, Summary가 `확인 필요`를 결정한다”는 규칙이 있으면 구현과 검사가 같은 책임을 기준으로 대화할 수 있습니다.

```text
이 프로젝트 README의 지원 요청 표시 규칙을 M3로 구현해 주세요.
Planner, Implementer, Tester, Security Reviewer, Integrator의 역할을 별도 에이전트 또는 작업으로 나눠 주세요.
Planner는 요구·책임·완료 판단 기준, Implementer는 구현, Tester는 실제 공통 검사,
Security Reviewer는 변경 코드의 실제 입력 처리 위험, Integrator는 남은 문제와 최종 결과를 맡습니다.
역할별 인계에는 코드 위치·확정한 함수의 입력·출력과 처리 규칙·미해결 사항·검사 근거만 전달해 주세요.
이 작은 표시 기능에 필요하지 않은 인증·서버·별도 보안 검사 체계를 추가하지 마세요.
통합 후 기존 표시와 새 요구의 실제 결과를 짧게 보고해 주세요.
```

이 과제에서 문자열은 표시 자료입니다. `Summary.main()`은 인자를 `render()`에 전달하고 결과를 출력합니다. 보안 검토는 이 경로에서 외부 입력이 문자열로 처리되는지, 실행 가능한 명령으로 바뀌는 지점이 있는지 확인합니다. 발견한 문제와 근거를 인계하고, 문제가 없으면 확인한 입력 처리 경로를 남깁니다.

역할 분리의 의미는 구현자가 본 요구와 검토자가 확인할 근거를 나누는 데 있습니다. 예를 들어 Tester가 제목 정리 함수만 확인했다면 빈 제목의 전체 표시를 놓칠 수 있으므로 `Summary.render()`까지 검사해야 합니다. 별도 역할을 만들었다는 사실만으로 관점이 달라지거나 누락이 발견되지는 않습니다. 추가 문제가 없었다면 이번에는 인계와 검토 경로를 경험한 것이며, 추가 품질 향상은 관찰되지 않은 것으로 해석합니다.

**남길 결과·완료 판단:** 실제 역할 분리와 인계가 확인한 문제를 기록합니다. 아무 문제도 새로 발견하지 않았다면 인계 비용과 함께 그 사실을 남깁니다. 역할 이름이나 검토 문서의 존재를 품질 향상으로 바꾸지 않습니다.

## Day 4 — M4와 M5의 결정 위치 비교하기

### M4: 아키텍처 판단과 Worktree 병렬 구현

`runs/M4/`에서 AI와 다음 설계 판단을 먼저 합니다. 우선순위 정리와 제목 정리는 서로의 내부 구현을 몰라도 만들 수 있지만, 빈 제목의 전체 표시는 두 결과를 사용하는 위치에서 결정해야 합니다. 입력·반환값의 형식이 정해지면 두 정리 함수의 구현을 병렬로 진행할 수 있습니다.

AI의 추천을 읽고 예를 들어 “Title은 빈 입력에 빈 문자열을 반환하고 Summary가 안내를 결정하자”처럼 짧게 제안에 대한 의견을 전합니다. 이 판단을 구현 전에 하는 이유는 두 작업이 각자 안내 문구나 접두어를 추가해 통합 때 중복하는 일을 피하기 위해서입니다.

```text
이 프로젝트 README의 지원 요청 표시 규칙을 M4로 구현하려고 합니다.
먼저 Priority, Title, Summary의 책임·입력·반환값의 형식, 파일 소유와 통합 순서를 추천해 주세요.
빈 제목에서 어떤 구성 요소가 '확인 필요'를 결정해야 하는지 이유와 예상 결과를 설명해 주세요.
내 짧은 판단을 받은 뒤 4주차에서 배운 Worktree로 Priority와 Title 구현을 병렬로 나누고,
Summary 연결과 전체 완료 판단 기준 확인은 통합 작업에서 처리해 주세요.
이미 정한 입력·출력에 따른 구현과 오류 수정은 같은 설계 질문을 반복하지 마세요.
실제 병렬 실행·통합과 검사 근거를 짧게 남겨 주세요.
```

4주차와 같은 방식으로 **M4 복사본 안에만** Git 초기 상태를 만들고 Worktree를 구성합니다. IDE의 Git·Worktree 기능을 사용할 수 있습니다. 터미널을 사용하면 Windows PowerShell과 macOS·Linux·WSL에서 다음 명령은 같습니다.

```text
git init
git add .
git commit -m "chore(lab): 비교 과제 시작 상태"
git worktree add -b priority ../M4-priority
git worktree add -b title ../M4-title
```

먼저 `.gitignore`에 `build/`, `.gradle/`, `.local/`이 제외되어 있는지 확인합니다. 각 작업은 담당 파일을 수정하고 커밋합니다. 통합 작업에서 해당 커밋을 합친 뒤 Summary를 연결하고 같은 `test acceptance`를 실행합니다. Worktree가 파일 상태를 나누어도 함수의 입력·출력과 처리 규칙은 자동으로 합쳐지지 않습니다. 실제 파일 충돌이 없어도 빈 제목의 접두어가 남는 의미상의 결함은 발생할 수 있습니다.

예를 들어 두 정리 함수만 합친 시점에 `[P0] `가 나오고, 예정된 Summary 연결 뒤 `확인 필요`가 된다면 통합 책임을 구현하기 전과 후의 차이입니다. 이를 병렬 담당의 실수나 병렬화가 발견한 결함으로 세지 않습니다. 반대로 모든 담당이 완료했다고 한 뒤에도 접두어가 남았다면, 빈 제목의 반환값과 전체 표시를 맡은 코드이 인계됐는지 확인합니다. 이 실습에서 배울 원리는 **파일을 따로 수정할 수 있는 조건과 결과를 함께 검증해야 하는 조건이 다르다**는 점입니다.

### M5: 자기 엔진 v1과 필요한 사람 개입

이번 M5는 사람이 자기 엔진을 시작해 한 개발 작업을 처리하는 방식입니다. 이 엔진을 선택한 효과는 실제 비교 결과에서 판단합니다. 종료 시 검사와 수정 피드백은 11주차의 Hook 구성으로도 연결할 수 있습니다. 12주차에는 새 이슈의 접수·중복 실행 방지·프로세스 중단 관찰처럼 실행 바깥에서 맡을 책임을 추가해, 외부 엔진을 사용하는 조건을 확인합니다.

`runs/M5/`에는 같은 시작 코드가 있습니다. 5주차에서 요구로부터 설계하고 완성한 **자기 엔진 v1의 실제 진입점**을 사용합니다. 작업 입력과 완료 조건·상태 또는 순서 흐름·프로그램 호출 부분·검사·실패 피드백·복구·종료가 이미 v1에서 연결되어 있어야 합니다.

`m5-execution.md`에는 M5의 공통 요구가 있습니다. 자신의 작업 입력과 실행 명령에서 이 요구가 어떻게 표현되는지 AI와 확인합니다.

| 공통 비교 요구 | 자기 엔진에서 대응할 의미 |
|---|---|
| 대상은 `runs/M5/` | 이번 작업의 실제 실행 위치 |
| 요구는 M5 README와 `m5-task.md` | 작업 목적과 제공 맥락 |
| 기존 표시와 새 요구를 만족 | 실제 `test acceptance` 결과로 판단하는 완료 기준 |
| 업무 검사 실패에 최대 한 번 복구 | 실패 근거·남은 복구 범위·재검사·중단의 연결 |
| 필요한 정보·실행 조건을 알 수 없음 | 사람에게 필요한 내용을 반환하고 기다리거나 중단 |

예를 들어 요청 파일과 작업 폴더를 명령행 인자로 받는 엔진이면 그 입력을 사용합니다. 작업 객체를 읽는 엔진이면 자신이 정한 필드에 목적·근거·검사 정책을 연결합니다. 특정 클래스·JSON·상태 이름에 맞추기 위해 엔진을 교체하지 않습니다. 필드 이름이 비슷하더라도 의미가 같아야 합니다. “실행 종료”를 나타내는 필드에 “검증된 완료”를 표시하면 M1과 구분하려던 판단이 사라집니다.

검사 명령은 M5 폴더의 Windows PowerShell `.\gradlew.bat test acceptance`, macOS·Linux·WSL `./gradlew test acceptance`입니다. 자기 엔진이 사용하는 프로세스 호출 방식에 맞게 연결하고, 실제 시작 명령 한 개를 노트에 남깁니다. 이미 선택한 구조의 명령·경로 설정을 AI와 맞출 수 있습니다.

```text
5주차에서 우리가 만든 엔진 v1의 실제 작업 입력·상태/흐름·프로그램 호출 부분·검사·복구·종료·진입점을 읽어 주세요.
M5의 공통 요구를 그 엔진의 의미에 맞춰 연결하려고 합니다.
m5-execution.md와 같은 시작 코드의 요구·검사를 근거로 어디에 무엇을 전달할지 추천해 주세요.
새 판단이 필요하면 이유와 예상 동작을 설명하고 내 짧은 의견을 받은 뒤 연결하세요.
자기 엔진의 실제 명령으로 과제를 한 번 수행하고, 모델 완료 응답과 실제 검사·복구·최종 결과를 구분해 주세요.
정보·실행 조건·해결 불가 판단이 필요한 상태는 필요한 내용을 알려 내 판단에 연결하세요.
실제 사람 개입이 없었다면 그 사실을 기록하세요. 비교용 예제 엔진을 실행해서 내 엔진 수행으로 대신하지 마세요.
```

M5를 시작하려면 자기 엔진의 작업 입력·실행·검사·복구·종료가 연결되어 있어야 합니다. 준비가 필요한 부분은 5주차의 해당 실습에서 완성한 뒤 같은 과제를 실행합니다.

사람 개입은 요구를 결정할 정보가 없거나 실행 조건을 해결해야 하거나 복구 이후에도 실패했을 때 다음 행동을 판단하는 것입니다. 엔진이 중단한 결과를 사람이 보완했다면 최초 결과와 사람 판단 뒤 결과를 구분합니다. 모든 단계에서 반복 승인을 받도록 만들거나 개입 장면을 만들기 위해 업무 코드를 손상시키지 않습니다.

M1에서도 모델이 테스트 도구를 사용할 수 있습니다. M5의 차이는 모델 응답 뒤에 하네스가 정해진 검사를 실행하고 그 결과로 재시도·종료를 결정한다는 것입니다. 예를 들어 모델이 완료라고 답해도 실제 `acceptance`가 실패하면 하네스는 성공으로 끝내지 않아야 합니다. 첫 검사에서 통과했다면 외부 검사에 따른 완료 판단은 경험했지만, 실제 작업의 자동 복구 효과는 관찰하지 않은 것입니다. 복구 분기의 대역 검사와 실제 모델이 결함을 고친 결과는 각각의 확인 범위로 해석합니다.

**남길 결과·완료 판단:** M4는 누가 함수의 입력·출력과 처리 규칙을 정하고 어떤 파일을 격리해 합쳤는지, M5는 어떤 외부 검사·복구·사람 판단이 결과를 결정했는지 실제 근거로 설명합니다.

도구에 시간·토큰·비용이 실제로 표시되면 조건과 함께 덧붙일 수 있습니다. M3·M4의 여러 작업 중 일부 값만 있으면 전체 합계로 쓰지 않습니다. 측정되지 않은 값은 추정한 0으로 채우지 않습니다. 수동 타이머나 전체 대화 수집을 추가하지 않습니다.

### 모두 통과했다면 무엇을 배운 것인가

다음은 **가상 비교 결과의 해석 예**입니다. 다섯 방식이 모두 5개 요구 확인 사례를 통과하고 추가 결함도 발견하지 않았다면, 확인된 사실은 이 입력과 검사 범위에서 모두 요구를 충족했다는 것입니다. M3의 역할 인계나 M4의 작업 분리는 여전히 구성상의 차이지만, 그것을 기능 품질 향상이라고 부를 근거는 없습니다. 검사에 포함되지 않은 동작까지 품질이 같다고 확장할 수도 없습니다.

이때는 작은 요구를 단일 실행으로 처리하는 것을 출발점으로 삼을 수 있습니다. 이는 “단일 실행이 항상 우수하다”는 판정이 아니라, 이번 결과에서 역할과 조정 단계를 더 둘 이점이 관찰되지 않았다는 선택입니다. 작업 실행 수가 많아졌다는 사실은 분담 규모를 보여 줍니다. 실제 시간·사용량이 없으면 그 수를 속도나 비용 차이로 환산하지 않습니다.

모델·추론 설정이나 제공 맥락이 달랐거나 확인되지 않았다면 그 조건도 함께 해석합니다. 절차와 완료 판단의 구조는 비교할 수 있지만, 출력 차이의 원인을 작업 방식 하나로 돌릴 수는 없습니다. 다음 실행에 조건 전달을 보완해도 이전 실행이 소급해 동일 조건의 비교가 되지는 않습니다.

### 관찰을 작업 방식의 선택으로 연결하기

아래는 제공 과제에서 출발한 **선택 기준**입니다. 조건이 달라질 때 살펴볼 지점을 설명하며, 추가 프로젝트나 다섯 방식의 재실행을 요구하지 않습니다.

| 선택할 구성 | 이번 과제에서 판단할 근거 | 요구가 달라지면 살펴볼 조건 |
|---|---|---|
| M1 단일 실행 | 한 실행이 요구와 실제 검사를 충족했는가 | 작업 범위가 작고 공유할 맥락을 한 작업에서 다룰 수 있는가 |
| M2 절차 명시 | 계획·검토가 실제 누락의 발견이나 판단에 쓰였는가 | 단계별 확인이 필요한 요구가 있거나 같은 누락이 반복되는가 |
| M3 역할 분리 | 별도 검토가 구현과 다른 근거·문제를 확인했는가 | 구분할 검토 관점이 있고, 필요한 코드와 판단 근거를 인계할 수 있는가 |
| M4 병렬 구현 | Priority·Title을 독립적으로 만들고 Summary에서 통합했는가 | 반환값의 형식과 담당 파일을 정할 수 있고, 선행 결과를 기다리지 않아도 되는 작업이 있는가 |
| M5 하네스 | 실제 검사 결과가 완료·재시도·중단에 연결됐는가 | 여러 실행에 일관된 검사와 재시도 상한을 적용할 필요가 있는가 |

실제 개발에서는 이 구성을 함께 사용할 수 있습니다. 예를 들어 하네스가 단일 구현 실행이나 병렬 작업을 호출하고 최종 검사를 맡을 수 있습니다. 다섯 방식을 모두 넣는 것이 목표는 아닙니다. 무엇을 나눌 이유가 있는지, 그 결과를 어디서 합치고 확인할지를 요구에 맞춰 정합니다. `tool-choice.md`의 기존 비교에 이번 요구에서 택할 구성과 그 근거, 선택이 바뀔 조건을 이어 씁니다. 추천 이유를 읽고 수용하거나 수정한 짧은 의견이면 충분합니다.

### 관찰에서 변경 요구를 도출하기

다음은 선택을 돕는 **예시**이며 모든 항목을 v2에 넣으라는 지시가 아닙니다.

| 실제 관찰이 이와 같다면 | 개선할 수 있는 부분 | 같은 과제에서 확인할 효과 |
|---|---|---|
| 제목 함수의 반환값이 제대로 전달되지 않아 접두어가 남음 | 작업 맥락·인계에 반환값의 형식과 통합 담당 명시 | 같은 요구 확인 검사에서 빈 제목 결과가 맞는지 |
| 모델이 검사했다고 보고했지만 해당 검사가 실행되지 않음 | 외부 검사 명령·결과가 있어야 완료로 판단하도록 연결 | 모델의 완료 보고와 엔진의 완료 판단 분리 |
| 환경 실패에도 같은 코드 수정 요청을 반복함 | 실패 분류·복구 조건·사람에게 넘길 정보 보완 | 해당 실패가 불필요한 재실행으로 이어지지 않는지 |
| 짧은 작업에 역할·인계가 과도함 | 이 요구에서는 단일 실행을 선택하는 작업 규칙 | 필요한 결과를 유지하며 불필요한 역할 단계가 줄었는지 |
| 하위 실행에 어떤 모델·추론 설정을 요청했는지 알 수 없음 | 작업 입력에서 실행 설정을 전달하고 요청값을 기록 | 최초·복구 호출에 설정이 전달되고 결과에서 요청 조건을 확인할 수 있는지 |

하네스 v2는 **5주차에서 연결한 맥락·작업 규칙·도구·환경·검사·피드백과 자체 실행 엔진을 비교 결과에 맞춰 개선한 구성**입니다. 작업 입력과 완료 조건·상태·검사·복구·종료의 기본 흐름은 v1에서 완성합니다. 이번에는 관찰된 문제가 어느 구성에서 생겼는지 판단해 필요한 작업 규칙·인계·정책·실행 제어를 바꿉니다. 기준 전달이 문제라면 맥락·지침을, 검사가 빠졌다면 완료 판단에 필요한 사례를 살피며 모든 개선을 엔진의 새 분기로 만들지는 않습니다. 기존 v1에 이미 필요한 통제가 있다면 그것을 유지할 근거와 불필요한 단계의 축소를 v2의 설계로 삼을 수 있습니다. 다섯 방식 모두 잘되었다면 가짜 결함을 만들지 말고 관찰한 분담·진행 비용에서 선택 기준을 정합니다.

```text
M1~M5의 실제 결과와 공통 조건을 읽고 같은 의미로 비교할 수 있는 수치와 관찰을 정리해 주세요.
어느 차이는 이번 실행에서 확인됐고, 어느 결론은 한 번의 실행만으로 말할 수 없는지 설명해 주세요.
이번 요구에서 사용할 구성을 실제 결과에 근거해 추천하고, 요구가 달라지면 어떤 조건에서 선택을 바꿀지 설명해 주세요.
관찰한 문제나 불필요한 단계에서 하네스 v2의 변경 요구를 도출하고 우리가 만든 v1의 실제 작업 입력과 완료 조건·상태/흐름·정책·프로그램 호출 부분 중 바뀔 위치를 추천해 주세요.
내 짧은 선택·수정 의견을 받은 뒤 필요한 작업 규칙·인계·검사·실행 제어만 반영해 주세요.
선택한 변경이 의미를 드러내는 같은 과제의 상황과 기존 정상 결과를 확인해 주세요.
기존 tool-choice.md에 내 선택 이유와 변경 전 문제·변경 경로·확인된 효과를 연결하고, 예상 효과와 구분해 주세요.
모든 기술 추가나 다섯 방식의 전체 재실행은 요구하지 마세요.
```

변경한 구성이 실제 파일·설정·실행 경로에 연결되어야 합니다. 한 항목을 고쳤다면 그 항목의 효과와 기존 정상 동작만 확인합니다. 비교 전체를 다시 수행할 필요는 없습니다. 예상과 결과가 다르면 원인을 요청·입출력 형식·코드·실행 상태에서 찾습니다.

### v2가 개선한 대상을 설명하기

개선은 **발견한 문제 → 바꾼 연결 → 그 문제를 확인하는 결과**로 설명합니다. 예를 들어 하위 실행 설정이 불명확했다면 작업 입력 → 모델 실행 인자 → 결과 기록에 설정을 연결할 수 있습니다. 이때 설정 전달을 검사하고 실행 결과에 요청값이 남는지 확인하면 실행 조건 관리의 개선을 뒷받침합니다. 요청값의 기록은 서비스가 실제 사용한 모델을 관측한 값과 구분합니다.

이 변경 뒤 코드가 검사에 통과했다는 사실은 정상 동작의 유지도 보여 줍니다. 그러나 이미 완성된 코드로 실행 조건을 확인했다면 코드 생성 품질의 전후 비교는 아닙니다. 더 좋은 코드를 생성했다거나 시간을 줄였다는 주장은 그 효과에 대응하는 별도 근거가 있을 때만 할 수 있습니다. 완료 근거 누락을 고쳤다면 완료 판단의 신뢰성을, 불필요한 역할을 줄였다면 진행 구성을 개선한 것으로 설명합니다. 실제로 해결한 문제를 정확히 설명하는 것이 v2의 학습 결과입니다.

**남길 결과·완료 판단:** M1~M5의 실제 비교에서 이번 요구에 사용할 방식과 선택 이유를 도출하고, v2의 문제·변경·확인 근거를 `tool-choice.md`에 연결합니다. 실행 방식의 경험, 관찰된 효과, 조건이 달라질 때의 예상을 구분해 설명합니다.

### 선택한 개발 방식을 상담 앱 제작에 적용하기

12주차에서 새 업무를 받으면 이번 비교의 결론을 작업 요구에 적용합니다. 예를 들어 단일 작업으로 충분하다고 판단했다면 핵심 입력·출력 규칙과 관련 검사를 한 작업에 전달합니다. 업무 흐름과 API 연결을 나누려면 반환할 상태·근거·오류를 먼저 합의하고 통합 입력을 지정합니다. 단순히 역할 이름을 늘리는 것으로 작업 사이에 전달할 값과 합치는 순서가 정해지지는 않습니다.

하네스를 사용한다면 작업 입력에 현재 요구·맥락·실제 검사 명령을 연결합니다. 검사 통과가 상담 답변의 의미까지 판정하는지는 별도로 확인합니다. 앱의 접수·검색·상태 연결은 대역 검사로, 실제 답변은 모델 실행과 원문 대조로 판단할 수 있습니다. 현재 구성으로 충분한지 이 차이를 근거로 정하고 필요한 연결만 수정합니다.

### 개발 방식의 품질과 AI 기능의 품질

이번 M1~M5 비교는 AI를 사용해 **코드를 개발하는 방식**의 비교입니다. 앱이 고객에게 내는 답변의 근거 정확성이나 도구 선택 품질과는 다른 결과입니다. 12주차에서는 이번에 선택한 지침·검사·개입 방식을 사용하면서 앱의 동일 입력·원문·도구 기록을 비교합니다. 역할 수나 사용량이 늘었다는 사실만으로 개발 결과나 답변 품질이 좋아졌다고 판단하지 않습니다.

작업 범위가 커지면 작업 간 필요한 정보, 반환할 항목과 형식, 통합에서 생긴 오류를 보고 분업을 조정합니다. 실제로 달라진 품질·수정 비용을 근거로 선택한 방법을 재사용합니다.
