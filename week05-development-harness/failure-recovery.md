# 5주차 개발 하네스와 실패 대응

하네스는 모델에 맥락과 도구를 연결하고 실행 결과를 다음 판단으로 돌려주는 실행 시스템이다. 프로젝트에서는 지침, 업무 요구와 검사, 실패 피드백을 이 경로에 연결한다. 계산 코드는 환불 규칙을, 검사는 실제값과 기대값의 비교를 맡는다.

현재 Day 1~2와 요구 A까지 진행했다.

## Day 1 — 시작 동작과 실행 경로

### 입력 거부와 결과의 하한

시작 기능은 결제액에서 수수료를 빼고 환불액 하한을 0으로 둔다. 결제액이나 수수료가 음수이면 계산 전에 거부한다. 현재 구현의 대응 위치는 `quality_demo/src/main/java/lab/week05/Refund.java`다.

| 입력 | 결과 | 확인하는 규칙 |
|---|---|---|
| 결제 10000, 수수료 2000 | 8000 | 기본 차감 |
| 결제 1000, 수수료 2000 | 0 | 유효한 입력으로 계산한 환불액의 하한 |
| 결제 -1, 수수료 0 | 금액 오류 | 잘못된 입력의 거부 |
| 결제 1, 수수료 -1 | 금액 오류 | 잘못된 입력의 거부 |

`1000, 2000`은 두 입력 모두 유효하지만 차감 결과는 음수다. 하한으로 0을 반환한다. `-1, 0`은 입력부터 유효하지 않으므로 거부한다. 두 경우를 모두 0으로 보정하면 잘못된 결제액을 정상 요청처럼 처리하게 된다. 결과가 음수가 아니라는 조건과 입력이 유효하다는 조건은 각각 확인해야 한다.

현재 계산의 공통 부분은 다음과 같다.

```java
if (paid < 0 || fee < 0) {
    throw new IllegalArgumentException(AMOUNT_ERROR);
}
return feeWaived ? paid : Math.max(0L, paid - fee);
```

면제가 없는 기본 동작은 기존 두 인자 호출이 사용한다. 시작 활동에서는 기본 출력 8000과 세 기존 검사 통과를 확인했다. 실제 오답에 맞춰 기대값을 바꾸면 요구와 결과를 비교할 기준을 잃는다.

### 내장 하네스에서 확인한 역할

작업 지침·업무 요구·소스·테스트를 읽고 프로젝트 폴더에서 검사를 실행한 결과가 도구 출력으로 돌아왔다. 모델은 출력과 종료 상태를 읽고 보고했다. 프로젝트의 `AGENTS.md`는 실행 방법을 안내하고, 파일·명령 실행과 결과 전달은 Codex 내장 하네스가 맡는다. 지침 파일 자체가 실행기는 아니다.

| 구성 | 이번 경로에서 맡은 일 |
|---|---|
| 모델 | 요구와 파일에 근거해 필요한 도구를 선택하고 결과를 해석 |
| Codex 내장 하네스 | 파일 읽기·명령 실행·권한과 결과 전달을 연결 |
| 업무 코드 | 입력 거부와 차감·하한의 업무 규칙 |
| 테스트 | 입력을 넣고 반환값·오류를 기대와 비교 |

검사는 모델을 호출하지 않고 로컬 입력과 결과를 비교한다. 코드와 기대값이 분리되어 있어 구현 변경 뒤 같은 요구가 유지되는지 확인할 수 있다. 모델의 도구 요청과 실행 환경의 실제 실행·결과 반환 구분은 [공식 도구 호출 흐름](https://developers.openai.com/api/docs/guides/function-calling#the-tool-calling-flow)에도 대응한다.

Hook 설정과 피드백 코드는 제공되어 있지만 Day 1에 실제 Hook 이벤트 연결까지 확인한 것은 아니다. 기본 도구 실행과 테스트 결과 전달의 확인 범위를 유지한다.

## Day 2 — 운영 지침 적용과 수수료 면제

### 운영 지침·실행 위치·권한

[학습 저장소 지침](../AGENTS.md)과 [프로젝트 지침](quality_demo/AGENTS.md)은 현재 README 요구를 읽고, 정해진 프로젝트 폴더에서 전체 검사를 실행하며, 실패하면 실행 환경 문제와 기능 오류를 구분하도록 안내한다. 현재 요구·실행 위치에 맞아 그 운영 방식을 사용했다.

작업 지침은 모델에 작업 방법을 알리고 권한 설정은 실제 편집·도구 사용의 범위를 정한다. 작업 폴더만 바꾸어 권한 경계가 바뀌는 것은 아니다. 학습 프로젝트를 기본 위치로 연 새 작업에서 지침 자동 적용과 기본 편집 권한을 확인하는 단계는 남아 있다.

### 입력 경계와 업무 계산의 책임

수수료 면제는 계산 방법을 바꾸지만 잘못된 금액을 허용하지 않는다. 처리 순서는 금액 검사 → 면제 여부 검사 → 계산이다. 금액과 면제 여부가 함께 잘못되면 금액 오류를 먼저 알리는 계약이다.

현재 경로는 다음과 같다.

```text
외부 JSON 요청
  → RefundInput: JSON 구조·금액 표현·면제 여부 검사
  → Refund.refundAmount: 유효한 금액의 업무 규칙과 면제·하한 계산
  → 환불액 또는 입력 오류
```

`RefundInput`은 Gson으로 JSON을 읽고 금액이 정수 숫자인지 확인한다. `"1000"`은 문자열이고 `true`는 면제 여부에 사용할 수 있는 불리언이므로 금액으로 변환하지 않는다. 이 경계에서 값의 의미를 확정하고 계산 메서드에는 금액과 면제 여부만 전달한다. 계산 메서드도 음수 입력을 거부하므로 JSON 밖의 호출에도 동일한 업무 규칙이 적용된다.

핵심은 특정 언어의 타입 관계가 아니라 **형식이 맞는 입력과 업무상 유효한 입력을 각 책임 위치에서 확인한다**는 것이다. 입력 채널이나 구현 언어가 바뀌어도 이 책임 구분은 유지된다.

면제 여부를 생략한 JSON과 기존 두 인자 호출은 비면제 계산을 사용한다. 면제 분기를 검사보다 앞에 두면 잘못된 수수료나 음수 결제액을 통과시킬 수 있으므로 공통 검사 뒤에서 계산을 나눈다.

금액은 정수 원이며 이번 구현의 저장 범위는 64비트 정수다. 범위를 넘은 값과 소수점·지수 표기 금액도 입력 오류로 거부한다. 다른 통화나 소수 단위 금액을 받아야 하면 금액 표현·오류 계약·검사 사례를 함께 다시 선택한다.

### 요구 A의 입력과 결과

`quality_demo/data/refund-cases.json`의 기대값은 업무 요구에서 정했다. A 활동에서는 여덟 사례의 반환값 또는 오류 메시지를 확인했고, 같은 요구를 현재 JSON 입력 경계 검사에 연결했다.

| 자료의 id | 결과 |
|---|---|
| regular | 8000 |
| waived | 10000 |
| lower-bound | 0 |
| negative-paid | 금액은 0 이상의 정수여야 합니다. |
| negative-fee-waived | 금액은 0 이상의 정수여야 합니다. |
| text-amount | 금액은 0 이상의 정수여야 합니다. |
| boolean-amount | 금액은 0 이상의 정수여야 합니다. |
| invalid-waiver | fee_waived는 불리언이어야 합니다. |

면제 10000원·기본 8000원·잘못된 금액 거부가 같은 입력 계약과 계산 분리에서 나온다. 자료 검사는 JSON 입력이 실제 계산으로 이어지는 경로를 확인하고, 계산 검사는 하한·음수·면제를 따로 확인한다. 여러 환불을 다루는 다음 요구도 이 경계를 재사용할 수 있다.
