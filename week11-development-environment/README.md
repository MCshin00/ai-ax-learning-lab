## 이번 주의 문제 — AI와 개발할 때 필요한 정보를 매번 다시 연결해야 한다

운영팀이 문의 목록을 CSV로 내려받습니다. 첫 구현은 단순한 제목만 처리합니다. 이제 쉼표와 줄바꿈이 있는 제목, 팀별 선택, 날짜가 있는 파일 이름, 중복 문의 처리까지 필요합니다. AI에 변경을 맡길 때마다 현재 구조와 요구를 설명하고, 검사 실행을 챙기고, 다음 세션에 남은 일을 다시 전달하면 작업이 길어질수록 빠뜨리는 조건이 생깁니다.

이번 주에는 이 Java 프로그램을 개선하면서 **개발 AI가 필요한 정보를 얻고, 코드를 바꾸고, 결과를 확인하고, 다음 작업을 이어 가는 환경**을 구성합니다. 이것이 여기서 다룰 개발 하네스입니다. 5주차의 실행·검사·재시도와 10주차의 개발 방식 선택을 프로젝트 환경으로 연결합니다.

하네스에는 모델을 호출하는 실행기, 작업 지침과 문맥, 사용할 도구, 작업 공간과 권한, 결과 검사와 피드백, 작업 상태와 재개 방법이 들어갑니다. Codex 같은 코딩 도구가 모델 호출과 도구 실행, 대화 저장을 제공하므로 이번에는 그 기능에 프로젝트 자료·Skill·MCP·Hook·검사를 연결합니다. 다른 코딩 도구에서도 같은 역할을 찾되 설정 형식과 지원 이벤트는 해당 도구에 맞춥니다.

```text
개발할 요구 + 완료할 행동
  → 프로젝트 지침·현재 구조·필요한 사례 가져오기
  → 코딩 도구: 계획 → 파일 수정·개발 도구 호출 → 결과 확인
       ├─ 독립 작업: worktree별 구현 → 인계 → 통합 검사
       └─ 종료 시 Hook: 현재 코드 검사 → 통과 / 수정 요청 / 사람에게 중단 사유 전달
  → 변경 코드 + 확인한 결과 + 남은 결정
  → 같은 세션 재개 또는 새 세션에서 현재 상태 복원
```

**환경의 구성은 실제 변경 작업으로 확인합니다.** 변경 요청이 필요한 자료와 코드로 이어지고, 실패가 수정에 전달되며, 작업을 나누거나 중단해도 다음 행동을 이어 갈 수 있어야 합니다.

## Day 1 — 개발 요청부터 결과 확인까지 경로 정하기

### 개념 — 지침·문맥·도구·검사의 책임

작업 지침은 반복해서 지켜야 할 개발 방법입니다. “입출력이 바뀌면 호출부와 업무 검사를 함께 변경한다”가 그 예입니다. 문맥은 현재 작업을 이해할 자료입니다. “CSV 열 순서는 id, team, status, title이다”는 이 프로젝트의 문맥입니다. Skill은 특정 종류의 요청에 적용할 절차이며, 도구는 파일 수정·검사·자료 조회처럼 실제 행동을 수행합니다.

예를 들어 “제목에 쉼표가 있어도 내보내기”라는 요청에는 CSV의 셀 표현과 기존 검사가 필요합니다. 전체 과거 대화와 모든 개발 규칙을 매번 넣으면 현재 요구를 찾기 어려워집니다. 상시 지침에는 작업 원칙을, 프로젝트 설명에는 현재 구조를, 요구별 자료에는 구체적인 입력과 기대 결과를 둡니다. 필요한 사례는 해당 요청에서 가져옵니다.

검사는 구현이 요구에 맞는지 판단할 구체적인 입력과 결과를 제공합니다. 코딩 도구의 “완료했습니다”라는 문장과 검사 결과는 서로 다른 근거입니다. 검사에 없는 조건은 코드와 요구를 함께 검토해야 합니다.

### 설계와 실행

`TicketExport.csv`에 `T-1 / OPS / OPEN / VPN 접속`을 넣는 경로를 따라갑니다. `TicketFilter`가 대상을 고르고 `CsvCell`이 각 값을 표현한 뒤 `TicketExport`가 연결합니다. 제목 `VPN, 접속`을 그대로 넣으면 쉼표가 열 구분자로 해석될 수 있습니다. 이 요구는 한 셀의 표현을 바꾸어 해결할 수 있습니다.

이 요구를 AI에 설명하고 필요한 지침과 자료 배치를 추천받습니다. `setup/AGENTS.example.md`를 참고해 **이 프로젝트의 `AGENTS.md`**를 작성하고 `docs/project.md`를 현재 구조에 맞춥니다. 권한은 프로젝트 코드 수정과 검사 실행에 맞춥니다. 개발 MCP에는 요구 조회 기능을 공개합니다.

Codex의 작업 폴더를 `development_harness`로 지정합니다. 도구 설정에서 workspace-write와 필요한 실행 승인을 사용합니다. CLI로 시작하는 경우 Windows PowerShell과 macOS·Linux·WSL 모두 이 폴더에서 다음 명령을 사용합니다.

```text
codex --sandbox workspace-write -a on-request
```

```text
제공 문의 내보내기 프로그램과 CSV-QUOTE 사례를 읽어 줘.
입력이 필터·셀 표현·CSV 조합을 거쳐 결과가 되는 경로를 실제 코드로 설명해 줘.
이번 개발에 상시 제공할 지침, 필요할 때 가져올 자료, 실행할 도구와 검사를 추천해 줘.
각 선택이 어떤 누락이나 반복 작업을 줄일지 예를 들면 내가 수용하거나 바꿀 부분을 말할게.
그 의견을 반영해 프로젝트 지침과 설명을 구성하고 기존 검사를 실행하자.
확장 기능은 다음 활동에서 구현할게.
```

완료 기준은 **요구 → 필요한 자료 → 변경할 코드 → 확인할 결과를 연결하고, 그 선택을 지침과 프로젝트 설명에 반영한 것**입니다. 기존 검사의 입력과 실제 결과, 쉼표가 있는 입력에서 예상하는 차이를 남깁니다.

## Day 2 — Skill과 개발 MCP로 필요한 정보를 가져오기

### 개념 — 작업 절차와 자료 접근을 연결하기

Skill은 “무엇을 어떤 순서로 확인할까”를 재사용합니다. 개발 MCP는 “필요한 사례를 어떤 기능으로 조회할까”를 제공합니다. 여기서는 `get_acceptance_case(id)`가 요구별 입력·기대 결과·판단 이유를 반환합니다. 예를 들어 `CSV-QUOTE`를 조회하면 제목 안의 쉼표와 큰따옴표를 보존하는 셀 표현을 확인할 수 있습니다.

공유된 요구 관리 서비스나 다른 프로그램에 자료가 있을 때 이런 도구 연결을 사용할 수 있습니다. 제공 예제는 같은 역할을 로컬 JSON으로 재현합니다. 작은 프로젝트에서는 JSON을 직접 읽어도 충분합니다. 두 경로의 차이는 자료가 있는 위치와 접근 방법이고, 구현할 업무 요구는 같습니다.

여기서 MCP를 호출하는 주체는 **개발 AI**입니다. 완성된 CSV 프로그램은 MCP와 모델 없이 실행됩니다. 개발 도구가 요구를 찾는 연결과 제품이 사용자의 업무를 처리하는 연결을 구별합니다.

### 설정과 실행

Gradle 창에서 `harnessJar`를 실행해 `build/libs/harness-kit.jar`를 만듭니다. CLI는 코딩 도구가 Hook 프로세스와 MCP 서버를 시작할 명령을 등록하는 데 사용합니다. `development_harness` 폴더의 IDE 터미널에서 다음을 실행합니다.

Windows PowerShell:

```powershell
java -jar .\build\libs\harness-kit.jar setup .
```

macOS·Linux·WSL:

```bash
java -jar ./build/libs/harness-kit.jar setup .
```

생성된 `.local/harness/mcp-snippet.toml`의 서버 항목을 Codex 프로젝트 MCP 설정에 넣습니다. CLI에서는 프로젝트의 `.codex/config.toml`에 해당 항목을 추가합니다. 기존 설정이 있으면 필요한 서버 항목만 병합합니다. 프로젝트를 신뢰한 상태에서 새 Codex 세션을 열고 `/mcp`로 `acceptance_cases`와 도구 목록을 확인합니다. [공식 MCP 설정 안내](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)를 함께 참고합니다.

`setup/export-change`를 프로젝트의 `.agents/skills/export-change`로 복사하고 현재 지침과 맞춥니다. 새 세션에서 Skill을 명시해 첫 발동을 확인한 뒤, 뒤의 요청에서는 해당 변경에 필요한 절차로 사용합니다. `setup`이 만든 Hook은 Day 3에서 검토하고 활성화합니다.

```text
export-change Skill로 CSV-QUOTE 요구를 구현하자.
먼저 개발 MCP의 get_acceptance_case로 사례를 가져와 원문과 기대 셀을 대조해 줘.
Skill의 절차와 MCP의 반환값이 설계와 검사에서 각각 어떻게 사용되는지 설명해 줘.
바꿀 코드와 검사 입력을 추천하면 내 의견을 반영해 구현해 줘.
쉼표·큰따옴표가 있는 제목과 단순한 제목의 실제 출력이 어떻게 달라지는지 확인하자.
```

예상 셀은 `"VPN, ""접속"""`입니다. 셀 전체의 따옴표는 쉼표가 열을 나누지 않게 하고, 셀 안의 두 따옴표는 원래의 한 따옴표를 나타냅니다. IDE에서 `ExportExample.main`을 실행해 CSV를 보고, 프로그램에서 표현을 바꾸는 이유와 실제 출력이 일치하는지 검사합니다.

완료 기준은 **Skill 적용과 실제 MCP 호출을 확인하고, 조회한 사례가 구현과 검사로 이어진 것**입니다. 자료를 직접 읽는 경우와 비교해 MCP가 필요한 조건도 노트에 짧게 설명합니다.

## Day 3 — 종료 전에 검사하고 실패를 수정에 돌려주기

### 개념 — Hook과 피드백 루프

Hook은 코딩 도구의 특정 사건에 연결하는 실행입니다. 이 예제의 `SessionStart`는 프로젝트 설명과 인계 메모를 전달하고, `PostToolUse`는 어떤 도구가 실행됐는지 기록합니다. `Stop`은 도구가 이번 응답을 끝내려 할 때 검사를 실행합니다. Hook이 실패 근거를 모델에 돌려주면 코딩 도구가 수정 작업을 이어 갈 수 있습니다.

`HookHandler`의 Stop 경로는 `GradleCheck`를 호출합니다. 검사는 별도의 새 빌드 폴더에서 실행하고 그 실행의 JUnit 결과를 읽습니다. 실패한 테스트가 있으면 검사 이름과 결과 위치를 전달합니다. 빌드 자체가 시작되지 않거나 검사 결과가 없으면 실행 환경을 확인하도록 종료합니다. 기능 실패와 실행 불가는 다음 행동이 다릅니다.

참고 구현은 최초 기능 실패에 **한 번의 자동 수정 요청**을 보냅니다. 이어진 종료 시점에도 새 검사를 수행하고, 계속 실패하면 사람에게 결과를 넘깁니다. `stop_hook_active`는 앞선 Stop에 의해 이어진 응답임을 알려 주므로 종료 요청이 계속 새 작업을 만드는 것을 막는 데 사용합니다. 이 횟수는 실습의 선택이며, 작업 비용과 실패 유형에 맞춰 바꿀 수 있습니다.

### 연결과 실제 실패 확인

IDE에서 생성된 `.codex/hooks.json`과 `HookHandler`를 읽습니다. Hook이 호출할 JAR, 프로젝트 폴더, 이벤트가 맞는지 확인하고 코딩 도구에서 `/hooks`를 열어 해당 Hook을 검토·신뢰합니다. Hook 설정은 명령을 실행하므로 프로젝트 신뢰와 Hook 검토를 거쳐 적용됩니다. [공식 Hook 안내](https://learn.chatgpt.com/docs/hooks)에 이벤트별 입력과 반환 형식이 있습니다.

현재 사용 중인 Codex가 `/hooks`를 제공하는지 먼저 확인합니다. 지원하지 않는 버전에서는 Hook을 지원하는 CLI를 준비한 뒤 이 활동을 진행합니다. 이 실습의 자동 연결 확인은 실제 Hook 발동을 포함합니다.

`CSV-LINE`의 `첫 줄\n다음 줄`을 다루는 검사를 추가합니다. 줄바꿈을 포함한 셀은 전체를 따옴표로 감싸 원문 줄바꿈을 보존해야 합니다. 아직 구현되지 않았다면 그 실패를 사용합니다. 이미 처리한다면 IDE에서 줄바꿈 조건만 잠시 제거해 실패를 재현하고, 그 변경을 작업 요청에 명시합니다. 확인하려는 것은 실패 → 피드백 → 수정 → 새 검사라는 실제 경로입니다.

```text
CSV-LINE 사례와 현재 실패한 검사를 확인하고 줄바꿈 셀 처리를 수정해 줘.
이번에는 종료 시 Hook이 실행한 검사 결과도 확인할게.
실패가 돌아오면 요구·기대 결과·실제 결과를 대조해 수정하고 다시 검사해 줘.
검사 실행 불가나 자동 수정 한도에 도달하면 현재 상태와 필요한 다음 조치를 알려 줘.
```

`.local/harness/events.jsonl`에서 Stop과 결과 순서를 보고 `last-check.json`과 해당 검사 결과를 확인합니다. 첫 수정에서 통과하면 그 경로를 기록합니다. 자동 수정 요청 자체도 확인하려면 재현한 실패를 둔 상태에서 “현재 변경을 검토하고 결과를 알려 줘”라고 요청해 Stop의 실패 전달과 다음 응답을 관찰합니다.

실행 결과가 `FAILED`일 때 코드를 다시 살펴보고, `UNAVAILABLE`일 때는 검사 명령·의존성·제한 시간을 확인합니다. 검사 프로그램 대역으로 이 분기가 동작하는 것은 `HarnessTest`에서 확인할 수 있으며, 실제 코딩 도구가 실패를 받고 수정하는지는 위 실행에서 확인합니다.

완료 기준은 **실제 Hook의 자동 검사, 실패 전달, 수정 후 재검사와 종료 조건을 설명할 수 있는 실행 근거가 있는 것**입니다. 코드 검사 통과와 CSV가 요구를 만족하는 이유를 연결합니다.

## Day 4 — 작업을 나누고 중단한 개발을 이어 가기

### 개념 — 대화 재개와 작업 상태 복원

같은 세션을 재개하면 코딩 도구가 저장한 대화를 이어 사용할 수 있습니다. 그러나 다른 작업자가 코드를 바꾸었거나 브랜치가 달라졌다면 대화에 남은 설명과 현재 파일이 다를 수 있습니다. 재개할 때는 현재 브랜치·변경·검사 결과를 대조합니다.

다른 세션으로 넘길 때는 필요한 정보가 더 작아집니다. 예를 들어 “CSV 따옴표 처리는 끝났고, 팀 필터는 다음 변경이다. `ExportAcceptanceTest`에서 쉼표와 줄바꿈을 확인했다”는 인계가 다음 행동을 정하는 데 도움이 됩니다. `.local/harness/checkpoint.md`에 목적·현재 변경·확인한 동작·남은 결정과 파일 위치를 남깁니다. `SessionStart`가 이 내용을 전달하되 새 세션은 현재 코드와 대조합니다.

Worktree는 별도 브랜치의 파일 공간이고, 서브에이전트는 작업을 맡는 실행 주체입니다. 팀 필터와 파일 이름은 서로 다른 책임이므로 나누기 쉽습니다. 여러 작업자가 같은 CSV 조합 코드를 동시에 수정하면 합칠 때 입력 형태를 맞춰야 합니다. 작업을 나눌 기준은 인원 수보다 변경 파일·입출력의 의존성입니다.

### 설계와 실행

`TEAM`과 `FILENAME` 사례를 읽고 같은 공간의 서브에이전트와 별도 worktree 중 이번 변경에 맞는 작업 분리 방법을 고릅니다. 이번 활동에서는 분리된 두 작업을 실제로 수행해 인계와 통합을 확인합니다. 4주차에서 사용한 IDE·Codex의 worktree 경로를 이용하거나 파일 소유 범위가 겹치지 않는 서브에이전트 두 개로 진행합니다.

팀 선택의 입력과 파일 이름에 전달할 날짜를 먼저 정합니다. 한 작업에는 `TicketFilter`와 팀 선택 검사, 다른 작업에는 `ExportFilename`과 날짜 검사만 맡깁니다. 연결부인 `TicketExport`는 통합하는 작업에서 변경합니다. 각 작업의 결과에는 변경 내용·공개 입력·검사·남은 연결을 담습니다.

Worktree를 쓰면 해당 폴더에서 의존성을 동기화하고 `harnessJar`와 `setup .`를 다시 실행합니다. `.codex`와 `.local`은 Git으로 복사되지 않으며, 이전 폴더를 가리키는 Hook 명령을 새 작업에 사용할 수 없기 때문입니다. Skill과 프로젝트 지침은 Git으로 공유할 수 있습니다.

한 작업의 중간에 인계 메모를 남기고 세션을 끝냅니다. 같은 폴더에서 `codex resume`을 실행해 세션 목록에서 선택하거나 Codex 앱의 기존 대화를 다시 엽니다. 남은 일을 이어 수행하고, 별도 새 세션에도 인계 메모와 현재 변경을 읽게 해 필요한 정보가 전달되는지 확인합니다. 대화 저장·재개는 [Codex의 실행 기능](https://learn.chatgpt.com/docs/non-interactive-mode)을 사용합니다.

```text
TEAM과 FILENAME 요구에서 독립적으로 바꿀 코드와 통합할 연결부를 추천해 줘.
내 의견을 반영해 작업을 두 개로 나누고 각 작업의 입력·결과·검사·인계 내용을 정하자.
각 작업은 정한 파일 범위에서 구현하고, 통합 작업에서 TicketExport의 호출을 맞추자.
작업 중 한 번은 현재 변경과 남은 일을 인계 메모에 남기고 세션을 재개할게.
재개할 때 현재 브랜치·변경 파일·검사 결과를 읽어 인계 내용과 대조해 줘.
합친 후 OPS 팀 선택, 팀 미지정, 날짜 지정과 앞서 만든 CSV 사례를 함께 확인하자.
```

완료 기준은 **실제 작업 분리·인계·재개·통합 검사를 수행하고, 무엇을 분리했기에 함께 진행할 수 있었는지 설명한 것**입니다. 팀 필터와 이름 변경을 같은 입력 흐름에서 확인합니다.

## Day 5 — 새 요구로 환경을 사용하고 다음 프로젝트 준비하기

### 개념 — 관찰 결과로 개발 환경 바꾸기

하네스의 관찰 정보는 다음 수정을 고를 수 있어야 합니다. 사례를 못 찾았다면 자료 연결을, 같은 실패를 반복했다면 피드백과 검사를, 오래된 설명으로 수정했다면 재개 정보를 확인합니다. 제공 로그는 도구 이름·세션·턴·검사 상태만 남깁니다. 필요한 실패 세부는 해당 검사 결과에서 읽습니다.

`DEDUP` 요구는 같은 ID가 여러 번 오면 첫 항목을 채택한 뒤 상태와 팀을 거릅니다. T-1의 첫 항목이 CLOSED이고 뒤 항목이 OPEN이면 T-1을 내보내지 않습니다. 먼저 OPEN만 고르면 뒤의 T-1이 살아남으므로 순서가 업무 결과를 바꿉니다. 중복 수와 내보낸 수를 함께 반환하려면 결과 형태와 호출부 검사도 달라집니다.

### 설계·실행·해석

이 요구를 지금 만든 환경에 넣습니다. Skill이 필요한 사례를 가져오고, AI가 처리 순서와 결과 형태를 추천하고, 선택을 반영해 구현한 뒤 Hook으로 검사합니다. Day 1의 “입출력이 바뀌면 호출부와 검사를 함께 바꾼다”는 지침이 실제로 어떤 파일에 적용되는지 확인합니다.

```text
지금 구성한 개발 환경으로 DEDUP 요구를 구현하자.
개발 MCP로 사례를 조회하고 중복 제거와 필터 순서에 따른 결과 차이를 설명해 줘.
중복 수·내보낸 수·CSV를 어떻게 반환할지 추천하면 내가 의견을 말할게.
기능·호출부·검사를 함께 변경하고 자동 검사 결과와 실제 CSV를 확인하자.
이번 변경에서 누락되거나 반복된 작업이 있었다면 원인을 지침·자료·도구·검사·재개 정보 중 실제 관련 위치에서 찾아 줘.
필요한 환경 변경을 적용한 뒤 같은 사례로 효과를 확인하자.
```

환경 설정 한 가지를 바꿀 때는 예상 효과와 확인할 결과를 정합니다. 예컨대 사례 ID를 매번 잘못 고른다면 Skill의 조회 순서를 바꾸고 같은 요청에서 조회한 ID와 결과를 비교합니다.

12주차에는 IT 문의 처리 앱을 개발합니다. 모델을 부르는 제품 코드, 대역을 사용하는 업무 검사, 개발 도구 설정을 나누어야 합니다. 지금 만든 환경에서 재사용할 것은 요구 조회·검사·재개 방식이며, 바꿀 것은 프로젝트 설명·사례·Skill의 적용 조건·검사 명령입니다. 다음 주차 Day 1에서 실제로 연결합니다.

## 완료 기준

- 상시 지침·프로젝트 설명·Skill·개발 MCP가 맡는 역할을 실제 입력과 사용 결과로 설명했습니다.
- 코딩 도구에 Hook을 연결해 실제 검사와 실패 피드백을 확인했고, 수정 요청 한도와 실행 불가의 다음 행동을 이해했습니다.
- 나눈 작업을 실제로 인계·재개·통합하고 이전 기능과 새 요구를 함께 확인했습니다.
- DEDUP 요구를 환경 안에서 구현하고 처리 순서·결과 형태를 선택한 이유를 실제 CSV와 검사로 해석했습니다.
- 다음 프로젝트에서 유지할 방식과 바꿀 프로젝트 정보·검사를 정했습니다.

오프라인 테스트는 Hook 반환값, 검사 판정, 자료 조회와 상태 전달을 확인합니다. 실제 코딩 도구의 Skill·MCP·Hook 사용, 모델의 수정, 세션 재개는 학습자가 실행한 결과로 판단합니다.
