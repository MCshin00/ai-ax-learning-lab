## 이번 주의 문제 — AI와 개발할 때 필요한 정보를 매번 다시 연결해야 한다

운영팀이 문의 목록을 CSV로 내려받습니다. 첫 구현은 단순한 제목만 처리합니다. 이제 쉼표와 큰따옴표·줄바꿈이 있는 제목, 팀별 선택, 날짜가 있는 파일 이름, 중복 문의 처리까지 필요합니다. AI에 변경을 맡길 때마다 현재 구조와 요구를 설명하고, 검사 실행을 챙기고, 다음 세션에 남은 일을 다시 전달하면 작업이 길어질수록 빠뜨리는 조건이 생깁니다.

이번 주에는 이 Java 프로그램을 개선하면서 **개발 AI가 필요한 정보를 얻고, 코드를 바꾸고, 결과를 확인하고, 다음 작업을 이어 가는 환경**을 구성합니다. 이것이 여기서 다룰 개발 하네스입니다. 5주차의 실행·검사·재시도와 10주차의 개발 방식 선택을 프로젝트 환경으로 연결합니다.

하네스에는 모델을 호출하는 실행기, 작업 지침과 문맥, 사용할 도구, 작업 공간과 권한, 결과 검사와 피드백, 작업 상태와 재개 방법이 들어갑니다. Codex 같은 코딩 도구가 모델 호출과 도구 실행, 대화 저장을 제공하므로 이번에는 그 기능에 프로젝트 자료·Skill·MCP·Hook·검사를 연결합니다. 다른 코딩 도구에서도 같은 역할을 찾되 설정 형식과 지원 이벤트는 해당 도구에 맞춥니다.

```text
개발할 요구 + 원하는 결과
  → 지침·프로젝트 설명·Skill에서 작업 방법과 필요한 자료 찾기
  → 개발 MCP로 사례 조회 → 코드와 검사 변경
       ├─ 독립 작업: 분담 → 인계·재개 → 통합 검사
       └─ 종료 시 Hook: 현재 코드 검사 → 실패 전달 → 수정·재검사 또는 중단
  → 업무 결과 확인 + 개발 중 사용한 정보와 다음 행동 연결
```

예를 들어 따옴표가 들어간 제목이 올바르게 출력되면 CSV 기능의 결과를 확인한 것입니다. 여기에 **Skill이 고른 절차, MCP에서 받은 사례, 실제로 추가한 검사**를 연결하면 개발 환경이 맡은 역할도 확인할 수 있습니다. 요청문에는 업무 요구를 담고, 반복할 절차는 구성한 환경에서 가져오도록 진행합니다.

## Day 1 — 지침을 적용해 첫 변경하기

### 개념 — 지침·문맥·도구·검사의 책임

작업 지침은 반복해서 지켜야 할 개발 방법입니다. “기능을 바꿀 때 해당 입력과 기존 대표 입력을 함께 검사한다”가 그 예입니다. 문맥은 현재 작업을 이해할 자료입니다. “CSV 열 순서는 id, team, status, title이다”는 이 프로젝트의 문맥입니다. Skill은 특정 종류의 요청에 적용할 절차이며, 도구는 파일 수정·검사·자료 조회처럼 실제 행동을 수행합니다.

상시 지침에는 작업 원칙을, 프로젝트 설명에는 현재 구조를, 요구별 자료에는 구체적인 입력과 기대 결과를 둡니다. “쉼표가 있는 제목도 처리해 달라”는 짧은 요청에서 지침이 사례를 찾는 위치와 검사 방법을 안내할 수 있습니다. 이후 프로젝트가 바뀌면 자료 위치와 검사 명령을 바꾸고, 입력과 결과를 확인하는 원칙을 재사용합니다.

검사는 구현을 구체적인 입력과 결과로 판단합니다. 이 프로젝트의 초기 검사는 단순 제목만 확인하므로 쉼표 처리를 잘못해도 통과할 수 있습니다. 새 요구를 확인할 입력을 추가해야 통과 결과의 의미도 달라집니다.

### 지침을 구성하고 실제 변경에 사용하기

`TicketExport.csv`에 `T-1 / OPS / OPEN / VPN 접속`을 넣는 경로를 따라갑니다. `TicketFilter`가 OPEN 문의를 고르고 `CsvCell`이 각 값을 표현한 뒤 `TicketExport`가 연결합니다. `CSV-COMMA`의 `VPN, 접속`은 제목 전체를 `"VPN, 접속"`으로 표현해야 쉼표를 제목의 일부로 보존합니다. 바꿀 책임은 셀 표현이며, OPEN 선택과 열 순서는 이 입력에서도 함께 확인할 조건입니다.

AI에게 다음 요청으로 지침 구성을 추천받습니다. 어떤 입력을 검사에 남길지 짧게 의견을 말한 뒤 `setup/AGENTS.example.md`를 참고해 프로젝트의 `AGENTS.md`를 작성하고 `docs/project.md`를 현재 코드와 맞춥니다.

```text
제공 문의 내보내기 프로그램과 CSV-COMMA 사례를 읽어 줘.
입력부터 CSV까지의 코드 경로를 설명하고, 이번 변경에 필요한 지침과 자료 배치를 추천해 줘.
어떤 누락이나 반복 설명을 줄일 수 있는지 실제 입력으로 설명하면 내 의견을 말할게.
의견을 반영해 프로젝트 지침과 설명을 구성하자.
```

권한은 프로젝트 코드 수정과 검사 실행에 맞춥니다. Codex의 작업 폴더를 `development_harness`로 지정하고 지침을 저장한 뒤 새 세션에서 변경을 요청합니다. CLI로 시작할 때는 이 폴더에서 다음 명령을 사용합니다.

Windows PowerShell / macOS·Linux·WSL:

```text
codex --sandbox workspace-write -a on-request
```

Codex는 시작할 때 프로젝트 경로의 지침을 읽습니다. 현재 세션에 전달된 지침과 실제 작업 폴더를 확인할 때는 [공식 지침 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)를 참고합니다. 새 세션에는 다음 업무 요청을 보냅니다.

```text
제목에 쉼표가 들어가도 원래 제목이 한 셀로 보존되도록 수정해 줘.
```

AI가 추천한 변경 위치와 검사 입력을 읽고 의견을 말한 뒤 구현합니다. IDE의 diff와 `acceptance` 결과에서 쉼표 입력과 기존 단순 제목을 확인합니다. `ExportExample.main`의 제목을 제공 사례로 맞춰 CSV도 확인합니다.

### 결과를 읽는 방법

`CsvCell.encode`가 바뀌고 `VPN, 접속`과 `VPN 접속`을 검사했다면 지침의 “변경 입력과 기존 대표 입력을 확인한다”는 원칙이 구체적인 코드·검사로 이어진 것입니다. 자료를 읽은 흔적, 추가한 검사와 실제 결과를 연결합니다. 누락됐다면 작업 폴더와 적용된 지침을 확인하고, 자료 위치나 검사 조건의 표현을 조정해 같은 변경에서 다시 확인합니다.

여기서 확인할 것은 **이번 요청에서 다시 적지 않은 원칙이 실제 작업에 적용됐는가**입니다. 노트에는 적용된 지침과 해당 변경·검사, 또는 누락과 조정 결과를 남깁니다.

완료 기준은 **지침을 사용해 첫 기능 변경을 수행하고, 지침의 어느 부분이 자료 확인·구현·검사에 쓰였는지 실제 결과와 연결한 것**입니다.

## Day 2 — Skill과 개발 MCP로 후속 요구 처리하기

### 개념 — 재사용할 절차와 조회한 자료의 역할

Skill은 “이 종류의 변경에서 무엇을 확인할까”를 재사용합니다. 개발 MCP는 “필요한 사례를 어떤 기능으로 조회할까”를 제공합니다. `get_acceptance_case(id)`는 입력·기대 결과·판단 이유를 반환합니다. `CSV-QUOTE`의 제목 `VPN, "접속"`은 셀 전체를 감싸고 내부 큰따옴표를 두 번 써서 `"VPN, ""접속"""`으로 표현해야 합니다. 셀을 감싸기만 하면 제목 안의 큰따옴표 처리가 빠집니다.

여기서 MCP를 호출하는 주체는 개발 AI이고, 완성된 CSV 프로그램은 MCP와 모델 없이 실행됩니다. 로컬 JSON은 공유된 요구 서비스의 역할을 재현합니다. 지금처럼 파일이 작업 폴더에 있으면 직접 읽을 수 있고, 자료가 외부 서비스에 있거나 여러 프로젝트가 같은 사례를 조회한다면 도구 연결을 사용할 수 있습니다.

### 연결을 준비하고 짧은 요청으로 사용하기

Gradle 창에서 `harnessJar`를 실행해 `build/libs/harness-kit.jar`를 만듭니다. CLI는 코딩 도구가 Hook 프로세스와 MCP 서버를 시작할 명령을 등록하는 데 사용합니다. `development_harness` 폴더의 IDE 터미널에서 실행합니다.

Windows PowerShell:

```powershell
java -jar .\build\libs\harness-kit.jar setup .
```

macOS·Linux·WSL:

```bash
java -jar ./build/libs/harness-kit.jar setup .
```

생성된 `.local/harness/mcp-snippet.toml`의 서버 항목을 Codex 프로젝트 MCP 설정에 넣습니다. CLI에서는 프로젝트의 `.codex/config.toml`에 해당 항목을 추가합니다. 기존 설정에는 서버 항목을 병합합니다. 프로젝트를 신뢰한 상태에서 새 세션을 열고 `/mcp`로 `acceptance_cases`와 도구 목록을 확인합니다. [공식 MCP 설정 안내](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)를 참고합니다. `setup`이 만든 Hook은 Day 3에서 검토하고 활성화합니다.

`setup/export-change`를 프로젝트의 `.agents/skills/export-change`로 복사하고 현재 지침과 맞춥니다. 사례를 가져오고 검사할 조건을 고르는 절차 중 어떤 부분을 반복 사용하려는지 AI의 추천을 읽고 의견을 반영합니다. Skill 목록에서 인식되는지 확인한 뒤 명시적으로 선택해 다음 요청을 보냅니다. [Skill 선택과 사용](https://learn.chatgpt.com/docs/build-skills)

```text
export-change Skill로 CSV-QUOTE 요구를 처리해 줘.
```

추천한 셀 표현과 검사 입력을 검토한 뒤 구현합니다. Day 1에서 이 조건까지 처리했다면 현재 구현으로 큰따옴표 사례와 기존 쉼표·단순 제목을 확인합니다. IDE에서 실제 CSV와 `acceptance` 결과를 읽습니다.

### 절차·자료·결과 연결하기

Skill을 읽은 흐름과 실제 `get_acceptance_case("CSV-QUOTE")` 호출을 확인합니다. 반환된 `expectedCell`의 두 큰따옴표가 검사 기대값에 반영되고, 구현에서 내부 따옴표를 바꾼 뒤 셀을 감싸는 처리가 이어지는지 봅니다. 이 순서를 뒤집어 바깥 따옴표까지 두 번 쓰면 결과가 달라집니다. 선택한 구현이 같은 표현을 만드는지 원문 제목과 대조합니다.

이때 Skill은 자료 확인·변경 제안·검사의 순서를 제공했고, MCP는 판단에 쓸 구체적인 사례를 제공했습니다. 실제 작업에서 가져온 조건과 바뀐 코드·검사를 노트에 연결합니다. Skill을 선택하지 않았거나 로컬 파일만 읽었다면 그 경로를 기록하고 연결 설정을 확인한 뒤 실제 Skill·MCP 사용까지 확인합니다.

완료 기준은 **짧은 후속 요청에서 Skill의 절차와 실제 MCP 조회가 사용되고, 가져온 조건이 구현·검사·CSV에 어떻게 반영됐는지 확인한 것**입니다.

## Day 3 — 종료 전 실패를 수정과 재검사로 연결하기

### 개념 — 사건에 반응하는 Hook과 피드백 루프

Hook은 코딩 도구의 특정 사건에 연결하는 실행입니다. 참고 구현의 `SessionStart`는 프로젝트 설명과 인계 메모를 전달하고, `PostToolUse`는 실행한 도구 이름을 기록합니다. `Stop`은 응답을 끝내려 할 때 `GradleCheck`로 업무 검사를 실행합니다. 실패 근거를 돌려주면 코딩 도구가 이어서 수정할 수 있습니다.

검사는 새 빌드 폴더에서 실행하고 그 실행의 JUnit 결과를 읽습니다. 기능 실패에는 검사 이름과 기대·실제 값을 볼 결과 위치를 전달합니다. 빌드 시작 실패나 결과 누락은 검사 실행 불가로 구분합니다. 이때 필요한 다음 행동은 실행 환경 확인입니다.

참고 구현은 첫 기능 실패에 한 번의 자동 수정 요청을 보냅니다. 다음 종료 시점에 다시 검사해 통과하면 마치고, 계속 실패하면 결과를 사람에게 넘깁니다. `stop_hook_active`로 같은 응답이 이미 Stop에 의해 이어졌는지 확인합니다. 수정 요청 횟수는 비용과 실패 유형에 맞춰 선택할 수 있습니다.

### Hook 연결과 실패 상태 준비

생성된 `.codex/hooks.json`과 `HookHandler`에서 JAR·프로젝트 위치·이벤트를 확인합니다. 코딩 도구의 `/hooks`에서 검토·신뢰하고 적용합니다. 사용 중인 버전에 이 기능이 없다면 Hook을 지원하는 CLI에서 진행합니다. 이벤트와 응답 형식은 [공식 Hook 안내](https://learn.chatgpt.com/docs/hooks)를 참고합니다.

먼저 `CSV-LINE`의 `첫 줄\n다음 줄`을 다루는 업무 검사를 추가하고 실행합니다. 원문 LF를 보존하면서 셀 전체를 감싼 `"첫 줄\n다음 줄"`이 기대 결과입니다. 기능이 아직 없다면 이 실패를 사용합니다. 이미 통과한다면 현재 diff를 보관하고 셀 표현에서 줄바꿈만 처리하지 않는 작은 결함을 임시로 넣습니다. 이는 Hook의 실패 전달을 확인할 재현이며 같은 프로젝트에서 진행합니다.

준비 단계에서는 Hook을 비활성화하고, IDE에서 줄바꿈 검사가 실패하며 쉼표·큰따옴표 검사는 통과하는지 확인합니다. 그 뒤 Hook을 활성화하고 다음 요청을 보냅니다. 첫 응답은 요약만 하게 해 종료 전 검사가 실패를 발견하는 장면을 만듭니다.

```text
지금은 Hook의 실패 피드백을 확인하는 실습이야.
먼저 현재 변경을 짧게 요약하고 응답을 마쳐 줘.
종료 Hook에서 수정 요청이 오면 실패 근거로 코드를 고치고 재검사까지 진행해 줘.
```

### 실패 근거가 다음 행동을 바꾸는 과정

도구 화면에서 종료 검사와 이어진 수정 응답을 확인합니다. `.local/harness/events.jsonl`의 같은 세션·턴에서 `FAILED` 후 `PASSED`가 나타나는지 보고, 피드백이 가리킨 JUnit 결과에서 줄바꿈 입력의 기대값과 실제값을 읽습니다. `last-check.json`은 마지막 검사 결과입니다.

예를 들어 실제값에 셀 바깥 따옴표가 없었다면 `CsvCell`의 감싸기 조건을 고칠 근거가 됩니다. 결과를 통과시키려고 제목의 LF를 제거하면 원문 보존 요구와 어긋납니다. 수정한 코드와 새 CSV에서 LF와 바깥 따옴표를 함께 확인합니다. 임시 결함은 이 수정으로 해소하고 기존 CSV 사례도 다시 통과해야 합니다.

사용자가 실패 내용을 다시 복사해 수정 지시를 보내는 부분을 Hook이 맡았습니다. 어떤 검사 실패가 어떤 코드 변경으로 이어졌는지 노트에 남깁니다. 수정이 이어지지 않으면 실패 전달과 수정 실행 중 멈춘 위치를 확인합니다. 계속 실패하거나 검사가 실행되지 않는 분기는 `HarnessTest`와 `HookHandler`의 반환값을 읽어 설명합니다. 실제 Host에서 관찰한 경로와 대역 검사로 확인한 분기를 구별합니다.

완료 기준은 **실제 Hook의 실패 전달 → 모델의 수정 → 새 검사 → 종료를 확인하고, 실패 근거와 수정 이유를 연결한 것**입니다. 한도에 도달했다면 남은 실패를 해결한 뒤 연결 확인을 마칩니다.

## Day 4 — 환경과 작업 정보를 이어 받아 분담·재개하기

### 개념 — 작업 공간과 다음 행동을 잇는 정보

Worktree는 별도 브랜치의 파일 공간이고, 서브에이전트는 작업을 맡는 실행 주체입니다. 팀 필터와 파일 이름은 서로 다른 책임이므로 나누기 쉽습니다. 연결부인 `TicketExport`와 같은 검사 파일을 동시에 바꾸면 합치는 작업이 늘어납니다. 따라서 구현 파일·검사 파일·통합할 호출부를 함께 보고 나눕니다.

같은 세션은 저장한 대화를 이어 사용할 수 있습니다. 새 세션은 목적·현재 변경·확인한 동작·남은 결정과 파일 위치를 담은 인계 메모로 다음 행동을 찾습니다. 예를 들어 “팀 선택 함수와 전용 검사는 끝났고 `TicketExport`의 호출은 아직 연결하지 않았다”는 내용은 다음 작업을 호출부 수정으로 좁힙니다. `SessionStart`가 메모를 전달하고, 현재 diff와 검사로 진행 상태를 대조합니다.

### 작업별 환경과 변경 범위 정하기

`TEAM`과 `FILENAME` 사례로 다음 요청을 보냅니다. AI의 분리 방법과 입력·결과 추천을 검토하고 의견을 말합니다.

```text
TEAM과 FILENAME 요구를 두 작업으로 나눠 구현하고 싶어.
각 작업의 코드·검사 범위와 합칠 연결부, 사용할 개발 환경을 추천해 줘.
추천을 검토한 뒤 한 작업은 중간에 인계하고 새 세션에서 이어서 통합할게.
```

같은 공간의 서브에이전트 또는 별도 worktree 중 선택합니다. 예를 들어 한 작업은 `TicketFilter`와 `TeamFilterTest`, 다른 작업은 `ExportFilename`과 `ExportFilenameTest`를 맡고, 통합 작업은 `TicketExport`·`ExportExample`·전체 CSV 검사를 맡습니다. `acceptance`는 `lab/export` 패키지의 모든 검사 클래스를 실행하므로 분리한 검사도 결과에 포함되는지 봅니다.

Worktree를 선택하면 프로젝트 지침과 Skill을 새 위치에 준비하고 의존성을 동기화합니다. 해당 폴더에서 `harnessJar`와 `setup .`로 Hook·MCP를 연결합니다. `.codex`와 `.local`은 Git으로 공유되지 않아 각 작업 폴더의 설정이 필요합니다. 서브에이전트는 사용할 지침·Skill·도구가 전달되는지 확인합니다. 제공 `Stop` 검사는 연결된 주 세션에서 실행되므로 하위 작업의 검사 결과를 받고 통합 후 주 세션에서도 검사합니다.

새 공개 메서드를 추가해 기존 호출을 유지한 채 각 기능을 검사하거나, 호출부 수정까지 필요한 작업을 순서대로 배치할 수 있습니다. 두 방법이 통합 전 빌드와 독립 검사에 주는 영향을 보고 고릅니다. 분리된 작업에서는 선택한 파일과 전용 검사를 변경하고, 연결부는 통합 담당이 처리합니다.

### 중단·재개와 통합 결과 읽기

한 작업을 전용 검사까지 끝낸 지점에서 `.local/harness/checkpoint.md`에 남은 연결과 필요한 판단을 적고 세션을 마칩니다. 같은 세션은 Codex 앱의 대화를 다시 열거나, 해당 폴더에서 `codex resume`으로 이어 갈 수 있습니다. 이번에는 **새 세션에서도** 다음 요청으로 작업 정보가 전달되는지 확인합니다.

```text
진행 중인 문의 내보내기 변경을 이어서 마무리해 줘.
```

시작 Hook이 전달한 메모에서 남은 호출부 연결을 찾았는지, 현재 코드와 대조해 이미 끝난 필터를 다시 만들지 않았는지 봅니다. 다른 작업이 먼저 연결했다면 그 차이를 확인하고 남은 검사로 이동해야 합니다. 전달되지 않은 정보가 있으면 인계 내용이나 시작 Hook의 연결을 조정합니다.

두 결과를 합친 뒤 OPS 선택·팀 미지정·지정 날짜와 앞서 만든 CSV 사례를 검사합니다. `TicketExport`에 팀 입력이 전달되는지와 날짜가 `ExportFilename`에 전달되는지 실제 실행 경로를 확인합니다. 노트에는 나눌 수 있었던 책임, 각 작업에서 사용한 환경, 인계 정보가 정한 다음 행동과 통합 결과를 남깁니다.

완료 기준은 **각 작업에서 자료·검사를 사용하고, 인계 정보로 새 세션의 다음 행동을 정해 두 변경을 통합한 것**입니다.

## Day 5 — 업무 요구로 전체 환경을 사용하고 조정하기

### 개념 — 관찰한 문제에 맞춰 환경 바꾸기

하네스는 반복할 방법을 제공하고, 요청은 이번에 필요한 업무 결과를 정합니다. 사례를 못 찾았다면 자료 접근과 Skill의 적용 조건을, 같은 실패를 반복했다면 검사 결과에 담긴 근거를, 끝난 일을 다시 했다면 인계 내용을 살펴봅니다. 관찰한 문제와 관련된 위치를 바꿔야 다음 실행의 차이를 해석할 수 있습니다.

`DEDUP`은 같은 ID의 첫 항목을 채택한 뒤 상태와 팀을 거릅니다. T-1의 첫 항목이 CLOSED이고 뒤 항목이 OPEN이면 T-1은 내보내지 않습니다. OPEN만 먼저 고르면 뒤의 T-1이 살아남습니다. 중복 수와 내보낸 수를 반환하려면 CSV 문자열만 반환하던 결과 형태와 호출부도 함께 살펴야 합니다.

### 업무 요구를 전달하고 전체 흐름 확인하기

다음 요청에는 업무 조건과 원하는 결과를 담습니다. 환경에서 가져올 절차가 실제로 사용되는지 봅니다.

```text
문의 내보내기에 DEDUP 요구를 적용해 줘.
같은 ID는 먼저 나온 문의를 채택한 뒤 상태와 팀을 거르고,
제외한 중복 수·내보낸 수·CSV를 함께 받을 수 있게 해 줘.
```

AI가 제안한 처리 순서와 결과 형태를 검토하고 의견을 말한 뒤 구현합니다. 개발 세션에서 Skill의 사용과 사례 조회를 확인하고, diff에서 결과를 받는 호출부와 검사가 함께 바뀌었는지 봅니다. 종료 Hook의 검사와 실제 CSV를 읽습니다. 제공 입력의 결과는 T-2만 포함한 CSV, 중복 수 1, 내보낸 수 1입니다.

여기서는 Day 1의 호출부 변경 지침이 적용됩니다. 예를 들어 결과가 문자열에서 CSV·중복 수·내보낸 수를 담는 값으로 바뀌었다면 `ExportExample`의 출력과 전체 CSV 검사가 그 값을 사용하는지 확인합니다. 수정 위치를 요청에서 열거하지 않아도 이 연결을 찾아 변경했는지가 지침 사용의 근거입니다.

### 실제 누락·반복에 맞춰 조정하기

요청 이후 실제로 사용한 절차·자료·검사와 결과를 연결합니다. Skill이 선택되지 않았다면 이름을 명시해 이어 진행하고, 요청과 Skill 설명의 연결을 살펴봅니다. 잘못된 사례를 조회했다면 선택 기준을, 호출부를 빠뜨렸다면 변경 지침과 관련 검사를 확인합니다. 로그의 도구 이름만으로는 어떤 조건을 반영했는지 알 수 없으므로 해당 호출 결과와 diff도 함께 읽습니다.

바꿀 부분이 있다면 예상 효과를 말하고 그 위치를 조정한 뒤 같은 요청이나 실패 사례에서 확인합니다. 같은 작업을 다시 시작해야 한다면 변경 전 상태의 별도 작업 공간을 사용해 완성한 결과와 비교합니다. 누락 없이 진행됐다면 어떤 정보가 다음 행동으로 이어졌는지 설명하고 현재 구성을 유지합니다.

12주차 IT 문의 앱에서는 프로젝트 설명·사례·Skill 적용 조건·검사 명령을 그 앱에 맞춥니다. 재사용할 방식은 요구를 찾고, 변경과 검사로 연결하고, 실패와 남은 일을 다음 행동으로 넘기는 흐름입니다. 다음 주차 Day 1에서 실제로 연결합니다.

완료 기준은 **업무 요구 중심의 요청으로 환경을 사용하고, 실제 사용 결과에서 유지할 구성과 조정할 부분을 판단한 것**입니다. 노트에는 업무 결과와 하네스가 맡은 구체적인 작업을 연결합니다.

## 완료 기준

- 지침을 사용한 첫 변경에서 적용된 원칙과 실제 코드·검사를 확인했습니다.
- 짧은 후속 요청에서 Skill의 절차와 MCP 사례가 구현·검사에 쓰이는 경로를 확인했습니다.
- 실제 Hook이 실패를 전달하고 수정·재검사로 이어지는 것을 확인했으며, 반복 실패와 실행 불가 때의 다음 행동을 설명했습니다.
- 나눈 작업에서도 필요한 환경을 사용하고, 인계 정보로 새 세션의 다음 행동을 정해 통합했습니다.
- DEDUP의 업무 결과와 개발 과정을 함께 읽고, 다음 프로젝트에 가져갈 방식과 바꿀 정보를 정했습니다.

오프라인 테스트는 Hook 반환값·검사 판정·자료 조회·상태 전달을 확인합니다. 실제 코딩 도구의 지침·Skill·MCP·Hook 사용, 모델의 수정과 새 세션의 재개는 학습자가 실행한 결과로 판단합니다.
