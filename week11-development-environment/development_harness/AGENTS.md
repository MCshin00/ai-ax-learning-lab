# 개발 지침

- 현재 기능과 파일 역할은 `docs/project.md`에서 확인한다. 현재 요청과 코드를 대조해 확정된 조건과 결정할 조건을 구분하고, 입력·기대 결과를 정해 검사에 반영한다.
- 반복할 작업 원칙은 이 파일에, 확정한 업무 조건·현재 구조·검사 위치는 `docs/project.md`에, 확인할 입력과 기대 결과는 검사 코드에 둔다. 기능 변경으로 설명이 달라지면 해당 자료도 갱신한다.
- 공개 메서드의 입력이나 결과가 바뀌면 호출부와 관련 업무 검사를 함께 확인하고 수정한다. 현재 클래스 배치를 고정하지 않고 요구에 맞춰 책임과 연결을 검토한다.
- 업무 기능을 변경하면 해당 요구의 입력을 검사에 반영하고 Gradle `acceptance`로 확인한다. 하네스 구현이나 공통 빌드 설정도 바뀌면 `test`로 전체 검사를 실행한다. IDE의 Gradle 실행으로 충분하면 그 경로를 사용한다.
- 검사 실패는 입력·기대값·실제값을 대조해 수정한다. 빌드나 검사 실행이 불가능하면 환경·설정 원인과 필요한 조치를 알린다. 검사가 없거나 실행되지 않은 상태를 통과로 판단하지 않는다.
- 확인한 동작과 아직 검사에 포함되지 않은 요구를 구분한다. 자동 검사 통과를 실제 코딩 도구의 Skill 사용·Hook 연결 확인으로 대신하지 않는다.
- 작업을 넘길 때 변경 파일·확인한 동작·남은 결정과 다음 행동을 `.local/harness/checkpoint.md`에 남긴다. 재개 시 인계 내용을 현재 코드와 검사 결과에 대조한다.

## 합의 후 변경 작업 진행

- 업무 조건과 공개 입출력·완료 기준을 합의한 요청은 메인 에이전트가 작업 공간 준비, 담당 배정, 결과 대기와 확인, 통합 인계, 최종 검사까지 이어 간다. 단계가 바뀔 때마다 사용자에게 진행 지시를 요청하지 않는다. 업무 의미가 미정이거나 바뀌면 입력별 결과 차이를 보여 주고 의견을 받는다.
- 분담 여부와 담당 수는 변경의 독립성, 공유 파일, 검사 비용을 보고 정한다. 서로 다른 파일과 전용 검사로 나눌 수 있는 작업만 동시에 맡기고, 공유 호출부와 통합 검사는 담당별 결과 확인 뒤 한 담당에게 맡긴다. Codex의 기본 서브에이전트 기능을 사용하며, 별도 요청이 없으면 메인의 모델·추론 설정을 바꾸지 않는다. 현재 작업 공간의 미커밋 변경과 기존 Worktree를 확인하고, 새 Worktree에 미커밋 상태가 자동 전달된다고 가정하지 않는다.
- 각 담당에게 확정 조건, 대표 입력과 기대 결과, 담당 파일과 수정 금지 경계, 검사 대상, 인계 항목을 전달한다. 담당은 작업 위치·변경 파일·확인한 입력과 결과·검사 위치·이미 시도한 실패 수정·남은 연결을 반환한다. 메인은 결과를 현재 코드에 대조하고 담당별 검사를 확인한 뒤 통합 담당에게 실제 결과와 남은 호출부를 전달한다. 인계 메모는 단계마다 현재 상태로 갱신한다.
- 메인이 실패 수정 요청을 한곳에서 관리한다. 실패한 입력·기대값·실제값을 대조해 해당 담당에게 같은 실패의 집중 수정을 한 번 요청하고 재검사한다. 담당이 이미 시도한 같은 실패의 수정도 이 한 번에 포함한다. Stop Hook은 최종 업무 검사 결과만 판정하며 별도의 수정 요청을 만들지 않는다. 같은 실패가 다시 남거나, 환경 조치 후에도 검사 실행이 불가능하거나, 수정에 새로운 업무 결정이 필요하면 이유와 결과 위치를 남기고 중단한다.
- 통합 후 메인이 합의한 업무 입력의 `acceptance`와 대표 실제 출력을 확인한다. 하네스나 공통 빌드 설정을 바꾼 경우 `test`도 실행한다. Hook 통과만으로 업무 결과나 실제 서브에이전트 인계를 확인했다고 판단하지 않는다.
