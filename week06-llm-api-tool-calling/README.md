## 중심 질문과 핵심 결과

애플리케이션이 모델과 Tool을 어떻게 호출할까요? 모델이 필요한 정보를 요청하면 프로그램이 실제 함수를 실행하고 그 결과를 다시 전달해야 합니다. 이번 결과물은 **SDK로 연결한 Tool Calling 앱과 사용자 답변을 이어받는 대화 흐름**입니다. 제공 고객 조회 업무에서 어떤 정보와 행동을 모델에 맡길지 판단하고, Tool 계약과 애플리케이션의 실행 흐름을 직접 설계합니다. Day 2에서 전체 고객 레코드를 반환하는 연결을 확인하고, Day 3에는 요금제·계정 상태 중 요청한 항목만 모델에 돌려주도록 같은 앱의 계약과 결과 처리를 바꿉니다. Day 5에는 같은 앱에서 “요금제를 알려주세요” → 고객 번호 확인 질문 → “C-100” → 실제 조회에 근거한 안내를 이어 갑니다.

`C-100 고객의 요금제를 알려주세요`라는 요구에서 모델은 고객 DB의 현재 값을 알 수 없습니다. 프로그램이 지침에 모든 고객 정보를 붙이는 대신 `get_customer_context(customer_id)`라는 좁은 조회 기능을 공개합니다. 모델은 조회의 필요성을 판단하고, 코드는 인자·허용 함수·호출 한도를 판단합니다. 반환값이 `basic`이면 실제 근거는 모델의 기억이 아니라 이번 조회 결과입니다.

## 기본 개념

### 모델 요청과 대화 상태

요청에는 모델, 지침, 사용자 입력, 사용할 도구 설명과 출력 제한이 들어갑니다. 응답은 자연어 답변뿐 아니라 함수 호출이나 불완전한 출력일 수 있습니다. HTTP 성공을 사용자 요구의 완료와 같게 보지 않습니다. SDK는 요청 형식과 통신을 도와주고, 다음 행동의 의미는 애플리케이션이 결정합니다.

대화 상태는 다음 호출에 전달할 이전 입력과 출력입니다. 사용자 질문만 다시 보내면 모델은 조회 결과를 모릅니다. 호출 요청과 실제 결과를 함께 보내야 `이 결과가 어떤 요청의 응답인가`를 연결할 수 있습니다. 사용자가 뒤이어 “C-100”이라고 답할 때도 앞선 요금제 질문과 앱의 고객 번호 확인 질문이 있어야 무엇을 조회할지 연결할 수 있습니다. 한 입력을 처리하는 모델·도구 왕복과 여러 사용자 입력을 이어받는 대화는 상태를 유지하는 기간이 다릅니다.

### Tool 정의와 실제 실행

`Quickstart.TOOL`의 JSON Schema는 `customer_id`라는 문자열 하나만 허용합니다. `strict(true)`와 `additionalProperties=false`는 모델에게 주는 형식 계약입니다. `executeCall`은 실제 입력을 다시 검사하고 등록한 함수만 실행합니다. 모델이 함수 이름을 써냈다는 이유로 같은 이름의 임의 코드를 실행하지 않습니다.

```java
if (!TOOL.name().equals(name)) return Map.of("error", "UNKNOWN_TOOL");
// JSON 구조와 customer_id 타입 검사 뒤
return getCustomerContext(data.get("customer_id").textValue());
```

형식이 맞는 `C-404`도 데이터에는 없을 수 있습니다. `INVALID_ARGUMENTS`는 요청 구조 문제이고 `CUSTOMER_NOT_FOUND`는 조회 결과입니다. 이 차이를 보존하면 다음 행동을 인자 수정과 고객 ID 확인으로 나눌 수 있습니다. 성공처럼 보이는 빈 객체로 합치면 모델이 무엇을 보완할지 알기 어렵습니다.

### 호출 루프와 종료 정책

```text
사용자 입력 → 모델 요청 → 응답 분류
                         ├─ 답변 / 거절 / 불완전 응답 → 종료
                         └─ 함수 호출 → 인자 확인 → 함수 실행
                                         → call_id와 실제 결과 전달 → 다음 모델 요청
```

제공 정상 대역의 고객 조회는 모델 요청 두 번과 로컬 함수 한 번입니다. 모델은 조회 뒤 추가 호출을 요청할 수도 있습니다. 제공 예제는 응답당 호출 하나를 순서대로 처리하고 모델 요청을 최대 세 번으로 제한합니다. 마지막 허용 응답에서 또 호출을 요청하면 함수를 추가로 실행하지 않고 `STOPPED`로 종료합니다. 결과를 모델에 돌려줄 기회가 없는 실행을 시작하지 않기 위한 선택입니다.

이 숫자는 모든 앱의 정답이 아닙니다. 두 시스템을 순차 조회해야 하는 요구라면 더 많은 단계가 필요할 수 있고, 쓰기 작업이라면 재호출 전에 승인과 중복 실행 방지를 추가로 판단해야 합니다. 이번 제공 함수는 조회이므로 업무 오류도 모델에게 반환해 사용자에게 보완을 요청하게 합니다.

### 토큰과 비용

토큰은 모델이 입력과 출력을 처리하는 단위이며, 사용량과 비용을 읽는 기준입니다. 입력에는 질문뿐 아니라 지침·도구 정의·재전달한 대화가 포함됩니다. 예를 들어 고객 번호를 추가로 받으면 다음 요청에는 앞선 질문과 확인 답변도 들어갑니다. 사용량은 이 구성이 요청에 어떤 영향을 주는지 이해하는 보조 정보입니다.

참고 예제의 `turns[].usage`는 SDK 응답의 사용량을 보존합니다. `UNAVAILABLE`과 `null`은 사용량을 받지 못했다는 뜻이며 0원과 다릅니다. 실제 요금은 선택한 모델·서비스 조건에 따라 달라집니다. 세부 토큰 분류와 금액 계산은 주차 끝의 **선택 참고: 사용량과 비용 읽기**에서 다룹니다.

## 요구에서 구조를 만드는 해설

### 먼저 결정할 것은 모델의 자리다

제공 요구는 “자연어로 요금제나 계정 상태를 물으면 현재 고객 값을 근거로 안내한다. 고객을 식별할 수 없으면 확인을 요청하고, 없는 고객을 존재하는 것처럼 설명하지 않는다”입니다. `CustomerDirectory.lookup("C-100")`은 `customer_id=C-100, plan=basic, status=active`를 반환합니다. 이 업무 함수에는 모델도 대화도 없습니다.

이 요구는 세 구조로 풀 수 있습니다. 정해진 화면에서 ID를 받는다면 일반 코드가 바로 조회하고 결과를 표시할 수 있습니다. 자연어 질문을 받아도 항상 같은 조회가 필요하다면 **코드가 조회한 다음 모델에 설명만 맡기는 흐름**이 가능합니다. 반면 요약·일반 안내와 고객 조회가 섞이고 필요한 입력을 대화에서 얻는다면 **모델이 공개된 Tool의 사용을 요청하고 앱이 실행하는 흐름**이 어울립니다. 이번에는 마지막 흐름을 구성해 Tool Calling을 배웁니다. 모델이 매번 도구를 고르는 것이 모든 앱의 기본값은 아닙니다.

### 업무 함수를 그대로 공개할지 결정한다

요금제와 계정 상태는 같은 고객 레코드에서 나옵니다. 다음은 두 계약의 차이입니다. 둘을 모두 구현하는 과제가 아니라 공개할 기능의 크기를 고르는 근거입니다.

| 후보 계약 | 정상 입력과 결과 예 | 책임과 선택 이유 |
|---|---|---|
| 고객 문맥 조회 한 개 | `{customer_id:"C-100"}` → `{customer_id:"C-100",plan:"basic",status:"active"}` | 두 질문에 같은 최신 레코드가 필요하므로 한 번에 반환. 모델에는 요금제와 상태의 의미를 설명 |
| 요금제 조회와 상태 조회 분리 | 요금제 Tool에 같은 ID → `{plan:"basic"}` | 각 기능의 권한·데이터 제공자가 다를 때 따로 공개하기 편함. 두 값을 함께 물으면 호출과 오류 결합을 앱이 관리 |

Day 2의 제공 요구는 같은 레코드를 함께 반환하므로 한 Tool이 간단합니다. Day 3에는 “요금제·상태 중 요청한 항목만 반환”하는 후속 요구를 적용해, 한 Tool에 조회 항목을 표현할지 기능을 나눌지 다시 판단합니다. 여기서 `customer_id`는 모델이 선택할 입력이고, DB 연결·허용 함수 목록은 앱이 소유할 설정입니다. 모델에 임의 SQL이나 실행 파일 경로를 입력받을 필요가 없습니다. 없는 ID를 빈 성공 데이터로 돌려주면 `basic`을 추측할 여지가 생기므로 오류임을 구별할 수 있게 반환합니다. 오류의 필드명이나 Java 타입은 설계 선택이고, 호출 결과를 원래 `call_id`에 대응시키는 것은 API 계약입니다.

참고 `Quickstart`는 한 계약을 다음처럼 코드로 표현합니다. `FunctionTool`의 스키마는 모델이 보내야 할 형식, `executeCall`의 분기는 앱이 실행할 행동, `CustomerDirectory.lookup`은 업무 사실의 출처입니다. 스키마를 바꿨다면 처리 함수도 같은 의미로 바뀌어야 합니다.

```java
// 참고 계약: 모델에 노출되는 인자와 실제 업무 호출의 대응
if (!TOOL.name().equals(name)) return Map.of("error", "UNKNOWN_TOOL");
// JSON 객체·허용 키·타입을 확인한 뒤
return CustomerDirectory.lookup(data.get("customer_id").textValue());
```

함수 이름이나 `Map` 형식에 맞추는 것이 설계 목표는 아닙니다. 예를 들어 `LookupResult` 타입을 만들면 성공 값과 오류를 코드에서 구별하기 쉽고, SDK로 보낼 때만 JSON으로 변환할 수 있습니다. 반대로 이 작은 앱은 검사한 JSON 객체를 직접 써도 읽기 쉽습니다. SDK의 요청 형식을 앱의 모든 계층에 그대로 퍼뜨릴지는 코드의 규모와 교체 필요로 결정합니다.

### 상태와 종료는 답변 문자열에서 나오지 않는다

최초 질문과 아직 완료되지 않은 도구 요청, 조회 결과, 요청 횟수는 앱이 다음 동작을 결정하는 데 필요한 서로 다른 정보입니다. 참고 예제는 `history`, `toolResults`, `turns`와 반복문의 인덱스로 관리합니다. 하나의 반복문으로 충분한 이 요구에서 상태 엔진을 별도로 만들 필요는 없습니다. 아래는 정상 입력의 **예상 경로**입니다.

```text
질문(C-100) → 요청 1 → call_id=x, 고객 조회 요청
  → 앱의 인자 검사 → lookup → basic/active
  → 이전 응답 항목 + x의 실제 결과를 이력에 추가
  → 요청 2 → 도구 호출 없는 설명 → 사용자에게 반환
```

이 경로에서 모델은 “실행해 달라”고 요청할 수 있지만 실제 실행 여부는 코드가 결정합니다. 고객 ID가 빠지면 ID 확인 질문으로 이번 호출을 마칩니다. 제공 `Quickstart`는 여기서 실행을 끝냅니다. Day 5에는 직접 만든 앱이 앞선 이력을 보관하고 다음 사용자 답변을 이어받도록 확장합니다. 한 실행에서 한 대화를 다룰 때는 메모리의 이력으로 충분하고, 여러 대화를 구분하거나 실행을 종료한 뒤 재개해야 할 때 대화 식별자와 저장소를 고려합니다.

`CUSTOMER_NOT_FOUND`는 모델에게 돌려보내 ID 확인 안내를 만들 수 있습니다. 전송 실패는 모델 응답 자체를 못 받은 상태여서 같은 업무 오류로 합치지 않습니다. 참고 구현은 전송 실패를 끝내고 SDK의 자동 재시도를 끕니다. 쓰기 함수라면 응답이 없다는 이유만으로 같은 요청을 반복했을 때 중복 실행될 수 있으므로, 실제 처리 여부와 재시도 가능성을 확인하는 계약이 추가로 필요합니다.

종료 기준도 요구에서 나옵니다. 제공 예제의 예상 정상 경로에는 두 번의 모델 요청이 필요합니다. 모델 요청 세 번을 허용하면 한 번 더 판단할 여유를 주되, 세 번째 응답이 다시 호출을 요구할 때는 결과를 전달할 여유가 없어 실행 전에 멈춥니다. 다른 정책으로 “같은 이름·인자를 다시 요청하면 즉시 중단”을 택할 수도 있습니다. 이 경우 비교 키에는 앱이 정규화한 인자를 쓰고, 최신 값 재조회가 실제로 필요한 업무인지 고려합니다. 숫자만 늘리는 대신 무엇이 달라져야 다음 실행이 유효한지 판단하는 것이 핵심입니다.

### 앞 주차와 연결해서 사용할 위치를 찾는다

MCP는 다른 프로세스의 기능을 발견·호출하는 계약이고, 이번 Tool Calling은 모델의 요청을 앱의 실행으로 연결하는 계약입니다. 앱의 Tool 실행기가 로컬 `lookup` 대신 3주차 MCP Client를 호출할 수 있습니다. 그때 MCP 서버의 오류를 모델에게 전달할 의미로 변환하는 책임은 앱에 남습니다. 이를 사용하기 위해 별도 통합 과제를 수행할 필요는 없습니다. 5주차 엔진이 Codex 프로세스의 실행·검사를 관리했다면, 이번 루프는 그 실행기 안에서 모델과 함수가 왕복하는 원리를 보여 줍니다.

## 준비와 파일

작업 폴더는 `week06-llm-api-tool-calling/llm_lab`입니다. JDK 17 이상으로 IDE에서 Gradle 프로젝트를 엽니다. `run`은 완성된 연결 예제, `assistant`는 Day 3에서 설계한 앱의 진입점을 실행합니다. 첫 빌드에는 SDK 의존성 다운로드가 필요합니다.

| 파일 | 읽거나 바꿀 이유 |
|---|---|
| `src/main/java/lab/week06/Quickstart.java` | 제공 업무 함수, Tool 계약, SDK 경계, 완성된 루프의 실제 연결 |

### 키 설정과 실행의 담당

API 키는 학습자가 IDE의 비공유 실행 설정에 직접 넣습니다. 애플리케이션은 실행 중 환경변수의 키를 SDK 인증에 사용하고, AI는 환경변수 이름을 기준으로 연결 코드를 작성합니다. AI에게 실제 키 값을 알려주거나 조회하게 할 필요가 없습니다. 환경변수에 저장하는 것은 코드에서 키를 분리하는 방법이며 AI 도구의 접근을 자동으로 차단하는 장치는 아닙니다.

이 주차의 요청문에서 **AI는 코드·대역 검사와 실행 방법을 준비하고, 실제 API 호출은 학습자가 IDE에서 수행합니다.** AI는 키 값을 조회하거나 키가 저장된 `.env`·비공유 실행 설정을 열람하지 않으며, 환경변수 전체나 인증 헤더를 출력하지 않습니다. 앱에도 키를 로그·오류 메시지로 내보내는 코드를 넣지 않습니다. IDE의 설정이 다른 실행 환경에 전달되지 않을 때는 AI가 키를 찾아 복사하는 대신 해당 IDE 실행 설정을 사용합니다. 결과를 함께 해석할 때는 키·인증 헤더가 없는 입력·Tool 결과·최종 답변을 사용합니다.

### OpenAI로 진행하기 — 제공 예제 그대로 사용

제공 `Quickstart`와 아래 코드·명령 예시는 OpenAI Java SDK의 Responses API를 기준으로 합니다. 실제 API 실행에는 학습자가 IDE의 비공유 실행 설정에 `OPENAI_API_KEY`, `OPENAI_MODEL`, `AI_AX_LIVE=1`을 준비합니다. 모델은 계정에서 사용할 수 있는 Responses·함수 호출 지원 모델을 선택합니다. 키를 파일·대화에 붙여 넣거나 출력하지 않습니다. 오프라인 예제는 계정 없이 진행할 수 있으며 모델 경계의 응답을 고정합니다.

### 무료로 진행하려면 — Gemini 선택 경로

Gemini API로도 일반 모델 호출, 고객 Tool 호출, 결과 전달과 종료, 사용자 답변 이어받기를 학습할 수 있습니다. **OpenAI와 Gemini 중 하나를 선택해 Day 1~5를 이어갑니다.** 두 제공자로 같은 앱을 중복 제작할 필요는 없습니다. 실제 API 키가 없어도 제공 오프라인 예제로 구조를 먼저 확인할 수 있습니다.

1. [Google AI Studio](https://aistudio.google.com/)에서 프로젝트와 API 키를 준비합니다. 구체적인 발급 화면은 [공식 키 안내](https://ai.google.dev/gemini-api/docs/api-key)를 따릅니다.
2. [공식 요금표](https://ai.google.dev/gemini-api/docs/pricing)에서 입력·출력이 무료인 모델을 찾고, 프로젝트가 Free Tier인지와 해당 모델의 실제 호출 가능량을 AI Studio에서 확인합니다. 키 발급 자체가 모든 모델의 무료 사용을 뜻하지는 않습니다. 무료 제공 모델과 한도는 바뀔 수 있어 특정 모델명·횟수를 고정하지 않습니다. 한도에 도달하면 [사용량 제한 안내](https://ai.google.dev/gemini-api/docs/rate-limits)에 따라 재설정 시점을 확인하고 오프라인 활동을 이어갑니다.
3. 학습자가 IDE의 비공유 실행 설정에 `GEMINI_API_KEY`, `GEMINI_MODEL=<선택한 모델 ID>`, `AI_AX_LIVE=1`을 준비합니다. `GEMINI_MODEL`과 `AI_AX_LIVE`는 이번에 만들 앱이 읽도록 정할 설정 이름이며, Google SDK가 자동으로 모델을 선택하거나 호출을 제한해 주는 설정은 아닙니다. 키 값은 코드·대화·공유 설정에 넣지 않습니다.
4. Day 1의 Gemini 요청문으로 **Java 연결 코드를 먼저 준비**합니다. 현재 `Quickstart`는 `client.responses().create(...)`를 사용하므로 `OPENAI_API_KEY`에 Gemini 키를 넣어도 실행되지 않습니다. Google의 [OpenAI 호환 문서](https://ai.google.dev/gemini-api/docs/openai)는 Chat Completions 형식을 안내하므로, 주소와 키만 바꾸는 것으로 현재 Responses 타입을 재사용할 수 없습니다.

이 경로에서는 [Google GenAI Java SDK](https://ai.google.dev/gemini-api/docs/libraries)로 요청·응답 연결을 구성하고 제공 `CustomerDirectory`를 재사용합니다. `Quickstart.Gateway`의 입력과 `Turn`의 출력도 OpenAI 타입이므로 그 인터페이스를 고정하지 않습니다. SDK는 통신과 응답 표현을 맡고, 앱은 허용 함수·인자 검사·실제 조회·다음 요청·종료를 맡습니다. 함수 호출 결과를 원래 요청에 대응시키는 원리는 같지만 필드와 이력 형식은 다릅니다. Gemini에서는 [함수 호출 공식 흐름](https://ai.google.dev/gemini-api/docs/function-calling)에 따라 모델의 호출 응답과 필요한 메타데이터를 보존하고 실제 함수 결과를 다음 요청에 전달합니다.

아래 Day의 완료 기준은 선택한 제공자의 실제 코드와 결과로 확인합니다. `call_id`, `ResponseInputItem`, `Turn.usage` 같은 OpenAI 예시를 Gemini의 필드명이나 필수 클래스 구조로 강제하지 않습니다. Gemini 실행 코드와 진입점은 아직 제공되지 않으므로, 다음 요청문으로 준비한 뒤 IDE에서 그 진입점을 실행합니다.

## Day 1 — 일반 API 호출에서 입력과 응답 구분하기

**할 일:** 도구 없는 요약 요청 한 번으로 **사용자 입력·지침 → SDK 호출 → 응답 해석**을 연결합니다. 입력과 지침을 구분하는 이유, 도구를 제외한 이유, 응답 종료와 내용의 정확성을 따로 확인해야 하는 이유를 실제 코드와 요약 문장에 연결합니다.

### 메모가 SDK 요청에 들어가는 경로

제공 입력은 `메모를 한 문장으로 요약해줘: 로그인 수정 완료, 배포 확인 필요.`입니다. `Quickstart.main`의 `--text` 값이 `run`의 `text`로 들어오고, 다음 실제 코드에서 사용자 메시지가 됩니다.

```java
history.add(ResponseInputItem.ofEasyInputMessage(EasyInputMessage.builder()
        .role(EasyInputMessage.Role.USER).content(text).build()));
```

아래 요청 구성에서 `history`는 처리할 입력이고, `instructions`는 그 입력을 다룰 공통 지침입니다. `plain=true`이면 “사용자의 요청에 한국어로 간결하게 답하세요”가 적용됩니다.

```java
var request = ResponseCreateParams.builder().model(model).inputOfResponse(history)
    .instructions(plain ? "사용자의 요청에 한국어로 간결하게 답하세요." : INSTRUCTIONS)
    .maxOutputTokens(700).store(false);
```

메모를 바꾸면 사용자 입력이 바뀌고, 답변 언어·길이의 기본 방침을 바꾸면 지침이 바뀝니다. 둘을 구분하면 업무 자료가 달라질 때마다 공통 방침까지 다시 작성하지 않아도 됩니다. `maxOutputTokens(700)`은 출력 상한이며 한 문장 요약이나 사실 보존을 보장하는 조건은 아닙니다. 참고 코드의 `if (!plain)` 아래에만 고객 Tool을 추가하므로 일반 요약에는 고객 조회가 공개되지 않습니다. 요약에 필요한 자료가 입력에 이미 있어 외부 조회를 요청할 이유가 없기 때문입니다.

### SDK 응답과 앱의 결과를 구분하기

`run`은 `client.create(request.build())`를 호출합니다. 여기서 `client`는 교체 가능한 모델 경계이며, 실제 API 연결인 `liveClient` 안에서는 다음 SDK 호출이 실행됩니다. 대역을 선택하면 같은 경계에서 고정 응답을 반환합니다.

```java
Response response = client.responses().create(request);
String answer = response.output().stream().flatMap(item -> item.message().stream())
        .flatMap(message -> message.content().stream()).flatMap(content -> content.outputText().stream())
        .map(ResponseOutputText::text).reduce("", String::concat);
```

SDK 응답에는 메시지 외의 항목도 올 수 있어 `liveClient`는 메시지의 텍스트를 모아 `answer`로 만들고 원래 응답 항목도 보존합니다. `run`은 응답 상태와 거절·함수 호출 여부를 분류한 뒤 앱의 `status`와 `answer`를 반환합니다. `MODEL_RESPONSE`는 완료된 응답에 텍스트가 있다는 앱의 분류입니다. 문장 내용이 요구에 맞는지는 별도로 판단해야 합니다.

예를 들어 “로그인 수정은 완료됐고 배포 확인은 필요합니다”는 원문의 두 상태를 보존한 **예상 요약 예**입니다. “로그인 수정과 배포 확인이 완료됐습니다”도 문장으로는 완성됐지만 아직 필요한 일을 완료된 사실로 바꿉니다. 응답 상태만 확인하면 이 차이를 놓칩니다.

참고 앱은 `completed`가 아닌 응답을 `INCOMPLETE`, 거절을 `REFUSED`, 빈 완료 응답을 `INVALID_OUTPUT`, 모델 경계에서 예외가 발생한 경우를 `PROVIDER_ERROR`로 묶습니다. 이는 SDK의 모든 상태·오류를 그대로 표현한 이름이 아닙니다. 원인을 해석할 때는 요청별 `turns`의 상태와 해당 분기를 연결하고, 오류 메시지나 인증 설정 전체를 수집하지 않습니다.

## Day 2 — 요청한 호출과 실제 함수 결과 연결하기

**할 일:** 전체 고객 레코드를 반환하는 제공 계약에서 호출 요청과 실제 결과가 어떻게 왕복하는지 확인합니다. OpenAI 경로는 IDE에서 `Quickstart.main`의 인자에 `--offline`을 넣어 정상 입력을 실행합니다. Gemini 경로는 Day 1의 연결에 아래 요청문으로 같은 제공 계약을 한 번 연결하고, 그 앱에서 정상·없는 고객을 확인합니다. 터미널 실행이 필요하면 Windows의 `.\gradlew.bat run --args='--offline'`, macOS·Linux·WSL의 `sh ./gradlew run --args='--offline'`을 사용할 수 있습니다.

제공 실행은 `offline-1` 호출에 `C-100`을 넣고 `getCustomerContext`가 반환한 값을 다음 모델 요청으로 전달합니다. 다음 코드는 해당 호출의 결과를 추가하는 실제 부분입니다.

```java
history.add(ResponseInputItem.ofFunctionCallOutput(
    ResponseInputItem.FunctionCallOutput.builder()
        .callId(call.callId()).output(json(toolResult)).build()));
```

`call_id`는 고객 ID와 다른 역할입니다. 같은 고객을 두 번 조회해도 각 호출과 결과를 대응시킬 수 있습니다. 제공 코드는 앞선 응답의 모든 출력 항목을 보존한 뒤 결과를 덧붙입니다. 추론 항목 등을 임의로 버리고 자연어만 다시 보내는 것은 같은 대화 상태의 재현이 아닙니다. [Function calling 공식 흐름](https://developers.openai.com/api/docs/guides/function-calling)

`--offline --case unknown`에서는 `CUSTOMER_NOT_FOUND`도 같은 연결로 전달됩니다. 최종 `MODEL_RESPONSE`와 도구 성공은 다릅니다. 정상적인 안내 문장이 만들어져도 조회 자체는 실패할 수 있으므로 `tool_results[].result`를 함께 읽습니다.

```text
정상 고객과 없는 고객의 실행에서 Tool 정의, 실제 arguments, executeCall의 반환값,
다음 요청의 call_id를 연결해 설명하세요. 업무 오류도 모델에 전달하는 이유와
전송 실패로 응답을 받지 못한 경우의 차이를 실제 코드로 짚어주세요.
```

**남길 결과·완료 판단:** 하나의 입력에서 도구 선택→인자→실행값→다음 응답까지 추적하고, 조회 실패와 모델 응답 완료의 차이를 설명합니다. 정상·없는 고객의 결과는 기존 노트에 이어 남깁니다. 여기서는 `plan`과 `status`를 함께 반환하는 연결을 확인하고, Day 3에서 이 연결의 공개 계약과 결과 처리를 수정합니다.

**Gemini를 선택했다면:** 위 Java 코드는 OpenAI의 결과 전달 사례로 읽고, Day 1의 연결에 제공 고객 Tool을 연결할 때 아래 요청을 사용합니다. 이후에는 해당 진입점에서 이 Day의 정상 고객·없는 고객 경로를 확인합니다.

## Day 3 — 요청한 항목만 반환하도록 Tool 계약과 앱 수정하기

**할 일:** Day 2에서 확인한 고객 조회 연결에 다음 업무 요구를 적용합니다. “요금제와 계정 상태 문의를 받되, 모델에게 전달하는 고객 정보는 요청한 조회 항목으로 한정한다. 두 항목을 함께 요청하면 둘 다 안내한다.” 기존 SDK 연결·조회 함수를 재사용하면서 Tool의 기능 단위·입력과 실제 결과 처리를 설계하고 수정합니다.

### 전체 레코드와 모델에 반환할 결과의 차이

제공 `CustomerDirectory.lookup`은 고객의 전체 레코드를 복사하고 ID를 붙여 반환합니다. 다음은 실제 코드입니다.

```java
var result = new LinkedHashMap<String, Object>(customer);
result.put("customer_id", id);
return result;
```

Day 2의 `Quickstart.executeCall`은 이 값을 그대로 Tool 결과로 사용합니다. 요금제만 물어도 모델에는 `plan=basic`과 `status=active`가 모두 전달됩니다. 최종 문장을 짧게 쓰라는 지침만 추가해도 이 데이터 전달은 달라지지 않습니다. 후속 요구를 구현하려면 **어떤 항목을 조회할지 Tool 계약에 표현하고, 앱이 해당 항목으로 반환값을 구성**해야 합니다. 업무 자료의 원본을 바꾸는 일이 아니라 업무 함수와 모델 사이의 계약을 바꾸는 일입니다.

아래는 제공 입력과 **요구상 예상 결과**입니다. 고객 ID는 결과의 대상을 식별하는 공통 값이고, 성공 값은 요청한 항목만 포함합니다. 표의 결과는 JSON 필드명을 강제하는 완성 답안이 아니라 전달할 정보의 범위입니다.

| 사용자 입력 | 모델에게 전달할 고객 정보 | 확인할 동작 |
|---|---|---|
| `C-100 고객의 요금제를 알려주세요` | 고객 ID와 `plan=basic` | `status`를 Tool 결과에 포함하지 않음 |
| `C-100 고객의 계정 상태를 알려주세요` | 고객 ID와 `status=active` | `plan`을 Tool 결과에 포함하지 않음 |
| `C-100 고객의 요금제와 계정 상태를 알려주세요` | 고객 ID와 `plan=basic`, `status=active` | 선택한 Tool 구성으로 두 항목 전달 |

한 Tool에 조회 항목 목록을 넣는다면 예를 들어 `customer_id`와 `fields=["plan"]`으로 요청하고, 앱은 허용 항목을 검사한 뒤 조회 결과에서 그 항목을 골라 반환할 수 있습니다. 요금제 Tool과 상태 Tool을 나누면 각 함수가 반환할 항목을 고정할 수 있지만, 두 항목을 묻는 요청의 호출·결과 전달도 연결해야 합니다. 현재 두 항목이 같은 업무 함수에 있으므로 한 Tool에 항목을 표현하는 구성이 간단합니다. 기능별 권한이나 데이터 제공자가 달라지면 분리할 이유가 생깁니다. 두 구성을 모두 구현하는 과제는 아닙니다.

허용할 항목과 결과를 구성하는 책임은 앱에 둡니다. 모델이 요청한 인자와 앱이 실제 반환한 필드가 일치하는지는 코드로 확인하고, 자연어 질문에서 모델이 적절한 항목을 선택했는지는 실제 모델 결과에서 확인합니다. 예를 들어 조회 항목을 인자로 받는 계약에서 지원하지 않는 항목은 다른 고객 값을 대신 반환하지 말고 입력 오류로 처리합니다. `C-404`처럼 고객이 없는 경우에는 성공 필드를 추리는 과정에서 오류를 빈 객체로 잃지 않도록 합니다.

## Day 4 — 업무 오류 전달과 반복 호출 중단을 구분해 확인하기

**할 일:** Day 3에서 수정한 앱에서 **없는 고객의 오류 전달**과 **반복 호출의 중단**을 각각 확인합니다. 두 상황은 다음 판단에 줄 정보와 실행을 끝낼 책임이 다르므로 하나가 다른 하나의 확인을 대신하지 않습니다.

### 업무 오류는 조회 결과로 전달한다

`C-404 고객의 요금제를 알려주세요`의 조회 결과는 `CUSTOMER_NOT_FOUND`입니다. 앱은 이 오류를 원래 호출의 결과로 모델에게 전달하고, 모델이 고객 ID 확인을 안내하도록 연결합니다. Day 3의 필드 선택이 성공 결과에만 적용되어야 하는 이유도 여기서 확인됩니다. 오류까지 요청 필드만 골라 반환하면 빈 성공 결과처럼 보일 수 있습니다.

Day 3의 변경을 반영한 현재 앱에서 이미 확인한 결과나 검사가 있으면 사용합니다. Day 2의 참고 구현 결과만 있다면 현재 앱에서 선택한 계약에 맞는 없는 고객 대역을 한 번 실행합니다. 실제 모델의 안내가 없다면 오류 전달까지 확인한 것으로 해석합니다.

### 반복을 끝내는 결정은 앱이 한다

반복 대역은 같은 유효한 고객 조회를 계속 요청하도록 만듭니다. 고객 조회가 성공해도 모델은 다시 도구를 요청할 수 있으므로, 업무 오류 처리만으로는 이 반복을 끝낼 수 없습니다. 반복 조건은 실제 모델을 여러 번 호출해 유도하지 않고 대역으로 고정합니다.

참고 `Quickstart.run`은 다음 코드로 마지막 허용 요청에서 추가 함수를 실행하기 전에 멈춥니다.

```java
if (index == maxRequests)
    return result("STOPPED", "모델 요청 한도에 도달해 추가 함수를 실행하지 않습니다.", toolResults, turns);
```

이 분기가 `executeCall`보다 앞에 있으므로 참고 반복 대역의 예상 결과는 모델 요청 세 번·실제 조회 두 번 뒤 `STOPPED`입니다. 세 번째 조회를 시작하면 그 결과를 모델에 돌려줄 요청 여유가 없습니다. 이 숫자는 참고 정책의 결과이며, 자기 앱은 Day 3에서 선택한 정책의 예상과 비교합니다. 같은 호출을 더 일찍 차단하기로 했다면 그 경계가 드러나야 합니다. 호출 한도나 책임 분담을 새로 바꿀 필요가 생겼을 때만 이유·예상과 학습자 의견을 먼저 확인합니다.

IDE에서 현재 앱의 메인 클래스를 사용하고, 계약을 바꿨다면 반복 대역도 함수 이름·인자·반환값에 맞춥니다. 인자를 유지했고 메인 클래스가 `lab.week06.CustomerAssistant`라면 다음은 터미널 실행 대안입니다.

Windows PowerShell:

```powershell

```

macOS·Linux·WSL:


```text

없는 고객 결과는 현재 계약에서 확인한 기존 결과·검사가 있으면 사용하고, 없으면 C-404 대역을 실행하세요.
오류가 성공 필드 선택 과정에서 사라지지 않고 원래 호출의 결과로 전달되는지 설명하세요.
반복은 현재 Tool의 유효한 호출을 계속 반환하는 대역으로 고정하고 실제 API를 호출하지 마세요.
선택한 종료 정책의 예상 경로를 짚은 뒤 실행해 마지막 분기와 추가 함수 실행 여부를 대조하세요.
단순 오류 수정은 영향을 받은 경로만 다시 확인하고,
호출 한도·책임 분담을 바꾸려면 이유와 예상을 설명한 뒤 내 의견을 기다려주세요.
결과를 보고 업무 오류 전달과 반복 중단이 다른 책임인 이유를 함께 해석하겠습니다.
```

**남길 결과·완료 판단:** 현재 앱의 없는 고객 오류가 호출 결과로 전달되고, 반복 대역에서는 선택한 경계에서 추가 실행이 중단되는지 확인합니다. 각 결과가 어느 코드 분기에서 결정됐는지와 두 책임을 구분한 이유를 기존 노트에 이어 남깁니다. 요청·함수 횟수는 종료 위치를 설명하는 근거로만 사용합니다.

## Day 5 — 실제 모델로 사용하고 대화 이어받기

**할 일:** Day 3~4에서 만든 고객 조회 앱을 실제 모델로 확인하고, 사용자가 고객 번호를 나중에 알려주어도 앞선 질문을 이어 처리하도록 확장합니다. 제공 요구는 **“요금제를 알려주세요” → 고객 번호 확인 질문 → “C-100” → 실제 요금제 안내**입니다. 아래 해설을 읽고 요청문을 대화형 도구에서 사용합니다.

### 기존 앱의 실제 연결 확인하기

학습자가 선택한 OpenAI 또는 Gemini 환경으로 자기 앱의 IDE 진입점에서 `C-100 고객의 요금제를 알려주세요`를 실행합니다. 모델의 Tool 이름·인자, 실제 함수 결과와 최종 안내를 대조합니다. `CustomerDirectory.lookup("C-100")`의 전체 값은 `plan=basic, status=active`이며, Day 3의 앱은 이 질문에 고객 ID와 `plan=basic`만 모델에게 반환해야 합니다. 업무 함수의 전체 값과 모델에게 공개한 값을 구분해 확인합니다. 이미 같은 계약과 연결을 실제 모델로 확인했다면 기존 결과를 사용합니다.

```text
현재 만든 고객 조회 앱의 실제 모델 연결을 확인하겠습니다.
기존에 같은 계약·진입점으로 확인한 실제 결과가 있으면 사용하고, 없으면
'C-100 고객의 요금제를 알려주세요'를 내가 IDE에서 실행하도록 안내하세요.
실제 키 값·비공유 인증 설정은 열람하지 마세요.
비밀값 없는 결과로 모델의 Tool 요청, 앱이 공개한 조회 항목과 마지막 답변을 대조하세요.
대역 실행만 있다면 실제 모델의 선택·답변은 아직 확인하지 않은 것으로 구분하세요.
```

### 응답이 끝나도 다음 입력에 필요한 상태는 남는다

`Quickstart.run`은 실행할 때마다 다음 코드로 이력을 새로 만듭니다. 아래는 제공 코드의 실제 부분입니다.

```java
var history = new ArrayList<ResponseInputItem>();
history.add(ResponseInputItem.ofEasyInputMessage(EasyInputMessage.builder()
        .role(EasyInputMessage.Role.USER).content(text).build()));
```

함수 호출이 없는 응답은 다음 분기에서 반환합니다.

```java
if (calls.isEmpty()) return result(turn.text().isBlank() ? "INVALID_OUTPUT" : "MODEL_RESPONSE", turn.text(), toolResults, turns);
```

따라서 `--offline --case missing`의 “고객 ID를 알려주세요”도 정상적인 모델 응답으로 끝납니다. 이 분기는 `turn.output()`을 이력에 추가하는 부분보다 앞에 있어 확인 질문은 다음 입력에 전달되지 않습니다. `run("C-100", ...)`을 다시 호출해도 새 이력에는 고객 번호만 있습니다. 모델이 우연히 요금제를 답하더라도 앞선 질문이 전달됐다는 근거가 되지는 않습니다.

변경할 것은 **이력을 한 사용자 입력보다 오래 보관하고, 답변을 반환한 뒤 다음 입력을 받을 책임**입니다. 같은 실행 안에서 한 대화를 이어받으므로 입력을 받는 쪽이 메모리의 이력을 보관하고 처리 함수에 전달하는 구성이 간단합니다. 이미 대화를 표현하는 객체가 있다면 그 객체가 이력을 소유해도 됩니다. 전자는 이력의 전달 경로가 드러나고, 후자는 이력과 갱신 동작을 한곳에 모읍니다. 클래스 이름이나 메서드 형태보다 현재 앱에서 상태의 소유자와 수명이 분명한지를 기준으로 선택합니다.

입력 이력에는 최초 질문, 모델이 보낸 확인 질문과 새 사용자 답변이 순서대로 들어가야 합니다. Tool 요청이 오면 Day 2처럼 모델의 호출 응답과 실제 함수 결과를 대응시켜 이어 붙입니다. OpenAI 참고 경로에서는 `Turn.text`만 남기지 말고 `Turn.output()`의 응답 항목을 보존해야 합니다. 응답을 대화에 연결하는 계약과 이력을 소유할 객체를 고르는 일은 다릅니다. [OpenAI 대화 상태 안내](https://developers.openai.com/api/docs/guides/conversation-state), [함수 호출의 응답 항목 보존](https://developers.openai.com/api/docs/guides/function-calling)

Gemini로 만든 앱도 선택한 API의 모델 응답과 함수 결과 형식으로 같은 흐름을 연결합니다. `generateContent` 경로에서 이력을 직접 관리한다면 응답의 content·parts와 반환된 thought signature를 보존해야 합니다. 서명은 응답에 붙는 불투명한 메타데이터이며 앱이 내용을 해석해 다시 만드는 값이 아닙니다. OpenAI의 `Turn`이나 `call_id`를 Gemini의 필수 타입·필드로 강제하지 않습니다. [Google의 응답·서명 보존 안내](https://ai.google.dev/gemini-api/docs/generate-content/thought-signatures)

아래는 **확장 후 예상 흐름**입니다. 모델의 실제 질문 문장은 달라질 수 있습니다.

```text
사용자: 요금제를 알려주세요
  → 모델: 고객 ID를 알려주세요 → 조회 없이 이번 입력의 응답 종료, 이력 유지
사용자: C-100
  → 앞선 질문·확인 응답 + 새 입력을 모델에 전달
  → 요금제 조회 요청 → 앱의 인자 검사·lookup → 고객 ID와 plan=basic 선택
  → 원래 호출에 대응하는 실제 결과 전달 → 요금제 안내
```

모델의 답변을 표시한 뒤에는 자동으로 같은 질문을 반복하지 않고 다음 사용자 입력을 기다립니다. 호출 한도는 한 사용자 입력을 처리하는 모델·도구 왕복에 적용하고, 다음 사용자 입력을 받으면 그 입력의 한도를 새로 시작하는 구성을 기본으로 삼습니다. 확인 질문과 조회 답변을 만드는 두 번의 사용자 입력에 대화 전체 한도를 같이 쓰면, 대화를 이어갔다는 이유로 정상 조회가 중단될 수 있기 때문입니다. 실패·거절·반복 한도로 멈추는 경우에는 Day 4에서 확인한 종료 이유를 보존하고 자동 재호출로 우회하지 않습니다. 한도로 실행하지 못한 Tool 요청을 다음 사용자 입력에서 자동 실행할 작업으로 넘기지 않습니다. 프로세스를 종료하면 메모리의 대화도 끝납니다. 여러 사용자의 대화를 구분하거나 재실행 후 이어야 하는 요구가 생기면 보관 위치와 식별 방식을 다시 선택합니다.

### 기존 앱을 수정하고 예상과 실제 결과 대조하기

```text
앞선 요금제 질문을 이어받아 실제 고객 조회 결과로 안내해야 합니다.
먼저 현재 코드에서 한 입력의 처리가 끝나는 위치와 이력을 만들거나 보관하는 위치를 짚으세요.
```

학습자가 IDE에서 수정한 앱의 메인 클래스를 실행하고, 같은 실행 콘솔에 두 입력을 차례대로 보냅니다. 확인 질문을 받은 뒤 `C-100`을 입력합니다. 제공 `Quickstart.main`은 한 번의 입력만 받으므로 이 실습의 대화 진입점은 직접 만든 앱에 연결해야 합니다. `--text`로 프로그램을 두 번 시작하는 것은 같은 메모리 대화를 이어받는 실행이 아닙니다. 입력 방식이나 종료 방법을 정했다면 앱의 실행 안내에도 반영합니다.

API 연결이 없으면 이 대화 순서를 고정하는 대역으로 실제 앱의 이력 전달·함수 실행·종료를 확인합니다. 제공 `OfflineClient("missing")`은 한 번의 확인 질문을 위한 대역이므로, 확인 응답과 다음 사용자 입력을 이어 주는 대역으로 맞춥니다. 대역이 고정 답변을 냈다는 사실보다 다음 요청에 앞선 질문과 응답이 실제로 전달됐는지를 봅니다. 실제 모델의 도구 선택과 대화 이해는 연결이 준비됐을 때 같은 진입점에서 확인합니다.

기존 출력에 사용량이 있다면 앞선 질문·확인 응답·도구 결과를 다시 보내는 이유에 연결해 짧게 읽습니다. 이력이 추가되면 모델이 처리할 입력도 늘 수 있지만 그 맥락이 있어야 후속 입력의 뜻을 알 수 있습니다. 반면 새 사용자 입력이나 새 정보 없이 같은 조회만 반복된다면 종료 정책을 살펴볼 근거가 됩니다. 호출 수가 적다는 이유만으로 좋은 설계라고 판단하지 않으며, 사용량 수집 기능 추가나 금액 계산을 이 실습의 과제로 두지 않습니다.

**남길 결과·완료 판단:** 고객 번호 없는 첫 질문에는 임의 조회 없이 확인을 요청하고, 후속 `C-100` 입력에는 앞선 질문을 이어 조회한 뒤 그 값으로 안내하는지 확인합니다. 실제 다음 요청의 맥락과 요청 항목만 포함한 Tool 결과·최종 답변, 기존 단일 질문의 결과를 근거로 삼습니다. 선택한 상태 보관·호출 종료의 이유와 예상·실제 결과에 대한 학습자의 해석은 기존 `api-note.md`에 이어 남깁니다. 대역으로 확인했다면 로컬 제작 결과와 실제 모델 연결 미확인을 구분합니다.

- 고객 조회 연결을 재사용해 요청한 항목만 모델에 반환하는 Tool 계약과 앱의 처리를 구현했습니다. 제공 세 입력의 결과와 그 계약의 선택 이유를 설명할 수 있습니다.
- 현재 앱의 업무 오류 전달과 반복 호출 중단을 각각 확인하고 결과를 결정한 책임·코드를 해석했습니다.

- 실제 모델의 Tool 선택과 대화 이어받기, 조회값을 보존한 최종 답변을 확인했습니다. 대역 실행과 구분합니다.
- 한 입력의 호출 종료와 다음 입력까지 상태를 유지하는 책임이 어떻게 나뉘는지, 그 선택이 이번 요구에 맞는 이유를 실제 코드와 결과로 설명할 수 있습니다.

## 선택 참고: 사용량과 비용 읽기

요청 크기나 서비스 비용을 더 살펴보고 싶을 때 기존 응답의 사용량으로 계산해 봅니다. 이 절의 계산과 금액 기록은 Day 5와 주차 완료에 필요한 활동이 아닙니다.

OpenAI 참고 예제의 `Quickstart.Usage`에서 `cachedInputTokens`는 입력 토큰의 일부이고 `reasoningTokens`는 출력 토큰의 일부이므로 합계에 다시 더하지 않습니다. 사용자에게 보이는 답변 길이만으로 출력 사용량을 알 수 없는 이유입니다. `model_requests`는 프로그램이 시도한 요청 수여서 응답이 유실된 요청의 청구 여부까지 확정하지 못합니다. 오프라인 응답이나 사용량이 빠진 요청에 임의 토큰 수나 0원을 붙이지 않습니다.

Gemini에서는 [토큰 안내](https://ai.google.dev/gemini-api/docs/tokens)와 선택한 API의 사용량 정의를 함께 확인합니다. OpenAI의 추론·출력 토큰 포함 관계를 그대로 적용하거나 서로 다른 API의 값을 같은 필드명으로 합치지 않습니다.

금액을 계산한다면 실행한 모델과 서비스 조건의 [OpenAI 공식 단가](https://developers.openai.com/api/docs/pricing)를 실행일에 확인합니다. 일반 입력·캐시 입력·출력의 백만 토큰당 단가를 각각 `p`, `c`, `o`라 할 때, 이 세 항목으로 청구되는 요청의 추정 비용은 다음과 같습니다.

```text
((입력 토큰 - 캐시 입력 토큰) × p + 캐시 입력 토큰 × c + 출력 토큰 × o) / 1,000,000
```

요청별로 계산해 더합니다. 별도 캐시 쓰기·도구 요금이나 서비스 등급에 따른 항목이 있으면 함께 반영합니다. 이 예제의 로컬 조회 횟수를 유료 제공자 도구 요금으로 바꾸지 않습니다. 계산했다면 단가·확인일·보고된 토큰과 추정액을 기존 노트에 짧게 남기고 실제 청구액과 구분합니다. 사용량이 빠진 요청은 0으로 채워 정확한 총액처럼 보고하지 않습니다.

Gemini 경로의 비용 근거는 [Google 공식 요금표](https://ai.google.dev/gemini-api/docs/pricing)입니다. Free Tier의 무료 대상 모델·기능·할당량 안에서 실행했다면 무료 적용 조건과 사용량을 구분해 읽습니다. 사용량을 몰라 비용을 계산하지 못하는 경우와 무료 조건으로 실행한 경우는 다릅니다. 선택한 모델의 유료 단가를 적용해 연습한다면 **유료 등급을 가정한 추정액**으로 표시합니다.
